### Note 1: ranks ("ranks don't live in agents names ... about 4 ranks, commander, captain, officer, worker. Its a responsibility axis.")

Section 3.2.
- Rank is no longer part of any agent's file name or `name:` (the owner: "ranks don't live in agents names"), and it is no longer tied to a model tier. By the lead's choice, agent descriptions describe the function and carry no rank either. Rank is given to a seat when work is handed out: the same agent definition can sit as an Officer in one team and a Worker in another. The roster can grow to 30 or more agents with the same four ranks. Sections 3.2 and 3.5.

Sections 3.2, 3.4, 3.5, 3.8, PR 1's file list and units (section 4 and section 5).

The owner's words fix the four ranks and what each is; the detailed behaviour rules (who decides what, escalation, address) are the lead's proposal, written in build-1's `decisions.md` for the owner to strike. An Officer may be spoken to directly by the Commander in its own session (the owner said he can hop on background sessions). Section 3.2.

### (c) How a retry works

- Whole plan: the owner adds dated lines to `.flightdeck/build-1/constraints.md` and asks Claude to rerun `.flightdeck/build-1/workflows/plan.js` with `outDir: ".flightdeck/build-1/attempts/plan/a<k>"`; `plan.js` always reads the owner's lines from `.flightdeck/build-1/constraints.md` (override with `args.constraints`), so nothing is copied. Earlier planning files stay where they are. This plan is attempt 2, made this way.
- One pull request: the owner adds a line that starts with the pull request number, for example `2026-10-12 PR 3: the interview asks at most three questions`, then says "retry PR 3". The build workflow runs with `prs: [3]` and the next attempt number: a fresh brief that includes every general line, every `PR 3:` line and attempt 1's findings; a fresh branch `build-1-pr3-workshops-a2` cut from the current `build-1`; a fresh pull request. Attempt 1's branch, pull request and folder stay until the owner closes them. Reason: "setup carries over, run output does not" (the flightcrew retry rule): a retry starts from better inputs, not from the failed output.
- A late PR 1 retry: if PR 1 is retried after wave 1 is built, the wave 1 pull requests that use what changed are rerun too; the retry report lists which.
- Any workshop (from PR 3): the owner adds a line to that workshop's `constraints.md`, answers a question, or has a line added to its `context.md` or `verify.md`, then runs `/flight:retry <workshop>`; the next attempt folder opens with the one change named at the top of its brief.
- Branch names never start with `build-1/`: the branch `build-1` exists and git cannot hold both `build-1` and `build-1/...` (a judge reproduced "cannot lock ref"). All branch names are computed by the workflow script, never chosen by an agent.

Activation starts with Haiku scouts reading the code so nothing they can find is asked, then one bundle of at most five plain questions about the owner's own ideas (each with why it matters and a recommended answer); one of them is always the adversary's challenge, "the weakest part of this ask is X: what should we do about it?", with options. The folder is then written: card, `context.md` (from the scouts' findings) and `verify.md` (from the done line and the answers); `constraints.md`, `questions.md` and `decisions.md` are created when something is first written to them. With PR 1 alone, the pilot activates from the templates without the interview.
- Settle: the owner writes `settled: <date>` in the workshop's card, or tells the pilot "settle <name>" and the pilot writes it in the main conversation. Settling promotes nothing; promoting is a later, optional step (3.4).
- Three doors, all optional: (1) plain `claude` chat, exactly as before; (2) `claude --agent flight:pilot --model opus --effort high` (the README suggests the shell alias `fly`); (3) `/flight:capture` and `/flight:workshop` directly, or the board's prompt builder, which produces that line to paste. Nothing starts on its own: launches begin only when the owner types `/flight:launch <workshop>` and says "go" after reading the launch card.
- Reason: owner-truth section 5.1 supports this: rough ask, a short interview that draws the owner's ideas out, then go; the owner's 2026-10-11 note adds the capture step ("captured from a simple task or goal mentioned or discovered, stored in a simple manifest first, awaiting activation"); the owner called typed orders, IDs and approval flags tedious, said "the one thing the human wants control of is what his agents do", and asked to have their intent challenged.

### (f) Where questions waiting on the owner are held

### 3.2 Roleplay: chain of command, voice and names

- What: the owner's four ranks as a responsibility axis and a hierarchy of influence, carried cheaply, separate from agent names and from model tiers.
  - The owner's words fix the four ranks and what each one is (the first line of each below). Everything else in this list, the escalation ladder and the address rule are the lead's proposal, written in build-1's `decisions.md` for the owner to strike.
  - Commander: the owner. Responsible for everything. Sets truth, activates and settles workshops, says go, merges. Human. May speak to any rank directly.
  - Captain: the lead session, such as a pilot session (`claude --agent flight:pilot`) or the lead of a build run. Decision maker and responsibility dispenser: picks the team plan, decides which Officer or Worker gets which responsibility, accepts or rejects findings when no Officer leads the team, files captured work and questions on the base branch, and is the rank that normally talks with the Commander. Does not build, and does not bulk read or bulk write (from the owner's earlier ranks note, `origin/cockpit:flightdeck/.cockpit-archive/commander/ideas/ranks.txt`: captain "does not bulk read or bulk write, uses its context to dispatch teams").
  - Officer: a team lead inside one piece of work (for example the lead of a Many hands team, or the lead of an agent team), or an autonomous long-lived character running as a background session (for example a runner on one workshop, or the librarian run as a standing session over the corpus). Single-shot workflow seats (brief, triage) are not Officers. Decides how to split and order work inside its brief, may send out Workers, accepts or rejects its Workers' findings with a reason. May not change the brief's done line, the workshop's `verify.md` or anyone's truth; reports to the Captain. The Commander may attach to an Officer's background session and speak to it directly (the owner: "I can hop on their sessions and answer questions"); the Officer acts on it and tells the Captain in its report.
  - Worker: always in a team, one responsibility. An agent the Captain sends out is in the Captain's team. Decides only how to do its own task, inside its own files. May not change scope, done, verify or truth, may not accept its own findings, does not send out agents, and never runs as a background session on its own. Reports to its Officer, or to the Captain when the Captain leads the team directly.
- Escalation: Worker to Officer to Captain to Commander. A Worker that finds its brief unclear, in conflict with truth, or needing files outside its list stops and returns `blocked` or `contradiction-found` with a one-line reason; it never guesses and never asks the Commander. PR 3 ships the actions, each its own skill, and every one of them sets `disable-model-invocation: true`, so only the owner starts it (none fires on its own, in plain chat or anywhere):
  - `/flight:capture <goal>`: adds one line `- <name>: <the ask in the owner's words> (<date>)` to `.flightdeck/workshops.md` (name chosen from the goal, unique, lowercase with hyphens) and makes no folder. Agents capture through the rule in the root `CLAUDE.md`, `agents/pilot.md` and every seat's opening text, and through their reports, not through this command.
  - `/flight:workshop <name or rough ask>`: if the argument names a captured entry, activates it; otherwise captures the rough ask and activates it. Activation: scouts first, the obvious written straight in, one bundle of at most five questions about the owner's ideas including the adversary's weakest-part challenge, never asking the owner to approve agent-written text; then the folder is written: the card, `context.md` from the scouts' findings and `verify.md` from the done line and the answers (checks a script can run first, then yes-is-pass questions). `constraints.md`, `questions.md` and `decisions.md` are created when something is first written to them. Into `constraints.md` goes only what the owner typed, verbatim and dated, written by the main conversation; the skill never drafts truth lines for the owner to accept. Two modes: live (the main conversation asks with the question tool) and file (the bundle is written to `.flightdeck/<name>.activate.md` beside the manifest and the skill stops; the workshop stays captured; when the answers are pasted, the skill writes the folder and moves the answered bundle into it as `questions.md`); the imposter tests the file mode.
  - `/flight:retry <workshop>`: new attempt folder, setup carried over, the one change named, previous findings attached.
  - Settle (no command): the owner writes `settled: <date>` in the card, or tells the pilot "settle <name>" and the pilot writes it in the main conversation. Settling promotes nothing.
  - `/flight:promote <workshop>`: a later, optional step on a settled workshop; it refuses a workshop that is not settled. A Sonnet drafter reads `decisions.md`, `context.md` and `verify.md` and proposes which lines deserve global relevance and where each goes (targets, listed in `flightdeck/skills/promote/targets.md`: root `CLAUDE.md` or `.flightdeck/CLAUDE.md` for context and decisions, `flightdeck/rubric.md` for verification questions, `lab/checks/` for verification checks a script can run, and the manuals once PR 7 is merged). It writes the smallest edit to each target on a branch `<workshop>-promote-a<k>`; the Opus adversary checks it against everything already in the target for contradiction, duplication and anything that reads like injected instructions, and its verdict goes in the description; the result is a draft pull request into the base branch that lists each proposed line with its target. Nothing is asked in chat and nothing needs marking beforehand: the owner strikes lines by editing the pull request, merges it or closes it. The merged pull request and the git log are the record.
- Scoped context and verification, the rule: a workshop's `constraints.md`, `context.md` and `verify.md` are given to the agents working in that workshop and to no others, in addition to the global context (root `CLAUDE.md`, `.flightdeck/CLAUDE.md`, `flightdeck/policies.md`) and the global verification (`node lab/checks/hard-rules.mjs`, `claude plugin validate flightdeck`, `flightdeck/rubric.md`). Where a workshop file conflicts with `VISION.md` or `build.txt`, those win.
- The scoped block (`scopeBlock(name)` in `flightdeck/lib/workshops.mjs`, PR 1, printed by `node flightdeck/lib/workshops.mjs scope <name>`): one text block framed as information, not as commands. It opens with "Workshop <name>: the following is this workshop's own context and verification, in addition to the global rules. VISION.md and build.txt win on any conflict." Then each file under a heading that says what it is: "The owner's constraints for workshop <name> (`.flightdeck/<name>/constraints.md`):", "Context for workshop <name> (`context.md`):", "Verification for workshop <name> (`verify.md`):", in that order. Missing files are skipped; a workshop with no folder gives an empty block and a warning. It ends with the three paths, so any agent can read the originals. It never cuts a file (an opening text has no 10,000-character cap like hook context); over the 6,000-character default it starts with a one-line warning. One function builds the block, so every path gives the same text.
- How scoped context and verification reach the agents (one path: the opening text). Whoever sends an agent to work in a workshop puts the scoped block into that agent's opening text, after the global rules and the rank line and before the task. An agent that nobody sends into a workshop gets no workshop text, so "that workshop only" holds by construction. The senders:
  - Launch workflows (PR 4), in code: a workflow script cannot read files or load modules (3.0), so each launch's first agent (Haiku, low) runs `node <plugin root>/lib/workshops.mjs scope <workshop> --json` and returns `{block, checks, questions}` through a schema. The script puts `block` into every later prompt, runs `checks` after the global checks, and gives `questions` to the reviewer, adversary and imposter with the global rubric. Builders in worktrees get the block in their prompt, so they depend on no file in the workshop folder and on no branch name.
  - The pilot, by instruction: when it sends an agent to work in a workshop, its body and every seat in `entry-points.md` tell it to run the `scope` command and paste the output into the opening text. This depends on the pilot following its instructions: [reviewed], and checked live (below).
  - Runners, at start: the ways-to-fly page gives a start command that puts the block into the runner's first prompt by shell command substitution (3.5); the runner, as an Officer, passes the block on in the opening text of every Worker it sends.
  - This build (`build.js`, section 5): from Run B, after PR 1 has put `.flightdeck/build-1/context.md` and `verify.md` on `build-1`, the gather agent runs the `scope` command for build-1 and returns `{block, checks, questions}`; the script adds the block to every prompt and the checks stage runs build-1's checks. In Run A those files do not exist yet and the plan's own checks are used.
  - Not built (dropped in verification): a scope hook on `SessionStart` and `SubagentStart` that chose the workshop from a `FLIGHTDECK_WORKSHOP` variable or the branch name. A background session does not carry shell variables (agent-view.md); a subagent worktree's branch is not the attempt branch (worktrees.md); a session-wide variable could hand one workshop's text to agents launched for another; and hook context phrased as rules can be shown to the user instead of used (hooks.md). If the owner later wants a hook, it comes as its own pull request.
- Truth guard (PR 1, part of `flightdeck/hooks/guard.mjs`): a `PreToolUse` hook on `Edit|Write`. It protects: an existing file inside the current project whose frontmatter on disk says `write: "human"`; any `constraints.md` under `.flightdeck/` (existing or new); and `.flightdeck/VISION.md` and `.flightdeck/build.txt`. Files under `flightdeck/templates/` are templates, not anyone's truth, and are not protected, so a builder (or a PR 1 retry) can write `flightdeck/templates/workshop/constraints.md` although it carries `write: "human"` for the files made from it. It denies the write when the caller is an agent: hook input has an `agent_id` (any subagent or workflow agent, including a subagent of type `flight:pilot`), or `agent_type` is `flight:runner`, or the environment variable `FLIGHTDECK_UNATTENDED=1` is set (every nested or background `claude` this plan starts gets it from a settings `env` block: runners, the imposter's nested sessions, evals, drills). The reason given: "This file holds the owner's own words; write a question in questions.md instead." The owner's own session, plain or pilot, has no `agent_id` and writes without a prompt. No approval prompt is ever shown. It fails open on an internal error. Limits stated plainly: it covers the Edit and Write tools only (a Bash redirect is not caught) and files inside the current project only (scratch clones elsewhere are not the owner's). `workshops.md`, `context.md` and `verify.md` are not owner-only: agents write them on the base branch.

## 5. The build run

The build is a series of workflow runs with the owner in between, because a workflow cannot wait for a person. Run A builds PR 1 only and stops. The owner tries PR 1 and merges it (or adds `PR 1:` lines and asks for a retry). Run B wave 1 builds PRs 2, 3 and 4 from the updated `build-1` and stops. After the owner has tried wave 1, Run B wave 2 builds PRs 6, 7 and 8 and stops. PR 5 is never built. Every run is a plain Claude Code workflow launched from a plain session (not a pilot session), with the flight plugin switched off in that session by the build settings (`enabledPlugins`), so FlightDeck's hooks, agents and skills take no part in building FlightDeck [probe item 11; fallback: the merged guards stay on in the build session, and the plan's writes are made to pass them: templates are not protected, no build agent writes a workshop's `constraints.md`, and the build's pushes match the git rule; the landing page says which held]. One exception, stated plainly: from Run B the gather agent runs one merged PR 1 script, the reader's `scope` command, to print build-1's scoped block (fallback: it prints the three files with `cat`). This keeps away from the owner's named mistakes "using the pilot to fitout the cockpit" and "using half built systems, to build out the half built system". One script serves all runs: `.flightdeck/build-1/workflows/build.js`, run by path with the Workflow tool, like `plan.js` (it is build residue, not a FlightDeck feature). Each run is launched from the owner's interactive session, so a usage-limit wait pauses the run instead of failing agents (harness-multi, workflows.md "When a run hits your usage limit"). The lead of each run sits as Captain; every other seat is a Worker (no seat in a build run is a team lead or a long-lived background session). Every prompt in every run carries its rank line: in Run A from this plan's 3.2 text, held in the script, and from Run B from PR 1's `entry-points.md`.

Fallbacks: no `effort` option means the script drops it and relies on agent files and the session's high effort; a multi-stage pipeline that does not behave means one stage function per pull request that calls the stages in order; if hooks cannot tell the owner's session from agents, the truth guard ships as a `CLAUDE.md` rule only and the review page is told; if a `--bg` session's hooks do not see a settings `env` variable, the truth guard still knows a runner by its `agent_type` and the README says the variable does not reach background sessions; if a `--bg` session does not receive a command-substituted first prompt, the ways-to-fly page starts the runner with a short prompt that tells it to run the `scope` command itself (marked [reviewed]); if `enabledPlugins` does not switch the plugin off, the guards stay on in the build session and the plan's writes are made to pass them (section 5 intro); if the allow rule does not cover the nested call, nested sessions run through a two-line wrapper script `.flightdeck/build-1/workflows/nested.sh` allowed by path; if `./flightdeck` does not load in place, the plugin stays at the repository root; if eval or an outside `--eval-dir` is unavailable, eval cases move to `flightdeck/evals/` or record "not available here"; if `agentType` fails, the script puts the agent file's body in the prompt; if `gh` fails, the land stage pushes branches and writes pull request bodies to files.

The date comes in through args because the script cannot read the clock.

### Script shape

- First statement `export const meta = { name: 'flightdeck-build-1-build', description: 'Build FlightDeck build-1 pull requests from the approved plan', phases: [...] }` with plain literals only; the body ends with a top-level `return`, never `export default`; no `Date.now` or `Math.random`.
- Constants: `OUT = '.flightdeck/build-1'`, `PLAN = OUT + '/attempts/plan/a2/plan.md'` (or the plan attempt the owner approves), a CONTEXT block every agent gets (the binding documents and `constraints.md` first; only owner documents bind; never push to main, never force-push, never delete a branch, never merge; the model ceiling in words; one paragraph per line; plain words; write only your owned files; report work outside your brief as a capture line, do not do it; from Run B, build-1's scoped block as returned by the gather agent), a findings schema (`severity` high, medium or low; `where`; `finding`; `evidence`; `suggested_fix`), and a build-return schema (`branch`, `commit`, `files`, `status` complete, blocked, contradiction-found or over-budget, `notes`, `captures`). The CONTEXT block contains no `model:` or `effort:` option literals, so the ceiling rule never matches it.
- Role text: builders and verifiers are plain workflow agents whose prompts include the role text from this plan, their rank line (in Run A from this plan's 3.2 text held in the script; from Run B from `entry-points.md`, whose rank lines the gather agent returns through its schema, because the script cannot read files), and, from Run B, the rubric in `flightdeck/rubric.md` and the seat text from `flightdeck/skills/team-plans/entry-points.md`; the project adversary (`agentType: 'adversary'`, fixed in stage 0) is used for the adversary seat in every run.
- Branch names are computed by the script: `build-1-pr<n>-<slug>-a<k>` for a pull request and `build-1-pr<n>-<slug>-a<k>-u<i>` for a unit. Slugs: 1 basic, 2 board, 3 workshops, 4 launches, 6 lab, 7 manuals, 8 band. The script refuses `prs` containing 5.
- Each pull request flows through `pipeline(prs, gather, brief, build, integrate, verify, triage, fix, land)` (or the single-function fallback), so pull requests move independently with no barrier. Every stage body is wrapped in try/catch and returns either its result or `{halt: reason}`, never `null`; a stage that receives `{halt}` passes it straight on; `land` opens a draft pull request explaining the halt, or, if nothing was pushed, marks the pull request "not built" in the return value. Nothing is retried silently inside the run.
- The nested installs are serialised: all imposter and live-check stages queue on one promise chain in the script, so two never touch the plugin registry at once.

### Stages, models and effort

- Gather (Haiku, low, one per pull request, not isolated): copies each source the plan names for this pull request with `git show origin/<branch>:<path>` into `<scratch>/pr-<n>/sources/` and returns the list; from Run B it also runs `node flightdeck/lib/workshops.mjs scope build-1 --json` on a checkout of `origin/build-1` and returns `{block, checks, questions}` plus the rank lines of the seats in `flightdeck/skills/team-plans/entry-points.md` (fallback: `cat` of build-1's three files and the `## checks` lines). Read-only to the repository.
- Brief (Opus, high, Worker, one per pull request): reads this plan's sections for the pull request, every `constraints.md` line that applies (untagged, `PR <n>:` or `persona:`), from Run B build-1's `context.md` and `verify.md`, on a retry the previous attempt's findings and report, and the gathered sources; returns, through a schema, the brief text: purpose; every owned file with a one-line content spec; files it must not touch; done written as yes-is-pass questions; the check commands with exact flags (from Run B including build-1's `## checks`); the five-minute try steps; the VISION sections served; the units (at most five for PR 1, three for the others, each with disjoint files).
- Build (Sonnet, high, Worker, `isolation: 'worktree'`, one per unit, in parallel): first command `git fetch origin && git switch -c <unit branch> origin/<base>`; writes only its owned files; adapts sources from `<scratch>/pr-<n>/sources/`; runs `node lab/checks/hard-rules.mjs` where it exists; commits by file name with the attribution lines; pushes the unit branch; returns the build-return schema. PR 1's units: (u1) the seven agents, the output style, `policies.md` with the chain of command, `rubric.md` and `persona.md`; (u2) the team-plans skill with all six team plans, the seat opening text with its rank line per seat and ways-to-fly, and the pre-flight skill; (u3) the hooks (card and guard), the shared reader with its `scope` command, and the test file; (u4) `CLAUDE.md`, `.flightdeck/CLAUDE.md`, the READMEs, `.flightdeck/workshops.md` and both manifests (including moving `plugin.json`); (u5) the six workshop templates, the build-1 workshop files (card, context, verify, questions, decisions), the hard-rule check, its test and `lab/owned/pr1.txt`.
- Integrate (Sonnet, medium, Worker, worktree, one per pull request): `git switch -c <PR branch> origin/<base>`, merges the unit branches, runs `node lab/checks/hard-rules.mjs --base origin/<base> --owned lab/owned/pr<n>.txt`, `claude plugin validate flightdeck` and the pull request's own tests (from Run B also build-1's `## checks`), commits, `git push -u origin <PR branch>`; writes `<scratch>/pr-<n>/diff.patch` (`git diff origin/<base>...<PR branch>`) and `<scratch>/pr-<n>/changed.txt`. Returns the branch and check results with exit codes and the last 20 lines of output.
- Verify (each in a fresh context, each a Worker; none sees another's output or the builders' transcripts):
  - Review (Sonnet, high, read-only, not isolated): reads the diff file and the brief, and `flightdeck/rubric.md` and build-1's `## questions` where they exist; checks every owned file exists and matches its spec, nothing outside the owned list changed, nothing under `dev/` or `.claude/rules/`, and the checks are real commands; findings only on correctness or the brief.
  - Adversary (Opus, high, cold mode, project agent `adversary`): its prompt opens with `=== The Work ===` giving the paths of the diff file, the changed-file list and the PR branch name, then `=== The Criteria ===`: the brief's done list, the VISION sections the pull request serves, `build.txt`, `constraints.md`, build-1's `verify.md` from Run B, the owner's pain points (`research/owner-truth.md` section 3), the model ceiling, and for any Claude Code claim section 3.0 of this plan with its sources; findings only on correctness or stated requirements, each with evidence a second reader can reproduce by reading files.
  - Human imposter (Sonnet, high): adopts `.flightdeck/persona.md` (in Run A, `research/owner-truth.md` and `dev/workspace/research/repo-reset/user-intent.md` directly, with the owner's `persona:` lines). Waits its turn on the install chain. Clones the repository into `<scratch>/pr-<n>/try/`, checks out the PR branch, creates a throwaway bare repository `<scratch>/pr-<n>/origin.git` and points the clone's `origin` at it, rewrites the clone's marketplace `name` to `DBHD-FlightDeck-try-pr<n>-a<k>`, records `claude plugin marketplace list`, then runs `claude plugin marketplace add <clone> --scope local` and `claude plugin install flight@DBHD-FlightDeck-try-pr<n>-a<k> --scope local` in the clone. A second fix round runs only when a script check is still red; after that the pull request opens as a draft marked "not green".
- Recheck (Opus, high, only when a high-severity finding was accepted): for each one, "is it fixed? yes or no, with a quote". An unfixed high finding makes the pull request a draft.
- Land (Sonnet, medium, Worker): writes `attempts/pr-<n>/a<k>/report.md` with provenance marks and `attempts/pr-<n>/a<k>/log.md` (stages, agents, ranks, models and effort, transcript paths, token totals where available), commits both to the PR branch, then `gh pr create --base build-1 --head <PR branch> --title "PR <n>: <title>" --body-file <report>`, adding `--draft` when anything is still open or any try step is [stated]. The body leads with the five-minute try and its measured time, then checks [checked], verification [reviewed], findings and their resolutions, size, the models used per stage, and how to retry this pull request alone. Never `main`, never `--force`, never a merge; the owner merges. Returns the URL.
- Combined check (Run B only; Sonnet, medium, worktree, after all pipelines of the wave): creates a local, unpushed branch from `origin/build-1`, merges every PR branch of the wave, runs the hard-rule check, `claude plugin validate flightdeck`, build-1's `## checks`, every pull request's tests and, in wave 2, `node lab/drills/remove-part.mjs` and `node lab/drills/sweep.mjs` from PR 6's branch; a Haiku agent lists any file changed by two pull requests. Reports merge conflicts and failures for the landing page.
- Landing page (Sonnet, high, after all pipelines): first a single real install rehearsal on the install chain (in a clone of the newest branch, with the renamed marketplace: add, install, one `claude -p` smoke, uninstall, compare the marketplace list); then `.flightdeck/build-1/attempts/run-<A|B1|B2>-a<k>.html` built with the page kit's rules (PR 2's `theme.css` once merged): one plain card per pull request with what it adds, its try steps with a copy button, results, open findings and how to retry it, plus a panel that copies a reply in the stage-0 format. The Run B wave 1 page also asks every build-1 question whose `ask-later:` line names that page (the workshop, launch and attempt reading), with the lead's reading as the recommended answer and an answer line in the reply panel. The imposter reads the page as the owner; one Sonnet fixer applies its findings.
- Clerk (Haiku, low, main checkout on `build-1`): commits the landing page, the probe record, the combined-check report and (in Run B, where `questions.md` and `workshops.md` already exist on `build-1` and no PR branch touches them) triage's questions in `.flightdeck/build-1/questions.md` and capture lines in `.flightdeck/workshops.md`, by file name, to `build-1`, and pushes `build-1`. After Run B wave 1 it also removes the `ask-later:` line from the questions that page asked, so they become ordinary open questions on the card and the board. The lead tells the owner where the page is and stops.
- Return: `{prs: [{n, branch, url, draft, checks, findings_open, status}], page}`.

### Numbers, time and cost

- Agents per pull request: gather 1, brief 1, build 1 to 3 (5 for PR 1), integrate 1, review 1, adversary 1, imposter 1, checks 1, live check 1, triage 1, fix 1, recheck 0 or 1, land 1: 12 to 15 (17 for PR 1). Tiers per pull request: Opus 3 or 4 (brief, adversary, triage, recheck), Sonnet 7 to 9 (1 to 3 builders, plus integrate, review, imposter, live check, fix, land; 11 for PR 1), Haiku 2 (gather, checks).
- Run A: about 21 agents (PR 1's 17 or so, plus landing page, page imposter, page fixer and clerk), plus the stage-0 probe (about 7 Haiku agents). Run B wave 1 (PRs 2 to 4): up to about 51 agents. Run B wave 2 (PRs 6 to 8): up to about 51 agents. Far inside the 1,000-agent cap; the concurrency cap (default up to 16, fewer on small machines; `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` raises it) queues the rest.
- Time and usage, the lead's rough guess and not measured: Run A one to two hours; each wave two to four hours. Run A has fewer Opus agents than a planning run, so it should use less of the weekly limit than planning did; each wave of three pull requests uses roughly two to three times Run A. Every `log.md` records actual use per stage, so the next estimate is measured, and the landing page shows the totals.
- If a usage limit is hit mid-run: the workflow pauses and waits for the reset (launched from an interactive session); nested `claude -p` sessions do not wait, so an imposter or live check that hits the limit reports [stated] and its pull request opens as a draft. The end of Run A and of each wave are the "stop here and show me" points.
- Models: Opus at high effort for the lead, briefs, adversary, triage and recheck. ## 6. Dogfooding

- The build is a workshop. `.flightdeck/build-1/` already holds the owner's truth (`constraints.md`), research, plans and review pages; PR 1 lists it in `.flightdeck/workshops.md` as the first active workshop and adds its card, `context.md`, `verify.md`, `questions.md` and `decisions.md` (the lead's decisions from this plan, each with a reason, ready for the owner to strike). The first pre-flight card the owner sees is FlightDeck reporting on its own build.
- The build uses its own scoped context and verification: from Run B, every build agent gets build-1's `context.md` and `verify.md` in its prompt, and every pull request must pass build-1's `## checks` on top of the global checks. A lesson that triage keeps hitting becomes a line in build-1's `context.md` on the base branch, so the next wave starts with it.
- The build captures what it finds: work outside a pull request's scope becomes a line in `.flightdeck/workshops.md`, waiting for the owner to activate, instead of being done unasked.
- The owner answers the build's questions through FlightDeck: questions triage could not settle land in `.flightdeck/build-1/questions.md`; the card counts them, and after PR 2 the owner answers them on the board and pastes the block back, so the board's first real use is about FlightDeck itself.
- The build's seats follow the chain of command: the lead is Captain and every other seat is a Worker. The rank lines in their prompts come from this plan's 3.2 text in Run A and from PR 1's `entry-points.md` from Run B.
- The build does not run FlightDeck: every build run is a plain Claude Code workflow from a plain session with the flight plugin switched off [probe item 11]. The one thing it uses from FlightDeck is the merged reader's `scope` command from Run B, with a `cat` fallback. Nothing from an unmerged pull request is used. If the plugin cannot be switched off, its merged guards stay on in the build session and the build's writes are made to pass them (section 5 intro).
- FlightDeck builds part of itself: the demo launch in PR 4's try is a real improvement to FlightDeck's own card (`demo-attempt-age`, an example task the lead made up and captured in PR 1; the owner activates it and launches it once PRs 1 and 4 are merged), returning a draft pull request.
- The lab tests the build: wave 2's combined check runs the sweep and remove-part drills across that wave's branches, and the interview drill pits PR 3's interviewer against the withheld-fact imposter. The first real climb (once PR 6 is merged) improves `flightdeck/skills/team-plans/SKILL.md`'s description (the team plans skill, which Claude may load by itself when choosing how to fly; the workshop skill is owner-only, so it is not a climb target) on should-fire and should-not-fire cases written for that climb and returns a draft pull request or an honest "within noise, do not merge".
- Promotion closes the loop: once PR 3 is merged, the owner settles build-1 with a `settled:` line and, if they want, runs `/flight:promote build-1`, which proposes lasting decisions, context lines and checks (for example "FlightDeck writes nothing into `.claude/`", or the branch-name trap) as a draft pull request against `CLAUDE.md`, `flightdeck/rubric.md` or `lab/checks/` that the owner merges or closes.
- After the build, "retry PR n" can run through `/flight:launch` on the build-1 workshop with the `PR n:` lines as extra truth, instead of `build.js`, once PRs 1 and 4 are accepted.

## 7. Risks, and what not to build

### Risks

- Protected paths: every Claude write under `.claude/` asks for approval outside bypass mode, and a directory loaded with `--plugin-dir` becomes protected for writes. Mitigation: FlightDeck lives in `flightdeck/` and `.flightdeck/`; the single `.claude/` edit happens in stage 0 with the owner present; the owner installs through the local marketplace; `--plugin-dir` is never used.
- The owner's real install: a nested `marketplace add` with the same name would repoint it (tested by the fact check). Mitigation: every scratch install uses a renamed marketplace, installs are serialised, the build settings deny removing or uninstalling the real one, and the marketplace list is compared before and after.
- Unverified features (section 3.0 [probe] items): stage 0 settles them before building, and each part names its fallback.
- Scoped context reaches an agent only when whoever sends it puts the block in its opening text. Launch workflows and `build.js` do this in code (tested with a stub agent); the pilot and the runner do it by instruction ([reviewed], checked live by the `scope-probe` check). An agent the owner starts by hand without naming a workshop gets no workshop text. Mitigation: the opening text of every seat says where the block goes; the live check shows whether the pilot does it; the landing page says what was seen.
- The launch's first agent returns the block through a schema, so a model copies it. Mitigation: the block ends with the three file paths so any agent can read the originals; the launch dry run checks that the fixture's checks arrive intact; the scope stage is Haiku at low effort, a simple copy.
- The owner's installed FlightDeck may stay active in the build session if `enabledPlugins` does not switch it off (probe 11); its merged guards would then run on build agents. Mitigation: the build's writes are made to pass them (templates are not protected; no build agent writes a workshop's `constraints.md`; build pushes go only to `build-1-*` branches), and the landing page says which held.
- Scoped files enter many prompts. A wrong or stale line in a workshop's `context.md` misleads every agent in that workshop, and text in them is agent-written. Mitigation: `context.md` and `verify.md` are edited only on the base branch; the block says `VISION.md` and `build.txt` win on conflict; the size default and lint warning keep them short; the adversary checks anything promoted to global files; the truth guard keeps agents out of `constraints.md`.
- A workshop's `## checks` are commands that agents run. Mitigation: they run only in a worktree under the launch's or the build's permissions, the git rule and the build's deny list apply to them, and the reviewer reads `verify.md` like any other changed file.
- The guards are safety nets, not a permission system: the git rule misses git run from scripts or aliases; the truth rule misses Bash redirects; the ceiling rule misses the session's own start-up model and effort. Mitigation: hook tests, the build's deny rules and push-check, GitHub branch protection (suggested by `/flight:preflight`), the managed ceiling settings (offered by `/flight:preflight`), review, and the owner's merge. No claim is made beyond what each rule does.
- Plugin hooks fire in every session and subagent where the plugin is enabled. Mitigation: narrow matchers and `if` rules, the card only in pilot sessions, no hook that adds workshop text, the git and truth rules only for agents, exit 0 on internal errors except the push rule.
- Ranks are guidance, not enforcement: a Worker that oversteps is not stopped by a hook. Mitigation: each seat's rank line says what it may not decide, and each agent body's fallback line covers agents sent without one; the reviewer checks scope against the brief; the ownership check fails a pull request that touched files outside its list; the owner merges. The owner's earlier note called ranks "not enforceable but role guidance northstar".
- Agent renames since attempt 1 (`officer` to `runner`, `worker` to `builder`): anything written against the old names (attempt 1's review page, notes on other branches) is out of date. Mitigation: only this plan's names are used in the build; the review page lists the renames.
- Agent `effort` in frontmatter may not apply to a main-thread agent (measured once on an older CLI in the cockpit's `pilot.sh`). Mitigation: the quick start passes `--model opus --effort high`.
- Two adversary definitions exist: the owner's project agent in `.claude/agents/adversary.md` (used by `plan.js` and the build) and the plugin's `flightdeck/agents/adversary.md`. Accepted: they serve different callers, and the owner said the adversary stays.
- The persona is agent-written and every imposter verdict leans on it. The owner called it "fine"; later corrections come as `persona:` lines.
- Nested `claude -p` sessions cost tokens and do not wait out usage limits. Mitigation: Sonnet or Haiku only, stop at the try steps, [stated] results open the pull request as a draft.
- Eval cases are model-graded and can be noisy. Mitigation: they never block, each run has `--max-cost-usd`, `--no-publish` keeps reports local, and the climb rule reverts changes inside the noise.
- Model aliases differ by provider (on Bedrock `sonnet` may be an older model). Mitigation: aliases kept for readability; the technical manual (PR 7) says how to pin full model ids.
- The workshop, launch and attempt reading ("a workshop is the place, a launch is one flight from it, an attempt is what a launch leaves behind") is still the lead's. The owner said to use it and ask again later; it waits in build-1's `questions.md` marked `ask-later` and is asked on the Run B wave 1 landing page.
- The rank behaviour beyond the owner's words (who decides what, escalation, address) is the lead's proposal. Mitigation: it is written in build-1's `decisions.md` and shown on the review page for the owner to strike; nothing in it is tested as a hard rule.
- Small machines run few workflow agents at once, so a build run is a queue and takes longer. Mitigation: stated on the review page; the owner can raise the concurrency variable.

### What not to build

- No central runner like `fc`, no launch state machine, no `run.json`, `launch.json`, `HALT.json`, gate switches, state manifests or escalation files: the folder listing, `workshops.md`, `settled:` lines and empty `answer:` lines are the state. The one manifest is `.flightdeck/workshops.md`: one markdown line per workshop, as the owner asked.
- No JSON files for owner-facing documents; questions, decisions, truth, context, verification and the workshop list are markdown.
- No rank in any agent's file name or `name:` (the owner's note), no rank in descriptions (the lead's choice), no rank-to-model mapping, and no rank as an agent's identity: an agent body holds only a fallback rank line for when its opening text gives none. Four ranks, as the owner foresaw; a fifth only if the owner adds one.
- No record prefixes, numbered requests, approval states or global registers; no required phrases, no fixed report line, no seat numbering and no callsign scheme; no truth statements required for every item; the owner is never asked to approve agent-written text in chat (promotions arrive as draft pull requests the owner merges, edits or closes).
- No automatic activation: a captured workshop waits until the owner activates it; no agent activates, settles or promotes a workshop; `capture`, `workshop`, `launch`, `retry` and `promote` cannot be started by the model.
- No scope hook in this build (dropped in verification, 3.4), no guessing a workshop from a branch name or a session variable, no `promote:` markers and no `promoted:` marks.
- No local CLI: PR 5 was skipped by the owner, so there is no `flightdeck/bin/`, no `flight` command, no web server and no bulk-commit command in this build.
- No rules in `.claude/rules/`, nothing under `dev/`, no changes to `INTENT.md` or `HISTORY.md`, no plan to retire dev-workspace.
- No replacement for Claude Code's teams, messaging, memory, worktrees, permissions or managed model settings; FlightDeck fills their slots, gives team plans and points at the native controls.
- No spec-first nine-domain spec chain as the default (Spec first ships as one of the six team plans).
- No large test suites of the tooling; one fast check per part, warnings for everything that is not a hard rule, and drills and eval cases in the lab.
- No default agent, no forced output style, nothing that starts on its own: no automatic launches, activations, promotions or climbs.
- No `fable`, `best`, `xhigh` or `max` in any model or effort value, and no ultracode.
- No push to `main`, no force-push, no deleted branch, no merge by an agent.
