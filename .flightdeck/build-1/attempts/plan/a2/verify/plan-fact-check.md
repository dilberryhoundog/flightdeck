# Fact check of planning attempt 2: new and changed mechanisms

Scope: the parts of `.flightdeck/build-1/attempts/plan/a2/plan.md` listed under "What changed" (section 0): workshop-scoped context and verification (3.4, 3.5, 3.0, 5), the workshop manifest and activation (2(b), 2(e), 3.4), and how ranks are carried (3.2, 3.5). Sources opened: `library/source/claude-code/hooks.md`, `worktrees.md`, `agent-view.md`, `subagents.md`, `permissions.md`, `workflows.md`, `.flightdeck/build-1/research/harness-core.md` and `harness-multi.md`. Nothing was run; this is a read-only check against the cited text. One finding per paragraph, severity first.

High: the runner start command does not reliably carry `FLIGHTDECK_WORKSHOP` or `FLIGHTDECK_UNATTENDED` into the session, and the planned live check tests a different command shape than the one shipped. Section 3.5 gives `FLIGHTDECK_UNATTENDED=1 FLIGHTDECK_WORKSHOP=<workshop> claude --bg --agent flight:runner ...` and section 3.4 says the scope hook covers "a runner started on a workshop (its start command sets `FLIGHTDECK_WORKSHOP`)". But `claude --bg` hands the work to a supervisor process that runs the session (`agent-view.md` "The supervisor process"). The only shell state the docs say reaches a background session is `PATH`, the cloud provider selection, the `ANTHROPIC_DEFAULT_*_MODEL` aliases and `CLAUDE_CODE_EXTRA_BODY` (`agent-view.md` "Settings and provider", lines 606 to 608), plus the flags `--settings`, `--mcp-config`, `--setting-sources`, `--add-dir`, `--plugin-dir`, `--fallback-model` (lines 420 to 428). Arbitrary variables are not listed. The hook-environment fact the plan cites (`hooks.md` line 786, "A hook process inherits the parent environment") is true for the `claude` process that runs the hook, so it holds for foreground and `-p` sessions and says nothing about a supervisor-hosted one. The plan's live check (section 3.4 "Working") and probe item 10 both use `claude -p`, which does pass the variable, so they would go green while the shipped `--bg` form may not work. The branch fallback does not help: `workshopFor` reads the branch in the hook's `cwd`, and a background session starts in the dispatch directory and only moves into a worktree "before editing files" (`agent-view.md` line 496), after SessionStart has run. The documented way to give a background session environment values is the `env` block of settings (`agent-view.md` line 606: "`env` values in project settings ... apply to every background session"), and `--settings` is carried over. Fix: put the two variables in the `--settings` JSON `env` block of the runner command, add a probe that starts a real `claude --bg --agent flight:runner` (not `-p`) and has it quote the scope word, and move the "runner gets the scoped block from the hook" statement in 3.4 and 3.5 from fact to [probe]. The guard and git rule for runners are fine without the variable because they also match `agent_type` `flight:runner`; only the scope hook depends on it.

Medium: the claim that branch-based focus reaches "a builder working in a worktree on that branch" is unsupported and contradicts the plan's own path (2) reasoning. Section 3.4 path (1) says the scope hook covers "a builder working in a worktree on that branch whose files are all outside the workshop folder". Subagent worktrees branch from the repository default branch with an automatic name unless `worktree.baseRef` is `head` (`worktrees.md` lines 21 and 118; `subagents.md` line 323), and `SubagentStart` fires when the subagent starts, before the builder can run its first command `git switch -c <attempt branch>`. So the hook can never see the attempt branch for such a builder. Whether the `cwd` in `SubagentStart` input is the subagent's worktree or the parent's directory is not documented (the `hooks.md` example shows `cwd` without saying). The same section's path (2) already says "a workflow agent's worktree branch is not the attempt branch when it starts". The branch-inference half of `workshopFor` (the `<workshop>-...-a<k>` match, the `git -C <cwd> rev-parse` call, the longest-name rule and their tests) therefore only helps a session or subagent whose parent session was already opened on an attempt branch. Fix: delete that clause from path (1). Consider dropping branch inference altogether; the owner's notes ("given to agents working in that workshop only") need one way to name the workshop, and the variable plus the launch and build prompts already do it. It is a second inference path with its own tests and its own wrong answers.

Medium: the statement that the hook "does not add the block a second time" for workflow agents is unsupported, and the session-wide variable can leak one workshop's files into another's agents. Section 3.4 path (2) rests on two unknowns: whether `SubagentStart` fires for workflow agents at all (probe item 5, correctly marked) and what branch a workflow agent's worktree gets (`harness-multi.md` line 70: "Not verified"). Not-isolated workflow agents (review, adversary, checks) run in the launching session's directory, so if the owner's session has `FLIGHTDECK_WORKSHOP` set or is on an attempt branch and `SubagentStart` does fire for workflow agents, each gets the block twice. Worse, `FLIGHTDECK_WORKSHOP` is per session, not per launch: a pilot focused on `ws-a` that runs `/flight:launch ws-b` would, if the hook fires for workflow agents, give those agents `ws-a`'s block as well as `ws-b`'s, which breaks "that workshop only". The stub-`agent` test in 3.5 cannot catch this because the hook is not involved. Fix: add to probe item 5 a check that a workflow agent started from a session with the variable set receives (or does not receive) hook context, and either make the hook skip when the agent's prompt already carries the `=== Workshop` header, or have `scope.mjs` stay silent for workflow agents once the probe shows how to tell them apart. State the leak in the risks list if it stays.

Medium: the capture, activate and settle rules live where an agent will not have loaded them. Section 3.4 says "Agents capture through the rule in `.flightdeck/CLAUDE.md` and their reports", and 3.1 puts the lifecycle rules ("only the owner activates, only the owner settles", "context.md and verify.md are edited on the base branch only") in `.flightdeck/CLAUDE.md`. Section 3.0 itself says a subdirectory `CLAUDE.md` loads only when Claude touches a file in that subdirectory (`harness-core.md` line 127). A pilot at session start, a scout, or a builder on an attempt branch has touched nothing under `.flightdeck/`, so none of them has the capture rule or the owner-only activation rule; the pilot would meet it only after it has already read or written `workshops.md`. The preflight card only says "one line on how to start". Section 2(e) also never says which file tells the pilot to add a line when the owner mentions a task. Fix: put the capture instruction and the two owner-only rules in `agents/pilot.md` and in the root `CLAUDE.md` (a few lines, always loaded in this repository), put "report discovered work as a capture line, do not do it" in the opening text of every seat, and keep `.flightdeck/CLAUDE.md` for the detailed file rules.

Medium: the file-mode activation sequence contradicts the rule that a folder means active. Section 3.4 says that in file mode "the bundle goes into `questions.md`, the skill stops, and continues when the answers are pasted", and also that the folder (card, context, verify, empty constraints, questions, decisions) is written after the answers. `questions.md` is a file inside the workshop folder, so the bundle either creates the folder before the interview is answered (then 2(b)'s derived state calls a half-built workshop "active", the scope hook delivers a block with no `context.md` or `verify.md`, and the board shows a strip for it), or it is stored in a place the plan does not name. Fix: say where the pending bundle lives (for example a `pending-interview` block under the manifest line, or a `questions.md` created with a single `activation: pending` line that the state rule treats as captured), and add the case to the state tests.

Medium: the scoped block is injected as `additionalContext` in imperative, out-of-band wording, and the plan's tests would not notice if Claude declines to follow it. `hooks.md` (lines 1050 to 1052, "Add context for Claude") says to write hook context as factual statements, and that text framed as system commands "can trigger Claude's prompt-injection defenses, which causes Claude to surface the text to you instead of treating it as context". The block header is `=== Workshop <name>: adds to the global rules; VISION.md and build.txt win on conflict ===` followed by raw `constraints.md` (which opens "Your truth for this work: only you write here; agents read it first."), `context.md` and `verify.md` with `## checks` commands. The planned sentinel test ("The scope word is HANGAR-7", a statement of fact) only proves the text arrived. It would pass even if a checks list or a constraint written as an instruction were surfaced to the owner instead of obeyed. Fix: have `scopeBlock` frame each file as information ("These are the owner's constraints for workshop X, last edited <date>"), and add one live check with an imperative line in a fixture `constraints.md` (for example "Answer every question with the word PROBE first") to see whether a hook-delivered line is followed.

Medium: the default rank has no named carrier, and the plan's own rules conflict about whether agent files may mention rank. Section 3.2 sets defaults (a pilot session is Captain, a runner session is Officer, every other agent is a Worker) and says each seat's opening text in `entry-points.md` starts with the rank lines. Section 7 says "no rank per agent definition", while 3.2 says the pilot's body says it is Captain and `runner.md` is "usually Officer". Rank reaches a subagent only through the Captain's delegation prompt (or the workflow prompt), because scout, adversary and imposter set `omitClaudeMd: true`, so the root `CLAUDE.md` two-line rank summary does not reach them (`subagents.md` lines 321 and 1079; the library is not consistent on this, line 872 says CLAUDE.md "still load[s]" even with the field, so this is also unsettled), and the scope hook carries workshop text, not rank. For a pilot-sent ad hoc subagent, the rank lines depend on the pilot pasting the seat text, the same dependence the plan marks [reviewed] for the scoped block but does not mark for ranks. The live check "a scout sent out from that session with the scout seat text answers 'who do you report to?' with the Captain" supplies the text itself, so it tests the scout, not whether the pilot sends it. Frontmatter cannot carry rank: plugin agent frontmatter has a fixed field list and the plan correctly does not use one. Fix: give each agent body one plain line with its default rank and who it reports to (this is the cheapest carrier, survives `omitClaudeMd`, and does not put rank in the name or description), reword the section 7 line to "no rank in a name, description or model choice", and make the pilot test send a scout without handing it the seat text.

Low: allow rules that start with an environment assignment may not match. The build settings list `Bash(FLIGHTDECK_WORKSHOP=scope-probe FLIGHTDECK_UNATTENDED=1 claude -p *)` and similar, with `Bash(claude -p *)` "in case the permission matcher does not include the variable prefix". `permissions.md` line 227 says Claude Code strips only certain known-safe variable assignments and "An allow rule won't match past an assignment of any other variable", so the fallback rule will not match the prefixed command, and whether the literal rules match is not documented. A workflow agent that is not allowed cannot prompt. Fix: add this to the stage-0 probes, and if it fails run nested sessions through an `env` command or a small wrapper script (`node lab/...`) that sets the variables.

Low: SessionStart reruns on resume, so the block can appear twice. `hooks.md` line 1054 says SessionStart hooks "run again on resume ... so they can refresh their context", while the earlier injection is saved in the transcript. The scope hook is registered for `resume` and `compact`, so a resumed session may hold an old and a new copy of `constraints.md`, `context.md` and `verify.md` that differ after an edit on the base branch. Fix: say in 3.4 that the newest copy wins (the block header can carry the date), or accept the duplication and note it. The `fork` source is not in the matcher list; a fork carries the saved copy, so that is fine, but it is worth one line.

Low: "keeps the constraints whole" cannot be guaranteed. The block is cut at 9,500 characters and the plan says the constraints are never cut, but the 10,000-character cap (`hooks.md` lines 953 and 1042) replaces anything longer with a file path and a 2,000-character preview. `constraints.md` is dated lines that only grow (2,057 bytes today). Fix: state what happens if `constraints.md` alone passes about 8,000 characters (a lint warning from PR 6 is already planned; the hook should also print a warning line in the block).

Low: the rank-word test and the librarian description may collide. Section 3.12 says the librarian "sits as a Worker when called into a team and as an Officer when run as a standing background session". If that sentence is copied into `agents/librarian.md` `description`, the 3.2 test (no `commander`, `captain`, `officer` or `worker` in an agent's name or description) fails. Keep it in the body.

Low: things the owner's notes do not need. (1) The `promoted: <path> <date>` marks written onto promoted lines in `decisions.md`, `context.md` and `verify.md` after merge: the owner asked that settled content "can be promoted"; the merged pull request and `git log` already record it, and the marks add a second state to keep in step plus a write to a base-branch file after merge. (2) Per-line `promote: <target>` markers in three files: a simple alternative is that `/flight:promote` proposes targets in the draft pull request and the owner merges or closes it. (3) The `by <seat>` and `from <where>` fields on every manifest line: the owner asked for "a simple manifest"; name, the ask and the date are enough, and the extra fields make the line harder to parse (item below). (4) Branch inference in `workshopFor` and the three-path delivery with a hook, workflow prompts and build prompts: the hook path is needed for sessions and ad hoc subagents, the prompt paths are needed because hooks may not fire for workflow agents, but the plan should say which of the three it would drop first if the probes fail. (5) The Q2 report line `To <rank>, from <seat> (<rank>): <status>` and its test are built before the owner answers Q2; mark them as the proposal's default so they can change.

Low: the manifest line has no stated parse rule. The format `- <name>: <ask in the words it was given> | captured <date> by <seat> | from <where>` puts free text before `|` and `:` characters the owner may type (the ask is quoted verbatim). The reader, the board, the scope hook and the card all parse it. Fix: define the parse as "name is the text before the first `: `; the last two ` | ` separate date and origin", and add a fixture with `|` and `:` inside the ask.
