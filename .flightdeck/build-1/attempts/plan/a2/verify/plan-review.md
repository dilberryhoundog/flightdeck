# Review of planning attempt 2 (plan.md) against the owner's notes, VISION.md and build.txt

Reviewed 2026-10-11 against `.flightdeck/build-1/constraints.md` (lines dated 2026-10-11), `.flightdeck/VISION.md` and `.flightdeck/build.txt`. Result of the leftover search: no old rank title (Major, Lieutenant, Sergeant, Corporal, Private, Warrant Officer), no `flight:officer` or `flight:worker`, no rank-to-model check and no PR 5, `bin/` or CLI item survives anywhere except in section 0 and the "not built" statements, where they are described as removed. File counts per pull request, the wave totals (51, 55, 50) and the overall totals (156 files, 8,450 lines) add up. The findings below are what remains.

medium: `/flight:workshop` (activation) is not marked `disable-model-invocation: true`, which contradicts "no automatic activation" and "nothing that starts on its own". Section 3.4 (Features) sets the flag only on `capture`, `retry` and `promote`; section 3.11 says "Capture, launch, retry and promote cannot start on their own" and the hard-rule check verifies only those four; activation is missing from both. The plan also builds evals named `pr3-workshop-fires` and a climb on the workshop skill's "should-fire and should-not-fire" cases, which only make sense if Claude may invoke it by itself. Q1 and section 7 say only the owner activates. Either set the flag and drop the should-fire eval and climb target, or state that model invocation is allowed and only on the owner's request.

medium: the demo workshop is activated by a pull request, not by the owner, and the files PR 4 lists cannot be written by a build agent. Section 3.5 lists `.flightdeck/demo-attempt-age/{workshop.md,constraints.md,questions.md,context.md,verify.md}` as PR 4 files, written by a PR 4 builder. (a) A folder is the definition of "active" (2(b)), so merging PR 4 activates the entry, while Q1, 2(e) and section 7 say only the owner activates and no agent does. (b) `constraints.md` carries `write: "human"` and the truth guard denies every agent write to such a file, including new content with that frontmatter and including workflow agents (they have an `agent_id`), so the PR 4 builder is blocked from creating it. The same clause blocks a PR 1 retry from writing `flightdeck/templates/workshop/constraints.md`. (c) The list has five files but activation makes six (`decisions.md` is missing; 3.4 tests "activation makes the six files"). (d) Once PR 4 is merged the demo is active, so the PR 2 try step "see `demo-attempt-age` under Waiting to start" and the first-hour line "one captured entry waiting to start" stop being true. Fix: have the owner activate the demo with `/flight:workshop demo-attempt-age` as a try step of PR 4 (so no demo folder ships), or have the main conversation write the folder, and say how the guard treats the template.

medium: settling and promoting are merged into one command, which differs from the owner's words. The owner wrote "once settled, workshop content can be promoted to global relevance" (settle first, promote as an option after). Section 3.4 and Q1 make `/flight:promote` write `settled: <date>` and promote in the same action, so a workshop cannot be settled without promoting, a workshop with nothing to promote needs a command named promote to be settled, and promotion cannot happen before settling. Section 0 presents the four-step lifecycle as the owner's. Either add a separate settle action (or a hand-written `settled:` line documented as the way), or put this coupling to the owner as a question; Q1 asks only who settles, not whether the two are one step.

medium: the status band cannot import the shared reader the plan says it imports. Section 3.1 says "the card, the scope hook, the board (PR 2), the launch workflows (PR 4) and the band (PR 8) import" `flightdeck/lib/workshops.mjs`, and 3.14 says the band reads the same files with the same focus rule, but the band is a separate plugin installed from its own marketplace in `mods/status-band/` with a 7-file list that contains no copy of the reader. A plugin installed from `mods/status-band` does not have `../../flightdeck/lib/` available (the plan's own 3.0 only tested loading in place for a plugin at the marketplace root). Decide: copy the logic into `mods/status-band/` (and add it to the file list and the 7-file count), or say the band does not use the reader and how it keeps the same focus rule.

low: the PR 1 agent descriptions the plan itself writes would fail the plan's own rank-word test. Section 3.2 lists `flight:imposter` as "plays the Commander from `.flightdeck/persona.md`" and `flight:pilot` as "usually Captain"; the test requires that no agent file name, `name:` or description contains `commander`, `captain`, `officer` or `worker`. A builder copying these phrases into the `description:` lines fails the test. The plan should say the imposter "plays the owner" and that the rank sits in the body and opening text only.

low: the rank line is described two ways. Section 3.2 says each seat's opening text "starts with four lines" (`Rank:`, `Reports to:`, `You decide:`, `You do not decide:`) but writes it as one line with four sentences, and 3.5, section 5 and the tests say "a `Rank:` line". Pick one (one line is what the tests check).

Also the report line `To <rank>, from <seat> (<rank>): <status>` cannot apply to workflow agents that return schema results; say which seats use it.
