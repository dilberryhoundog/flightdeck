## 1. Purpose

PR 1 gives the owner a working Claude Code plugin called `flight`, in the folder `flightdeck/`, installed from this repository's local marketplace `DBHD-FlightDeck`. It holds everything a Claude Code user would recognise as content, plus the core files and locations build.txt names: seven agents named by function (pilot, runner, scout, builder, reviewer, adversary, imposter), the four-rank chain of command (Commander, Captain, Officer, Worker) in `flightdeck/policies.md`, the hooks (a pre-flight card for pilot sessions and guards for agents), rule files where the work happens (`CLAUDE.md`, `.flightdeck/CLAUDE.md`), the `/flight:preflight` skill, all six team plans with the opening text per seat and the ways-to-fly page, a one-page rubric, an optional radio output style, the workshop list `.flightdeck/workshops.md` and six workshop templates, build-1 as the first active workshop with its own `context.md` and `verify.md`, the reader's `scope` command, and the hard-rule check with its owned-file list.

After it lands the owner can fly with the pilot and crew, run recons and adversary attacks, have the pilot capture work and activate a bare workshop from the templates, start a runner on a workshop with its scoped context, and see the build's own state on the card at the start of every pilot session. Nothing in PR 1 starts on its own, and plain `claude` chat stays plain for the owner's own actions.

Owner's word on PR 1: "PR 1: okay as shown" (review replies of 2026-10-11). It grew from attempt 1 only where the owner's notes force it (four ranks and renames, three more team plans, the manifest, two more templates, build-1's context and verification files, the `scope` command): about 48 files and 2,300 lines.

## 2. VISION sections served

- Accelerate Claude Code: the plugin core in Claude Code's own places (agents, skills, hooks, output style, rules), a short pre-flight card instead of a large always-loaded document, short skill descriptions, blind roles that skip `CLAUDE.md`.
- Roleplay: the four ranks as a responsibility axis, rank given per seat (never in agent names), the pilot's one in-character greeting, the card title, the opt-in radio voice.
- Workshops: the manifest (capture), the templates (activate), build-1 as the first active workshop with its own context and verification, the `scope` command that hands a workshop's own files only to agents working there, the truth guard.
- Launches (content only): the six team plans, the opening text per seat, the ways-to-fly page with the runner command. The runnable launch is PR 4.
- dev-workspace: sits beside it; FlightDeck never writes under `dev/` or `.claude/rules/` and no FlightDeck script calls `dw`.
- Cheap tokens, smart agents: model and effort per agent by function, the ceiling guard, workshop-scoped context keeps prompts lean.
- Built with quality: the hard-rule check, the owned-file list, one test file per part.
- Human energy: truth devices (`constraints.md` guarded, `context.md`, `verify.md`, questions and decisions formats, the rubric, the persona, policies).
- Keep it simple: plain chat gets no card, no ranks, no workshop text, and the owner's own actions are never guarded.

Not served by PR 1: Themed HTML page suite (PR 2), Local CLI (PR 5, skipped by the owner, not built), Manuals and libraries (PR 7), Laboratory beyond the hard-rule check (PR 6).

## 5. Shared formats (every unit builds against these; nothing here may be changed by one unit alone)

### 5.1 Writing rules for every file

- One paragraph per line in markdown, no hard wrapping. Plain words, literal and direct. No tables in owner-facing text. Agent descriptions, skill descriptions and agent `name:` fields never contain the words commander, captain, officer or worker (any case).
- Model and effort only from plan section 3.8 (table in 5.9), never copied from a source. No `fable`, `best`, `xhigh` or `max` as a model or effort value anywhere.
- Never call `dw` or `dev-workspace` from an executable file. Prose may mention dev-workspace.

### 5.2 The manifest `.flightdeck/workshops.md`

- No frontmatter (it must never carry `write: "human"`, which would make the truth guard block agents). A heading `# Workshops`, then one plain sentence explaining the list (not starting with `- `), then one line per workshop: `- <name>: <the ask in the words it was given> (<YYYY-MM-DD>)`.
- Parse rule: only lines starting with `- ` are entries. The name is the text before the first `: `; the date is the last `(YYYY-MM-DD)` at the end of the line; everything between is the ask, which may contain `:`, `|` or brackets. Names are lowercase letters, digits and hyphens. A line with no date is kept with `date: null` and a warning; a line with a bad name gives a warning and is skipped. HTML comments (`<!-- ... -->`) and fenced code blocks are removed before parsing (Decided here: this lets templates and files carry format examples without being counted).
- State is derived, never stored: a line with no folder `.flightdeck/<name>/` is captured (and `pendingActivation: true` when `.flightdeck/<name>.activate.md` exists); a folder is active; a folder whose `workshop.md` has a line matching `^settled:\s*\d{4}-\d{2}-\d{2}\s*$` is settled. A folder that has a `workshop.md` but no manifest line is listed as active with a warning "not in workshops.md".

### 5.3 The card `.flightdeck/<name>/workshop.md`

- `# <title>`, a blank line, `work: <one paragraph>`, `done: <one line>`, and optionally `settled: <YYYY-MM-DD>` on its own line. No status field, no frontmatter.

### 5.4 `questions.md`

- A heading, then blocks. Each block starts `## q<n>: <question>` and holds lines `why: <text>`, `options: a) <text>; b) <text>; c) <text>`, `recommended: <letter>) <text and reason>`, `asked: <YYYY-MM-DD> by <who>`, optional `ask-later: <when>`, and `answer:` (empty while open). A block runs until the next `## ` heading.
- A question is open while its `answer:` line is empty (only spaces after the colon). A block with no `answer:` line counts as open and adds a warning. A block with a non-empty `ask-later:` line is not counted as open; it is counted separately as held for later.
- The paste-back block (used by PR 2's board and the pilot): first line `FlightDeck answers for workshop <name>: file these into .flightdeck/<name>/questions.md`, then one line per question `q<n>: <option letter or text> | note: <text>` or `q<n>: (unanswered)`, then `Other notes: <text>`.

### 5.5 `decisions.md`

- A heading, then one line per decision: `- <YYYY-MM-DD>: <decision>. Reason: <one line>.`

### 5.6 `verify.md`

- `# Verification for workshop <name>`, then `## checks` with lines `- \`<command>\`: <what passing looks like>`, then `## questions` with lines `- <yes-is-pass question>`. The command is the first backticked span of a check line; a check line with no backticks is taken whole and gives a warning. Headings match case-insensitively.

### 5.7 `context.md` and `constraints.md`

- `context.md`: `# Context for workshop <name>`, then one paragraph per line, about 40 lines at most. Edited on the base branch only.
- `constraints.md`: frontmatter `read: "agents"` and `write: "human"`, then the line "Your truth for this work: only you write here; agents read it first.", then one dated line per item. Only words the owner typed go here.

### 5.8 Attempts and the latest-attempt rule

- An attempt is any folder named `a<k>` (k a positive integer) at any depth under `.flightdeck/<name>/attempts/`. Attempts are grouped by their parent folder relative to `attempts/` (`""` for `attempts/` itself, `pr-1`, `plan`). The latest in each group is the highest k. Labels: `a3` for the root group, `pr-1/a2`, `plan/a2`.

### 5.9 Agents: names, models, tools (plan 3.2 and 3.8)

- `flight:pilot`: `model: opus`, `effort: high`, tools `Agent, Workflow, AskUserQuestion, Skill, Bash, Read, Grep, Glob, Edit, Write`, color blue.
- `flight:runner`: `model: sonnet`, `effort: high`, tools `Agent, Workflow, Skill, Bash, Read, Grep, Glob, Edit, Write`, color purple.
- `flight:scout`: `model: haiku` (no effort line; Decided here), tools `Read, Grep, Glob`, `omitClaudeMd: true`, `maxTurns: 40`, color cyan.
- `flight:builder`: `model: sonnet`, `effort: high`, tools `Read, Edit, Write, Bash, Grep, Glob`, `isolation: worktree` (Decided here), color green.
- `flight:reviewer`: `model: sonnet`, `effort: high`, tools `Read, Grep, Glob, Bash` (Bash for read-only `git show`, `git diff`, `node --test`; Decided here), color yellow.
- `flight:adversary`: `model: opus`, `effort: high`, tools `Read, Grep, Glob`, `omitClaudeMd: true`, color red.
- `flight:imposter`: `model: sonnet`, `effort: high`, tools `Read, Grep, Glob, Bash, Edit, Write` (it makes the edits the owner would make by hand in a scratch clone; Decided here), `omitClaudeMd: true`, color orange.
- Every agent body holds exactly one line starting `Fallback rank: `, used only when the opening text gives no `Rank:` line. Exact lines: pilot `Fallback rank: Captain unless told otherwise; you report to the Commander (the owner).`; runner `Fallback rank: Officer when run as a background session, reporting to the Captain.`; every other agent `Fallback rank: Worker in the team of whoever sent you, reporting to them; if you do not know who sent you, you report to the Captain.`
- Plugin agents ignore `hooks`, `mcpServers` and `permissionMode`, and `initialPrompt` is ignored for plugin agents: do not use them.

### 5.10 Ranks and the `Rank:` line

- The four ranks, in `flightdeck/policies.md` under the heading `## Ranks`, one line each starting exactly `- Commander: `, `- Captain: `, `- Officer: `, `- Worker: `. Tests read the rank names from these lines.
- A seat's rank line, first non-empty line of each seat section in `entry-points.md`: `Rank: <Commander|Captain|Officer|Worker>. Reports to: <who>. You decide: <...>. You do not decide: <...>.` (one line; tests match `^Rank: (\w+)\. Reports to: .+\. You decide: .+\. You do not decide: .+\.$`).

### 5.11 The opening text order

- Global rules (binding documents first, hard rules, the ceiling in words), then the seat's `Rank:` line, then the workshop's scoped block when the work belongs to a workshop, then the line `Work outside your brief: report it as a capture line; do not do it.`, then the task.

### 5.12 The scoped block (`scopeBlock`, printed by `node <plugin root>/lib/workshops.mjs scope <name>`)

- Framed as information, not commands. Exact shape, sections separated by one blank line:
- Optional first line, only when `constraints.md`, `context.md` and `verify.md` together exceed 6,000 characters: `Warning: the scoped files for workshop <name> total <n> characters, over the 6,000-character default; all three are given whole.`
- `Workshop <name>: the following is this workshop's own context and verification, in addition to the global rules. VISION.md and build.txt win on any conflict.`
- `The owner's constraints for workshop <name> (\`.flightdeck/<name>/constraints.md\`):` followed by the whole file.
- `Context for workshop <name> (\`context.md\`):` followed by the whole file.
- `Verification for workshop <name> (\`verify.md\`):` followed by the whole file.
- `Original files: .flightdeck/<name>/constraints.md, .flightdeck/<name>/context.md, .flightdeck/<name>/verify.md`
- Missing files are skipped (their heading too). A workshop with no folder gives an empty block and the warning `workshop <name> has no folder (captured or unknown)`. Files are never cut. The block never names or reads another workshop.
- `--json` prints one JSON object `{"block": <string>, "checks": [<commands from ## checks>], "questions": [<items from ## questions>], "warnings": [<strings>]}`. Without `--json` the block goes to stdout and warnings to stderr. Exit code 0 in every case (it never throws).

### 5.13 Hook input and output facts (plan 3.0, library `hooks.md`)

- Hook input arrives as JSON on stdin with `hook_event_name`, `cwd`, and, for tool events, `tool_name` and `tool_input`. `agent_id` is present only inside a subagent or workflow agent; `agent_type` is present inside a subagent and in a `claude --agent` session, as `flight:<name>` for plugin agents. `tool_input.file_path` is absolute for Edit and Write. `CLAUDE_PROJECT_DIR` is the project root even inside a worktree.
- Deny from `PreToolUse` or `PreModelSwitch`: print `{"hookSpecificOutput":{"hookEventName":"<event>","permissionDecision":"deny","permissionDecisionReason":"<reason>"}}` and exit 0. `PreModelSwitch` input carries `from_model`, `to_model`, `requested_model`.
- `SessionStart` output: `{"systemMessage": <card>, "hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <card>}}`; each string is capped at 10,000 characters; write it as factual statements.

### 5.14 Node and test commands

- Node is v22 here. `node --test <directory>` fails on Node 22 ("Cannot find module"); always use the quoted glob form, which node expands itself: `node --test 'flightdeck/tests/*.test.mjs'` and `node --test 'lab/checks/*.test.mjs'`. (Decided here: the plan wrote `node --test flightdeck/tests/`; this brief and every file PR 1 writes use the glob form.)
- All scripts are dependency-free ES modules (`.mjs`), Node built-ins only, no `package.json`.
