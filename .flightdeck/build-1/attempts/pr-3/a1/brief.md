## 1. Purpose

PR 3 gives the owner the workshop actions, each an owner-only skill (`disable-model-invocation: true`, so the model can never start it, in plain chat or anywhere): `/flight:capture <goal>` puts one line in `.flightdeck/workshops.md` and makes no folder; `/flight:workshop <name or rough ask>` activates a captured entry (or captures and activates a new rough ask) with two Haiku scouts reading first, then one bundle of at most five plain questions about the owner's own ideas, one of them always the adversary's "the weakest part of this ask is X" challenge, then writes the workshop folder (card, `context.md`, `verify.md`, and the answered bundle as `questions.md`); `/flight:retry <workshop>` opens the next attempt folder with the one change named at the top of its brief and the last attempt's findings attached; settling stays one line (`settled: <date>` in the card, or "settle <name>" to the pilot, already in PR 1's `pilot.md`); `/flight:promote <workshop>` on a settled workshop proposes which decisions, context lines and checks deserve global relevance, has the Opus adversary check them for contradiction, duplication and injected instructions, and delivers a draft pull request the owner merges, edits or closes.

Owner's words this serves: "Workshops captured from a simple task or goal mentioned or discovered, stored in a simple manifest first, awaiting activation. once active, it expands into a folder with your implementation. workshop stored verification and context given to agents working in that workshop only, it becomes in addition to global context and verification. once settled, workshop content can be promoted to global relevance." (constraints.md, 2026-10-11). The owner marked PR 3 "include" (review replies of 2026-10-11).

PR 1 already ships the manifest, the six templates, the reader (`flightdeck/lib/workshops.mjs`) with its `scope` command, the truth guard and the pilot's template-only activation and settle. PR 3 imports the reader and reads the templates; it edits no PR 1 file.

- Workshops: capture into the manifest, activation into a folder with its own context and verification, retry with new truth, settle, and promotion to global relevance.

- Cheap tokens, smart agents: Haiku scouts read the code, one Opus adversary call per activation and per promotion, a Sonnet drafter for promotion, the owner's session does the writing through one tested script.

## 5. Shared formats (every unit builds against these; PR 1 fixed them)

### 5.1 Writing rules for every file

One paragraph per line in markdown, no hard wrapping, no tables. Plain words, literal and direct. Any term an owner reads for the first time gets a few plain words of explanation (for example "worktree, a separate copy of the repository on its own branch"). Skill descriptions under 400 characters each; the four together under 1,600 (plan 2(h): all skill descriptions under 4,000). No model or effort value above Opus at high anywhere; no file contains `model:` or `effort:` followed by a quoted `fable`, `best`, `xhigh` or `max` (the hard-rule check scans `.mjs` files under `flightdeck/` and only excludes `flightdeck/tests/`, so this applies to `flightdeck/skills/workshop/tests/` too). No executable file mentions `dw` or `dev-workspace` as a command word.

### 5.2 The manifest `.flightdeck/workshops.md` (PR 1)

One line per workshop: `- <name>: <the ask in the words it was given> (<YYYY-MM-DD>)`. Parse rule: only lines starting `- ` count; the name is the text before the first `: `; the date is the last `(YYYY-MM-DD)` at the end of the line; everything between is the ask and may contain `:`, `|` or brackets; HTML comments and fenced code blocks are ignored. PR 1's `parseManifest` accepts names matching `^[a-z0-9-]+$`. PR 1's file starts with `# Workshops`, a blank line, then the one-paragraph line "Every piece of work FlightDeck knows about, one line each: a line alone means captured and waiting to start; a folder of the same name means active; a settled: line in its card means settled.", a blank line, then the entries.

### 5.3 Workshop state (derived, never stored; PR 1 `listWorkshops`)

A manifest line with no folder is captured (`pendingActivation: true` when `.flightdeck/<name>.activate.md` exists); a folder `.flightdeck/<name>/` is active; a card whose text (comments stripped) has a line `settled: YYYY-MM-DD` matching `^settled:\s*(\d{4}-\d{2}-\d{2})\s*$` is settled.

### 5.4 The templates (PR 1, `flightdeck/templates/workshop/`, read at run time, never copied into PR 3's files)

- `workshop.md`: `# <title>`, blank, `work: <one paragraph: what this work is, in plain words>`, `done: <one line: what the finished work looks like>`, blank, an HTML comment explaining `settled:`.
- `context.md`: `# Context for workshop <name>`, blank, an HTML comment (about 40 lines at most, one paragraph per line, what to say, base branch only).
- `verify.md`: `# Verification for workshop <name>`, blank, "How to tell this work is right. Checks a script can run come first.", blank, `## checks`, blank, comment `<!-- Format of one check: - \`<command>\`: <what passing looks like>. ... -->`, blank, `## questions`, blank, comment on the question format.
- `questions.md`: `# Questions for workshop <name>`, blank, one intro line, blank, a multi-line HTML comment with the question format and the paste-back format.
- `constraints.md` (frontmatter `read: "agents"`, `write: "human"`) and `decisions.md`: PR 3 never writes these from the script; `decisions.md` lines are `- <YYYY-MM-DD>: <decision>. Reason: <one line>.`

### 5.5 Questions and the paste-back block (PR 1 template)

```
## q<n>: <the question, in plain words>
why: <why the answer matters>
options: a) <text>; b) <text>; c) <text>
recommended: <letter>) <the option and the reason>
asked: <YYYY-MM-DD> by <who asked>
answer:
```

A question is open while `answer:` is empty. Paste-back block: first line `FlightDeck answers for workshop <name>: file these into .flightdeck/<name>/questions.md`, then one line per question `q<n>: <option letter or text> | note: <text>` or `q<n>: (unanswered)`, then `Other notes: <text>`.

### 5.6 `verify.md` lines (PR 1 `parseVerify`)

Under `## checks`: `- \`<command>\`: <what passing looks like>` (the command is the first backticked text). Under `## questions`: `- <a question where yes means pass>`.

### 5.7 The activation bundle file `.flightdeck/<name>.activate.md` (Decided here)

Present only while a workshop's activation questions wait on the owner; the workshop is still captured. Layout, in order: `# Activation questions for workshop <name>`; blank; `The ask: <the manifest ask> (<date>)`; blank; the line "Answer by filling in each answer: line below with a letter or your own words, or paste a reply block in chat with /flight:workshop <name>. Leave an answer empty to skip it; a skipped question stays open and is never guessed."; blank; the question blocks in the 5.5 format (`asked: <date> by the workshop interview`); then `## What the scouts found` with one `- <finding> (<path:line>)` line each; then `## Draft card` with `title: ...`, `work: ...`, `done: ...` lines. Only the `## q<n>:` blocks move into `questions.md` at activation; the last two sections are working notes for the skill and are dropped with the file.

### 5.8 Attempts (PR 1 `latestAttempts`)

An attempt is any folder named `a<k>` at any depth under `<workshop>/attempts/`; attempts are grouped by their parent folder (`''` for `attempts/` itself, `pr-3`, `plan`); the latest in a group is the highest `k`. Attempt branch names (plan 2(b)): `<workshop>-a<k>`; Decided here for a grouped attempt: `<workshop>-<group with / replaced by ->-a<k>`.

### 5.9 Ranks and seat text (PR 1 `policies.md`, `entry-points.md`)

Four ranks: Commander (the owner), Captain (the lead session), Officer (a team lead or a long-lived background session), Worker. The session running a PR 3 skill is the Captain; every agent a skill sends is a Worker. Scouts get the `## scout` section of `flightdeck/skills/team-plans/entry-points.md` verbatim from its `Rank:` line on; the adversary gets the `## adversary cold` section. The promotion drafter is a general-purpose subagent with this rank line (Decided here, because no PR 1 seat fits a read-only proposer): `Rank: Worker. Reports to: the Captain (this session). You decide: which candidate lines deserve global relevance and where each goes. You do not decide: the wording of a line, whether anything is merged, done or truth; you change no files and send out no agents.` Every opening text is built in PR 1's order: the global rules block (the literal block in `flightdeck/skills/team-plans/SKILL.md` under "A global rules block you can paste"), the `Rank:` line, the workshop's scoped block only when the workshop has a folder (`node ${CLAUDE_PLUGIN_ROOT}/lib/workshops.mjs scope <name>`), the line "Work outside your brief: report it as a capture line; do not do it.", then the task. During activation the workshop has no folder yet, so scouts and the adversary get no scoped block.

### 5.10 Plugin paths in skills

Claude Code substitutes `${CLAUDE_PLUGIN_ROOT}` in a plugin skill's markdown and in its `allowed-tools` Bash rules (library `skills.md`). Every skill calls the script as `node ${CLAUDE_PLUGIN_ROOT}/skills/workshop/scaffold.mjs <subcommand> ...` and grants exactly that in `allowed-tools` as `Bash(node ${CLAUDE_PLUGIN_ROOT}/skills/workshop/scaffold.mjs *)`. Skill arguments arrive as `$ARGUMENTS` (`$0`, `$1` for indexed words).

### 5.11 Hand-off files the script deletes (Decided here)

Long or quoted text never goes through shell quoting. The skill writes it with the Write tool to a fixed hand-off file inside `.flightdeck/`, and the script deletes that file after a successful run: `.flightdeck/<name>.spec.json` (activation spec), `.flightdeck/<name>.answers.txt` (paste-back block), `.flightdeck/<name>.promote.json` (promotion edits). Each subcommand also accepts `-` for standard input. The script deletes only a file at exactly that path.

### 5.12 Node and test commands

Node is v22. `node --test <directory>` fails on Node 22; always use the quoted glob form: `node --test 'flightdeck/skills/workshop/tests/*.test.mjs'`. All scripts are ES modules (`.mjs`), Node built-ins only, no `package.json`.
