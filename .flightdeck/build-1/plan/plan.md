# FlightDeck build-1: final plan

Final plan for side build 1 of FlightDeck, planning run attempt 1, written by the lead architect on 2026-10-10 and revised the same day after verification by review, fact check, adversary and human imposter (every finding and what was done about it is in `.flightdeck/build-1/verify/plan-resolution.md`). It is based on the candidate "Fly it today" (`candidates/fly-today.md`), with ideas grafted from "Harness-native and lean" (`candidates/harness-lean.md`) and "A machine that improves" (`candidates/improving-machine.md`). The owner's binding documents are `.flightdeck/VISION.md`, `.flightdeck/build.txt` and `.flightdeck/build-1/constraints.md` (empty today: "(none yet)"). Every choice below is a decision made for the owner and can be overruled; nothing here is the owner's own statement unless quoted, and quotes were checked against `dev/workspace/research/repo-reset/user-intent.md`, `interview-record.md` or `.flightdeck/build-1/research/owner-truth.md`. Earlier work on other branches is mined as material, never treated as canon, and never called finished.

## 1. What the owner gets and how they try it straight away

- FlightDeck is an ordinary Claude Code plugin called `flight`. All of it lives in one folder, `flightdeck/`, and the owner installs it from this repository through the local marketplace `DBHD-FlightDeck` that already exists.
- PR 1 (basic) gives: a pilot agent (rank Captain, Opus at high effort) who leads and sends out agents but does not do the work itself; a small crew (Haiku scouts for cheap reading, a Sonnet worker, a Sonnet reviewer, an Opus adversary, a Sonnet human imposter who plays the owner, and an officer agent for unattended background sessions); three team recipes (Recon, Build and check, Decide) with the opening text each crew member gets; a pre-flight card the owner sees at the start of every pilot session, which says where things stand; guards that stop agents pushing to main, launching a model or effort above the owner's ceiling, or editing the owner's own files; short rule files where the work happens; a one-page review rubric; and an optional radio voice.
- The starter set, built after the owner has tried PR 1: PR 2 the flight board (a page showing every piece of work and the questions waiting on the owner, with a button that copies the owner's answers back, and a prompt builder), PR 3 workshops (start work with a rough ask and a short interview, retry, promote a decision), PR 4 launches (one command turns "go" into a reviewed draft pull request).
- Optional, built only if the owner ticks them on the review page: PR 5 a small `flight` command, PR 6 a laboratory that drills and measures FlightDeck, PR 7 manuals and a library with a librarian, PR 8 a status band above the prompt.
- Plain `claude` chat stays plain: no card, no git or truth rule. It gains only the plugin's skill and agent descriptions in Claude's context (the size is printed by `/flight:preflight`) and a check that refuses an agent launch naming `fable`, `best`, `xhigh` or `max`.
- Try PR 1 in five minutes, in the repository: `claude plugin marketplace add "$PWD" --scope local`, `claude plugin install flight@DBHD-FlightDeck --scope local`, then `claude --agent flight:pilot --model opus --effort high`. The pre-flight card shows FlightDeck's own build: the `build-1` workshop, its pull requests and the questions it is waiting on. `/flight:preflight` runs FlightDeck's checks on itself. Asking the pilot to push to main (with `--dry-run`) is refused.
- FlightDeck works on itself: the board's first real job is answering build-1's own questions, and PR 4's demo launch has FlightDeck improve its own pre-flight card and return a draft pull request.

## 2. Decisions the owner left to the lead ("let em cook")

### (a) What "working" means for each part

- Choice: a part works when four things are true. (1) The hard-rule check passes (`node lab/checks/hard-rules.mjs`, a quick script with no model calls) and the part's own test passes (listed in section 3). (2) Its "try it in five minutes" steps work as written when the human imposter follows them literally as the owner, timed per step; a step the imposter could only read about, not run, is marked [stated], counts as not tried, and the pull request opens as a draft that says so. (3) Removing the part's files leaves the hard-rule check, the other parts' tests and `claude plugin validate flightdeck` green, so nothing depends on it except through PR 1. (4) Every finding from the review, the adversary and the imposter is fixed or listed in the pull request with a reason.
- Only hard rules fail a check: nothing pushed to main, no model or effort above Opus at high, nothing changed under `dev/` or `.claude/rules/`, no executable FlightDeck file that calls `dw` or `dev-workspace`, and no changed file outside the pull request's own list. Everything else (lengths, description sizes, frontmatter fields plugins drop) is a warning from a separate lint in PR 6 and never blocks.
- Eval cases (a prompt plus a grader that `claude plugin eval` runs) ship with some parts so the lab can measure them later; results are reported, never used to block a pull request.
- Reason: the owner said "show me something that works great. and fits the goal". A script proves it works, the imposter proves it suits the owner, the removal test proves "if i like it but its too big, I cut it down", and keeping invented numbers out of failing checks avoids a test suite the owner has to fight.

The test includes a nested fixture.

A workshop does not get a long-lived branch of its own. This is the lead's reading of "Branch isolated" and is put to the owner as a question on the review page.

### (c) How a retry works

- Whole plan: the owner adds dated lines to `.flightdeck/build-1/constraints.md` (for example `2026-10-12 all pages must work offline`) and asks Claude to rerun `.flightdeck/build-1/workflows/plan.js` with `outDir: ".flightdeck/build-1/attempts/plan/a2"`; `plan.js` always reads the owner's lines from `.flightdeck/build-1/constraints.md` (override with `args.constraints`), so nothing is copied. Attempt 1's planning files stay where they are.
- One pull request: the owner adds a line that starts with the pull request number, for example `2026-10-12 PR 3: the interview asks at most three questions`, then says "retry PR 3". The build workflow runs with `prs: [3]` and the next attempt number: a fresh brief that includes every general line, every `PR 3:` line and attempt 1's findings; a fresh branch `build-1-pr3-workshops-a2` cut from the current `build-1`; a fresh pull request. Attempt 1's branch, pull request and folder stay until the owner closes them. Reason: "setup carries over, run output does not" (the flightcrew retry rule): a retry starts from better inputs, not from the failed output.
- A late PR 1 retry: if PR 1 is retried after the starter set is built, the starter pull requests that use what changed are rerun too; the retry report lists which.
- Any workshop (from PR 3): the owner adds a line to that workshop's `constraints.md` or answers a question, then runs `/flight:retry <workshop>`; the next attempt folder opens with the one change named at the top of its brief.
- Branch names never start with `build-1/`: the branch `build-1` exists and git cannot hold both `build-1` and `build-1/...` (a judge reproduced "cannot lock ref"). All branch names are computed by the workflow script, never chosen by an agent.

### (e) How the owner starts a piece of work

- Choice: by talking, with no forms, IDs or approval flags. Three doors, all optional: (1) plain `claude` chat, exactly as before; (2) `claude --agent flight:pilot --model opus --effort high` (the README suggests the shell alias `fly`) and a rough ask in normal words; when the ask is bigger than one sitting, the pilot offers a workshop (with PR 1 alone, a bare workshop from the template; with PR 3, the interview); (3) `/flight:workshop <rough ask>` directly, or the board's prompt builder, which produces that line to paste. ### (f) Where questions waiting on the owner are held

- Choice: in `questions.md` inside the workshop the question belongs to (for this build, `.flightdeck/build-1/questions.md`). A question is open while its `answer:` line is empty. They surface in three places: a one-line count on the pre-flight card, the board page (PR 2) with an answer box per question and a "Copy my answers" button, and the pilot asking them live in chat when the owner is present. A skipped question stays open; it is never guessed.
- Paste-back block: first line `FlightDeck answers for workshop <name>: file these into .flightdeck/<name>/questions.md`, then one line per question `q<n>: <option letter or text> | note: <text>` or `q<n>: (unanswered)`, then `Other notes: <text>`.

## 4. Pull requests, in order

All pull requests open into `build-1`. PR 1 is built first; the owner tries and merges it. The starter set (PRs 2 to 4) is then built from the updated `build-1`; after the owner has tried it, any optional PRs the owner ticked (5 to 8) are built as a second wave. No pull request is stacked on another and none needs retargeting. Every pull request description leads with the five-minute try and its measured time, then the checks marked [checked], the verification marked [reviewed], findings and what was done about each, the size, the models used per stage, and how to retry it alone.

## 5. The build run

The build is a series of workflow runs with the owner in between, because a workflow cannot wait for a person. Run A builds PR 1 only and stops. The owner tries PR 1 and merges it (or adds `PR 1:` lines and asks for a retry). Run B wave 1 builds the starter set (PRs 2 to 4) from the updated `build-1` and stops. Run B wave 2 builds any optional PRs the owner ticked. Every run is a plain Claude Code workflow launched from a plain session (not a pilot session): the build does not depend on FlightDeck to build FlightDeck, which keeps away from the owner's named mistakes "using the pilot to fitout the cockpit" and "using half built systems, to build out the half built system". One script serves all runs: `.flightdeck/build-1/workflows/build.js`, run by path with the Workflow tool, like `plan.js` (it is build residue, not a FlightDeck feature). Each run is launched from the owner's interactive session, so a usage-limit wait pauses the run instead of failing agents (harness-multi, workflows.md "When a run hits your usage limit").

### Stage 0: pre-flight in the owner's session (owner present, about five minutes)

- What the owner does: paste one block to restart the session, then paste the review page's reply. The block: `claude --settings .flightdeck/build-1/workflows/build-settings.json --permission-mode acceptEdits --model opus --effort high`. The one approval click: Claude Code asks once to edit `.claude/agents/adversary.md` (every edit under `.claude/` asks); say yes.
- The review page reply format: first line `FlightDeck build-1 review reply`, then one line per pull request `PR <n>: keep | change | cut | note: <text>`, then `Layout: keep | change: <text>`, `Recipes: keep <names>`, `Theme: more | less | as is`, `Persona: <corrections or none>`, `Decision <letter>: keep | change: <text>` for any of 2(a) to 2(h) the owner wants changed, and `Other: <text>`.
- The lead files the reply: kept and ticked pull requests become the `prs` list and the waves; every change, persona correction and note goes verbatim into `.flightdeck/build-1/constraints.md` as one dated line each (tagged `PR <n>:` or `persona:` where it applies), written by the main conversation. The lead shows the lines it wrote; nothing is reworded, and the date on each line lets a wrong one be found and removed.
- The lead writes and commits to `build-1` (outside `.claude/`, so no approval prompt): `.flightdeck/build-1/workflows/build-settings.json`, `.flightdeck/build-1/workflows/push-check.mjs`, `.flightdeck/build-1/workflows/build.js` and `.flightdeck/build-1/workflows/build.test.mjs`.
  - `build-settings.json` allows only what the build needs: `Bash(git status*)`, `Bash(git diff *)`, `Bash(git log *)`, `Bash(git show *)`, `Bash(git ls-tree *)`, `Bash(git rev-parse *)`, `Bash(git fetch *)`, `Bash(git switch -c build-1-*)`, `Bash(git add *)`, `Bash(git commit *)`, `Bash(git merge build-1-*)`, `Bash(git clone *)`, `Bash(git init --bare *)`, `Bash(git push -u origin build-1-*)`, `Bash(git push origin HEAD:build-1-*)`, `Bash(git push origin build-1)`, `Bash(gh pr create *)`, `Bash(gh pr view *)`, `Bash(gh pr list *)`, `Bash(gh auth status*)`, `Bash(node --test *)`, `Bash(node lab/*)`, `Bash(node flightdeck/*)`, `Bash(node .flightdeck/*)`, `Bash(claude plugin validate *)`, `Bash(claude plugin details *)`, `Bash(claude plugin eval *)`, `Bash(claude plugin list*)`, `Bash(claude plugin marketplace list*)`, `Bash(claude plugin marketplace add *)`, `Bash(claude plugin install flight@DBHD-FlightDeck-try-*)`, `Bash(claude plugin uninstall flight@DBHD-FlightDeck-try-*)`, `Bash(claude plugin marketplace remove DBHD-FlightDeck-try-*)`, `Bash(FLIGHTDECK_UNATTENDED=1 claude -p *)`, `Bash(claude -p *)` (in case the permission matcher does not include the variable prefix) and `Workflow`. It denies (deny wins over allow): `Bash(git push *:main*)`, `Bash(git push *:refs/heads/main*)`, `Bash(git push * main)`, `Bash(git push *main:*)`, `Bash(git push * +*)`, `Bash(git push * :*)`, `Bash(git push *--force*)`, `Bash(git push * -f*)`, `Bash(git push *--mirror*)`, `Bash(git push *--delete*)`, `Bash(git push * -d *)`, `Bash(git branch -d*)`, `Bash(git branch -D*)`, `Bash(gh pr merge*)`, `Bash(claude plugin marketplace remove DBHD-FlightDeck)`, `Bash(claude plugin uninstall flight@DBHD-FlightDeck)`. It also registers `push-check.mjs` as a `PreToolUse` hook with `if: "Bash(git *)"`: the same parser as PR 1's git rule (global options, refspecs, bare push on main), failing closed. The patterns are coarse; the hook is the precise layer; GitHub branch protection on `main`, if the owner turns it on, is the hard stop that also covers git run from inside a script.
  - `build.test.mjs` runs with plain node: `push-check.mjs` against a table of commands (every deny form above, `git -C x push origin main`, `git push --dry-run origin HEAD:main`, and the allowed build pushes), with no real push; and `build.js` wrapped with stub `agent`, `parallel`, `pipeline`, `phase` and `log` to prove it compiles and that every stage's `{halt}` reaches `land`.
- The lead makes the one protected-path edit (the `model: fable` line in `.claude/agents/adversary.md` becomes `model: opus` and `effort: high`), commits it to `build-1` and pushes.
- The lead runs a probe workflow of Haiku agents at low effort, before anything is built, and records the results in `.flightdeck/build-1/attempts/probe-a<k>.md`: (1) an agent with `effort: 'high'` returns normally; (2) an agent with `isolation: 'worktree'` can run `git switch -c build-1-probe-a<k> origin/build-1`, commit a file and report the branch, without pushing; (3) `gh auth status` succeeds; (4) the multi-stage `pipeline` form runs, and what a later stage receives when an earlier stage returns `null` or throws; (5) in a scratch folder with a tiny throwaway plugin (as the fact check did), a hook logs `agent_id` and `agent_type` for a `claude -p --agent` session, for a subagent, and for a workflow agent, confirming the guard can tell them apart and that hooks fire inside workflow agents; (6) a scratch clone with `source: "./flightdeck"` and a renamed marketplace installs with `--scope local` and loads in place; (7) `claude plugin eval` runs one trivial case with `--runs 1`, and with `--eval-dir` pointing outside the plugin; (8) `claude plugin marketplace list` is the same before and after (the owner's install untouched). Run B adds (9) an agent with `agentType: 'flight:scout'` runs. Fallbacks: no `effort` option means the script drops it and relies on agent files and the session's high effort; a multi-stage pipeline that does not behave means one stage function per pull request that calls the stages in order; if hooks cannot tell the owner's session from agents, the truth guard ships as a `CLAUDE.md` rule only and the review page is told; if `./flightdeck` does not load in place, the plugin stays at the repository root; if eval or an outside `--eval-dir` is unavailable, eval cases move to `flightdeck/evals/` or record "not available here"; if `agentType` fails, the script puts the agent file's body in the prompt; if `gh` fails, the land stage pushes branches and writes pull request bodies to files.
- The lead launches `build.js` with `args: {run: "A" | "B", wave: 1 | 2, prs: [...], attempt: <k per PR or one number>, base: "build-1", today: "<date>", scratch: "<absolute scratch path>", settings: "<absolute path of build-settings.json>"}`. The date comes in through args because the script cannot read the clock.

### Script shape

- First statement `export const meta = { name: 'flightdeck-build-1-build', description: 'Build FlightDeck build-1 pull requests from the approved plan', phases: [...] }` with plain literals only; the body ends with a top-level `return`, never `export default`; no `Date.now` or `Math.random`.
- Constants: `OUT = '.flightdeck/build-1'`, `PLAN = OUT + '/plan/plan.md'`, a CONTEXT block every agent gets (the binding documents and `constraints.md` first; only owner documents bind; never push to main, never force-push, never delete a branch, never merge; the model ceiling in words; one paragraph per line; plain words; write only your owned files), a findings schema (`severity` high, medium or low; `where`; `finding`; `evidence`; `suggested_fix`), and a build-return schema (`branch`, `commit`, `files`, `status` complete, blocked, contradiction-found or over-budget, `notes`). The CONTEXT block contains no `model:` or `effort:` option literals, so the ceiling rule never matches it.
- Role text: builders and verifiers are plain workflow agents whose prompts include the role text from this plan and, from Run B, the rubric in `flightdeck/rubric.md`; the project adversary (`agentType: 'adversary'`, fixed in stage 0) is used for the adversary seat in every run.
- Branch names are computed by the script: `build-1-pr<n>-<slug>-a<k>` for a pull request and `build-1-pr<n>-<slug>-a<k>-u<i>` for a unit. Slugs: 1 basic, 2 board, 3 workshops, 4 launches, 5 cli, 6 lab, 7 manuals, 8 band.
- Each pull request flows through `pipeline(prs, gather, brief, build, integrate, verify, triage, fix, land)` (or the single-function fallback), so pull requests move independently with no barrier. Every stage body is wrapped in try/catch and returns either its result or `{halt: reason}`, never `null`; a stage that receives `{halt}` passes it straight on; `land` opens a draft pull request explaining the halt, or, if nothing was pushed, marks the pull request "not built" in the return value. Nothing is retried silently inside the run.
- The nested installs are serialised: all imposter and live-check stages queue on one promise chain in the script, so two never touch the plugin registry at once.

### Stages, models and effort

- Gather (Haiku, low, one per pull request, not isolated): copies each source the plan names for this pull request with `git show origin/<branch>:<path>` into `<scratch>/pr-<n>/sources/` and returns the list. Read-only to the repository.
- Brief (Opus, high, one per pull request): reads this plan's sections for the pull request, every `constraints.md` line that applies (untagged, `PR <n>:` or `persona:`), on a retry the previous attempt's findings and report, and the gathered sources; returns, through a schema, the brief text: purpose; every owned file with a one-line content spec; files it must not touch; done written as yes-is-pass questions; the check commands with exact flags; the five-minute try steps; the VISION sections served; the units (at most five for PR 1, three for the others, each with disjoint files).
- Build (Sonnet, high, `isolation: 'worktree'`, one per unit, in parallel): first command `git fetch origin && git switch -c <unit branch> origin/<base>`; writes only its owned files; adapts sources from `<scratch>/pr-<n>/sources/`; runs `node lab/checks/hard-rules.mjs` where it exists; commits by file name with the attribution lines; pushes the unit branch; returns the build-return schema. PR 1's units: (u1) the seven agents, the output style, `policies.md`, `rubric.md` and `persona.md`; (u2) the shapes skill with recipes, opening text and ways-to-fly, and the pre-flight skill; (u3) the hooks, the shared reader and `flightdeck/tests/core.test.mjs`; (u4) `CLAUDE.md`, `.flightdeck/CLAUDE.md`, the READMEs and both manifests (including moving `plugin.json`); (u5) the workshop templates, the build-1 workshop files, the hard-rule check, its test and `lab/owned/pr1.txt`.
- Integrate (Sonnet, medium, worktree, one per pull request): `git switch -c <PR branch> origin/<base>`, merges the unit branches, runs `node lab/checks/hard-rules.mjs --base origin/<base> --owned lab/owned/pr<n>.txt`, `claude plugin validate flightdeck` and the pull request's own tests, commits, `git push -u origin <PR branch>`; writes `<scratch>/pr-<n>/diff.patch` (`git diff origin/<base>...<PR branch>`) and `<scratch>/pr-<n>/changed.txt`. Returns the branch and check results with exit codes and the last 20 lines of output.
- Verify (each in a fresh context; none sees another's output or the builders' transcripts):
  - Review (Sonnet, high, read-only, not isolated): reads the diff file and the brief, and `flightdeck/rubric.md` where it exists; checks every owned file exists and matches its spec, nothing outside the owned list changed, nothing under `dev/` or `.claude/rules/`, and the checks are real commands; findings only on correctness or the brief.
  - Adversary (Opus, high, cold mode, project agent `adversary`): its prompt opens with `=== The Work ===` giving the paths of the diff file, the changed-file list and the PR branch name, then `=== The Criteria ===`: the brief's done list, the VISION sections the pull request serves, `build.txt`, `constraints.md`, the owner's pain points (`research/owner-truth.md` section 3), the model ceiling, and for any Claude Code claim section 3.0 of this plan with its sources; findings only on correctness or stated requirements, each with evidence a second reader can reproduce by reading files.
  - Human imposter (Sonnet, high): adopts `.flightdeck/persona.md` (in Run A, `research/owner-truth.md` and `dev/workspace/research/repo-reset/user-intent.md` directly, with the owner's `persona:` lines). Waits its turn on the install chain. Clones the repository into `<scratch>/pr-<n>/try/`, checks out the PR branch, creates a throwaway bare repository `<scratch>/pr-<n>/origin.git` and points the clone's `origin` at it, rewrites the clone's marketplace `name` to `DBHD-FlightDeck-try-pr<n>-a<k>`, records `claude plugin marketplace list`, then runs `claude plugin marketplace add <clone> --scope local` and `claude plugin install flight@DBHD-FlightDeck-try-pr<n>-a<k> --scope local` in the clone. It follows the try steps literally through `FLIGHTDECK_UNATTENDED=1 claude -p --model sonnet --settings <settings> --permission-mode acceptEdits --output-format json "<step>"` sessions in the clone, continuing with `--resume <session id>` to answer any question the feature asks in the owner's voice (for PR 3 it answers the interview bundle in file mode with the paste-back format). Any edit the owner would make by hand (such as adding a line to a workshop's `constraints.md`) it makes itself in the clone. It records minutes per step, where it got stuck, what confused it, any jargon, anything that smells like the owner's past complaints, and what it would cut. At the end it uninstalls `flight@DBHD-FlightDeck-try-pr<n>-a<k>`, removes that marketplace, and compares `claude plugin marketplace list` with the record; any change to the owner's `DBHD-FlightDeck` entry is a high finding and stops the run. A step it could not run is marked [stated]. It writes only inside its scratch folder. For PR 8 it reads instead of running.
  - Checks (Haiku, low, worktree on the PR branch): runs the brief's script check commands and, where the pull request ships eval cases and the probe found plugin eval available, `claude plugin eval flightdeck --eval-dir lab/evals --case 'pr<n>-*' --runs 3 --no-publish --trust-plugin --max-cost-usd 3 --json <scratch>/pr-<n>/eval.json`, adding `--scaffold` and `--allow-tools` only where a case says so. Returns pass or fail per command with the last 20 lines. A failing eval case becomes a finding, not an automatic block.
  - Live check (Sonnet, high, on the install chain, in the same kind of scratch clone): runs the pull request's live checks with the exact commands from the brief (for PR 1 the list in section 4), each nested call as `claude -p --model haiku --settings <settings> --permission-mode acceptEdits --output-format json`, with `--agent flight:pilot` or `--agent flight:officer` and `FLIGHTDECK_UNATTENDED=1` as each check needs; a check it cannot run is reported [stated] with the reason.
- Triage (Opus, high, one per pull request): accepts or rejects every finding with a one-line reason, applying a severity bar (a reviewer told to find gaps always finds some) and verifying factual claims against the cited source; a finding that needs the owner's view becomes a question block for `.flightdeck/build-1/questions.md`; returns the fix list, the questions and the pull request body draft.
- Fix once (Sonnet, high, worktree): `git switch -c <PR branch>-fix origin/<PR branch>`, applies the accepted fixes, writes `.flightdeck/build-1/attempts/pr-<n>/a<k>/findings.md` (every finding, who raised it, severity, decision, reason) and `brief.md`; in Run A it also adds triage's questions to the PR 1 branch's `.flightdeck/build-1/questions.md` (which PR 1 creates), so nothing is written to `build-1` directly; reruns the checks, commits, and pushes fast-forward with `git push origin HEAD:<PR branch>` (never force). A second fix round runs only when a script check is still red; after that the pull request opens as a draft marked "not green".
- Recheck (Opus, high, only when a high-severity finding was accepted): for each one, "is it fixed? yes or no, with a quote". An unfixed high finding makes the pull request a draft.
- Land (Sonnet, medium): writes `attempts/pr-<n>/a<k>/report.md` with provenance marks and `attempts/pr-<n>/a<k>/log.md` (stages, agents, models and effort, transcript paths, token totals where available), commits both to the PR branch, then `gh pr create --base build-1 --head <PR branch> --title "PR <n>: <title>" --body-file <report>`, adding `--draft` when anything is still open or any try step is [stated]. The body leads with the five-minute try and its measured time, then checks [checked], verification [reviewed], findings and their resolutions, size, the models used per stage, and how to retry this pull request alone. Never `main`, never `--force`, never a merge; the owner merges. Returns the URL.
- Combined check (Run B only; Sonnet, medium, worktree, after all pipelines of the wave): creates a local, unpushed branch from `origin/build-1`, merges every PR branch of the wave, runs the hard-rule check, `claude plugin validate flightdeck`, every pull request's tests and, if PR 6 was built, `node lab/drills/remove-part.mjs` and `node lab/drills/sweep.mjs` from its branch; a Haiku agent lists any file changed by two pull requests. Reports merge conflicts and failures for the landing page.
- Landing page (Sonnet, high, after all pipelines): first a single real install rehearsal on the install chain (in a clone of the newest branch, with the renamed marketplace: add, install, one `claude -p` smoke, uninstall, compare the marketplace list); then `.flightdeck/build-1/attempts/run-<A|B>-a<k>.html` built with the page kit's rules (PR 2's `theme.css` if it built cleanly): one plain card per pull request with what it adds, its try steps with a copy button, results, open findings and how to retry it, plus a keep, change or cut panel that copies a reply in the stage-0 format. The imposter reads the page as the owner; one Sonnet fixer applies its findings.
- Clerk (Haiku, low, main checkout on `build-1`): commits the landing page, the probe record, the combined-check report and (in Run B, where `questions.md` already exists on `build-1` and no PR branch touches it) triage's questions in `.flightdeck/build-1/questions.md`, by file name, to `build-1`, and pushes `build-1`. The lead tells the owner where the page is and stops.
- Return: `{prs: [{n, branch, url, draft, checks, findings_open, status}], page}`.

### Numbers, time and cost

- Agents per pull request: gather 1, brief 1, build 1 to 3 (5 for PR 1), integrate 1, review 1, adversary 1, imposter 1, checks 1, live check 1, triage 1, fix 1, recheck 0 or 1, land 1: 11 to 15. Tiers per pull request: Opus 3 or 4 (brief, adversary, triage, recheck), Sonnet 6 to 9 (builders, integrate, review, imposter, live check, fix, land), Haiku 2 (gather, checks).
- Run A: about 21 agents (PR 1's 17 or so, plus landing page, page imposter, page fixer and clerk), plus the stage-0 probe (about 6 Haiku agents). Run B wave 1 (PRs 2 to 4): up to about 51 agents. Wave 2: up to about 67 if all four optional PRs are ticked. Far inside the 1,000-agent cap; the concurrency cap (default up to 16, fewer on small machines; `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` raises it) queues the rest.
- Time and usage, the lead's rough guess and not measured: Run A one to two hours; wave 1 two to four hours. Run A has fewer Opus agents than this planning run, so it should use less of the weekly limit than planning did; each wave of three pull requests uses roughly two to three times Run A. Every `log.md` records actual use per stage, so the next estimate is measured, and the landing page shows the totals.
- If a usage limit is hit mid-run: the workflow pauses and waits for the reset (launched from an interactive session); nested `claude -p` sessions do not wait, so an imposter or live check that hits the limit reports [stated] and its pull request opens as a draft. The waves are the "stop here and show me" points.
- Models: Opus at high effort for the lead, briefs, adversary, triage and recheck. Sonnet for builders, integrators, review, imposter, live checks, fixers and the landing page (high), land and integrate (medium). Haiku for gather, checks, probes and the clerk. Every `agent()` call names its model and effort; nothing above Opus at high.

## 6. Dogfooding

- The build is a workshop. `.flightdeck/build-1/` already holds the owner's truth (`constraints.md`), research, plan and review page; PR 1 adds its `workshop.md` card, `questions.md` and `decisions.md` (the lead's decisions from this plan, each with a reason, ready for the owner to strike). The first pre-flight card the owner sees is FlightDeck reporting on its own build.
- The owner answers the build's questions through FlightDeck: questions triage could not settle land in `.flightdeck/build-1/questions.md`; the card counts them, and after PR 2 the owner answers them on the board and pastes the block back, so the board's first real use is about FlightDeck itself.
- The build does not use half-built parts: every build run is a plain Claude Code workflow from a plain session. FlightDeck's merged guards are active in the owner's session once PR 1 is installed, and stop build agents pushing to main or writing the owner's files; nothing from an unmerged pull request is used.
- FlightDeck builds part of itself: the demo launch in PR 4 is a real improvement to FlightDeck's own card, run through `/flight:launch` once PRs 1 and 4 are merged, returning a draft pull request.
- If PR 6 is built: the combined check runs the sweep and remove-part drills across that wave's branches, and the interview drill pits PR 3's interviewer against the withheld-fact imposter. The first real climb (once PRs 3 and 6 are merged) improves `flightdeck/skills/workshop/SKILL.md`'s description on should-fire and should-not-fire cases and returns a draft pull request or an honest "within noise, do not merge".
- Promotion closes the loop: once PR 3 is merged, `/flight:promote build-1` turns lasting decisions from `.flightdeck/build-1/decisions.md` (for example "FlightDeck writes nothing into `.claude/`") into a draft pull request against `CLAUDE.md` that the owner merges or closes.
- After the build, "retry PR n" can run through `/flight:launch` on the build-1 workshop with the `PR n:` lines as the brief's extra truth, instead of `build.js`, once PRs 1 and 4 are accepted.

## 7. Risks, and what not to build

### Risks

- Protected paths: every Claude write under `.claude/` asks for approval outside bypass mode, and a directory loaded with `--plugin-dir` becomes protected for writes. Mitigation: FlightDeck lives in `flightdeck/` and `.flightdeck/`; the single `.claude/` edit happens in stage 0 with the owner present; the owner installs through the local marketplace; `--plugin-dir` is never used.
- The owner's real install: a nested `marketplace add` with the same name would repoint it (tested by the fact check). Mitigation: every scratch install uses a renamed marketplace, installs are serialised, the build settings deny removing or uninstalling the real one, and the marketplace list is compared before and after.
- Unverified features (section 3.0 [probe] items): stage 0 settles them before building, and each part names its fallback.
- The guards are safety nets, not a permission system: the git rule misses git run from scripts or aliases; the truth rule misses Bash redirects; the ceiling rule misses the session's own start-up model and effort. Mitigation: hook tests, the build's deny rules and push-check, GitHub branch protection (suggested by `/flight:preflight`), the managed ceiling settings (offered by `/flight:preflight`), review, and the owner's merge. No claim is made beyond what each rule does.
- Plugin hooks fire in every session and subagent where the plugin is enabled. Mitigation: narrow matchers and `if` rules, the card only in pilot sessions, the git and truth rules only for agents, exit 0 on internal errors except the push rule.
- Agent `effort` in frontmatter may not apply to a main-thread agent (measured once on an older CLI in the cockpit's `pilot.sh`). Mitigation: the quick start passes `--model opus --effort high`.
- Two adversary definitions exist: the owner's project agent in `.claude/agents/adversary.md` (used by `plan.js` and the build) and the plugin's `flightdeck/agents/adversary.md`. Accepted: they serve different callers, and the owner said the adversary stays.
- The persona is agent-written and every imposter verdict leans on it. Mitigation: shown in full on the review page for correction.
- Nested `claude -p` sessions cost tokens and do not wait out usage limits. Mitigation: Sonnet or Haiku only, stop at the try steps, [stated] results open the pull request as a draft.
- Eval cases are model-graded and can be noisy. Mitigation: they never block, each run has `--max-cost-usd`, `--no-publish` keeps reports local, and the climb rule reverts changes inside the noise.
- `bin/` blocks installing the plugin on claude.ai and Cowork. Mitigation: the CLI is optional and off by default.
- Model aliases differ by provider (on Bedrock `sonnet` may be an older model). Mitigation: aliases kept for readability; the technical manual (PR 7) says how to pin full model ids.
- The three shipped recipes and the reading "a workshop is the place, a launch is one flight from it, an attempt is what a launch leaves behind" are the lead's guesses at the owner's meaning. Mitigation: shown on the review page with keep, rename or drop choices and an "is this right?" box, and seeded as questions in build-1.
- Small machines run few workflow agents at once, so a build run is a queue and takes longer. Mitigation: stated on the review page; the owner can raise the concurrency variable.

### What not to build

- No central runner like `fc`, no launch state machine, no `run.json`, `launch.json`, `HALT.json`, gate switches, manifests or escalation files: the folder listing and empty `answer:` lines are the state.
- No JSON files for owner-facing documents; questions, decisions and truth are markdown.
- No record prefixes, numbered requests, approval states or global registers; no vocative rules; no truth statements required for every item; the owner is never asked to approve agent-written text in chat (promotions arrive as draft pull requests the owner merges or closes).
- No rules in `.claude/rules/`, nothing under `dev/`, no changes to `INTENT.md` or `HISTORY.md`, no plan to retire dev-workspace.
- No replacement for Claude Code's teams, messaging, memory, worktrees, permissions or managed model settings; FlightDeck fills their slots, gives recipes and points at the native controls.
- No spec-first nine-domain spec chain as the default (it survives as an optional recipe).
- No large test suites of the tooling; one fast check per part, warnings for everything that is not a hard rule, and drills and eval cases in the optional lab.
- No web server unless PR 5 is ticked, and never one that binds beyond localhost, writes files, runs commands from page input or serves files outside `.flightdeck/`.
- No default agent, no forced output style, nothing that starts on its own: no automatic launches, promotions or climbs.
- No `fable`, `best`, `xhigh` or `max` in any model or effort value, and no ultracode.
- No push to `main`, no force-push, no deleted branch, no merge by an agent.
