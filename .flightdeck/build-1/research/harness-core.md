# Harness core: what FlightDeck can ship in Claude Code content

This report fixes the exact facts about the Claude Code content FlightDeck can ship (agent definitions, skills, hooks, CLAUDE.md and rules, output styles, settings, and the plugin that carries them), with each fact tied to a file and heading. The network was open, so I fetched the live Claude Code docs from https://code.claude.com/docs/en/ on 2026-10-10 (the plugin pages, the real memory page, the settings reference) and then tested the risky claims against the installed Claude Code 2.1.296 using throwaway plugins in the scratchpad. The headline findings are these. A plugin can ship agents, skills, commands, hooks, output styles, workflows, MCP and LSP servers, monitors, themes, `bin/` executables and a `settings.json`, but it cannot ship CLAUDE.md, `.claude/rules/`, permissions, `env`, or any setting other than `agent` and `subagentStatusLine`. Plugin agents silently ignore `permissionMode`, `hooks`, `mcpServers` and `initialPrompt`, so the previous branches' agents (which use `permissionMode: acceptEdits` and `initialPrompt`) would change behaviour if moved into a plugin's `agents/` folder. Loading the repo with `--plugin-dir` makes every write under it a protected-path write that is refused or prompted even in `acceptEdits` mode, whereas adding the repo as a local marketplace and installing the plugin loads it in place with no such write protection, so that is the right route for instant dogfooding. On this machine the `opus`, `sonnet` and `haiku` aliases resolve to Opus 5.5, Sonnet 5.5 and Haiku 5.5, and `fable` (used by many earlier agents, including the current `.claude/agents/adversary.md`) is above the owner's Opus ceiling.

## 2. Verified by running Claude Code 2.1.296 here

I built throwaway plugins under the scratchpad and ran `claude plugin validate`, `claude --plugin-dir`, and short `claude -p` sessions (cheap models). Nothing was written into the repo. Test side effects in `~/.claude/plugins` were removed afterwards.

- `claude --model sonnet|opus|haiku` initialised as `claude-sonnet-5-5`, `claude-opus-5-5`, `claude-haiku-5-5`. So agent frontmatter `model: sonnet` means Sonnet 5.5 on this provider.
- A plugin's agents appeared in the session's agent list as `tp:a1` and, for a file in a subfolder, `tp:sub:a2`. Its skill appeared as `tp:hello`. Plugin name prefix, then subfolder segments, then name.
- A plugin `settings.json` containing `{"agent":"a1","model":"opus","permissions":{"allow":["Bash"]}}` made the main thread run as agent `a1`: the session's tool list was exactly `Read, Grep` (a1's `tools:`), whereas the same plugin without `settings.json` had 40 tools. The permission mode stayed `default` even though `a1` declared `permissionMode: acceptEdits`, which fits the documented "ignored for plugin agents". I could not separate the `model` result because the account default is also Sonnet 5.5, so treat "plugin `model` key is dropped" as documented, not tested.
- A plugin agent with `skills: [hello]` and another run with `skills: [tp:hello]` both received the full skill body when spawned as a subagent through the Agent tool, and `${CLAUDE_PLUGIN_ROOT}` inside the skill body was substituted with the plugin path. Both the bare and the namespaced skill name work in a plugin agent's `skills:` list. (It did not preload when the agent was the main thread through the `agent` setting; I only tested that once, so do not rely on preloading for a main-thread agent.)
- A plugin agent with `isolation: worktree` really tried to create a worktree (it failed with `Cannot create agent worktree: not in a git repository and no WorktreeCreate hooks are configured` when run from `/tmp`). So `isolation` works for plugin agents, and a plugin agent that sets it cannot run outside a git repo.
- A plugin `hooks/hooks.json` with a shell-form `SessionStart` command ran, received `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` in its environment (data dir became `~/.claude/plugins/data/tp-inline`), and its stdout reached Claude's context. Pitfall confirmed: `{"command":"echo ctx","args":[]}` fails with `Executable not found in $PATH: "echo ctx"`, because an `args` key, even empty, switches the hook to exec form where `command` must be a bare executable.
- `claude plugin validate <plugin>` passes a plugin that has a `CLAUDE.md` at its root but warns `CLAUDE.md at the plugin root is not loaded as project context`. It did not warn about the ignored agent fields (`permissionMode`, `hooks`, `mcpServers`), a `rules/` folder, or a `settings.json` full of dropped keys. So validation will not catch those mistakes; a rule of our own must.
- `claude plugin validate /home/user/flightdeck` (the repo) passes with one warning (the marketplace has no `description`) and one advice line (README has no install line). `claude plugin validate /home/user/flightdeck/.claude` passes, including `.claude/agents/adversary.md` with `model: fable`.
- Loading the repo with `claude --plugin-dir /home/user/flightdeck` registers plugin `flight@inline` (name from `.claude-plugin/plugin.json`) and the project agent `adversary` appears unprefixed. The `dev-workspace@DBHD-dev-workspace` plugin enabled in `.claude/settings.json` is not installed here, so the dev-workspace CLI and skills are absent.
- Protected-path test. In a directory loaded with `--plugin-dir`, asking the model to create a file with `--permission-mode acceptEdits` failed with `Claude requested permissions to edit .../note.txt which is a sensitive file`. The same request in a directory not loaded as a plugin succeeded. The live `permission-modes.md` heading "Protected paths" lists "A directory you loaded with `--plugin-dir`" among protected directories.
- Local marketplace route. I created a git repo whose `.claude-plugin/marketplace.json` lists one plugin with `"source": "./"` (the repo root is the plugin) and ran `claude plugin marketplace add <repo> --scope local` then `claude plugin install <plugin>@<marketplace> --scope local`. ## 3. Agent (subagent) definitions

Source: `library/source/claude-code/subagents.md`, headings "Choose the subagent scope", "Write subagent files", "Frontmatter reference" (anchor `supported-frontmatter-fields`), "Choose a model", "Control subagent capabilities". Plugin rules: live `plugins/components.md`, heading "Agents" and "Frontmatter fields in plugin agents".

File format: a markdown file with YAML frontmatter, then the body as the system prompt. A subagent receives only that prompt plus basic environment details, not the Claude Code system prompt. Field names are camelCase and must match exactly; an unknown field is ignored without any error.

Frontmatter fields (all from "Frontmatter reference"):
- `name` (required). Unique id, at most 256 characters on the live page. Hooks receive it as `agent_type`. It cannot contain `:` (reserved for plugin scoping) or start with `-`; such a file is skipped with only a debug-log entry. The filename need not match.
- `description` (required). When Claude should delegate. Phrases like "use proactively" encourage automatic delegation. Combined descriptions of all agents over 15,000 tokens produce a startup warning (heading "Understand automatic delegation").
- `tools`. Allowlist as a comma string or YAML list. Omitted means inherit every tool available to subagents. If nothing in the list resolves to a tool, the subagent usually fails to launch. Supports MCP patterns `mcp__server` and `mcp__server__*`. `Agent(worker, researcher)` restricts which subagent types can be spawned but only for an agent running as the main thread via `--agent`; inside a subagent definition the parenthesised list is ignored. Do not list `Skill` to preload skills; use `skills`.
- `disallowedTools`. Denylist applied before `tools`; a tool in both is removed. An entry with a specifier like `Bash(git push *)` still removes the whole tool.
- `model`. `sonnet`, `opus`, `haiku`, `fable`, a full id such as `claude-opus-5-5`, or `inherit`. Resolution order (heading "Choose a model"): per-invocation `model` parameter from the Agent tool call, then the definition's `model`, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main conversation's model. Setting `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` makes the environment model override every definition, and Claude cannot pass a model; it applies to subagents, teammates and workflow agents. The model is also checked against the organisation `availableModels` allowlist.
- `permissionMode`. `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan`, or `manual` (alias for `default`). If the main conversation is in `bypassPermissions`, `acceptEdits` or `auto`, that mode wins over the subagent's. A subagent declaring `bypassPermissions` keeps the main mode instead. Ignored for plugin agents.
- `maxTurns`. Stops the subagent; the result is marked partial and Claude can resume it.
- `skills`. Preloads the full content of listed skills at startup (the live page adds: up to the first 32 distinct names). Skills with `disable-model-invocation: true` cannot be preloaded. A missing skill is skipped with a debug-log warning. The subagent can still invoke other skills through the `Skill` tool unless `Skill` is withheld.
- `mcpServers`. Names of configured servers, or inline definitions. Ignored for plugin agents. Inline servers from a project agent file need the folder to be trusted.
- `hooks`. Same format as settings hooks, scoped to the time the subagent runs; `Stop` becomes `SubagentStop`. Ignored for plugin agents. For project agents the workspace trust dialog must have been accepted for the folder (a `-p` run does not count).
- `memory`. `user` (`~/.claude/agent-memory/<name>/`), `project` (`.claude/agent-memory/<name>/`, recommended default) or `local` (`.claude/agent-memory-local/<name>/`). The first 200 lines or 25 KB of `MEMORY.md` go into the system prompt and Read, Write and Edit are enabled automatically. It does nothing if auto memory is turned off (`autoMemoryEnabled` false or `CLAUDE_CODE_DISABLE_AUTO_MEMORY`). Supported for plugin agents.
- `background`. `true` keeps it in the background even when Claude asks for foreground.
- `omitClaudeMd`. `true` launches it without user, project and local CLAUDE.md files (managed policy files still load). Needs v2.1.271.
- `effort`. `low`, `medium`, `high`, `xhigh`, `max`; the levels offered depend on the model. Overrides the session level for that subagent, but not `CLAUDE_CODE_EFFORT_LEVEL`, and a `maxEffortLevel` cap still applies (live `model-config.md`, heading "Set the effort level").
- `isolation`. Only `worktree`: a temporary git worktree branched by default from the default branch, cleaned up if nothing changed. Verified to work for plugin agents.
- `color`. `red`, `blue`, `green`, `yellow`, `purple`, `orange`, `pink`, `cyan`.
- `initialPrompt`. Auto-submitted first turn when the agent runs as the main session agent via `--agent` or the `agent` setting. Ignored for plugin agents.
- `experimental.cacheTtl` (`5m` or `1h`). Supported for plugin agents.

Which fields work when shipped by a plugin (live `plugins/components.md`, "Frontmatter fields in plugin agents"): supported are `name`, `description`, `model`, `effort`, `maxTurns`, `tools`, `disallowedTools`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation` and `color` (plus `experimental.cacheTtl`). Ignored are `permissionMode`, `hooks`, `mcpServers` and `initialPrompt`. The stated reason is security. The plugin author's alternatives: ship hooks in the plugin's `hooks/hooks.json` and MCP servers in `.mcp.json`, which apply whenever the plugin is enabled rather than only while that agent runs. A plugin agent whose frontmatter does not parse still loads, named after its file, with every field ignored and description `Agent from <plugin> plugin`.

Scopes and names (heading "Choose the subagent scope"): priority 1 managed settings, 2 the `--agents` JSON flag, 3 project `.claude/agents/`, 4 user `~/.claude/agents/`, 5 plugin `agents/`. Project and user folders are scanned recursively but subfolders do not change the name. Plugin folders are scanned recursively and subfolders do become part of the name: `agents/review/security.md` in plugin `my-plugin` is `my-plugin:review:security` (verified). Frontmatter `name` replaces only the last segment; a path listed in the manifest `agents` field loads without subfolder segments. The `--agents` JSON accepts `prompt` plus the frontmatter fields except `color` and `experimental`, and may be a file path in `-p` mode (v2.1.281). Project agent files are watched live except when the agents directory did not exist at session start.

Invoking (heading "Invoke subagents explicitly"): natural language, `@agent-<name>` (plugin: `@agent-<plugin>:<name>`), `claude --agent <name>` (a plugin agent can be named bare or scoped; scoped is needed if two plugins collide), or the `agent` setting (project `.claude/settings.json`, or a plugin's `settings.json`). With `--agent`, the agent's prompt replaces the default Claude Code system prompt entirely; CLAUDE.md files still load.

What a subagent gets and does not get (heading "What loads at startup"): its own prompt, the delegation message, every CLAUDE.md level (unless `omitClaudeMd`; Explore and Plan skip them), a git status snapshot, preloaded skills, and a sibling roster if it has `SendMessage`. It does not get the main conversation's output style (except a fork), the main auto memory, or the parent's history. Hooks from settings files, managed settings and plugins do fire inside subagents with `agent_id` and `agent_type` added.

Tool limits (heading "Available tools"): every subagent loses `AskUserQuestion`, `EnterPlanMode`, `ScheduleWakeup`, `WaitForMcpServers`, `Workflow`, `EndConversation`, and `ExitPlanMode` (unless `plan`), and loses `Agent` at the depth limit. Background subagents (the default when fork mode is on, which is the interactive default) keep only: Read, Grep, Glob, LSP, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, EnterWorktree, ExitWorktree, Monitor, TaskStop, SendMessage, Artifact, and all MCP tools. Limits: nesting depth 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), 20 concurrent subagents (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). Subagent final reports are scanned and flagged if they imitate system tags (heading "Subagent output scanning"). Subagents can be resumed with `SendMessage`; transcripts live at `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl`.

Deny or limit specific agents: `permissions.deny: ["Agent(Explore)"]`, `Agent(model:opus)` style parameter rules, or `--disallowedTools`.

## 4. Skills

Source: `library/source/claude-code/skills.md`, headings "Choose where skills load", "Frontmatter reference", "How a skill gets its command name", "Available string substitutions", "Add supporting files", "Control who invokes a skill", "Skill content lifecycle", "Run skills in a subagent".

Layout: one folder per skill containing `SKILL.md` (required) plus optional supporting files such as `reference.md`, `examples.md`, `scripts/helper.py`. Keep `SKILL.md` under about 500 lines and link the other files so Claude loads them on demand. Locations: managed, `~/.claude/skills/<name>/`, project `.claude/skills/<name>/`, nested `<subdir>/.claude/skills/` (loads when Claude touches files there), `--add-dir` directories, and a plugin's `skills/<name>/SKILL.md` which becomes `/<plugin>:<name>`. A `SKILL.md` placed at the plugin root with no `skills/` folder loads as one skill (set `name`). Commands (`commands/*.md`, `.claude/commands/`) are the older format with the same frontmatter minus `name` and `paths`; skills win on a name clash.

Frontmatter (all optional; only `description` recommended; a misspelled field is ignored; hyphenated names except `when_to_use`): `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`. The combined `description` and `when_to_use` text is cut at 1,536 characters in the skill listing, and the whole listing has a budget of about 1% of the context window (settings `skillListingBudgetFraction`, `skillListingMaxDescChars`; env `SLASH_COMMAND_TOOL_CHAR_BUDGET`); over-budget listings drop descriptions starting with the least-used skills. Boolean fields accept yes/no/on/off/1/0. Only the Agent Skills spec fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`) survive upload to claude.ai or the Skills API; the rest are Claude Code extensions.

Invocation control (heading "Control who invokes a skill"):
- Default: you and Claude can both invoke; the description is always in context and the body loads when invoked.
- `disable-model-invocation: true`: only the user (`/name`); the description is not in context; the skill cannot be preloaded into subagents or fired by a scheduled task.
- `user-invocable: false`: only Claude; hidden from the `/` menu.
- `paths:` globs limit automatic activation to matching files.
- `allowed-tools` pre-approves tools for the turn that invokes the skill only; it does not restrict. `disallowed-tools` removes tools while the skill is active. Workspace trust does not gate `allowed-tools`.
- `context: fork` runs the skill in a fresh subagent with the skill body as its task; `agent:` picks the type (`Explore`, `Plan`, `general-purpose`, or any custom agent, default `general-purpose`); `background` defaults to true for forked skills (v2.1.218), `false` waits for the result. A forked skill must contain a real task, not just guidelines. The subagent does not see the conversation.
- `hooks:` in a skill registers hooks when the skill is invoked and keeps them for the rest of the session; `once: true` removes a hook after its first success (only honoured in skill frontmatter).
- `model` and `effort` in a skill apply for the rest of the current turn only.

Content lifecycle (heading "Skill content lifecycle"): the rendered body enters the conversation as one message and stays; it is carried through auto-compaction within a budget (first 5,000 tokens of each skill, 25,000 combined, most recent first). Re-invoking an identical skill adds only a short "already loaded" note.

Substitutions in skill bodies and in `allowed-tools` Bash rules: `$ARGUMENTS`, `$ARGUMENTS[N]`, `$N`, `$name` (from `arguments:`), `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`, `${CLAUDE_SKILL_DIR}` (for plugin skills, the skill's own subfolder, not the plugin root), `${CLAUDE_PROJECT_DIR}`, and in plugin skills only `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}`. Dynamic context: `` !`command` `` inline (must follow whitespace or line start) and fenced ` ```! ` blocks run before the body is sent; `disableSkillShellExecution` turns this off; injected commands go through the normal permission rules and abort on deny.

Permissions on skills: `Skill(name)` and `Skill(name *)` rules; `skillOverrides` in settings (`on`, `name-only`, `user-invocable-only`, `off`) does not affect plugin skills (those are managed through `/plugin`). Synced claude.ai skills use the reserved `anthropic-skills:` namespace; do not name anything `anthropic-skills` or `synced`. Cloud and Cowork sessions do not read `~/.claude/skills` or user-scope plugins; project `.claude/skills/` committed to the repo does load there.

Naming (heading "How a skill gets its command name"): plugin skill is `/<plugin>:<dir>`; frontmatter `name` replaces only the last segment (`name: fancy` gives `/my-plugin:fancy`), and a `name` that already starts with the plugin prefix is not doubled (v2.1.246+). Verified here: plugin `tp`, skill dir `hello`, listed as `tp:hello`.

Live-change detection: skill text edits are picked up in-session; for a skill folder that is also a plugin, changes to `hooks/`, `.mcp.json`, `agents/` and `output-styles/` need `/reload-plugins`. `/reload-skills` picks up a newly created top-level skills folder. A `SessionStart` hook can return `reloadSkills: true` after installing skills.

## 5. Hooks

Source: `library/source/claude-code/hooks.md` (reference) and `hooks-guide.md` (guide), plus live `plugins/components.md` heading "Hooks".

The 33 events (hooks.md, heading "Hook lifecycle" table). Per session: `SessionStart`, `Setup` (only with `--init-only`, or `--init`/`--maintenance` under `-p`), `SessionEnd`. Per turn: `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `StopFailure`. In the agentic loop: `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`. Environment and file: `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`. Context and model: `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`. MCP: `Elicitation`, `ElicitationResult`.

Config shape (heading "Configuration"): three levels. Event name maps to an array of matcher groups `{ "matcher": "...", "hooks": [ handler, ... ] }`. In `settings.json` the object is under the key `hooks`. In a plugin's `hooks/hooks.json` the same event map sits under a top-level `"hooks"` key, with an optional top-level `"description"`; a file without the `"hooks"` wrapper fails to load. The manifest `hooks` field (file path, inline object without wrapper, or array of both) merges with `hooks/hooks.json`. Hooks from all sources (user, project, local, managed, plugin, skill and subagent frontmatter) are merged, never replaced; all matching hooks run in parallel; identical handlers in different settings files run once but a plugin's copy stays separate. Where hooks can live (heading "Hook locations"): `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed settings, plugin `hooks/hooks.json`, skill frontmatter, subagent frontmatter.

Matchers (heading "Matcher patterns"): `"*"`, empty or omitted matches all. A value made only of letters, digits, `_`, `-`, spaces, `,` and `|` is an exact string or a list (`Edit|Write`). Anything else is an unanchored JavaScript regular expression. What is matched depends on the event: tool name for the tool events; `startup|resume|clear|compact|fork` for `SessionStart`; agent type for `SubagentStart` and `SubagentStop` (plugin agents are `plugin:name`, which contains a colon and so is a regex; anchor it as `^flight:reviewer$`); `manual|auto` for the compaction events; notification type; config source; load reason; MCP server name; and so on. `UserPromptSubmit`, `PostToolBatch`, `Stop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `WorktreeCreate`, `WorktreeRemove` and `MessageDisplay` have no matcher support (a matcher there is silently ignored). MCP tools are `mcp__<server>__<tool>`; a plugin's own server is `mcp__plugin_<plugin>_<server>__<tool>`, and a matcher on the bare server name never fires.

Handler types (heading "Hook handler fields"): `command`, `http`, `mcp_tool`, `prompt` (single-turn model call, default Haiku-class fast model), `agent` (experimental multi-turn verifier with Read, Grep, Glob, up to 50 turns). Support by event (heading "Prompt-based hooks"): all five types on `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `PermissionDenied`, `Stop`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `UserPromptSubmit`, `UserPromptExpansion`; `PermissionRequest` supports all but `agent`; `SessionStart` and `Setup` support only `command` and `mcp_tool`; the remaining events support `command`, `http` and `mcp_tool`. Common fields: `type`, `if` (one permission-rule string, only evaluated on the five tool events, otherwise the hook never runs), `timeout` (defaults 600 s for command, http and mcp_tool; 30 s for prompt; 60 s for agent; 30 s for `UserPromptSubmit`, `PreModelSwitch`, `PostModelSwitch`; 10 s for `MessageDisplay`; `SessionEnd` shares a 1.5 s budget), `statusMessage`, `once`. Command fields: `command`, `args`, `async`, `asyncRewake`, `shell`. Exec form (when `args` is present, even empty) spawns `command` directly with no shell; shell form (no `args`) runs through `sh -c`. Prefer exec form when a path placeholder is used; in shell form wrap `${CLAUDE_PLUGIN_ROOT}` in double quotes. `${user_config.*}` is allowed only in exec form for plugin hooks.

Input (heading "Hook input and output"): JSON on stdin (HTTP: POST body). Common fields: `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort.level`, `hook_event_name`, and inside a subagent or `--agent` session `agent_id`, `agent_type`. Event extras: `PreToolUse` and `PostToolUse` get `tool_name`, `tool_input`, `tool_use_id` (PostToolUse adds `tool_response`, `duration_ms`); `SubagentStart` and `SubagentStop` get `agent_id`, `agent_type` (plus `agent_transcript_path`, `last_assistant_message`, `stop_hook_active` on stop); `Stop` gets `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`; `TaskCreated` and `TaskCompleted` get `task_id`, `task_subject`, `task_description`, `teammate_name`; `SessionStart` gets `source` and maybe `model`, `agent_type`. File tool paths are always absolute. `CLAUDE_ENV_FILE` is available in `SessionStart`, `Setup`, `CwdChanged`, `FileChanged` for persisting environment variables. `CLAUDE_PROJECT_DIR` stays at the project root even inside a worktree; read `cwd` from the input for the real directory.

Output (headings "Exit code output", "JSON output", "Decision control"):
- Exit 0: success; for `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, `PostModelSwitch` plain stdout is added to Claude's context; for other events stdout goes only to the debug log. A stdout that starts with `{` and ends with `}` is parsed as JSON.
- Exit 2 is the only code that blocks by itself; its effect varies by event (table "Exit code 2 behavior per event"): it blocks `PreToolUse`, `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `ConfigChange`, `PostToolBatch`, `PreCompact`, `PreModelSwitch`, `Elicitation`, `ElicitationResult`, `WorktreeCreate`, `WorktreeRemove`; it only shows stderr for `PostToolUse` and `PostToolUseFailure`; it is ignored for `PermissionRequest`, `Notification`, `Setup`, `StopFailure`, `PermissionDenied`, `InstructionsLoaded`, `MessageDisplay`, and shows stderr to the user only for `SessionStart`, `SubagentStart`, `SessionEnd`, `CwdChanged`, `FileChanged`, `PostCompact`, `PostModelSwitch`. Exit 1 and other codes are non-blocking errors.
- Universal JSON fields: `continue`, `stopReason`, `suppressOutput` (no effect), `systemMessage`, `terminalSequence`. Strings `additionalContext`, `systemMessage`, `initialUserMessage` and plain stdout are capped at 10,000 characters (overflow is saved to a file and replaced with a path and a 2,000-character preview).
- Decision patterns: top-level `decision: "block"` plus `reason` for `UserPromptSubmit`, `UserPromptExpansion`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`; `PreToolUse` uses `hookSpecificOutput.permissionDecision` of `allow`, `deny`, `ask` or `defer`, with `permissionDecisionReason`, `updatedInput` (replaces the whole input) and `additionalContext` (precedence `deny` over `defer` over `ask` over `allow`); `PermissionRequest` uses `hookSpecificOutput.decision.behavior`; `PostToolUse` can replace output with `updatedToolOutput`; `SessionStart` can return `additionalContext`, `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`; `SubagentStart` can only return `additionalContext` (it cannot block spawning); `Stop` and `SubagentStop` can block with `decision: "block"` or continue with `hookSpecificOutput.additionalContext` (feedback without an error). A Stop hook may block at most 8 times in a row (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); check `stop_hook_active` to avoid loops.
- `PreToolUse` hooks run before any permission-mode check and can deny even in `bypassPermissions`; a hook `allow` does not override deny or ask rules. Hooks tighten but cannot loosen past permission rules.

Hooks in agent and skill frontmatter (heading "Hooks in skills and agents", live `sub-agents.md` "Hooks in subagent frontmatter"): same format. Subagent frontmatter hooks run only while that agent runs, need folder trust, and are ignored for plugin agents. Skill frontmatter hooks register at invocation and persist for the session. A plugin's `hooks/hooks.json` hooks register when the session loads the plugin and fire on their events from then on, not only when the plugin's skills are used; narrow the `matcher` to limit them.

Operational facts: hooks are held until the workspace trust dialog is accepted in interactive sessions (not required in `-p`/SDK runs); `/hooks` is a read-only browser; `disableAllHooks` turns them off (managed hooks survive a non-managed `true`); `allowManagedHooksOnly` blocks user, project and plugin hooks; `--settings '{"disableAllHooks": true}'` is the per-run switch. Async hooks (`async: true`, command type only) cannot block; their `additionalContext` arrives next turn. Debug with `claude --debug-file <path>`.

## 6. CLAUDE.md, `.claude/rules/`, imports, auto memory

Source: live `memory.md` (the library copy is a duplicate of `claude-directory.md`), headings "Choose where to put CLAUDE.md files", "Import additional files", "How CLAUDE.md files load", "Organize rules with .claude/rules/", "Path-specific rules", "Rule frontmatter reference", "AGENTS.md", "Auto memory".

- CLAUDE.md locations in load order (broadest first): managed policy (`/etc/claude-code/CLAUDE.md` on Linux), `~/.claude/CLAUDE.md`, project `./CLAUDE.md` or `./.claude/CLAUDE.md`, `./CLAUDE.local.md` (private; add to `.gitignore`). Files in the working directory and every parent load at launch, concatenated root to cwd; files in subdirectories load on demand when Claude touches a file there. Treated as context, not enforcement; target under 200 lines; a file up to 4 MiB loads. Block-level HTML comments are stripped before injection.
- Imports: `@path/to/file` anywhere in a CLAUDE.md (or rule file) imports the file at launch. Relative paths resolve from the importing file, recursion depth is 4, spaces need a backslash, and code spans and fenced blocks are not scanned. Imports outside the working directory trigger a one-time approval dialog for project files. Imports do not reduce context cost.
- `.claude/rules/*.md`: all `.md` files, recursively. Without `paths` frontmatter they load at launch with the same priority as `.claude/CLAUDE.md`. With `paths:` (a YAML list or comma string of globs, brace expansion allowed within a budget) they load only when Claude reads, writes or edits a matching file. `paths` is the only frontmatter field read. Symlinks are supported; a symlink pointing outside the working directory needs the external-import approval. User rules in `~/.claude/rules/` load before project rules.
- `claudeMdExcludes` (any settings layer) skips files by absolute glob. `claudeMd` is honoured only in managed settings. `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` loads memory files from `--add-dir` directories.
- `AGENTS.md`: read when there is no CLAUDE.md or CLAUDE.local.md in or above the working directory (v2.1.277+); a CLAUDE.md can `@AGENTS.md`. Setting **Project instructions** (`pluginConfigs["cc-plugin-agents-md@builtin"].options.instructionFiles`) changes this.
- Auto memory: Claude's own notes at `~/.claude/projects/<project>/memory/` (machine-local, shared by all worktrees of a repo); `MEMORY.md` first 200 lines or 25 KB load each session; topic files load on demand. Off with `autoMemoryEnabled: false` or `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; `autoMemoryDirectory` relocates it. Not passed to non-fork subagents.
- Hooks `InstructionsLoaded` fires for CLAUDE.md and rules loads (not for `AGENTS.md` read through the setting).
- A plugin cannot ship any of this: live `plugins/components.md` heading "Skills" says "Claude Code doesn't load a `CLAUDE.md` at the plugin root", and live `plugins/manifest-reference.md` heading "Standard layout" repeats it and lists no rules component. The documented substitute is a skill. Other substitutes that exist: a `SessionStart` hook (its stdout or `additionalContext` becomes context, verified), a CLI under `bin/` that copies files into the project, or a bootstrap skill that writes `.claude/rules/` and CLAUDE.md into the user's repo.
- Observed in this repo: `.claude/rules/context.md` imports `@../../dev/workspace/context/tree.md`, a file that does not exist (only `.keep` is there), so the import resolves to nothing without any error.

## 7. Output styles

Source: `library/source/claude-code/output-styles.md`.

- A style is a markdown file with frontmatter `name`, `description`, `keep-coding-instructions` (default false: the style replaces Claude Code's software-engineering instructions), and `force-for-plugin` (plugin styles only; applies automatically when the plugin is enabled and overrides the user's `outputStyle`; if several enabled plugins set it, the first loaded wins).
- Locations: `~/.claude/output-styles/`, project `.claude/output-styles/` (discovered from the working directory up to the repo root, closest wins), managed `.claude/output-styles/`, plugin `output-styles/<name>.md` shown as `<plugin>:<name>` (manifest key `outputStyles` replaces the folder scan).
- Selected by `/output-style <name>`, `/config`, or the `outputStyle` setting (built-ins are case-sensitive: `Proactive`, `Concise`, `Explanatory`, `Learning`; a mismatch silently gives Default). The command and menus write to `.claude/settings.local.json`. A plugin's `settings.json` cannot set `outputStyle` (only `agent` and `subagentStatusLine` survive).
- Style files are read at startup, so a new or edited custom style needs a restart. A style applies to the main conversation and to forks, not to ordinary subagents. It is an instruction, not enforcement.

## 8. Permissions and settings keys that matter to agents

Sources: `library/source/claude-code/permissions.md`; live `settings.md` heading "Settings precedence"; live `settings-reference.md` (headings below); `library/source/claude-code/claude-directory.md` heading "Choose the right file".

Settings files and precedence (highest first): managed settings, then the `--settings` flag, then `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`. Array keys such as `permissions.allow` merge across files; `fallbackModel`, `modelPicker`, `availableModels` (when managed) do not. A deny at any level cannot be allowed by another. Project `permissions.allow` and `additionalDirectories` apply only after the workspace trust dialog; `deny` and `ask` always apply.

Permission rules (permissions.md): `Tool` or `Tool(specifier)`; order deny, then ask, then allow, first match wins; a bare tool name in `deny` removes the tool from Claude's context. Bash patterns use `*` (put it after the subcommand: `Bash(git log *)`), `Read(...)`/`Edit(...)` use gitignore-style paths, `WebFetch(domain:x)`, `mcp__server__tool`, `Agent(Name)`, `Skill(name)`, and parameter matching `Agent(model:opus)`, `Agent(isolation:worktree)`, `Bash(run_in_background:true)` (deny and ask only; cannot match a tool's primary content field). Modes: `default` (shown as Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`; `permissions.defaultMode` sets the start mode; `disableBypassPermissionsMode` and `disableAutoMode` can lock modes. A subagent's `permissionMode` yields to the main mode in `bypassPermissions`, `acceptEdits` and `auto`. Permissions guard Claude's tool calls; they do not constrain a plugin's own hooks, monitors, MCP/LSP servers, or mod code, which run with the user's full permissions outside the sandbox (live `plugins/security.md`).

Keys relevant to FlightDeck (live `settings-reference.md`):
- Agents and sessions: `agent` (run the main thread as a named agent), `subagentStatusLine`, `teammateMode`, `worktree` (`baseRef`, `symlinkDirectories`, `sparsePaths`, `bgIsolation`), `enableWorkflows`, `disableWorkflows`, `statusLine`, `outputStyle`.
- Models: `model`, `effortLevel`, `modelSettings` (per-model saved effort), `maxEffortLevel`, `fallbackModel` (ordered chain, at most three), `availableModels`, `deniedModels`, `ultracode`.
- Permissions: `permissions.allow|ask|deny|additionalDirectories|defaultMode|disableBypassPermissionsMode|blockReadsOutsideWorkingDirectories`, `disableAutoMode`, `autoMode`, `sandbox.*`.
- Environment and memory: `env` (object of strings; project and local settings cannot set variables that choose storage locations, telemetry exporters, plugin cache or seed directories, dialog timers and similar), `autoMemoryEnabled`, `autoMemoryDirectory`, `claudeMd` (managed only), `claudeMdExcludes`, `plansDirectory`, `includeGitInstructions`, `attribution`, `cleanupPeriodDays`.
- Hooks and plugins: `hooks`, `disableAllHooks`, `allowManagedHooksOnly`, `allowedHttpHookUrls`, `httpHookAllowedEnvVars`, `enabledPlugins` (keyed `plugin@marketplace`; project scope shares the on/off switch but each person must still install), `extraKnownMarketplaces`, `pluginConfigs` (user or managed only), `strictKnownMarketplaces`, `strictPluginOnlyCustomization` (can lock `skills`, `agents`, `hooks`, `mcp` to plugin sources; project-agent locking leaves plugin agents working), `skillOverrides`, `disableSkillShellExecution`, `disableBundledSkills`.
- Environment variables useful to a multi-agent product: `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, `CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`, `CLAUDE_CODE_FORK_SUBAGENT`, `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, `CLAUDE_CODE_DISABLE_WORKFLOWS`, `CLAUDE_CODE_PLUGIN_DIRS` (absolute or `~` paths, `:`-separated, v2.1.280+), `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`, `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS` and `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS`. Source: `library/source/claude-code/env-vars.md` (table rows by name).

Protected paths (live `permission-modes.md`, heading "Protected paths"; `permissions.md` heading "Permission modes" warning): writes to `.git`, `.vscode`, `.idea`, `.husky`, `.mcp.json`, `.claude.json`, shell rc files, package-manager config and, with exceptions, `.claude` are never auto-approved: prompted in `default` and `acceptEdits`, routed to the classifier in `auto`, denied in `dontAsk`, allowed only in `bypassPermissions`. `permissions.allow` rules do not pre-approve them. Exceptions inside `.claude`: `.claude/worktrees/`, the session's own plan files, and markdown files in an auto-memory or subagent-memory directory such as `.claude/agent-memory/`. A directory loaded with `--plugin-dir` is protected as a whole (verified). So any agent that must write `.claude/agents/`, `.claude/rules/`, `.claude/settings.json` or `.claude/skills/` in a non-bypass unattended run will be blocked or prompted; this includes a headless build agent.

Sandbox (`library/source/claude-code/sandboxing.md`): OS-level filesystem and network isolation for Bash, PowerShell and Monitor commands only (not for Read/Edit tools, hooks, MCP servers or plugin processes); `sandbox.enabled`, `sandbox.filesystem.*`, `sandbox.network.*`, `autoAllowBashIfSandboxed` (default true). Security overview (`library/source/claude-code/security.md`): Manual mode is read-only by default; trust verification is skipped under `-p`.

## 10. Plugins: layout, components, limits, loading

Sources are live pages: `plugins/overview.md` (served at `/plugins`), `plugins/components.md`, `plugins/manifest-reference.md` (also served at `/plugins-reference`), `plugins/create.md`, `plugins/cli-reference.md`, `plugins/loading.md`, `plugins/marketplace-reference.md`, `plugins/create-marketplace.md`, `plugins/security.md`, `plugins/mods/*.md`, `plugin-evals.md`, `workflows.md` heading "Distribute a workflow in a plugin".

Standard layout (manifest-reference, heading "Standard layout"). Only `.claude-plugin/plugin.json` lives inside `.claude-plugin/`; every other folder sits at the plugin root.
- `.claude-plugin/plugin.json`: manifest, optional (without it the name is the directory name for `--plugin-dir`, or the marketplace entry name).
- `skills/<name>/SKILL.md`; `commands/*.md` (older, flat); `agents/*.md`; `hooks/hooks.json`; `monitors/monitors.json`; `output-styles/*.md`; `themes/*.json`; `workflows/*.js`; `bin/` (executables); `settings.json`; `.mcp.json`; `.lsp.json`.
- `scripts/` and similar helper folders are a convention only; hooks point at them by path. `evals/` is the conventional folder for `claude plugin eval` cases (manifest `experimental.evals` can relocate it).

Every component type a plugin can ship (components.md, headings "Skills" through "Monitors"):
- Skills: `/<plugin>:<name>`; manifest `skills` adds to the default scan (other component keys replace). `"."` or `"./"` makes the plugin root itself a skill folder.
- Commands: `/<plugin>:<file>`, subfolders add segments; manifest `commands` replaces the scan and also accepts an object of inline `content` commands.
- Agents: `<plugin>:<name>` with the ignored-field list above; manifest `agents` (files only, not directories) replaces the scan.
- Hooks: all five handler types and the events above; `hooks/hooks.json` plus manifest `hooks`, merged.
- Hooks module (a "mod"): JavaScript or TypeScript event handlers run inside Claude Code that can draw panes, add `/commands`, and guard tool calls; declared with `"modules": ["./register.js"]` in `hooks/hooks.json`; needs Claude Code v2.1.287+; unsandboxed; `claude plugin validate` lists the events and API calls a mod makes; `claude plugin test` runs `*.test.ts` files (`plugins/mods/overview.md`, `plugins/mods/reference.md` heading "Files").
- MCP servers: `.mcp.json` (with or without the `mcpServers` wrapper) plus manifest `mcpServers` (inline map, file path, `.mcpb` bundle or https URL); named `plugin:<plugin>:<server>`; tools `mcp__plugin_<plugin>_<server>__<tool>`; local stdio servers do not run on claude.ai.
- LSP servers: `.lsp.json` (server name maps straight to its config, no wrapper) plus manifest `lspServers`; `validate` does not check this file.
- Output styles: `output-styles/<name>.md`, appears as `<plugin>:<name>`; `force-for-plugin` available.
- Themes: `themes/<slug>.json` (manifest key `experimental.themes`).
- Workflows: `workflows/*.js`, run as `/<plugin>:<meta.name>` (manifest `workflows` replaces the scan).
- Monitors: `monitors/monitors.json`, an array of `{name, command, description, when}` where `when` is `always` or `on-skill-invoke:<skill>`; start only in interactive sessions; run unsandboxed in the session cwd with the user's permissions; cannot use `${user_config.*}`; manifest key `experimental.monitors`.
- Executables: files in `bin/` are added after the user's own entries to the PATH of the Bash tool's shell while the plugin is enabled; claude.ai and Cowork refuse to install a plugin with a top-level `bin/`.
- Default settings: `settings.json` at the root or manifest `settings`; only `agent` and `subagentStatusLine` take effect, everything else is dropped; the file wins over the manifest key; user settings override plugin defaults; two plugins setting the same key: the later loaded wins. Verified that `agent` works.
- Channels (`channels` manifest key bound to an MCP server) and `userConfig` prompts (types `string`, `number`, `boolean`, `directory`, `file`; `sensitive: true` goes to the keychain; surfaced as `${user_config.KEY}` in MCP/LSP config, exec-form hook args, and skill/agent content (non-sensitive only) and as `CLAUDE_PLUGIN_OPTION_<KEY>` in hook environments; values stored in `pluginConfigs`).
- Manifest also carries `dependencies` (other plugins, optionally with version ranges), `defaultEnabled`, `displayName`, `version` (pins the install until changed), `author`, `homepage`, `repository`, `license`, `keywords`, `metadata`, `types`, directory-listing fields.

What a plugin cannot ship:
- `CLAUDE.md` or any rules (`.claude/rules/`), as shown above; `claude plugin validate` warns about a root `CLAUDE.md`. Nothing in the docs lists a plugin component for `.claude/rules/`; I tested that `rules/` at the plugin root produced no validation message and I have no evidence it loads, so treat it as not loadable.
- Permission rules, `env`, `model`, `outputStyle`, `hooks` (inside settings.json), or any settings key other than `agent` and `subagentStatusLine`.
- Agent frontmatter `permissionMode`, `hooks`, `mcpServers`, `initialPrompt`.
- Auto memory contents, managed policy, or output of `/init`.
- Files outside the plugin directory: component paths containing `..` or symlinks that escape the plugin root are rejected; a marketplace-installed copy does not include files outside the plugin directory, so scripts must not reach into `../shared`.
- A plugin installed through a marketplace is copied into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` (the whole directory, so a plugin whose root is the whole repo copies the whole repo, including `library/`). Do not write state there; use `${CLAUDE_PLUGIN_DATA}`.

Variables (manifest-reference heading "Environment variables"; components.md heading "Reference plugin paths and store data"): `${CLAUDE_PLUGIN_ROOT}` (install directory; changes with every version), `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`, survives updates; verified present in a hook's environment), `${CLAUDE_PROJECT_DIR}`. They are substituted in skill, command and agent bodies, hook and monitor commands, and MCP/LSP config. They are exported to hook, MCP and LSP processes but are not present in commands the Bash tool runs for Claude. Quote them in shell-form commands. Skills additionally get `${CLAUDE_SKILL_DIR}`. `${CLAUDE_PLUGIN_ROOT}` is only substituted in plugin skills.

Naming rules: plugin names are kebab-case; names starting `claude-`, `anthropic-`, `anthropics-` or `cc-plugin-`, or equal to `claude`, `anthropic`, `claude-code`, `claude-mods`, or combining `official` with `claude`/`anthropic`, are rejected by `validate` (error). `flight` is fine. Marketplace names cannot be `inline`, `skills-dir` or `synced`. Unknown top-level manifest keys are stripped with a warning; unknown keys inside `userConfig`, `channels`, `lspServers` or `monitors` entries make the plugin fail to load.

How to load a plugin locally for instant testing (create.md heading "Develop without a marketplace"; cli-reference heading "Flags that load a plugin for one session"):
- `claude --plugin-dir ./path` (directory or `.zip`; repeat the flag; a folder of plugins loads each child with a manifest, v2.1.265+). Session-only; listed as `<name>@inline`; shown by `claude --plugin-dir ./p plugin list`. `CLAUDE_CODE_PLUGIN_DIRS` does the same through the environment. `--plugin-url <zip url>` fetches an archive. Managed settings can disable these flags (`disableSideloadFlags`). Pointing `--plugin-dir` at a marketplace root does not load the plugins under it. Edits made during the session apply with `/reload-plugins`. Caution (verified): the directory becomes a protected path for writes.
- `claude plugin marketplace add <path>` for a local directory (or `./path`, `owner/repo`, git URL, a hosted `marketplace.json`); `--scope user|project|local`. Then `claude plugin install <plugin>@<marketplace> --scope ...`. A relative-path plugin in a marketplace added from a local path loads in place, so edits take effect at the next session or `/reload-plugins` without a version bump (verified that the repo-root plugin loaded and was writable). `/plugin marketplace add` and `/plugin install` do the same inside a session.
- `claude plugin init <name>` scaffolds a plugin under `~/.claude/skills/<name>/`, which then auto-loads every session as `<name>@skills-dir`; the same layout under a project's `.claude/skills/<name>/` (with `.claude-plugin/plugin.json`) loads after workspace trust, only from the primary working directory. Claude Code does not scan a project `.claude/plugins/`.
- `claude plugin validate <dir> [--strict] [--json]` (the authoritative manifest and frontmatter check; given a directory holding both marketplace.json and plugin.json it checks both, v2.1.289+). `claude plugin list`, `enable`, `disable`, `update`, `uninstall`, `tag`, and `claude plugin eval` exist (cli-reference).
- Sharing with a team without publishing: commit `enabledPlugins` and `extraKnownMarketplaces` to `.claude/settings.json`; every collaborator still has to install the plugin themselves. Cloud sessions do not add repository-listed marketplaces and do not load user-scope plugins; they do load committed project `.claude/` content.

Marketplace (marketplace-reference.md): `.claude-plugin/marketplace.json` with `name`, `owner`, `plugins[]` (each `name` and `source`; `source` `"./"` means the marketplace root is the plugin); `description` is recommended. Strict mode (default true) means `plugin.json` is authoritative and entry component fields are appended; `strict: false` plus any entry component field plus a `plugin.json` is a load-failing conflict. Relative-path sources need `./` and no `..`. Existing repo state: `.claude-plugin/plugin.json` (name `flight`, version `0.1.0`, author dilberryhoundog) and `.claude-plugin/marketplace.json` (marketplace `DBHD-FlightDeck`, one entry `flight` with `source: "./"`, no top-level description). So installed names would be `flight@DBHD-FlightDeck`, skills `/flight:<name>`, agents `flight:<name>`.

Evals (plugin-evals.md): `claude plugin eval` runs `evals/<case>/` folders (a prompt plus graders: regex, `tool_used`, rubric judged by a model) three times each by default, with and without the plugin (`WITH`, `W/OUT`, delta), in fresh non-interactive sessions; needs v2.1.269+, uses real model calls; the page mentions an early-access gate in its troubleshooting headings, so check availability before depending on it. This matches VISION.md "Laboratory" and "Built with quality" closely.

## Facts that constrain FlightDeck's layout

- The plugin root can hold `.claude-plugin/plugin.json` plus `agents/`, `skills/`, `commands/`, `hooks/hooks.json`, `output-styles/`, `workflows/`, `monitors/monitors.json`, `themes/`, `bin/`, `settings.json`, `.mcp.json`, `.lsp.json`. Nothing but `plugin.json` goes inside `.claude-plugin/`. Everything else in the repo (`library/`, `dev/`, `lab/`, `.flightdeck/`, `INTENT.md`) is not a plugin component, and with `source: "./"` it is copied into the install cache wholesale, so keep bulky non-plugin material small or move the plugin source into a subfolder (for example `plugins/flight/` with `source: "./plugins/flight"`) if install size matters.
- A plugin cannot ship CLAUDE.md or `.claude/rules/`. FlightDeck's always-on instructions and rules must live in the repo's own `.claude/` (loaded when working in this repo, which is the dogfooding case), be delivered by a `SessionStart` hook that prints context (verified to reach Claude) or by a skill, or be copied into a user's project by a bootstrap skill or `bin/` CLI. Anything the owner wants to hold "every time" belongs in a hook or permission rule, because CLAUDE.md, rules and output styles are advice only.
- Two homes for agents, with different power. Agents under the plugin's `agents/` are namespaced `flight:<name>` and silently lose `permissionMode`, `hooks`, `mcpServers` and `initialPrompt`. Agents under the repo's `.claude/agents/` keep every field but are unprefixed and only exist where that folder exists. If an agent needs `permissionMode`, frontmatter hooks, scoped MCP servers or `initialPrompt` (the earlier `orchestrator.md` and `implementer.md` on `origin/flightcrew-core:.claude/agents/` use `initialPrompt` and `permissionMode: acceptEdits`), keep it in `.claude/agents/` or replace the field with plugin-level hooks, `.mcp.json`, session `agent` setting or a launch prompt.
- Plugin agents that should run safely everywhere must set `tools`/`disallowedTools` explicitly, since they cannot declare a permission mode; and they must tolerate `isolation: worktree` only inside git repositories.
- Model ceiling. Use `model: sonnet` (Sonnet 5.5 here), `model: haiku` (Haiku 5.5) and `model: opus` (Opus 5.5) with `effort: high` set explicitly on Opus-class agents, because Opus 5.5 defaults to medium. Do not use `model: fable` or the `best` alias anywhere in shipped content: `origin/cockpit:.claude/agents/*.md`, `origin/flightcrew-core:.claude/agents/*.md` and the current `.claude/agents/adversary.md` all use `fable`. `CLAUDE_CODE_SUBAGENT_MODEL` with `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` in the `env` of a settings file can force one model on every subagent, teammate and workflow agent, and `availableModels` or `deniedModels` can forbid models (all settings-level, so they must live in repo or user settings, not in the plugin). A `PreToolUse` hook matched on `Agent` could in principle rewrite the call's `model` through `updatedInput` (the per-invocation parameter has the highest priority), but I did not test that, so treat it as an untested idea.
- The `model` aliases move over time and differ by provider; the full ids `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5` pin a version. Pinning costs readability and portability; aliases follow the user's provider, so on Bedrock `sonnet` is Sonnet 4.5. Decide once and document it.
- Settings the plugin cannot deliver (permissions, `env`, `model`, `outputStyle`, `enabledPlugins`, sandbox) must be delivered through the repo's `.claude/settings.json` (shared) or `.claude/settings.local.json` (personal; gitignored when Claude Code writes it), or a setup step. Only `agent` and `subagentStatusLine` can ride in a plugin `settings.json`.
- Dogfooding and "instant try". Do not rely on `claude --plugin-dir .` for the repo root: it makes the whole directory a protected path, so agents that write reports and workshop files there will be prompted, routed to the classifier or denied in unattended runs. Use `claude plugin marketplace add <repo-path> --scope local` then `claude plugin install flight@DBHD-FlightDeck --scope local` (the plugin loads in place and edits show after `/reload-plugins`), or commit `extraKnownMarketplaces` and `enabledPlugins` in `.claude/settings.json` (still needs each person to install). Use `--plugin-dir` only for short read-only trials, and always add `claude plugin validate .` (and `claude plugin validate .claude`) to the checks, remembering validation does not warn about ignored agent fields or an inert `rules/` folder.
- Writes to `.claude/` (agents, skills, rules, settings) are protected-path writes: refused in `dontAsk`, classifier-routed in `auto`, prompted in `default` and `acceptEdits`, allowed only in `bypassPermissions`; `permissions.allow` does not change that. A build workflow that creates `.claude/agents/*.md` must expect this (the exceptions are `.claude/worktrees/` and markdown inside `.claude/agent-memory/`). Plain `.flightdeck/` paths are not protected, which is a reason to keep workshop output outside `.claude/`.
- Skills are the only plugin-native way to ship instructions Claude loads on demand; descriptions are always in context (budget about 1% of the window, 1,536 characters per skill including `when_to_use`), so keep descriptions short and keyword-led, use `disable-model-invocation: true` for side-effecting launches and manual checklists, and put long material in supporting files under the skill folder reached via `${CLAUDE_SKILL_DIR}`. A forked skill (`context: fork`, `agent:`) is the way to give a skill its own context and an agent type, but a background fork gets the reduced tool set unless `background: false`.
- Hook design. Plugin hooks fire for every session where the plugin is enabled, in every subagent as well, so scope each with a `matcher` and `if`. Use exec form (`args`) for any path placeholder, never `args: []` with a shell command string. Use `SubagentStart` (context injection only) and `SubagentStop` (can block with `decision: "block"`) matched on `^flight:<agent>$` for agent-level guards. `Stop` and `SubagentStop` blocks are capped at 8 consecutive. `PreToolUse` deny is the only hard enforcement that also works under `bypassPermissions`. Hooks cannot be per-agent for plugin agents, so per-agent behaviour must be routed by `agent_type` inside the script.
- Names are stable contracts: plugin `flight` yields `/flight:<skill>`, `flight:<agent>`, `flight:<subfolder>:<agent>`, `mcp__plugin_flight_<server>__<tool>`, hook matcher `^flight:<agent>$`. Renaming the plugin renames all of them. Skill and agent `name` fields must not contain `:`.
- Retry isolation. Workflows can ship in `workflows/` and run as `/flight:<name>`; `${CLAUDE_PLUGIN_DATA}` survives updates but is per user machine (not in the repo). Branch-isolated, retryable workshop state therefore has to live in the repo (for example under `.flightdeck/`), not in the plugin cache or data directory, and not in `${CLAUDE_PLUGIN_ROOT}`, which changes every version and is rebuilt on update.
- Auto memory and agent memory: `memory: project` for an agent writes under `.claude/agent-memory/<name>/` (a protected-path exception for markdown only, shareable by git); the main auto memory is machine-local (shared by the worktrees of one repo on that machine, not across machines or cloud sessions), so it cannot carry owner truth. Owner truth belongs in committed files.
- Limits that shape multi-agent design: nesting depth 3, 20 concurrent subagents, background subagents have a reduced tool set (no `AskUserQuestion`, no `Workflow`, no `Agent` at depth), subagents do not see the parent's output style or auto memory, and a subagent's CLAUDE.md load can be skipped with `omitClaudeMd` to save tokens. Agents cannot ask the owner questions from the background: questions waiting for the owner have to be written to files and surfaced by the main thread.
- Output styles can be shipped (`output-styles/`), but cannot be turned on by the plugin except through `force-for-plugin: true`; otherwise the user selects them. They do not reach ordinary subagents.
- Evals fit the Laboratory: `evals/` inside the plugin with `claude plugin eval`, run with and without the plugin; confirm it is available on the owner's account before planning around it.
- Mods (JavaScript hooks that draw panes and commands) are plugin components that run unsandboxed inside Claude Code and need v2.1.287+; they are a candidate for the "themed HTML interface" idea only in the terminal and Desktop app, and they are advanced enough to belong in a separate pull request.
- Version dependence. Everything above was true on Claude Code 2.1.296 and the docs of 2026-10-10. The owner's machine may differ; `claude plugin validate`, `claude --version` and `claude plugin list --json` are the cheap checks.
