# Claude Code multi-agent features: exact facts

Summary: this report states, with file and heading citations, what Claude Code documents about running many agents: the Workflow tool (dynamic workflows), agent teams, background sessions and agent view, cross-session messaging, worktrees, headless `claude -p`, and usage monitoring, plus a list of the shapes of multi-agent work Claude Code supports natively and the facts that constrain how FlightDeck can launch work. The most decision-relevant facts are these. A dynamic workflow is a JavaScript file that starts with a literal `export const meta = {name, description}` block, can be saved to `.claude/workflows/<name>.js` (project) or `~/.claude/workflows/` (personal) and then runs as `/<name>`, takes input through the `args` global, and cannot pause for a human mid-run, so a human gate means one workflow per stage. Workflows are capped at 1,000 agents per run, 4,096 items per `parallel()` or `pipeline()` call, and 16 concurrent agents by default (fewer on small machines; this sandbox reports 4 CPUs). Per-agent `model`, `effort` and `isolation: 'worktree'` options exist, but the documented per-agent `effort` option appears only in the `workflow-authoring` skill text, not in the library docs. Agent teams are experimental, off by default, interactive-only, one team per session, with no project-level team file. Background sessions (`claude --bg`, `claude agents`) are local, auto-isolate edits in worktrees, and never push to main, force-push or merge. `/effort ultracode` means `xhigh` effort, which is above the owner's "Opus at high" ceiling, so FlightDeck must never turn it on. `--bare` mode does not use the subscription login. Source facts come from `library/source/claude-code/*.md` and `library/source/claude-dev-blog/a-harness-for-every-task-dynamic-workflows-in-claude-code.md`; where a fact came from somewhere else (the `workflow-authoring` skill text that this session loaded, `subagents.md`, or a local command run) the report says so.

## How to read this report

- Paths are relative to the repository root. "§" means the heading inside the file. The files are agent-downloaded copies of the Claude Code docs (pages carry the note "Documentation Index ... code.claude.com/docs/llms.txt").
- Version numbers are the docs' own "requires Claude Code vX" notes. The Claude Code installed in this sandbox reports `2.1.296` (`claude --version`), `tmux` is installed (`/usr/bin/tmux`), and `nproc` reports 4. Those were checked by running commands, not read from the docs.
- "Not verified" marks things the library does not state. The Workflow tool's own input schema is documented in the Agent SDK TypeScript reference, which is not in `library/source/`, so anything about the tool's input fields beyond what `workflows.md` says is marked as coming from the `workflow-authoring` skill.

## 1. The Workflow tool (dynamic workflows)

Source: `library/source/claude-code/workflows.md` unless stated. Blog context: `library/source/claude-dev-blog/a-harness-for-every-task-dynamic-workflows-in-claude-code.md` (published 2026-06-02, "Last week, we released dynamic workflows").

What it is (§ "Orchestrate subagents at scale with dynamic workflows", § "When to use a workflow"):

- A dynamic workflow is a JavaScript script that orchestrates many subagents. Claude writes the script, a runtime executes it in the background, and the session stays responsive.
- The plan lives in code: the script holds the loop, branching and intermediate results in script variables, and Claude's context holds only the final answer. With subagents, skills and agent teams Claude decides turn by turn and results land in its context window.
- Scale stated in the comparison table: "Dozens to hundreds of agents per run". Interruption: "Resumable in the same session".
- Availability (§ top Note): all paid plans, Anthropic API access, Bedrock, Google Cloud Agent Platform, Microsoft Foundry. On Pro it is turned on from the Dynamic workflows row in `/config`.

Script API (§ "What the saved script looks like", § "Edit a saved script"; the `workflow-authoring` skill text loaded in this session adds detail and is marked as such):

- The file is plain JavaScript (not TypeScript) with top-level `await`. Documented calls: `agent()` spawns one subagent, `pipeline()` runs one per item in a list, `parallel()` runs a set of tasks at the same time and waits for all, `phase()` groups following agents under a title in the progress view, `log()` shows a message above the phases, and the `args` global holds invocation input (`undefined` if omitted).
- `agent(prompt, opts)`: the docs example uses `schema` and `label`. The blog figure (§ "How dynamic workflows work") lists options `schema` (validated JSON), `model` ("picks opus, sonnet or haiku"), `isolation` ("worktree or remote") and `agentType` (selects a subagent). The `workflow-authoring` skill text lists: `label`, `phase`, `schema`, `model`, `effort` ('low' | 'medium' | 'high' | 'xhigh' | 'max'), `isolation: 'worktree'`, `agentType`. The skill says to omit `model` by default so the agent inherits the main-loop model, and to omit `effort` to inherit session effort.
- `agent()` resolves to `null` if the agent is stopped mid-run or hits an unrecoverable API error (workflows.md § "What the saved script looks like"). `pipeline()` keeps each `null` in its results array, so scripts end with `.filter(Boolean)`.
- With a `schema`, the subagent returns JSON matching the shape. The schema is checked before the agent starts; a self-contradicting schema (for example a `required` key that `additionalProperties: false` rules out) fails the call. After five failed validation attempts the call fails; `MAX_STRUCTURED_OUTPUT_RETRIES` changes the count. Skill text: root must be `{type: 'object', properties: {...}}` and `required` must be a subset of `properties`.
- `pipeline()` has no barrier between stages; `parallel()` is a barrier (skill text). A `pipeline()` stage callback receives `(prevResult, originalItem, index)` and a stage that throws drops that item to `null`. A `parallel()` thunk that throws resolves to `null`.
- Skill text only (not in the library docs): `budget` global (`budget.total`, `spent()`, `remaining()`) tied to a "+500k"-style token directive and a hard ceiling once reached; `workflow(nameOrRef, args)` runs another workflow inline as a sub-step, sharing the concurrency cap, agent counter, abort signal and token budget, with nesting limited to one level. The blog (§ "Tips for building dynamic workflows" → "Token usage budgets") says you can prompt a budget such as "use 10k tokens" to set the cap.
- Determinism rules (workflows.md § "Edit a saved script"): `Date.now()`, `Math.random()` and a no-argument `new Date()` throw inside the script so that a relaunched run repeats the same `agent()` calls. Pass timestamps in through `args`. The skill text says to stamp results after the workflow returns and vary prompts or labels by index for randomness.
- No `import()`: a script containing `import()` fails before the run starts. No direct filesystem or shell access from the script itself; "Agents read, write, and run commands. The script coordinates the agents" (§ "Behavior and limits").

Saved workflows: location and format (§ "Save the workflow for reuse", § "What the saved script looks like", § "Edit a saved script"):

- Save from the `/workflows` view: select a run and press `s`. Two locations, toggled with Tab: `.claude/workflows/` in the project (shared with everyone who clones) or `~/.claude/workflows/` (personal, every project; under `$CLAUDE_CONFIG_DIR/workflows/` if that variable is set).
- The saved file is a `.js` file. `export const meta = {name, description}` must be the first statement and must be a plain object literal; anything other than literal values (a variable, function call or spread) makes Claude Code drop `/<name>` from autocomplete. Optional `meta` fields per the skill text: `whenToUse`, `phases` (array of `{title, detail}`, titles must match `phase()` calls exactly; a `phase()` title with no entry gets its own progress group), and `model` on a phase entry.
- Monorepo: saving to the project location writes to the closest existing `.claude/workflows/` between the working directory and the repository root (or the repository root if none exists). Project workflows load from every `.claude/workflows/` along that path; on a name clash the one closest to the working directory runs. A project workflow beats a personal workflow of the same name.
- Plugins (§ "Distribute a workflow in a plugin"): put scripts in a `workflows/` directory at the plugin root, or point to another location with the `workflows` manifest field. Plugin workflows are namespaced: a plugin `acme-tools` with a script whose `meta.name` is `release-audit` runs as `/acme-tools:release-audit`.
- Skills can carry workflow templates (blog § "Saving and sharing dynamic workflows"): put the `.js` files in a skill folder, for example `~/.claude/skills/deep-verify/verify-claims.workflow.js`, and reference them from `SKILL.md`; the blog suggests telling Claude to treat them as templates rather than scripts to run verbatim.
- Symlink safety: Claude Code refuses to save if the target file (personal) or `.claude`, `.claude/workflows` or the target file (project) is a symlink. Before v2.1.216 it followed links.
- Not verified: how a file's name on disk relates to `meta.name` (the docs only say the workflow "runs as `/<name>`" and give the plugin example in terms of `meta.name`). Treat `meta.name` as the command name and keep the filename equal to it.

How a saved workflow is invoked by name, with args (§ "Run a bundled workflow", § "Pass input to a saved workflow", § "Approve the plan before it runs"):

- By typing `/<name>` (saved workflows appear in `/` autocomplete next to the bundled `/deep-research`). Example from the docs: `/deep-research What changed in the Node.js permission model between v20 and v22?`.
- Input: "A saved workflow can accept input through the `args` parameter. The script reads it as a global named `args`." The docs example is a natural-language prompt, "Run /triage-issues on issues 1024, 1025, and 1030", and "Claude passes the list as structured data". So args are passed by Claude when it calls the Workflow tool, as real JSON values (skill text: arrays and objects must be passed as JSON values, not as JSON-encoded strings, or `args.map` will throw).
- The Workflow tool can also run from a script file path (skill text: `Workflow({scriptPath})`, plus `script` inline, plus `{name}` for saved ones). Claude can start a workflow "only from a script file the session is already allowed to read" (§ "How a workflow runs"); a script outside the working directory needs `/add-dir` or a Read allow rule first.
- Every run writes its script to a file under the session directory in `~/.claude/projects/`; Claude receives the path at start, and you can edit it and relaunch from the edited version (§ "How a workflow runs").
- Not verified: whether `claude -p "/<name> <args>"` expands a saved workflow the way it expands a user-invoked skill (headless.md § "Create a commit" Note says "User-invoked skills and custom commands work. Include `/skill-name` in the prompt string"; workflows.md says saved workflows "become commands the same way" as `/deep-research`, which suggests it works, but no page states it for `-p`).
- Permission to launch (§ "Approve the plan before it runs"): Auto mode prompts on first launch only (skipped if ultracode is on); Manual and accept-edits prompt every run unless "Yes, and don't ask again for `<name>` in `<path>`" was chosen (offered only for bundled, saved or plugin workflows run by name, not for a script Claude wrote for the current task); bypass-permissions never prompts; in `claude -p` and the Agent SDK nothing prompts and the launch goes through ordinary permission evaluation. To let it start unattended use an allow rule `Workflow` (all) or `Workflow(<name>)` (one saved workflow), auto mode, bypass mode, a `PreToolUse` hook returning `allow`, or `--permission-prompt-tool` / `canUseTool` / a `PermissionRequest` hook. Subagents use the session's permission rules, with permission mode chosen by the rules in `subagents.md` § "Permission modes"; add the tools agents need to allow rules before a long run.

Starting a workflow (§ "Have Claude write a workflow", § "Ask for a workflow in your prompt", § "Where the keyword works"):

- Say "use a workflow" or "run a workflow" in a prompt, or include the keyword `ultracode`; "The keyword only chooses how Claude structures the work" and does not change the session's effort level or permissions.
- The keyword only counts as an opt-in in a prompt a human types (interactive prompt, IDE panel, Remote Control client, or an Agent SDK app that stamps input `origin: { kind: "human" }`). It does not start a workflow when it arrives by `-p`, an unstamped Agent SDK prompt, a scheduled task prompt, or a webhook payload or PR comment relayed into the conversation (before v2.1.210 it did).
- `/effort ultracode` (§ "Let Claude decide with ultracode"): "combines `xhigh` reasoning effort with automatic workflow orchestration" and plans a workflow for every substantive task. It turns off the `Large workflow` warning, the concurrent subagent limit for the Agent tool, and the auto-mode first-launch approval. Requires v2.1.203 or later. It also needs `xhigh`, so an organization effort cap below `xhigh` removes it.
- Skill-text note: the `workflow-authoring` skill says "Pass the script inline via `script` — do not Write it to a file first" because every invocation persists its script automatically and returns the path. The library docs do not state this; they say only that every run writes its script under `~/.claude/projects/`.

Model and effort per agent (§ "Cost", `subagents.md` § "choose a model", `agent-teams.md` § "Specify teammates and models"):

- "Claude Code picks each workflow agent's model in the same order it uses for subagents. A model the script names for a stage counts as the per-invocation model in that order. When nothing else assigns one, the agent runs on your session's model." So `agent(prompt, {model: 'sonnet'})` is the per-call override and wins over a subagent definition's `model` and the session model. (The exact order list is in `subagents.md` § "Choose a model", not re-read here beyond the quoted workflows.md sentences.)
- If an organization `availableModels` allowlist blocks a requested model, that agent runs on a substituted model and the `/workflows` view shows a warning naming both models.
- Effort: the library's workflows.md does not document an `effort` option on `agent()`. The skill text does ('low' | 'medium' | 'high' | 'xhigh' | 'max'). Corroborating: workflows.md § "Prompt caching in a fan-out" lists "effort level" among what must match for agents to share a cache prefix, and `monitoring-usage.md` § "Cost counter" records an `effort` attribute per request. Subagent definitions have an `effort` frontmatter field overriding session effort (`subagents.md` line 322). The agent session's effort defaults to inherit from the session.
- The size guideline (§ "Set a size guideline") is advice not a cap: `unrestricted`, `small` (<5 agents), `medium` (<10), `large` (<50). Default `medium` (`small` on Pro with v2.1.271+). Set by `/config workflowSizeGuideline=...` or the `workflowSizeGuideline` settings key (v2.1.219+, wins over `/config`). A prompt that calls for a different scale overrides it, and the runtime caps still apply.

Worktree isolation inside workflows:

- `agent(..., {isolation: 'worktree'})` runs that agent in a fresh git worktree (skill text: roughly 200 to 500 ms setup plus disk per agent, use only when agents mutate files in parallel; "auto-removed if unchanged"). The docs example prompt: "migrate every component ... working on each file in its own isolated copy" (§ "Migrate many files in parallel"). Blog § "Migrations and refactors": "Spin off a subagent for every fix in a worktree to make the fix, then have another agent adversarially review, and merge them."
- Subagent worktrees follow `worktrees.md` § "Isolate subagents with worktrees": a temporary worktree removed automatically when the subagent finishes without changes; a worktree with changes stays on disk until the periodic sweep can remove it without losing work. They use the same base branch rule as `--worktree` (see section 5).
- Not verified: what branch name a workflow agent's changed worktree gets, and how its result gets back into another branch. The library only says the worktree stays on disk; the agent itself (or a later agent) has to commit, push or report the path.

Limits and behavior (§ "Behavior and limits"):

- No mid-run user input. "A run pauses on its own only for agent permission prompts and a usage-limit wait. For sign-off between stages, run each stage as its own workflow."
- No module loading; no filesystem or shell from the script.
- 16 concurrent agents by default, "fewer when Claude Code has fewer CPUs available, including inside a CPU-limited container". `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` takes 1 to 256 (v2.1.269+). The skill text gives the formula `min(16, available CPUs - 2)`. This sandbox reports 4 CPUs, so the cap here is probably 2 unless the variable is set (inferred from the two statements, not tested).
- Agents in a fan-out that share a prompt-cache prefix start up to 5 seconds after the first (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, default 5000, 0 disables). Workflow agents' cache TTL is 5 minutes unless `subagentPromptCacheTtl` is `1h` (§ "Prompt caching in a fan-out").
- Up to 4,096 items in a single `parallel()` or `pipeline()` call (error beyond that). 1,000 agents total per run.
- Cost flag: a run scheduling more than 25 agents or projecting more than 1.5 million tokens shows a `Large workflow` warning (advisory only; the size guideline's count replaces 25; ultracode hides it).
- Workflows are available in the CLI, Desktop, IDE extensions, `claude -p` and the Agent SDK. Disable with `/config`, `"disableWorkflows": true` in settings, or `CLAUDE_CODE_DISABLE_WORKFLOWS=1`. When disabled the bundled commands and the `/workflow-authoring` skill vanish; a run in progress keeps going.

Watching, pausing, resuming (§ "Watch the run", § "Manage runs", § "Resume after a pause"):

- `/workflows` lists runs; Enter opens a progress view (phases, agent counts, tokens, elapsed). Keys: `p` pause/resume, `x` stop agent or run, `r` restart a running agent, `s` save as command, `f` filter, arrows to drill in. A one-line progress summary also shows in the task panel under the input box.
- Resume replays in agent start order: completed agents return saved results; the first agent whose prompt differs (script edit, or an earlier agent returned something different) runs again, and so does every agent after it; agents still running when stopped start over; a failed agent runs again together with every agent that started after it. Stopping one agent alone with `x` counts as failing it. Example in the docs: A, B, C, D start in order and B fails, so relaunch returns A from cache and reruns B, C, D.
- Resume is "within the same Claude Code session". Backgrounding the session replays the run in the background session. Exiting while a workflow runs with agent view on offers `Move to background and exit`; choosing `Exit and stop tasks` stops the run, but saved results stay under the session's directory in `~/.claude/projects/` so `claude --resume` can replay them. In a fresh session Claude has no earlier run and starts over. Cloud sessions also save results with the conversation history. If saved results cannot be found at all, relaunch fails with `nothing to resume`.
- Skill text on resume: relaunch with `Workflow({scriptPath, resumeFromRunId})`; same script plus same args gives a 100 percent cache hit; the run journal is `<transcriptDir>/journal.jsonl`.
- Usage limit (§ "When a run hits your usage limit"): the run pauses and waits for the reset rather than failing agents (v2.1.271+), at most twice, only if the reset is within 24 hours, `autoContinueAtUsageLimit` is on, and the session is interactive and signed in with a claude.ai subscription. It does not pause in `claude -p` / the Agent SDK, in a background session, in a Remote Control session, or in an agent-team teammate session; there the affected agents fail.

Telemetry for workflows (`monitoring-usage.md` § "Standard attributes"): events from workflow agents carry `workflow.run_id` (prefixed `wf_`, matching the run id in the Workflow tool result) and `workflow.name` (the script's `meta.name`; user-authored names show as `custom` unless `OTEL_LOG_TOOL_DETAILS=1`). Requires v2.1.202+.

Patterns the blog names (§ "Helpful patterns when using dynamic workflows"): classify-and-act, fan-out-and-synthesize (the synthesize step is a barrier), adversarial verification, generate-and-filter, tournament (pairwise judging), loop until done. Use cases: migrations and refactors, deep research, deep verification, sorting by tournament, rule-by-rule review with a skeptic, root-cause investigation with disjoint evidence, triage with a quarantine pattern (read-only reader agents, a separate privileged actor agent), exploration with a rubric, evals, model routing by a classifier agent. The blog (§ "When not to use dynamic workflows") warns they "may end up using significantly more tokens" and that most ordinary coding tasks do not need a panel of reviewers. It also says to combine with `/goal` (hard completion requirement) and `/loop` (repeat at intervals); those two pages are not in the library.

The bundled `/deep-research` workflow (§ "Bundled workflows") fans out web searches, cross-checks, votes on each claim, and needs the WebSearch tool.

## 2. Agent teams

Source: `library/source/claude-code/agent-teams.md`.

- Status and enabling (§ top Warning, § "Enable agent teams"): "experimental and disabled by default". Enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in the environment or in settings `env`. Without it no team is set up and no team directories are written. Enabling also changes ordinary delegation: a subagent that Claude names launches as a teammate. Setting the variable to `0` in user settings makes named subagents launch as subagents again (settings-file `env` changes apply to the running session; project, local, `--settings` and managed sources can still override).
- Interactive only: "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates, and a subagent that Claude names runs as an ordinary subagent."
- How a team is defined and started (§ "Start your first agent team", § "How Claude starts agent teams", § "Architecture"): there is no team definition file. You describe the task and roles in natural language and Claude spawns teammates ("Spawn three teammates to explore this from different angles: one on UX, one on technical architecture, one playing devil's advocate"). Claude launches a teammate when it calls the Agent tool with a `name` while teams are enabled (unless it is a fork or passes `isolation` itself), and Claude Code does not ask you to confirm. Runtime config is `~/.claude/teams/{team-name}/config.json` and the task list is `~/.claude/tasks/{team-name}/`, with the team name `session-` plus the first eight characters of the session id. "The team config holds runtime state ... so don't edit it by hand or pre-author it." "There is no project-level equivalent of the team config. A file like `.claude/teams/teams.json` ... is not recognized."
- Reusable roles (§ "Use subagent definitions for teammates"): define a role once as a subagent definition (project, user or managed scope) and name it in the spawn prompt ("Spawn a teammate using the security-reviewer agent type"). Applied from the definition: `tools` (plus `SendMessage` and the Task tools added), `model` (when the spawn prompt names none), and the body (appended to the default system prompt for in-process teammates; replaces it for split-pane teammates). `skills` is not applied; `mcpServers` is applied only for split-pane teammates. For a teammate brought back later, a definition from a project's `.claude/agents` directory is re-applied only if the folder is trusted.
- Teammates: each is "a full, independent Claude Code session" with its own context window; it loads CLAUDE.md, MCP servers and skills like a regular session but not the lead's conversation history, only the spawn prompt (§ "Context and communication"). The lead names every teammate; tell it names in the spawn prompt to get predictable ones. A teammate can be messaged directly by the human (agent panel: arrow keys, Enter to open, Escape to interrupt its turn, `x` to stop it).
- Display modes (§ "Choose a display mode"): `in-process` (default; any terminal) or split panes (needs tmux or iTerm2 with `it2`); setting `teammateMode` (`auto`, `tmux`, `iterm2`, `in-process`) or experimental flag `--teammate-mode`. Split panes are not supported in the VS Code integrated terminal, Windows Terminal or Ghostty.
- Shared tasks (§ "Assign and claim tasks"): states pending, in progress, completed; tasks can depend on others (a pending task with unresolved dependencies cannot be claimed); the lead assigns or teammates self-claim the next unassigned, unblocked task; claiming uses file locking. Agents without the Task tools coordinate by messages only. Known limit: task status can lag, teammates sometimes fail to mark tasks completed.
- Messaging (§ "Architecture", § "Context and communication", § "Messages between agents"): mailbox files `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; messages go to one named teammate at a time ("To reach everyone, send one message per recipient"); delivery is automatic; an idle teammate sends the lead a notification with its final answer. A message from another agent is marked as coming from another Claude session, not the human, so it cannot approve a permission prompt or grant consent. In auto mode the classifier reviews each inter-agent message and treats relayed approval claims as untrusted.
- Models and effort (§ "Specify teammates and models"): model order is the spawn prompt, then the definition's `model`, then `CLAUDE_CODE_SUBAGENT_MODEL` (if not `inherit`), then the lead's model; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) overrides the first two. A teammate's model and fast mode are fixed at spawn (`/model` only changes the lead). Teammates inherit the lead's effort level (split-pane from v2.1.186), and `/effort` still applies to a viewed teammate's later turns.
- Permissions (§ "Permissions"): teammates start with the lead's permission mode except `dontAsk`; `--dangerously-skip-permissions` on the lead applies to all; per-teammate modes cannot be set at spawn; teammate permission prompts bubble up to the lead session. Plan approval (§ "Have teammates plan before implementing"): a teammate spawned while the lead is in plan mode works read-only until its plan is ready, and Claude Code approves the plan in the lead's session as soon as it arrives, without the lead reviewing it.
- Hooks for quality gates (§ "Enforce quality gates with hooks"): `TeammateIdle`, `TaskCreated`, `TaskCompleted`; exit code 2 sends feedback and keeps the teammate working or blocks creation or completion.
- Limits (§ "Limitations", § "Choose an appropriate team size"): no session resumption of in-process teammates (`/resume` and `/rewind` do not restore them); one team per session, not shared across sessions; no nested teams; no background subagents from in-process teammates; the lead is fixed for the session's life; shutdown can be slow. "There's no hard limit on the number of teammates"; guidance is 3 to 5 teammates and 5 to 6 tasks per teammate; token cost scales linearly. Two teammates editing the same file overwrite each other, so give each its own files. The docs advise starting with research and review tasks, not parallel implementation.
- Best-fit uses (§ "When to use agent teams", § "Use case examples"): research and review, new modules where each teammate owns separate files, debugging with competing hypotheses ("Have them talk to each other to try to disprove each other's theories, like a scientific debate"), cross-layer coordination. Poor fits: sequential tasks, same-file edits, many dependencies.
- Teammate sessions are exempt from workflow usage-limit waiting (workflows.md § "When a run hits your usage limit").

## 3. Background sessions and agent view

Source: `library/source/claude-code/agent-view.md`. Status: "Agent view is in research preview. The interface and keyboard shortcuts may change" (§ top Note).

- What it is: `claude agents` opens one screen listing every background session grouped by state (Needs input, Working, Ready for review, Completed). "Each background session is a full Claude Code conversation that keeps running without a terminal attached." Interactive sessions in other terminals do not appear until backgrounded; subagents and teammates a session spawns are not listed as separate rows (§ "Monitor sessions with agent view").
- Starting background sessions (§ "Dispatch new agents"): type a prompt in agent view's input (each prompt is a new session); `claude --bg "<prompt>"` from a shell (prints `backgrounded · <short id> · <name>` plus attach, logs and stop commands); `/background` or `/bg` inside a session; `/fork` copies the current conversation into a new background session while the original continues (v2.1.212+; before that `/fork` meant a forked subagent, now `/subtask`); `←` on an empty prompt backgrounds and opens agent view. `claude --bg --exec 'pytest -x'` runs a shell command as a background job with no model.
- Flags with `--bg`: `--name`, `--model`, `--agent <subagent>`, `--resume <full session id>` (v2.1.257+). `--bg` is rejected with `-p`/`--print` ("`--print` never starts the interactive session that `claude agents` attaches to"). `claude --bg` checks workspace trust for the directory first (v2.1.281+) and exits with `Workspace not trusted` in a script if untrusted. `claude --bg --permission-mode bypassPermissions` is refused until the bypass disclaimer was accepted once interactively.
- Agent view dispatch defaults (§ "Dispatch defaults"): `claude agents --permission-mode plan --model opus --effort high`; `--effort` also accepts `ultracode`. `--agent` sets the subagent used when a dispatch prompt names none. `@<agent-name>` or a leading agent name in the dispatch prompt runs that custom subagent as the session's main agent; `@<repo>` targets a sibling repository or registered worktree. `/<command>` dispatches a skill or command as the first prompt, so "Packaging a recurring task as a skill lets you start the same workflow from agent view repeatedly".
- Shell management (§ "Manage sessions from the shell"): `claude agents --json` (add `--all` for completed, `--cwd <path>` to scope), `claude attach <id>`, `claude logs <id>`, `claude stop <id>` (alias `kill`), `claude respawn <id>` / `--all`, `claude rm <id>`, `claude daemon status`, `claude daemon stop --any [--keep-workers]`. Session ids are the directory names under `~/.claude/jobs/`.
- Reading state from a script (§ "Read session state from a script"): `claude agents --json` is "the supported way to read session state from outside Claude Code, for example from a status bar, a scheduler, or another Claude session that supervises background work". Fields: `cwd`, `kind`, `startedAt`, `id`, `state` (`working`, `blocked`, `done`, `failed`, `stopped`), `pid`, `status` (`busy`, `waiting`, `idle`), `waitingFor` (`permission prompt`, `input needed`, `sandbox request`, `worker request`, `dialog open`), `sessionId`, `name`. The files under `~/.claude/jobs/<id>/` are not a stable interface. A session wanting to report progress should write its own file under `$CLAUDE_JOB_DIR/tmp`.
- Hosting (§ "How background sessions are hosted"): a supervisor process runs sessions so they survive closing the terminal. Working, paused-on-dialog, attached or pinned sessions stay running; finished or waiting sessions unattended for about an hour are stopped to free resources and resume on attach or reply; machine shutdown stops running sessions (shown failed within 48 hours, stopped after); sleep does not stop them. State lives in `~/.claude/daemon/roster.json`, `~/.claude/jobs/<id>/state.json` and `tmp/`. `CLAUDE_CONFIG_DIR` gives a separate supervisor instance. Turn off with `disableAgentView: true` or `CLAUDE_CODE_DISABLE_AGENT_VIEW`.
- File edit isolation (§ "How file edits are isolated"): "Every background session ... starts in your working directory. Before editing files, Claude moves the session into an isolated git worktree under `.claude/worktrees`." Skipped if already in a linked worktree, if the directory is not a git repository with no `WorktreeCreate` hook, or if the write is outside the working directory. Turn off with `worktree.bgIsolation: "none"`. A background session that changed code in a worktree is instructed to commit without asking and push the branch when a remote exists, open a draft PR when the task calls for it, and never push to main or master, never force-push, never merge. Git instructions in the task, CLAUDE.md or memory take precedence. Every job ends with a report of what it did and where the work is.
- Deleting (§ "What deleting a session removes"): deleting in agent view removes a Claude-created worktree including uncommitted changes (commit first); unpushed commits cause a refusal naming the branch; `claude rm` keeps a worktree with uncommitted changes. A transcript always stays available via `claude --resume`.
- What carries over when backgrounding (§ "What carries over when you background"): background shell commands, backgrounded subagents, dynamic workflows, `/loop` tasks carry over; a running monitor is stopped. A workflow with running subagents triggers the `Background this session?` dialog, and confirming restarts those subagents from the beginning (tokens spent again). Launch flags `--mcp-config`, `--strict-mcp-config`, `--settings`, `--setting-sources`, `--add-dir`, `--plugin-dir`, `--fallback-model` carry through.
- Permission, model and effort persistence (§ "Permission mode, model, and effort", § "What persists across restarts"): a background session reads settings from the directory it runs in and the `PATH` and provider variables of the dispatching shell; permission mode, model and effort persist across supervisor restarts.
- Limitations (§ "Limitations"): "background sessions consume your subscription usage the same as interactive sessions, so running ten agents in parallel uses quota roughly ten times as fast as running one"; sessions are local and stop on shutdown; Claude-created worktrees are deleted with the session in agent view.
- Notifications: while agent view is open it fires the `Notification` hook with `agent_needs_input` or `agent_completed` types.
- Row summaries are written by a Haiku-class model, one short request per turn end plus periodic rewrites (§ "Row summaries"); small extra cost.
- Terminology collision: agent view uses "dispatch" for starting a background session, and `glossary.md` § "Dispatch" defines Dispatch as a phone-initiated task router in the Desktop app. FlightDeck's own words should not reuse these loosely.

## 4. Cross-session messaging

Source: `library/source/claude-code/cross-session-messaging.md`.

- Requirements (§ top Note, § "Availability"): Claude Code v2.1.224+ on macOS and Linux (including WSL 2), v2.1.234+ on native Windows; on by default with nothing to enable. Same-machine messaging works on every provider (v2.1.248+ on third-party providers or with feature-flag fetching off) and never goes through Anthropic servers (per-session Unix socket or named pipe).
- Tools: Claude uses `ListAgents` to discover reachable agents and `SendMessage` to send to one by name. A message is plain text only, never conversation history or files. `/list-agents` (alias `/peers`) shows what is reachable: subagents, this session's teammates, other local sessions (including background sessions) that bound an inbox socket, and, only while connected to Remote Control, cloud sessions and Remote Control sessions on other machines.
- Addressing: a session answers to the name set with `/rename` or `--name`. Duplicate names get a variant; with several matches Claude adds a short identifier. The human can target with `@name` mentions (v2.1.232+).
- Delivery (§ "Message delivery"): an active receiving Claude reads the message between tool calls; an idle session gets a new turn. Refused: over the size cap (about a million characters), a rapid burst, a failed safety check on the reply target, or a message to the sender's own name. Receiving side keeps at most 50 accepted messages queued, rate-limits per sender and drops identical repeats; holds at most 100 held messages.
- One-shot idle notice (§ "Get a notice when another session goes idle"): `SendMessage` with `notify_when_idle` asks a local session (v2.1.236+ in both) to send one notice when it next goes idle or exits; expires after 12 hours; only the main-conversation Claude can subscribe, and only to local sessions.
- Trust (§ "How a session treats an incoming message"): a message from another session "can't approve anything", "can't change configuration" (permission settings, CLAUDE.md), commands in its text are not executed, and the receiving session's permission prompts still fire. Claude is instructed never to ask another session for an action its own permissions deny.
- Inbound controls (§ "Control inbound messages"): setting `crossSessionInbound` is `accept`, `hold` or `refuse`. With no value set, the default depends on permission mode classes: a prompting receiver delivers unless the sender is bypassing prompts; a bypass-mode receiver holds each message for human approval unless the sender is also bypassing. A held message opens an approval dialog that expires after `dialogExpiry` (default five minutes). Held-message notices flow back to a same-machine sender.
- Non-interactive (§ "Non-interactive sessions"): a `claude -p` session binds an inbox socket like an interactive one, so a long-running `-p` worker can receive messages and appears in the listing. `--bare` mode does not bind the socket, so a bare session cannot receive messages and is not listed. A `-p` worker cannot show the approval dialog, so held messages expire at the deadline; "To let a `-p` worker take messages unattended, start it with `crossSessionInbound` set to `accept` in its `--settings` value."
- Inbox socket (§ "The session's inbox socket"): path shown in `/status` as `Peer address` (prefix `uds:`) and exported to hooks and Bash commands as `CLAUDE_CODE_MESSAGING_SOCKET`, with a per-session token in `CLAUDE_CODE_MESSAGING_TOKEN`. A script may post to its own session's socket by connecting and (on Windows, required) sending `{"type":"auth","token":"<token>"}` first. Own-child messages (hook or Bash posting back to its own session) are delivered when no `crossSessionInbound` value applies if Claude Code can verify the child; a sandbox may block the socket unless `sandbox.network.allowUnixSockets` allows it. Containers: a session inside a container cannot reach a host session; two sessions inside the same container can.
- Turning it off (§ "Restrict cross-session messaging"): deny rules for `SendMessage` and `ListAgents` stop sending and listing (and also remove messaging to subagents and teammates); `crossSessionInbound: refuse` stops receiving. `isolatePeerMachines: true` requires human approval for any message beyond the machine.
- Message-loop protection: a loop between two sessions stops on its own through the throttles above (§ "Limitations").
- The docs say to use messaging "between independent sessions that you start and steer yourself", and point to resume (continue one conversation), agent teams (a coordinated team Claude supervises), agent view (watch many), Remote Control (steer from a phone), and channels (push external events into a session) for the other cases.

## 5. Worktrees

Source: `library/source/claude-code/worktrees.md`; large-repo settings in `library/source/claude-code/large-codebases.md` § "Scope worktrees and file access".

- Start: `claude --worktree <name>` (or `-w`) creates `.claude/worktrees/<name>/` at the repo root on a new branch `worktree-<name>`; omitted name gets a generated one. Interactive runs require workspace trust; `claude -p --worktree` skips the trust check (§ "Start Claude in a worktree"). Claude can also be asked to "work in a worktree" and uses the `EnterWorktree` tool (and `ExitWorktree`). Entering a path outside `.claude/worktrees` asks the human first.
- Base branch (§ "Choose the base branch"): `worktree.baseRef` is `"fresh"` (default: branch from the repository's default branch on the remote, usually `main`) or `"head"` (branch from the current local `HEAD`, carrying unpushed commits and feature-branch state; "Use this when isolating subagents that need to operate on in-progress work"). It cannot be a branch name; to start from a specific existing branch create it with `git worktree add`. If no remote or no cached `origin/HEAD`, a fresh worktree falls back to local `HEAD`. This applies to subagent worktrees and background-session worktrees too.
- PR start: `claude --worktree "#1234"` (or a PR/MR URL) fetches that PR head and makes `.claude/worktrees/pr-<number>`.
- Reuse (§ "Reuse a worktree name"): passing an existing name reopens it; with the `fresh` base a clean worktree whose work is already merged resets to the default branch, otherwise it reopens at its old tip.
- `.worktreeinclude` (§ "Copy gitignored files into worktrees"): a file in the project root, `.gitignore` syntax, listing gitignored files (like `.env`) to copy into every worktree Claude creates; only files that match and are gitignored are copied. Applies to `--worktree`, subagent worktrees and Desktop parallel sessions, not to `WorktreeCreate` hook worktrees.
- Sparse and shared dirs (large-codebases.md § "Check out only the directories you need"): `worktree.sparsePaths` (git sparse checkout of listed directories plus root-level files; include `.claude` if worktrees need the root `.claude/` settings and rules) and `worktree.symlinkDirectories` (for example `node_modules`) in `.claude/settings.json`. These are read from the starting directory before creation; inside the worktree, project settings come from the worktree root's checked-out `.claude/settings.json`.
- Cleanup (§ "Clean up worktrees"): on exiting an interactive worktree session a clean unnamed worktree is removed with its branch; a named one prompts; a worktree with work prompts keep or remove. `claude -p` has no exit prompt, so its worktrees are never cleaned up and keep their lock until a later session's stale-lock sweep releases it; remove manually with `git worktree remove` (and `git worktree unlock` if locked).
- Sweep (§ "Clean up subagent and background-session worktrees"): a periodic sweep removes subagent and background-session worktrees older than `cleanupPeriodDays`, but leaves any that still hold changed or untracked files or unpushed commits, any belonging to a `--worktree` session not backgrounded, and any you created with `git worktree add`. Claude Code writes a marker into the git metadata of worktrees it creates.
- Isolation enforcement (§ "How Claude Code enforces isolation"): while isolated in a worktree, Claude Code blocks `Edit`, `Write` and `NotebookEdit` that target the main checkout, Bash/PowerShell/Monitor commands whose working directory resolves to the main checkout, git redirects into the main checkout (`git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE`, a `cd` back), and commands whose git target cannot be verified from the text (computed command names, unparseable syntax). The same rules apply to every subagent spawned from an isolated session. The command-shape check cannot be turned off.
- What worktrees share (§ "What worktrees share with the main checkout"): the repository's `.git` directory (so `git commit` works with the sandbox on), project-scope plugins, permission approvals saved to the main checkout's `.claude/settings.local.json`, and untracked project skills, agents and commands when the worktree checkout lacks its own directory (skills read-through needs v2.1.277+). Auto memory is also shared across worktrees of one repository (`glossary.md` § "Auto memory").
- Resume (§ "Resume a worktree session"): resuming a session that ended inside a worktree returns it there, including `--continue` and `--resume` under `-p`. In `-p` a refusal stops the resume with a stderr error (and a `result` message subtype `error_during_execution` in stream-json, with `startup_failure_reason` of `worktree_unverified` or `worktree_resume_refused` from v2.1.274).
- Non-git: `WorktreeCreate` and `WorktreeRemove` hooks replace the git logic. Limitations: LFS pointer files appear in worktrees when LFS filters are installed with `--local`; Claude Code refuses symlinked `.claude` or `.claude/worktrees` paths.
- Manual: `git worktree add ../project-feature-a -b feature-a` then run `claude` there; `/batch` splits a change across subagents each in its own worktree (best-practices.md § "Fan out across files").

## 6. Headless / print mode for scripted runs

Source: `library/source/claude-code/headless.md`. Glossary: `glossary.md` § "Non-interactive mode" ("Formerly called headless mode"; the run is still saved as a resumable session unless `--no-session-persistence`).

- Basic: `claude -p "prompt" --allowedTools "Read,Edit,Bash"`. Exit code 0 on success, non-zero on failure, 143 on SIGTERM (the in-progress turn is left unfinished; send SIGINT or SDK `interrupt()` first to end the turn). Not every CLI flag combines with `-p`: `--bg` is rejected, `--cloud` with a task description is rejected (§ "Basic usage").
- Bare mode (§ "Start faster with bare mode"): `--bare` skips auto-discovery of hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md, for identical results on every machine. "bare mode doesn't use your subscription login": it never reads OAuth credentials or the keychain, so it needs `ANTHROPIC_API_KEY` (or an `apiKeyHelper`, or Bedrock, Vertex or Foundry credentials). Context must be passed by flags: `--append-system-prompt[-file]`, `--settings`, `--mcp-config`, `--agents <json>`, `--plugin-dir`/`--plugin-url`. "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." Without `--bare`, `-p` loads the project's hooks and `.mcp.json` servers even in an untrusted folder (no trust dialog).
- Output (§ "Get structured output", § "Stream responses"): `--output-format text|json|stream-json`; `json` returns result, session id and metadata, including `total_cost_usd` and a per-model cost breakdown (client-side estimate, can differ from the bill; a `--continue` or `--resume` run reports the whole conversation's total). `--json-schema '<schema>'` puts validated output in `structured_output` (invalid schema errors out). `stream-json` needs `--verbose` and optionally `--include-partial-messages`; the last line is a `result` message. Subagent messages carry `parent_tool_use_id`; `--forward-subagent-text` (v2.1.211+) adds subagent text and thinking. The `system/init` event reports model, tools, MCP servers, plugins, `plugin_errors` and `mcp_server_errors` (a CI gate can fail on a non-empty array). `system/api_retry` events report retries.
- Permissions (§ "Auto-approve tools", § "Turn off permission prompts in unattended runs"): `--allowedTools` uses permission rule syntax (`Bash(git diff *)`, with a space before `*` for prefix matching); `-p` starts in Manual mode on every plan, so pass `--permission-mode auto|dontAsk|acceptEdits`; `--permission-prompts none` (v2.1.259+) denies everything that would prompt and tells Claude not to retry, removing tools like `AskUserQuestion`.
- Sessions (§ "Continue conversations"): `--continue` continues the most recent conversation, `--resume <id>` a specific one (id from the `json` output's `session_id`; findable from any directory since v2.1.223; also accepts a transcript `.jsonl` path). With `--continue`, a finished background session can be reopened (v2.1.257+).
- Background work at exit (§ "Background tasks at exit"): a background Bash task is terminated about five seconds after the final result and stdin close; a background subagent or workflow keeps `claude -p` open until that work completes, with the wait ending after 10 minutes of continuous idle waiting (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, 0 means no ceiling), at which point partial results are dropped. A Monitor watch times out after five minutes by default.
- Piped stdin is capped at 10 MB. Commands: user-invoked skills and custom commands work; terminal-only built-ins do not; `/model`, `/effort`, `/fast`, `/color`, `/rename` accept a value as an argument (v2.1.205+); `/config key=value` changes a setting.
- Workflows and `-p`: the `ultracode` keyword does not start a workflow from a `-p` prompt (workflows.md § "Where the keyword works"), the Workflow tool launch is never prompted in `-p` (needs an allow rule or a permissive mode), and usage-limit waits do not apply (agents fail instead).
- Fan-out by script (best-practices.md § "Fan out across files"): loop `claude -p "Migrate $file ..." --allowedTools "Edit,Bash(git commit *)"` over a task list; test on 2 or 3 files first; or `/batch <instruction>` to split a change across 5 to 30 subagents, each in its own worktree. Piping: `claude -p "<prompt>" --output-format json | your_command`.
- Tracing with `-p` (`monitoring-usage.md` § "Traces (beta)"): `-p` and Agent SDK sessions read `TRACEPARENT` and `TRACESTATE` from the environment, so Claude Code's spans nest under the caller's trace and events carry `trace_id` and `span_id`.
- Scheduled/unattended safety (`sandbox-environments.md` § "How isolation relates to permission modes"): `--dangerously-skip-permissions` should only run inside a container, VM or the sandbox runtime; Claude Code refuses to start with that flag as root on Linux and macOS. Auto mode is a per-action classifier, not an isolation boundary, so isolation still adds defence in depth for unattended runs. The sandboxed Bash tool alone "is not sufficient for fully unattended runs in either mode".

## 7. Usage and cost monitoring

Sources: `library/source/claude-code/monitoring-usage.md` (OpenTelemetry), plus the cost fields in `headless.md` and the usage figures in `workflows.md` and `agent-view.md`.

- What it is: export of metrics, events (logs) and optional traces over OpenTelemetry. Enable with `CLAUDE_CODE_ENABLE_TELEMETRY=1`, pick `OTEL_METRICS_EXPORTER` (`otlp`, `prometheus`, `console`, `none`) and `OTEL_LOGS_EXPORTER`, set `OTEL_EXPORTER_OTLP_PROTOCOL` and endpoint (§ "Quick start"). The `console` exporter prints to the terminal, which suits a local, no-collector check; a collector is otherwise needed.
- The OpenTelemetry exporter variables in a repository's `.claude/settings.json` or `.claude/settings.local.json` are ignored, so a repository cannot turn telemetry on or choose a destination; set them in managed settings, the shell, or `~/.claude/settings.json` (§ "Administrator configuration"). `OTEL_*` variables are not passed to subprocesses Claude Code spawns.
- Metrics (§ "Metrics"): `claude_code.session.count` (with `start_type` of `fresh`, `resume`, `continue` or `agents_view`), `claude_code.lines_of_code.count`, `claude_code.pull_request.count`, `claude_code.commit.count`, `claude_code.cost.usage` (USD), `claude_code.token.usage`, `claude_code.code_edit_tool.decision`, `claude_code.active_time.total`. Cost and token counters carry `model`, `query_source` (`main`, `subagent` or `auxiliary`), `speed`, `effort`, `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, `mcp_tool.name` (custom names are redacted to `custom` unless `OTEL_LOG_TOOL_DETAILS=1`). "Cost metrics are approximations" (§ "Cost monitoring").
- Events: `claude_code.subagent_completed` (agent type, `total_tool_uses`, `duration_ms`, `model`, `final_model`, `model_swapped`; its `total_tokens` covers only the final request, so use the token and cost counters filtered to `query_source` `subagent` for rollups) (§ "Subagent completed event"); `api_request`, `api_error`, `tool_result`, `user_prompt` and more; events carry `prompt.id` linking everything from one prompt. Workflow events carry `workflow.run_id` and `workflow.name`.
- Standard attributes include `session.id`, `user.account_uuid`, `organization.id`, `app.entrypoint` (`cli`, `sdk-cli`, `sdk-ts`, `sdk-py` and others), and custom ones via `OTEL_RESOURCE_ATTRIBUTES`; `OTEL_METRICS_INCLUDE_REPOSITORY=true` adds `vcs.*` repository identity (v2.1.269+).
- Without a collector, usage surfaces are: the `/workflows` view (per-agent and per-phase token totals, elapsed time, and the usage-limit reset time when waiting); `claude -p --output-format json` (`total_cost_usd`, per-model breakdown); the `Large workflow` warning (more than 25 agents or more than 1.5 million projected tokens); and agent view's count of background sessions. The docs in the library do not describe a local command that sums subscription usage for a day or week; `workflows.md` points to a "Manage costs" page (`/docs/en/costs`) that is not in the library.
- Subscription facts that bear on FlightDeck: "Runs count toward your plan's usage and rate limits" (workflows.md § "Cost"); "running ten agents in parallel uses quota roughly ten times as fast as running one" (agent-view.md § "Limitations"); teams use "significantly more tokens" (agent-teams.md § "Token usage"); with ultracode on, a session "reaches a session or weekly limit sooner than the same work at `high`" (workflows.md § "Let Claude decide with ultracode").

## 8. Other relevant context from the reading list

- Best practices (`best-practices.md`): the binding constraint is the context window. Give Claude a way to verify its work (§ "Give Claude a way to verify its work": tests, `/goal` condition, a Stop hook as a deterministic gate, or "a verification subagent or a dynamic workflow that checks its own findings has a fresh model try to refute the result"). Failure patterns: kitchen-sink session, correcting over and over (after two failed corrections `/clear` and rewrite the prompt), over-specified CLAUDE.md, trust-then-verify gap, infinite exploration. CLAUDE.md should stay short ("Would removing this cause Claude to make mistakes?"). ## Shapes of multi-agent work Claude Code supports natively

Each entry says what it is, when it fits, and its main limit. The list is ordered roughly from least to most machinery.

- Single human-in-the-loop chat. One session, one context, the human steering turn by turn, optionally with plan mode and checkpoints/rewind. Fits small, uncertain or taste-driven work, and is the "keep it simple" mode: `best-practices.md` says "If you could describe the diff in one sentence, skip the plan". Limit: context fills, so `/clear` between unrelated tasks.
- Subagent fan-out from a chat. Claude calls the Agent tool to start helpers with their own context windows; results return as summaries into the parent context (`subagents.md`; `glossary.md` § "Subagent"; best-practices § "Use subagents for investigation"). Fits research, exploration and review that would pollute the main context. Limits: Claude decides turn by turn and every result lands in its context; default 20 concurrent subagents; `agent-teams.md` says subagents "work within a single session". Per-agent isolation with `isolation: worktree`.
- Bundled and packaged fan-outs (`/batch`, `/code-review`, `/deep-research`, skills that fan out). `/batch <instruction>` splits a change across 5 to 30 subagents each in its own worktree (best-practices.md § "Fan out across files"). `/deep-research` is a bundled dynamic workflow. Fits common jobs with no custom script. Limit: you get the pre-built shape.
- Ad-hoc dynamic workflow. Ask in plain words or use the `ultracode` keyword and Claude writes a script (workflows.md § "Ask for a workflow in your prompt"). Fits one-off large or adversarial jobs: audits, migrations, cross-checked research, competing-plan drafts. Limits: no human input mid-run; keyword works only when a human types it; script is per-task unless saved.
- Saved dynamic workflow. The same script saved to `.claude/workflows/` (or a plugin or skill) and rerun as `/<name>` with `args`. Fits FlightDeck's repeatable launches: a fixed orchestration (for example plan, build, review, adversary, imposter) rerun on new inputs, a "retry" that reruns the same script with extra constraints. Limits: a resume replays the longest unchanged prefix, so editing early prompts reruns everything after; runs only inside one session; 1,000-agent and 16-concurrent caps.
- Staged workflows with a human gate. Because a workflow "pauses on its own only for agent permission prompts and a usage-limit wait", sign-off needs one workflow per stage and the human (or a chat session) in between (workflows.md § "Behavior and limits"; the `workflow-authoring` skill text says the same: "several in sequence — read each result before deciding the next phase"). Fits plan, review page, wait for owner, then build.
- Dynamic workflow with a tournament, judge panel or adversarial verifier inside. Patterns from the blog (tournament, adversarial verification, loop until done) and the skill text (perspective-diverse verifiers, completeness critic, loop-until-dry). Fits quality gates: review, adversary and "human imposter" agents are all just differently-prompted agents in the same script, each in a clean context. Limit: all agents are Claude subagents; a "live" adversary that argues back needs a team or messaging instead.
- Agent team with a live adversary. A lead plus named teammates with a shared task list and direct messaging; the docs' example has "one playing devil's advocate" and teammates "talk to each other to try to disprove each other's theories". Fits debate, competing hypotheses, cross-layer work where peers must discuss. Limits: experimental, interactive only (no `-p`), one team per session, no nesting, no resume of in-process teammates, no team-definition file (roles come from subagent definitions), more tokens.
- Background sessions managed in agent view. `claude --bg`, `claude agents`, `/bg`, `/fork`: independent full sessions that keep running without a terminal, each auto-isolated in a worktree, readable from scripts with `claude agents --json`. Fits several independent tasks the human wants to watch, peek at and reply to from one screen, and long-running work that must outlive the terminal. Limits: research preview, local only, quota burns per session, stops on shutdown, dispatching a workflow inside one means no usage-limit wait.
- Background or foreground sessions messaging each other. `ListAgents` and `SendMessage` between independent sessions on the same machine (or across machines through Remote Control). Fits handing a finding to the session working in a related area, coordinating sessions in parallel worktrees, and asking a long job for a one-time idle notice. Limits: plain text only, receiver controls via `crossSessionInbound`, bypass-mode receivers hold messages for the human by default, a message can never carry consent.
- Headless batch (`claude -p`). Scripts or CI call `claude -p` per item with `--allowedTools`, `--output-format json`, `--json-schema`, `--bare`. Fits mechanical, independent, embarrassingly parallel jobs where the shell owns the loop and cost tracking (`total_cost_usd`), and anything that must run unattended on a schedule. Limits: no teammates, no `ultracode` keyword, workflow launch needs an allow rule, `--bare` needs an API key rather than the subscription login, worktrees from `-p` are never auto-cleaned.
- Headless worker that receives messages. A long-lived `claude -p` session started with `--settings` setting `crossSessionInbound: accept` can be reached by `SendMessage` and appears in `/list-agents` (not under `--bare`). Fits a script-owned worker pool that a coordinating session can steer. Limits: the shape is described for receiving messages, not for any queue semantics; held messages expire after five minutes by default.
- Writer/Reviewer pair of sessions. One session implements, a fresh one reviews and the human or a messaging step carries feedback (best-practices.md § "Run multiple Claude sessions"). Fits low-ceremony independent review. Limits: manual unless combined with messaging.
- Programmatic orchestration with the Agent SDK (Python or TypeScript). `headless.md` says the CLI `-p` is the same engine, and workflows.md notes workflows are also available in the Agent SDK. Fits custom applications with callbacks (`canUseTool`, hooks). Not covered in the library beyond cross-references, so not described further.
- Cloud sessions and routines. Sessions running on Anthropic infrastructure (`claude --cloud`), reachable by messaging only while connected to Remote Control; the library only mentions them in passing (`sandbox-environments.md` § "Cloud sessions", `glossary.md`). Fits work that must run when the laptop is closed. Not researched here.
- `/loop` and `/goal`. The blog pairs workflows with `/loop` (repeat at intervals; triage example) and `/goal` (hard completion requirement checked by a separate evaluator after every turn). Their own pages are not in the library; they are referenced from best-practices.md and agent-view.md (a `/loop` session shows a `✢` row with run count). Not researched here.

## Facts that constrain how FlightDeck launches work

1. A workflow cannot wait for the owner. Any "stop and show the review page" moment must be a boundary between two workflow runs, so a planning workflow ends at the review page and the build is a later, separately launched run (workflows.md § "Behavior and limits"). Resume does not help here: it replays within the same session only.
2. Resume is a prefix replay. Editing any early prompt, or an earlier agent returning something different, reruns every agent after it; stopping one agent alone counts as a failure and also reruns what started after it. FlightDeck should keep early stages' prompts stable across retries if cache hits matter, and feed owner constraints in at a defined point (for example `args`) rather than rewriting prompts early.
3. A retry is a new run of the same script with new input, not a resume. A saved workflow takes `args`; Date, random and wall-clock values must come in through `args` too (workflows.md § "Edit a saved script"). Saved scripts persist per run under `~/.claude/projects/` (outside the repo), so the version in the repository is the saved copy.
4. Where a workflow lives decides how it is launched. A script at `.claude/workflows/<name>.js` runs as `/<name>`, can be pre-approved with the `Workflow(<name>)` allow rule or the "don't ask again" choice (offered only for named bundled, saved or plugin workflows), and a name clash resolves to the closest `.claude/workflows/`. A script kept elsewhere in the repository (the existing `.flightdeck/build-1/workflows/plan.js`) can only be run by pointing the Workflow tool at its path; that path must be inside a location the session may read, and each such launch is a "script Claude wrote for the current task" in the permission prompt. Plugin-delivered workflows are namespaced `/<plugin>:<name>`.
5. The owner's ceiling ("Opus at high effort") holds only if ultracode is never turned on. `/effort ultracode` means `xhigh` effort (workflows.md § "Let Claude decide with ultracode"), which exceeds "Opus at high". FlightDeck launches must pass `effort: 'high'` (or lower) on agents, keep the session at `/effort high`, and never set the `ultracode` setting or `claude --effort ultracode`. The plain word "workflow" or the keyword `ultracode` in a prompt does not change effort, but the per-agent `effort` option is documented only in the skill text, so confirm it works before depending on it. Agent teammates inherit the lead's effort, so a lead on high keeps teammates on high; subagent definitions can pin `effort` in frontmatter.
6. Model choice per agent: a script can name `model` per `agent()` call (blog: opus, sonnet or haiku); it overrides the subagent definition's model and the session model; an organization `availableModels` allowlist can silently substitute another model (shown as a warning in `/workflows`). Teammates take the model from the spawn prompt first. Background sessions take `--model` or the agent view `/model` override. Exact accepted model strings (aliases versus full ids, and whether a "Sonnet 5.5" id is accepted) are not stated in the files read; `monitoring-usage.md` shows `claude-sonnet-5` as an example id.
7. Concurrency is machine-bound. A workflow runs at most 16 agents at once, and fewer when CPUs are few (skill text: min(16, CPUs minus 2), so about 2 on this 4-CPU sandbox); raise it with `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` (1 to 256, v2.1.269+). Subagents from the Agent tool default to 20 concurrent. Total per run: 1,000 agents; per fan-out call: 4,096 items. "No limit on agents" from the owner is bounded by these caps, so a very large fan-out is a queue, not parallel.
8. Parallel editing needs isolation, and isolation has a base-branch trap. `isolation: 'worktree'` on an agent, `isolation: worktree` in a subagent definition, `claude --worktree`, and background sessions all branch from the repository's default branch on the remote (`worktree.baseRef: "fresh"`) by default. If FlightDeck builds on `build-1` and expects agents to see `build-1`'s unpushed or unmerged state, set `worktree.baseRef` to `"head"` in settings (or push first), otherwise worktree agents start from `main`. Worktrees do not carry gitignored files unless `.worktreeinclude` lists them.
9. The isolation blocks are real and affect scripts. A session isolated in a worktree cannot edit the main checkout or run git redirected at it, and the same applies to its subagents; an orchestrator that expects a worker to write into the main checkout from an isolated worktree will be refused. Changed worktrees from workflow agents stay on disk until the sweep (older than `cleanupPeriodDays` and no unpushed commits), and `-p` worktrees are never cleaned automatically.
10. Background sessions follow the owner's git rules by default but not exactly: they commit without asking, push the branch when a remote exists, open a draft PR when the task calls for it, and never push to main or master, force-push or merge (agent-view.md § "How file edits are isolated"). That is compatible with "never push to main", but a task, CLAUDE.md or memory that says otherwise takes precedence, so FlightDeck's rules must say it explicitly. Deleting a session in agent view deletes its worktree with uncommitted changes, so work must be committed first.
11. Unattended runs lose some safety nets. A workflow inside `claude -p`, a background session, a Remote Control session or a team teammate does not wait out a usage limit (agents fail instead), so a long run near a weekly limit can lose agents. Background sessions consume subscription quota "roughly ten times as fast" for ten agents. A weekly cap is a planning input for a 20x Max plan: size runs, stage them, and log what was dropped.
12. Headless needs credentials the plan may not have: `--bare` never reads the subscription login, so a scripted `claude --bare -p` loop needs `ANTHROPIC_API_KEY` (or a provider's credentials), and the subscription-saving goal in `VISION.md` ("Effective use of Claude 20X max subscription") is incompatible with `--bare`. Plain `claude -p` (no `--bare`) uses the normal login but loads the host's hooks, plugins, `.mcp.json` and CLAUDE.md, which differs per machine.
13. Agent teams cannot be a launch target for unattended or scripted runs: they need an interactive session, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, one team per session, and there is no committed team definition. FlightDeck can ship reusable teammate roles as subagent definitions in `.claude/agents/` and a launch recipe (prompt text naming roles, counts and models) for the owner to paste into an interactive lead session; the "team" itself exists only at runtime in `~/.claude/teams/`.
14. A "live adversary" has two implementations: a team teammate who argues back in real time (interactive, experimental) or an adversary agent inside a workflow that reads the work and tries to refute it in a clean context, with no back-and-forth. The second is scriptable, retryable and resumable; the first is not. The blog and best-practices.md both prefer a fresh-context reviewer for verification; they warn a reviewer prompted to find gaps will report some even when the work is sound, so give it a severity threshold.
15. Cross-session messaging is advisory, not authority. It needs no setup on the same machine, but a message cannot approve anything or change configuration; a receiver in bypass-permissions mode holds messages for the human by default; a `-p` worker needs `crossSessionInbound: accept` in its `--settings` to take messages unattended; bare-mode sessions are invisible to it; sessions in different containers cannot reach each other. Questions waiting on the owner must therefore be held somewhere the owner reads (a file or the review page), because a message into a session can wait or expire (default five minutes unless the receiver is prompting).
16. State FlightDeck can rely on from the CLI: `claude agents --json [--all] [--cwd <path>]` is the supported machine-readable view of background sessions (`state`, `status`, `waitingFor`), and `claude --bg`, `attach`, `logs`, `stop`, `respawn`, `rm` are the lifecycle commands. `~/.claude/jobs/` files are not a stable interface. In a workflow, `/workflows` is the live view; run ids are `wf_` prefixed, and per-run journals are under the session transcript directory. A `Notification` hook fires `agent_needs_input` and `agent_completed` while agent view is open.
17. Cost visibility is thin without a collector. A local cost figure comes from `claude -p --output-format json` (`total_cost_usd`, client-side estimate) and the `/workflows` token totals. Anything per-agent or per-role over time needs OpenTelemetry (`CLAUDE_CODE_ENABLE_TELEMETRY=1` plus an exporter; repository settings cannot set the exporter variables, so the owner or managed settings must). The telemetry carries `workflow.run_id`, `query_source`, `effort`, `model` and `agent.name`, which is enough to attribute spend to FlightDeck roles if roles are subagent types and `OTEL_LOG_TOOL_DETAILS=1` is set.
18. Per-directory content cost: every spawned agent loads the same CLAUDE.md files and rules as a regular session (skill text; teams doc); `--bare` skips all of it. This repository's `.claude/rules/context.md` imports a project tree file, so that import is paid by every agent. Large always-loaded context multiplies by the number of agents, so FlightDeck should keep always-loaded files short and push the rest into skills and on-demand files (`large-codebases.md` § "Centralize conventions when layering stops scaling").
19. `claude --bg`, `claude agents`, `ultracode` keyword behavior, `Workflow` allow rules and the `.claude/workflows/` loader are all version-gated (for example workflow-authoring skill needs v2.1.248, workflow concurrency env var v2.1.269, workflow usage-limit wait v2.1.271, `--permission-prompts` v2.1.259, `claude --bg` trust check v2.1.281, messaging v2.1.224). The sandbox here has 2.1.296. FlightDeck docs for the owner should state a minimum version rather than assume.
20. Terminology to avoid colliding with: "dispatch" (agent view: start a background session; Desktop: phone-initiated router), "workflow" (the Workflow tool), "team" (agent teams, one per session), "skill" and "command" (merged), "workshop" or "launch" are free. The existing repository word "dispatch" in team-dispatch ideas will read as agent-view dispatch to Claude Code users.
21. Not verified and worth one cheap test before the build: (a) that `agent(..., {effort: 'high'})` is accepted by the installed version (skill text only); (b) that `claude -p "/<saved-workflow-name> ..."` launches a saved workflow with args; (c) that a saved workflow in `.claude/workflows/` loads in a fresh session of this checkout and shows in `/` autocomplete; (d) the branch name and result path of a changed worktree left by a workflow agent; (e) accepted `model` strings including a Sonnet 5.5 id; (f) the Workflow tool's own input field list (it is in the Agent SDK TypeScript reference, which is not in `library/source/`).
