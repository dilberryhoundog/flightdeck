## 3. The interviewer agent spec (use for an interview feature and for a human imposter)

Location: origin/engage-crew:flightdeck/launch/agent-spec-interviewer/. Files: spec.v1.json (draft status, owner Dylan), interview/problems.json and interview/bundles/P-dispatch-tier.json, P-freeze-commit.json, P-intent-outcome.json (real question bundles), interview/findings.json, judge/verdict-v1*.md (runs 1 to 8) and dispatch-report.json, attacker/findings-v1-run1.md. Rules for the session are in origin/constitution-research:library/spec/interview-session-conventions.md (also on the archive branch).

What the agent is: its intent is "an agent that turns a brief description or intention into a self contained, precise spec by extracting the provider's tacit knowledge through interview questions"; obvious things are written straight in, and the effort goes into edges, tradeoffs, failure modes and hard parts the provider would not volunteer. It never drafts for approval, never asks the provider to approve text it wrote, and never edits anything outside its run folder.

Design points worth reusing, quoted in short:

- Explorer wave before any question. Cheap explorers return cited answers (answer, confidence certain|probable|guess, pointers, candidate nodes). Only a certain return with a pointer is trusted; probable or guess returns become questions, never facts. This keeps the interviewer's own context small. Matches the owner's "Cheap tokens, smart agents" (Haiku explorers, Opus asker).
- Problem register. Every hole the interviewer can name is registered with a kind (gap, dual-path, tradeoff, failure-mode, hard-part; the list is open) and a state (open, asked, answered, closed). An answer that closes a problem becomes its node in the same turn. A settled question is never asked twice. Done means nothing open or asked.
- Bundles. Questions reach the human in bundles, one per problem, at most five questions, each with an explanation ("why"), options (one marked recommended where there are grounds), a free comment, and a bundle comment. Answers come back under the same marker, with "(unanswered)" for skipped ones. Skipped questions become open questions, never guesses. The bundle JSON is the seam between the interviewer and any surface (HTML page, question tool, plain chat). This is the shape the owner's HTML page suite ("Prompt builder and other ai tools... the human returns content back to the agent") needs: the page renders bundles and returns answer blocks.
- Fatigue lesson. The owner on the earlier interview agent (user-intent.md, 2026-09-09): "That interview process failed hard. It was riddled with 'master, what do I do with this node?' questions that fatigued me." The conventions answer this: no approval questions, no questions whose answers are already known, recommendations offered, bundles instead of single questions. VISION.md's "Human energy" section says the same thing. A new interviewer must meet this.
- Judge and attacker gating. A linter gates the judge; the judge (sees only rubric and draft) runs as soon as the linter is clean; the attacker (sees only draft and project root) runs as soon as the judge says ready; every finding is closed through a ledger with one state (asked, absorbed into a named node, rejected with reason). The provider alone decides to freeze.
- Paths. Run files live together under one folder per spec. This is close to the "workshop" idea in VISION.md: a directory holding state, decisions and verification for one piece of work.

How to use it for a human imposter: the imposter is the "provider" side of this loop. Give an agent (Sonnet 5.5) a persona sheet (a short statement of what the human wants, what they will not say unprompted, and which answers they would give) and let it answer bundles in the answer format of interface I4 (`## <marker>`, `### <id>`, `answer:`, `comment:`, `(unanswered)`). Then run the interviewer and check mechanically: no question repeated, at most five per bundle, no approval question, recommended option present when grounds exist, unanswered becomes an open question. The strongest test of the interviewer is the imposter that withholds a fact the persona "knows": the interviewer must ask an edge question to find it. Owner's quote in the launching brief: "great for testing stuff like interview questions." The persona sheets should be built from the owner's dated statements in dev/workspace/research/repo-reset/user-intent.md (63 KB, dated, verbatim), not invented. Verdict: ADAPT for both purposes. Rebuild the interviewer as a lighter agent file plus the bundle JSON contract; do not carry the 33-behaviour, 17-constraint spec or the validators over.

Status caveats: spec.v1.json was still in draft after 8 judge runs; the judge chain disagreed from run to run (section 4). The interviewer body (spec-interviewer.md) was never written; only the spec for it exists.

## 4. Rubric lessons (origin/rubric-testing:flightdeck/testbench/runs/, origin/constitution-research:flightdeck/manuals/rubrics/ and flightdeck/testbench/benches/rubrics/spec/)

The owner's own statement (dev/workspace/research/repo-reset/user-intent.md line 185, 2026-09-14, session 9b679556): "your guidance here may cause a rubric to underperform. questions are not yes-or-no, they all answer the same (default is yes). And inability to answer yes is a finding." My reading: every rubric question is written so that yes is the pass answer; the judge starts at yes; a question that cannot honestly be answered yes is itself a finding, to be reported with a quotation, not scored on a scale. library/rubrics/rubric-guide.md (constitution-research and archive) says the same ("Yes means pass, always"), and the later bench shows why: when yes did not uniformly mean pass, or when a question could not be decided from the page, the judges flipped.

What the guide gets right (origin/constitution-research:library/rubrics/rubric-guide.md, 7.8 KB): a rubric has a header (what the judge receives and must ignore), question blocks of two to five binary questions per behaviour marked critical or advisory, pass rules, and a fixed verdict sheet format (question id, verdict, quotation, one line of reasoning; an answer with no quotation is invalid). Write questions that are answerable from the material alone, quotable by construction, one fact each, observable words only. Calibrate against three to five pre-graded examples including a failure; include a control scenario where the behaviour must not fire. Anti-patterns: compound question, scale, mind-reader, unquotable, editable rubric, impression smuggle, uncalibrated edit, rubric without a control. Verdict: USE nearly as written for the library.

What the bench measured (comparison.md and two-spec-bench.md in rubric-testing and constitution-research; harness in testbench/benches/rubrics/spec/HARNESS.md; visualisation rubric-bench.html, 38 KB, in rubric-testing). 19 judge runs over one start draft with 3 models and two input sets, then 2 more specs with 2 models:

- Questions with a mechanical test settled in one run and agreed across models: draft-is-done boundary orphan checks (QDOD.1, QDOD.2), interface shape (QIFC.2), edge-case outcome (QEDG), constraint checkability (QCON.1). Questions that needed judgement flipped: QBEH.2 ("is each behaviour a single decision") flipped four times on unchanged text for the same model. Lesson: a question with no operational test is decided by sampling luck. Fix it with a test written into the question ("one decision is one trigger producing one result; a second state change or separately prohibited action is a second decision") or move it to a script.
- Giving the judge more material made it worse, not better. Fable with rubric only converged in 2 runs; with the standard and addendum it took 7. The judge should receive the rubric and the artefact and nothing else; every rule it needs goes inside the question. Matches the owner's "no agent grades its own work" and the rubric-guide header rule.
- Judges differ in temperament: fable literal, opus charitable, sonnet in between. Findings that depend on model (QGEN.1, QIFC.1, QBEH.2) are rubric defects, not model defects. For build-1: run the same rubric on Opus and Sonnet 5.5; a finding raised by one and not the other marks a question that needs a sharper test.
- Sampling ("judge the three longest behaviours") was a mistake: each run found the next compound sentence. Judge every item and report every instance.
- An absorber that edits the draft to satisfy findings introduces new findings of its own. The bench should score findings on original text separately from findings on text the absorber wrote.
- Advisory questions that fire on every run (QINT.3 fired on all 19) are noise unless a decision node can close them by id. Add "advisory closure by named decision".
- Cost per judge run: roughly 100 to 350 seconds and 23k to 39k tokens, fable fastest, sonnet slowest. A cheap pre-judge linter that returns drafts before the judge is cost-saving and was kept.
- Stability finding: five chains reached "ready" on five different drafts. "Ready" depends on the judge, which is why the owner wants adversary and imposter checks and not a single rubric gate.

Rubric files to reuse: origin/constitution-research:flightdeck/manuals/rubrics/spec/spec-readiness-rubric.md (v2.3 with a 9-block question list: GEN, INT, SCO, CON, IFC, BEH, EDG, PRI, VER, DOD) and flightdeck/testbench/benches/rubrics/spec/rubric-v2-proposal.md (every change cites bench evidence) and two-spec-bench.md. Deprecated v1, v2, v2.1, v2.2 are in manuals/rubrics/spec/deprecated/ and are IGNORE except as history. Verdict: ADAPT the rubric guide and the v2.3 question structure; USE the bench lessons as a short "lessons" page in the library; IGNORE the bench scripts (absorb.mjs, collect.mjs, render.mjs) unless a lab bench is built later. The spec-readiness lint script (flightcrew/checks/spec-readiness-lint.mjs, 9 KB) and the validators are MINE-LATER; they enforce a nine-section JSON spec that this build does not need.

Rubric-style tests for build-1 items: write every acceptance rubric as yes-is-pass questions; if an item cannot honestly be answered yes, record that as a finding on the item (not a score); give each rubric one control case; give judges only the rubric and the artefact.
