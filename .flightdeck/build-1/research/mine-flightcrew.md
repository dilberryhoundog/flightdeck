# Mining the flightcrew branches for FlightDeck build-1

Summary: the flightcrew line is a large, carefully written but never-lived-in system (about 10,000 lines of node runner, hooks, validators, schemas and templates, plus about 2,100 lines of manuals) whose one shipped runner, `fc`, grew into the thing the owner hated, so the value for build-1 is in the small, portable parts and the doctrine, not the machinery. Worth taking: the crew role set with its "what you read, what you never read" bodies and structured return shapes (adapt, with models cut to Opus and below and the `fc` references removed); the hook patterns that enforce role guarantees (lock guard, boundary guard, stop gate with a block ceiling, event log) as small fail-closed scripts; the launch/run shape from the flightcrew-core spec (launch is the unit of work, run is the unit of attempt, no phase field, no gate switch, the latest run is read from the folder); the retry doctrine in `endings.md` ("setup carries over, run output does not", one change per retry); the verification doctrine (the seven check classes, the agent-shaped addendum, rubrics as yes/no questions with quotations, the blind judge); the report shape with provenance marks; the question-bundle-to-HTML-page precedent for the human-return loop; the toy `export-html` sample project as a drill fixture; and the mutation-style sweep idea for the laboratory. Ignore: `fc` itself (19 subcommands, 887-line `launch.mjs`), `launch.json` as a state machine with phases and three gate switches, the 30 and 47 and 33-suite test suites, the kickoff part library, the `MANIFEST.txt`, the per-check permission allow lists, and every spec/tests-map/interview artifact of the flightcrew specs themselves. Hard blockers found in the files: six role files carry `model: fable` (above the owner's Opus ceiling), two workflow scripts hard-code `/Users/dylangraham/...` and `effort: 'xhigh'`, shipped workflow scripts end with `export default` (the runtime wants a top-level `return`), and plugin-shipped agents ignore the `hooks`, `permissionMode`, `mcpServers` and `initialPrompt` frontmatter that several roles rely on.

### Launch and run folder shapes, retry

## What went wrong here, in the files

This is evidence for the "ignore" calls above, with paths.

- The runner became the system. `fc` is 19 subcommands, `bin/cmd/launch.mjs` alone is 887 lines, and the human types fifteen commands across a run of which eight advance state (`flightcrew-core:dev/workspace/filebox/fc-problems.md`, problem 1, citing `launch-anatomy.md:93-102`). The sources the system was meant to follow have no central runner; the owner: "The first build agent, built a highly complex and hard to learn/use fc command as the core of the system because it was (deterministic) testable" (2026-09-11) and "I hated it" (2026-09-19) (`user-intent.md`). The system's own record of itself shows it: no hook was installed in the build that created it and "the system did not build itself and its record reads as if it did" (`system-problems.md`, problem 2); the buildout runs were driven by Claude Code workflow scripts and `fc` was used afterwards to record them by hand.
- Invented state files. `launch.json` carries 28 fields, 8 phases and 3 gate switches (`manuals/launch/launch-anatomy.md`), plus `escalation.json`, `events.jsonl`, `hooks.log`, `evidence/summary.json`, `locked.json`, `boundary.json`, `budget.json`, `returns/*.prompt.md`, `review/resolutions.json`. The owner on gates: "never needed to flip gate switches" (2026-09-09). `run.json`, `fc-end` and `HALT.json` appeared in a later spec draft and the owner's reaction is recorded: "umm where the F did run.json come from?", "HALT.json wtf is this? never heard of it?", "ASK ME ABOUT MY IDEAS ON HOW TO SOLVE THE PROBLEMS, dont invent shit and say 'done'" (2026-09-09, `user-intent.md`); the owner's answer on `P10-diagnosis` removed `run.json` (`flightcrew-core:.../bundles/P10-diagnosis.json`). `escalation.json` holds only the newest escalation (run 1 fault 9). The tree-wide lesson: every state the system keeps must be a state the owner asked for, and a folder listing is state.
- State the agent should not own was owned by the agent. The orchestrator filled the run-log diagnosis fields, versioned the tests map to v2 and opened the retry before the human had closed the run; the commits later relabelled the fields `draft (orchestrator):` (`system-problems.md`, problem 1; `flightcrew-buildout:flightdeck/launch/RUNLOG.md`). - Tooling faults that stopped real work. ## What I would take, in one list

- Roles: `adversary` (as-is), `critic` and `verifier` and `explorer` (adapt), `implementer` (adapt, Sonnet), `test-builder`/`spec-attacker`/`spec-judge` (adapt as blind-reader patterns), `planner` (adapt the decomposition rules only). - Enforcement: lock guard, boundary guard, structural check and stop gate as four small fail-closed hook scripts keyed to a workshop-local file; use `permissions.deny` and sandbox deny for the Bash hole.
- Shapes: workshop = the launch, with `specs/` (truth) and numbered `runs/run-N/` (attempts), the latest run read from the folder; a `FLIGHTLOG` of diagnoses written by the owner; a hand-written brief like run-2's `kickoff.md`.
- Verification and lab: the seven classes and the agent-shaped addendum, rubric-guide, provenance marks, the sweep (mutation) drill, the `export-html` fixture, the rubric bench pattern, and the suite output protocol.
- Human loop: bundle JSON plus a self-contained HTML page with a paste-back block.
- Skip: `fc`, `launch.json` as a state machine, gates as switches, the kickoff library, `MANIFEST.txt`, `crew.json`, spec/versioning manuals, and every flightcrew suite.
