# Layout precedents for build-1

This report records what the owner's installed plugins, this repository's `.claude/` and `.claude-plugin/` folders, the dev-workspace docs, and the local `claude` CLI already show about layout, loading and testing, so the planning and build agents can copy proven shapes instead of inventing them. The owner's installed plugins are chat-tools, classroom and cowork-plugin-management, all under `P` below; the strongest precedent is a plugin folder with `.claude-plugin/plugin.json` at its root, `agents/*.md` and `skills/<name>/SKILL.md` beside it, a `CHANGELOG.md` in Keep a Changelog form, and a `templates/` folder that gets copied into a project (classroom does this with `CLAUDE.md` and `.claude/rules/*.md`). None of the three ships a `hooks/` folder or `hooks.json`, so hook shape has no precedent here and must come from the Claude Code docs in `library/source/`. Caveat on this checkout: the working tree is on branch `claude/flightdeck-build-1-v0md4i`, not `build-1`; `origin/build-1` exists, and every path below is from the working tree or from the installed plugin folder, not from another branch. `P` means `/root/.claude/plugins/synced/25397929-49cc-4e0c-b857-ab4cb7eed4c9_347b8b41-1f84-4c77-b76d-9c1db96e84b3`.

## How the owner's own plugins lay things out

- The catalogue is `P/manifest.json`. It lists three plugins with `pluginId`, `name`, `version`, `marketplaceName` and `installationPreference: "available"`. chat-tools (version `0006`) and classroom (`0009`) come from marketplace `agent-library`. cowork-plugin-management (`0040`) comes from `knowledge-work-plugins`. Each plugin also has a sidecar `P/<name>.meta.json` holding `server_plugin_id`, `marketplace_name` and `installation_preference`. The catalogue version numbers (`0006`, `0009`, `0040`) are not the semver in each plugin's own manifest, so the two numbering schemes differ.
- Every plugin uses the same skeleton. The plugin root holds `.claude-plugin/plugin.json`, then optional `agents/`, `skills/`, `CHANGELOG.md`, `LICENSE`, and a hidden `.in_use/` marker folder that holds a runtime marker (`.in_use/88`) and carries no content. Plugin folders sit one level below `P` (`P/chat-tools/`, `P/classroom/`, `P/cowork-plugin-management/`).
- Manifests are minimal. `P/chat-tools/.claude-plugin/plugin.json` has `name`, `version` (2.1.2), `description`, and `author` with name and email. `P/classroom/.claude-plugin/plugin.json` (0.5.1) adds `displayName` and `keywords`. `P/cowork-plugin-management/.claude-plugin/plugin.json` (0.2.2) has `author.name` set to "Anthropic" and no email. No manifest declares components; the folders carry them by convention.
- Agent frontmatter is the same across the two agent-bearing plugins. `P/chat-tools/agents/doc-reviewer.md` has `harness-format: DraftHorse`, `name`, `description`, `tools: Read, Grep, Glob` and `model: opus`. `P/classroom/agents/course-researcher.md` adds `user-invocable: false`, `model: sonnet` and `color: blue`, and sets `tools: WebSearch, WebFetch, Read`. The `harness-format: DraftHorse` key is a house convention and not a documented Claude Code field. Each agent body opens with an "Agent Invariants" block of bold **DO NOT** and **NEVER** lines, followed by a "# --- REFERENCES ---" section holding the return shape and the defect or option lists. That split (invariants up top, reference data below) is the clearest pattern for keeping an agent short.
- Skill frontmatter is `name` and `description`, plus `allowed-tools` in the classroom skill. `P/classroom/skills/classroom/SKILL.md` declares `allowed-tools: Task, Read, Write, Edit, Glob, WebSearch, WebFetch, Bash(cp:*), Bash(bash:*), mcp__plugin_classroom_classroom-pdf__html_to_pdf`. The chat-tools skills (`P/chat-tools/skills/magic-reply/SKILL.md`, `P/chat-tools/skills/markdown/SKILL.md`) have only `name` and `description`. `P/cowork-plugin-management/skills/*/SKILL.md` carry a `compatibility` line saying they require the Cowork desktop app, so they will not run in Claude Code.
- Skill sub-docs follow a naming convention. Classroom keeps step detail in files named `*-handover.md` beside `SKILL.md`: `P/classroom/skills/classroom/setup-handover.md`, `mark-review-handover.md`, `media-processing-handover.md`, `deliver-without-renderer-handover.md`. Its CHANGELOG records the rename. Chat-tools keeps trigger text in `references/*.txt`, one per trigger (`P/chat-tools/skills/magic-reply/references/show-working.txt`, `show-options.txt`, and so on).
- Templates that get copied into a user's project live in `templates/`. `P/classroom/templates/CLAUDE.md`, `P/classroom/templates/.claude/rules/classroom.md`, `P/classroom/templates/.claude/rules/classroom-signal.md`, `P/classroom/templates/global-requirements.md` and `P/classroom/templates/students/README.md` are the project scaffold the skill instantiates. This is the nearest precedent for "a plugin ships a project scaffold, and the project gets CLAUDE.md plus `.claude/rules/`".
- Changelogs use Keep a Changelog 1.1.0 with semver. `P/chat-tools/CHANGELOG.md` runs 2.0.0 to 2.1.2 and uses `### Changed` and `### Added` sections. `P/classroom/CHANGELOG.md` has a `### Fixed` section that describes a real bug and its effect on the user. `P/cowork-plugin-management` has no CHANGELOG.
- MCP wiring exists in one plugin only. `P/classroom/.mcp.json` declares server `classroom-pdf` as `node ${CLAUDE_PLUGIN_ROOT}/mcp/server.js`, with `env` set to `NODE_PATH=${CLAUDE_PLUGIN_DATA}/node_modules` and `PUPPETEER_CACHE_DIR=${CLAUDE_PLUGIN_DATA}/puppeteer`. The server sits in `P/classroom/mcp/` with its own `package.json`, `server.js`, `pdf-inspect.js`, `css-inspect.js`, `print-base.css`, and a `test/` folder with `run-tests.js` and about a dozen HTML fixtures.
- Install-time setup is a script, not a hook. `P/classroom/scripts/install-deps.sh` is idempotent: it diffs `mcp/package.json` against `$CLAUDE_PLUGIN_DATA/package.json` and runs `npm install` only when they differ. Its header says it is meant to run "on every SessionStart", but no hook in the synced plugins calls it, so the wiring is not visible here.
- No plugin ships `hooks/` or `hooks.json`. The only executable scripts are `P/classroom/scripts/install-deps.sh` and the classroom MCP server.

## What dev-workspace does and which parts overlap with the FlightDeck vision

- dev-workspace is enabled for this repository in `/home/user/flightdeck/.claude/settings.json` as `"dev-workspace@DBHD-dev-workspace": true`. That is the only setting in the file. It has no `hooks`, no `permissions` and no `env`. The plugin key format `name@marketplace` shown here is the same format a `flight@DBHD-FlightDeck` install key would use (an inference from this one example).
- The working copy is in `/home/user/flightdeck/dev/workspace/`. It contains `README.md`, `WORKSPACE.md`, `workspace-config.yml`, and the folders `context/`, `filebox/`, `history/`, `plans/`, `prompts/`, `research/`, `reviews/`, `tasks/`. I did not check whether `dev/branches/` (the archive folder named in the rules) exists in this checkout.
- `dev/workspace/README.md` describes an older install: Ruby 3.0+, the `claude_hooks` gem, hook entrypoints at `.claude/hooks/entrypoints/session_start.rb`, `user_prompt_submit.rb` and `session_end.rb`, a `.claude/config/config.json` with `contextPreLoad`, `treeFolders` and `treeOutputPath`, and a `/workspace:new-workspace` command. The README itself says "I recommend not mixing hook systems". The rules in `.claude/rules/dev-workspace_commands.md` describe a different, newer `dev-workspace` CLI with no Ruby dependency. The two documents disagree, so treat the README's install steps as stale until checked against the installed CLI.
- `dev/workspace/WORKSPACE.md` is the per-branch context card. It has `Name`, `Started`, `Status` (In Progress, Discard, Complete), `Purpose`, `Workflow` (Quick, Single plan, Multi-stage), `Track Issues`, `Testing`, `Plans` (`plans/prd.md`, `plans/architecture.md`, `context/discover.md`) and `Discoveries`. It uses `%% Claude: ... %%` placeholders, and the file says it "is not read by the dev-workspace script".
- `dev/workspace/workspace-config.yml` holds the machine config. `repo_config` sets `main_branch: main`, `parent_branch: main` and the origin URL. `workspace_protection.directories` lists `dev/workspace` and `.claude/rules`, and the file says these "MUST be identical across all branches". `init.git_ignore` and `exclude_workspace_from_docker` add the `dev/` and `.claude/` folders to ignore lists. A MERGE section follows; I read only the first part.
- The CLI commands, from `.claude/rules/dev-workspace_commands.md`, are `init`, `new`, `push`, `sync`, `merge` (with `--check` to be run first), `commit`, `archive` (writes to `dev/branches/`), `latest`, `transfer-latest`, `rebuild`, `deploy push`, `cleanup`, and `tree` (with `--show`). Most commands take `--check` and `--json`.
- Overlap with the vision (`/home/user/flightdeck/.flightdeck/VISION.md`):
- Workshops: dev-workspace already gives one directory per branch, with `plans/`, `research/`, `reviews/`, `tasks/` and a context card, and it protects those paths during merge and sync. The "branch isolated, discrete unit with output, reports, plans, state" idea is the same shape.
- Archives and snapshots: dev-workspace's `dev/branches/` snapshots and `archive --sync` answer the vision's "Manuals and libraries" and "promote important stuff" ideas only partly; it archives branch context but does not curate a library.
- Chat history: `dev/workspace/history/` keeps conversations, each with a five-line `[SUMMARY]` block. That is a precedent for agent output that can be searched later.
- Local CLI: the vision wants a local CLI for agents. `dev-workspace` is exactly that for git and branches, so FlightDeck's CLI should not duplicate it.
- Context preload and tree: the vision's "keep context fresh" overlaps with `context/tree.md`, generated by `dev-workspace tree`, and with the `@`-import in `.claude/rules/context.md`.
- The vision says dev-workspace "was built for the first era" and that "Keep it simple" must remain possible: a human with one agent in a chat window. dev-workspace is that single-agent HITL model, so it can sit beside FlightDeck rather than being replaced by it.
- Non-overlap: multi-agent workflows (launches), the roleplay ranks, the themed HTML page suite, the laboratory (drills and evaluations), and the adversary or review workflow have no counterpart in dev-workspace.
- Collision risks to decide on: both systems want `.claude/rules/` and both use `dev/` or `.flightdeck/` folders. dev-workspace's protection list restores `.claude/rules` on merge, so any FlightDeck rule file placed there will be treated as workspace-owned. `.claude/rules/context.md` already pulls in `dev/workspace/context/tree.md`, so anything FlightDeck adds to `.claude/rules/` must not break that import.

## How to load a local plugin for instant testing

- `claude --plugin-dir <path>` loads a plugin from a directory or `.zip` for one session only. A folder of plugins loads each child. The flag is repeatable, so `--plugin-dir A --plugin-dir B.zip` works. From the help text in `claude --help`. This is the fastest route for the owner to try a build: `claude --plugin-dir /home/user/flightdeck` from the repo root. The repo root has `.claude-plugin/plugin.json`, so it is a valid plugin root. Whether `agents/`, `skills/` and `hooks/` at the repo root are picked up is an inference from the synced layout, not a result I ran.
- `claude --plugin-url <url>` fetches a `.zip` for one session. Useful only once a build is published.
- `claude plugin validate <path>` checks a plugin or marketplace manifest and the skills, agents and commands in a directory. `--json` gives a machine-readable report and `--strict` fails on warnings. I ran it on the repo root: it passed with one warning (`marketplace.json` has no `description`) and one advice line that the README lacks an install line. The advice gives the install line `/plugin install flight --marketplace dilberryhoundog/flightdeck`. This command starts no session and is safe to run in planning and in build checks.
- `claude plugin marketplace add <source>` takes a URL, a path or a GitHub repo, and `claude plugin install <plugin>@<marketplace>` installs from it. This is persistent, not instant. `claude plugin update` needs a restart before it applies.
- `claude plugin init|new <name> --with skills,agents,hooks,mcp,lsp,output-style,channel` scaffolds a plugin at `~/.claude/skills/<name>/`, which auto-loads next session as `<name>@skills-dir`. This is for personal scratch plugins, not for a repository build. It is a useful reference for which component folders the scaffold creates, but I did not run it.
- `claude plugin eval [target]` runs eval cases from `<eval dir>/**/case.yaml`, or `prompt.md` with `graders/*.md`, against a plugin, with the eval dir defaulting to `evals/`. It runs on the owner's machine, and its help text says a no-plugin baseline arm is added. This is the CLI's own evaluation hook and fits the vision's "Laboratory" section.
- `claude plugin test [dir]` runs `*.test.ts` and `*.test.tsx` files against a "mod" (a change to Claude's own interface, per the `plugin-authoring` skill). It is for mods, not for agents or skills.
- `claude plugin tag [path]` creates a `{name}--v{version}` git tag and checks that `plugin.json` and the marketplace entry agree. `--dry-run` previews; `--push --remote origin` pushes the tag. Do not run it in a planning step.
- For agents without installing: `--agents <json-or-file>` defines custom agents for one session (with `--print`, a path to a file holding the JSON). `--agent <name>` picks one as the session's agent.
- Background and parallel sessions: `--bg` (alias `--background`) starts a session and returns its id. Then `claude agents` lists them, `claude attach <id>` opens one, `claude logs <id>` prints its output, and `claude stop <id>`, `claude rm <id>` and `claude respawn` manage it. `--resume <id>` with `--bg` continues a session in the background.
- Worktrees: `-w, --worktree [name]` creates a git worktree for a session, and `--tmux` (requires `--worktree`) opens it in a tmux session. This matches the vision's "worktrees" line.
- Isolation for test runs: `--bare` skips hooks, plugin sync and CLAUDE.md discovery, and needs explicit `--plugin-dir`, `--agents`, `--mcp-config` or `--settings`. `--safe-mode` disables CLAUDE.md, skills, plugins, hooks, MCP servers, custom agents and workflows, and keeps built-in tools. `--restricted` removes the code-running tools and ignores project and local settings files. Use one of these to check that a build does not silently depend on the owner's personal setup.
- Scripted and structured runs: `-p/--print` with `--output-format json` or `stream-json`, `--json-schema` for validated output, `--max-budget-usd`, `--no-session-persistence`, and `--permission-prompts none` (which denies anything that would prompt). `--include-hook-events` adds hook events to the stream.
- Model and effort: `--model` accepts aliases `fable`, `opus` and `sonnet`, or a full name. `--effort` accepts `low`, `medium`, `high`, `xhigh` and `max`. `--fallback-model` takes a comma-separated list. Pin `--effort high` and `--model opus` (or `sonnet` for workers) to stay under the owner's ceiling.
- Review: `claude ultrareview [target]` runs a cloud-hosted multi-agent review of the current branch or a PR and prints findings. It is a built-in second reviewer to weigh against the adversary.
- I found no CLI flag specific to the Workflow tool. The `--safe-mode` help lists "workflows" among the things it disables, so workflows are loaded like other customisations. Workflows are started from inside a session, not from the shell.

## Model note
