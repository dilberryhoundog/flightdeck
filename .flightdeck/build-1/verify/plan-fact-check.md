# Plan fact-check: Claude Code claims in plan.md

Fact-check of `.flightdeck/build-1/plan/plan.md` against `library/source/claude-code/`, the live docs at code.claude.com (fetched 2026-10-10), `harness-core.md`, `harness-multi.md`, and tests run on the installed Claude Code 2.1.296 in throwaway folders (isolated `HOME` for plugin tests, a scratch plugin for hook input). Nothing in the repository was changed except this file. Findings are ordered by severity. A short list of claims that held up is at the end.

## Findings

**High: the imposter's nested install and the landing-page "install rehearsal" would overwrite the owner's real FlightDeck install.** Plan section 5 (Verify, imposter; Landing page) has agents run `claude plugin marketplace add <scratch clone> --scope local`, `claude plugin install flight@DBHD-FlightDeck --scope local` and later an uninstall. The marketplace registry is user-level and keyed by name; `--scope local` only controls which settings file records it. Test with an isolated HOME: adding a second clone with the same marketplace name printed "Marketplace 'DBHD-FlightDeck' was already added from dir:.../ra and now points at dir:.../rb. Plugins already installed from it now update from the new source"; `claude plugin list` run from the first project then read the plugin from the second clone; `claude plugin uninstall` plus `claude plugin marketplace remove DBHD-FlightDeck` in the second clone left the first project with "No plugins installed". In Run B this would repoint or remove the install the pilot session is running on. Fix: before installing, the imposter rewrites the `name` in the scratch clone's own `.claude-plugin/marketplace.json` to a unique value such as `DBHD-FlightDeck-try-pr<n>-a<k>`, installs and uninstalls only that id, and never touches `DBHD-FlightDeck`; add that rule to the imposter brief, the rehearsal step and the static check on workflow scripts (no `marketplace remove DBHD-FlightDeck`). Also run `claude plugin marketplace list` before and after the rehearsal and fail the stage if the owner's entry changed.

**High: the ceiling scanner (section 3.8) denies the owner's own planning retry and contradicts the plan's static scan.** The hook denies any Agent or Workflow call whose "workflow script ... contains `fable`, an `xhigh` or `max` effort, or `ultracode`" and "reads every string field of the input". The existing `.flightdeck/build-1/workflows/plan.js` line 75 contains the literal word `fable` (in a task string that notes `adversary.md` sets `model: fable`), so once the plugin is installed, rerunning `plan.js` (which `constraints.md` and the plan's retry section tell the owner to do) is denied, and so is any agent prompt that merely says "never use fable" because the hook reads prompt text. The same words also break the plan's own checks: the static scan "finds no `fable` ... in ... `hooks/`, `lab/` and `.flightdeck/*/workflows/`" would fail on `plan.js`, and `hooks/guard.mjs`, `hooks/tests/hooks.test.mjs`, `lab/checks/static.mjs` and the sweep drill must contain the literal words they search for. Fix: for the Agent tool, check only the structured fields (`model`, and `subagent_type` resolved to a definition if wanted); for Workflow, test option keys with anchored patterns (`model:\s*['"](fable|best)`, `effort:\s*['"](xhigh|max)['"]`, a bare `ultracode` token outside comments), never prompt text; exempt the guard, its tests and the static check by file name (or build the words from pieces); change the static scan to the same anchored patterns so `plan.js` passes, and add a test that runs the scan on `plan.js`.

**High: the pre-flight card reaches Claude, not the owner.** Plan section 1, 3.1 and the first-hour script say the card "is printed", "shows" and "Read the pre-flight card". `hooks.md` "Exit code 0" says SessionStart plain stdout is added "as context that Claude can see"; for other output it only goes to the debug log, and `hooks.md` says "To surface a message to the user on any platform, return `systemMessage` in JSON output". As written, the owner sees nothing at 0:01 unless the pilot repeats it. Fix: print one JSON object with both `systemMessage` (the card, for the owner) and `hookSpecificOutput.additionalContext` (the same card, for Claude), keep the 10-line and 800-character limits, make the hook test assert both fields, and add an interactive check that the card is visible (the imposter cannot see a terminal, so list it as an owner check). Note that JSON output must start with `{` and end with `}` or it is treated as plain text.

**Medium: the truth guard is built on a misreading of hook input.** Plan section 3.4 and the "Judge problems fixed" list say `agent_id` and `agent_type` are both present in a `claude --agent` session and design the pilot exception around that (the sentence is copied from `harness-core.md` section 5, which is wrong on this). `hooks.md` common fields says `agent_id` is "Present only when the hook fires inside a subagent call" and `agent_type` is present "when the session uses `--agent` or the hook fires inside a subagent". Test with a scratch plugin: a Write in a `claude -p --agent tp:pilot` session logged `agent_id` absent and `agent_type` `tp:pilot`; a Write from a subagent logged `agent_id` set and `agent_type` `tp:grunt`. So the owner's pilot session already has no `agent_id` and the "main conversation" rule covers it; the extra rule "allow when `agent_type` names the pilot" is both unnecessary and unsafe, because a subagent of type `flight:pilot` has `agent_type` pilot and would be allowed. Also the plugin agent's `agent_type` is the scoped name `flight:pilot`, not `pilot`. Fix: allow if and only if `agent_id` is absent; delete the pilot special case and the "judge problem" claim; keep the live check (pilot session writes, workflow agent is refused).

**Medium: the same guard still lets unattended sessions write the owner's files, and the plan says it does not.** Plan section 3.4 says the static check ensures "the pilot exception only covers the owner's own session". But a session started from a shell is its own main conversation with no `agent_id`: the officer recipe (`claude --bg --agent flight:pilot ...`, section 3.2), the imposter's nested `claude -p` sessions, and the plan's own live checks (`claude -p --agent flight:pilot ...`) can all write `constraints.md`, `VISION.md` and `build.txt`. The static check that no skill or workflow spawns the pilot as a subagent does not see these. Bash redirects (`echo >> constraints.md`, `sed -i`) also pass, which the risks section admits, but section 1 still says the guards "stop agents writing the owner's own files". Fix: every shell-spawned `claude` command the plan writes (officer recipe, imposter, evals, drills) sets an environment variable such as `FLIGHTDECK_UNATTENDED=1`, which child hook processes inherit, and the guard denies owner-file writes whenever it is set; add `Bash` coverage with an `if` such as `Bash(*constraints.md*)` or word the claim as "stops the Edit and Write tools only".

**Medium: the ceiling rule claims more than it can enforce.** Section 1 says guards "refuse models above the owner's ceiling" and 3.8 says the guard "refuses anything above Opus at high effort". It only sees an explicit `model` on an Agent or Workflow call and text in a workflow script. It does not see `/model fable` or `--model fable` for the session, `/effort xhigh`, `--effort ultracode`, the `ultracode` setting, `CLAUDE_CODE_SUBAGENT_MODEL`, or a user or project agent whose own file says `model: fable` (the Agent input carries `subagent_type` and an optional `model`, per `hooks.md` "Agent"). Claude Code already has real controls: settings `deniedModels`, `availableModels`, `maxEffortLevel` (listed in `harness-core.md` section 8) and a documented `PreModelSwitch` hook event that "can block the switch". A plugin cannot ship the settings but it can ship a `PreModelSwitch` hook. Fix: add a `PreModelSwitch` guard denying fable, best and any effort above high; make `/flight:preflight` report whether `maxEffortLevel` and `deniedModels` are set in the owner's settings and print the two lines to add if not; reword the claims to say what is covered.

**Medium: the git guard's `if` filter is narrower than the plan assumes, and the plan's risk note about it is wrong.** Plan PR 1 uses `PreToolUse` on `Bash` with `if: "Bash(git push*)"`, and the risks section says "a push hidden inside a compound command may not match". `hooks.md` ("Bash if matching") says each subcommand is checked (`npm test && git push` runs the hook) and that unparseable commands run the hook anyway; the real gaps are forms that do not start with `git push`: `git -C <dir> push`, `git --git-dir=... push`, `git -c key=val push`, a `git` alias, and a bare `git push` while on `main`. The docs also say "the `if` filter is best-effort, use the permission system rather than a hook to enforce a hard allow or deny", and a plugin cannot ship permission rules. Fix: use `if: "Bash(git *)"` and parse the command in `guard.mjs` (skip global options, find the subcommand, read the current branch for a refspec-less push); correct the risk text; keep the build's `permissions.deny` list as the second layer for Run A and tell the owner to copy the same deny lines into their settings for everyday use.

**Medium: background officers edit a worktree, not the owner's checkout.** Plan section 3.2 and 3.5 define officers as `claude --bg --agent flight:pilot --name officer-<topic>` and add only `--settings '{"worktree":{"baseRef":"head"}}'`. `agent-view.md` "How file edits are isolated" says every background session moves into an isolated git worktree under `.claude/worktrees` before editing (off only with `worktree.bgIsolation: "none"`), and deleting the session deletes the worktree with uncommitted changes. An officer that writes a question into `.flightdeck/<w>/questions.md`, a workshop file or an attempt report writes it on its own branch; the pre-flight card, the board and the owner never see it until it is committed, pushed and merged. The plan's rule "any agent that would otherwise guess writes a question there" is only true for agents that are not isolated. Fix: say in the officer recipe and in `workshop` rules that isolated agents commit and push their branch and report the branch name, and that the triage stage (not isolated) is the writer of `questions.md`; or set `bgIsolation: "none"` for officers that must write `.flightdeck/` and accept the risk in the recipe.

**Medium: the eval commands and case designs do not match how `claude plugin eval` runs.** Plan 3.13, PR 6's try step, the Run A checks and several cases (`pr2-board-shows-waiting`, `pr3-*`, `pr7-librarian-cites`) assume fixtures and shell commands. The live `plugin-evals.md` ("How runs are isolated") says each run has a temporary home and empty workspace with only the plugin loaded: no `.claude/`, no `CLAUDE.md`, no project config, read-only tools only unless `--allow-tools`, and `scaffold_script` only runs with `--scaffold`. The plan's command (`--eval-dir lab/evals --case ... --runs 1 --no-publish --trust-plugin --max-cost-usd 2`) passes neither flag, so a board case that must run `node render.mjs` over fixture workshops cannot work, and no case can rely on the repository's rules or on `.flightdeck/` existing. Cases also cannot start an agent as the main thread; `pr1-adversary-planted-defect` must ask for delegation in its prompt. Results are written to `lab/evals/results/<timestamp>/` inside the repository, which the docs say to add to `.gitignore`; the plan has no such entry, so `git status` would be dirty and the ownership check would flag it. The plan's phrase "the docs mention an early-access gate" is also off: the live page lists "your build predates general availability" and "plugin eval is currently unavailable ... switched off server-side"; the planned honest "not available" fallback still fits. Fix: write each case self-contained (fixtures in `context.add_dirs` or `resources/`), pass `--scaffold --allow-tools 'Bash(node *)'` only for the cases that need them and say so in the PR, add `lab/evals/results/` to `.gitignore` and to the static check's ignore list, and reword the gate sentence.

**Medium: the multi-stage `pipeline` and "halt or null passes on to land" are not in the docs and not covered by the probe.** Plan section 5 uses `pipeline(prs, gather, brief, build, verify, triage, fix, land)` and says a stage that returns a halt or `null` "passes it on to `land`". The library `workflows.md` documents only `pipeline(items, fn)` with one callback and says only that `pipeline()` keeps each `null` in the results array; the stage-callback signature and "a stage that throws drops that item to null" come from the `workflow-authoring` skill text quoted in `harness-multi.md` section 1. Whether a later stage still runs with a `null` previous result is not stated. Fix: add a probe for a three-stage pipeline where one stage returns `null` and one throws, and see whether the next stage runs; or avoid the question by having every stage return an explicit `{halt: reason}` object, never `null`, with each stage body in try/catch and `land` handling `{halt}`.

**Low: `.flightdeck/CLAUDE.md` as a one-line import of `../templates/flightdeck/CLAUDE.md` only works inside this repository.** Imports resolve relative to the importing file (`harness-core.md` section 6), and a plugin's `templates/` folder lives in the plugin cache, not in another project; plugin path variables are not expanded in CLAUDE.md, and imports from outside the working directory trigger an approval dialog. Plan 3.4 says the first `/flight:workshop` in another project "asks the owner whether to create `.flightdeck/CLAUDE.md`" but not how. Fix: in this repo put the workshop rules directly in `.flightdeck/CLAUDE.md` (one fewer file and no indirection), and have the skill copy `${CLAUDE_SKILL_DIR}/../../templates/flightdeck/CLAUDE.md` into the other project as plain text after the owner says yes.

**Low: the radio output style with `--agent flight:pilot` is untested.** `output-styles.md` says styles apply to the main conversation, and `subagents.md` says `--agent` replaces the default system prompt; nothing says how the two combine, and `keep-coding-instructions: true` may have no effect on a replaced prompt. Plan 3.2 says the style is chosen with `/output-style flight:radio` while flying the pilot. Fix: add a PR 1 live check that the voice appears in a pilot session; if it does not, move the voice into `agents/pilot.md` as an opt-in paragraph and keep the style for plain chat.

**Low: invented or duplicated mechanisms the plan does not need.** (1) Three separate readers of workshop and `questions.md` files, `hooks/preflight.mjs`, `skills/board/render.mjs` and `bin/flight status`, each counting empty `answer:` lines; the ownership rule keeps them from sharing code even though every later pull request depends on PR 1. Put one small reader module in PR 1 (for example `hooks/lib/workshops.mjs`) and import it. (2) `flight commit` repeats `git add .flightdeck && git commit` and `dev-workspace commit`; keep `flight status` and `flight serve` and treat `commit` as the first thing to cut inside PR 5. (3) The `templates/flightdeck/CLAUDE.md` indirection (see the Low finding above). (4) A custom string-scanning ceiling hook where Claude Code has `deniedModels`, `availableModels`, `maxEffortLevel` and `PreModelSwitch` (see the Medium finding above). The other state files (`questions.md`, `decisions.md`, `attempts/`, `constraints.md`) map to things the VISION asks for and have no native Claude Code equivalent for background agents, so they are not flagged.

**Low: `bin/flight` needs an exec bit, and the plan does not say so.** The live `plugins/components.md` says "Make it executable with `chmod +x`" and that `bin/` is on the PATH of the Bash tool's shell only (not hooks, not the owner's terminal). The plan lists the file and its tests but not the shebang or file mode. Fix: add `#!/usr/bin/env node`, commit mode 100755, and have the static check assert both; the README should say the owner's terminal needs `node bin/flight`.

**Low: pilot tool list is not specified.** The pilot is the main-thread agent. If `agents/pilot.md` sets `tools:`, it must include `Agent`, `Workflow`, `AskUserQuestion`, `Skill`, `Bash`, `Read`, `Edit` and `Write` (the pilot writes workshops and the owner's words), and an `Agent(...)` allowlist (main thread only, per `subagents.md`) must use the scoped names `flight:scout` and so on. A pilot told not to do the work but given no Write would fail the "pilot session may write constraints.md" design. Fix: list the tools explicitly in section 3.2 and add a hook test that the pilot's tool list includes what its job needs.

## Checked and supported

- Plugin layout and names: `agents/`, `skills/<name>/SKILL.md`, `hooks/hooks.json`, `output-styles/`, `workflows/`, `bin/` at the plugin root; `/flight:<skill>` and `flight:<agent>`; `CLAUDE.md` and `.claude/rules/` cannot ship (live `plugins/components.md`, `harness-core.md` sections 6 and 10). `${CLAUDE_PLUGIN_ROOT}` is substituted in skill, command and agent content (live `plugins/components.md` "Reference plugin paths"; `harness-core.md` contradicts itself on this, the live page is clear).
- Plugin agents ignore `permissionMode`, `hooks`, `mcpServers`, `initialPrompt` and support `model`, `effort`, `maxTurns`, `tools`, `omitClaudeMd`, `isolation`, `color` (live `plugins/components.md` line 739).
- Plugin workflows run as `/flight:<meta.name>` (live `workflows.md` "Distribute a workflow in a plugin"); `isolation: 'worktree'`, `model`, `agentType`, `schema` exist per the blog; per-agent `effort` is from the skill text only and the stage-0 probe covers it.
- Hooks: exec form with `args`, `SessionStart` matcher values, `PreToolUse` deny via JSON, hooks firing inside subagents, `PreToolUse` working under bypass mode, `if` allowed only on tool events.
- CLI: `claude plugin details <name>`, `claude plugin eval` with `--eval-dir`, `--case`, `--runs`, `--judge-model` (default haiku), `--max-cost-usd`, `--json`, `--no-publish`, `--trust-plugin`, `claude plugin test`, `claude --bg`, `--agent`, `--name`, `--settings <file-or-json>`, `--effort` all appear in `--help` or the live docs on 2.1.296; eval cases as `prompt.md` plus `graders/*.md` are the documented layout.
- Local marketplace install with `--scope local` works and writes only `.claude/settings.local.json` in the project (re-confirmed in an isolated HOME); `--plugin-dir` makes the directory protected for writes (`permission-modes.md`).
- Mods: `modules` in `hooks/hooks.json`, `$.state` and a band above the prompt exist (live `plugins/mods/overview.md` and `reference.md`); `claude plugin test` runs `*.test.ts`.
- Agent teams: experimental, interactive only, no team file, teammate roles from project, user or managed subagent definitions only; `bin/` blocks claude.ai and Cowork install; background sessions never push to main, force-push or merge; `worktree.baseRef` defaults to branching from the default branch; `AskUserQuestion` is removed from subagents.
