# Human imposter findings on the plan (attempt 1)

Written by the human imposter agent, reading `.flightdeck/build-1/plan/plan.md` in the owner's voice after reading `user-intent.md`, `interview-record.md` and `owner-truth.md`. It is a role-play of the owner built from agent-written summaries of the owner's words, so every finding is a guess at the owner's reaction, not the owner's own statement. Quotes are the owner's as relayed in those summaries.

What I like, in my own voice: the pre-flight card showing FlightDeck's own build is the first thing I see, and that is exactly the "show me something that works" I asked for. Refusing a push to main on my first day is a nice little win I can feel. Recon with cheap scouts and an adversary attacking the README is a first hour I would actually do. Plain chat staying plain, the cut order at the end of section 2(d), the board with a copy button for my answers, and the rule that nothing from PRs 2 to 8 builds PRs 2 to 8 all read as someone who listened. Run A using no FlightDeck part and Run B using only the merged PR 1 is a clean answer to "half built systems building the half built system is a fail HARD".

What I would ask the agent first: why is the plugin not under the `flightdeck/` folder I keep talking about; what happens if a guard blocks me in my own chat; how long will Run A take and how much of my weekly limit does Run B burn; if you could only build three pull requests which three; and which of these 14 decisions do you most want me to overrule.

Could I try it straight away? After Run A, yes: three commands, then a chat with the pilot. Before Run A there is nothing to run, which is fine. The try steps need fixing in one place (finding 3 below) or step 6 of the first hour will not be true.

High: The plugin sits at the repository root, which ignores the `flightdeck/` and `lab/` folders I named in the interview and the "imports a single flightdeck directory" line in my CONCEPT note. Section 2(b) puts agents, skills, hooks, output styles, workflows, templates, bin, manuals, library, lab, mods and `.flightdeck/` all at the top of the repo next to `dev/` and `.claude/`, which is about a dozen top-level folders, and I said I can't act on what I can't SEE ("I couldn't SEE my project"). The plan only gives a loader reason, and its own risks section admits a non-local install copies `library/source/` into the plugin cache and names `source: "./plugins/flight"` as the alternative. Suggested fix: make the plugin root a single `flightdeck/` folder (marketplace `source: "./flightdeck"`), keep `lab/`, `library/source/`, `dev/` and `mods/` outside it so they never ship, keep per-project work in `.flightdeck/`, and put a plain folder picture at the top of the review page with a keep-or-change choice, because I said "see where they put stuff" and I want to see it before it is built.

High: The default build is too big and goes all at once, which is the mistake I named twice ("all at once", "too much"). Run B builds seven pull requests together with about 75 agents, 105 files and 6,500 lines, and I have to read and try all of it; "if i like it but its too big, I cut it down" should not mean I am handed everything first. PR 1 is also not basic: at about 43 files it carries custom code (a hook script with three rules, a card hook, a static check with ownership lists, hook tests, eval cases, a persona), not just agent definitions, rules, CLAUDE.md and recipes as build.txt describes. Suggested fix: on the review page show a starter set that is built by default (PR 1 trimmed, plus PRs 2, 3 and 4, which the plan itself calls my first hour) and list PRs 5 to 8 as "tick to include, off by default"; move the static check, ownership enforcement and eval cases out of PR 1 into PR 6 except the few checks that protect hard rules; build only what I tick.

High: The guards bite in my own plain chats, and that breaks the promise in section 3.11 that installing changes nothing about plain chat. The git rule refuses force-push, branch deletes and pushes to main for every session where the plugin is enabled, but those are rules for this build, not for me ("force push anything thats needed. im the only one on this repo"); the ceiling rule scans every string in every Agent or Workflow call for words like `fable` and `max`, which can refuse harmless text; and the pre-flight card prints at every session start, so step 7 of the first hour ("run plain `claude` to see ordinary chat is unchanged") would show the card and the guards. This is exactly "fighting the machine" in my own prompt window. Suggested fix: apply the guards only to agents (subagents, workflows, `--agent flight:pilot`) and not to my main plain session, or ship them behind one named switch that is on for this build and off by default for ordinary use; print the card only in pilot sessions or as a single line; change 3.11 and the first-hour text to say honestly what plain chat does and does not do.

High: The static check turns the lead's invented numbers into failing checks, and that is the test suite I said I must not have to fight ("I dont want a test suite I have to 'fight' each time i make some changes"). The plan fails a branch on a 60-line root CLAUDE.md, 40-line workshop rules, a card of 10 lines and 800 characters, skill descriptions over 400 characters or 4,000 together, 100-line manual pages, a 30-day library age, five questions per bundle and at most three units, plus changed-file ownership lists, and I never chose any of them ("how did the cap arrive at 40 lines?"). Each is marked as the lead's choice, but there are too many to read as separate choices. Suggested fix: let only the hard rules fail a check (nothing on main, no model above Opus high, nothing under `dev/`, no `dw` dependency, files outside the pull request's own list); make every other limit a warning; gather all the tunable numbers into one short box on the review page headed "defaults I picked, change any".

Medium: Several of the features the plan stands on are unverified, and the riskiest are only tested late. The truth guard depends on how the `agent_type` value looks inside a `claude --agent` session, workflow agents using `agentType: 'flight:...'`, a hook's denial reaching a workflow agent, plugin workflows running as `/flight:<name>`, plugin `bin/` on the PATH, and `claude plugin eval` being available on my account. The stage 0 probe covers only effort, worktree branching and `gh`; the guard's live check happens in PR 1's verification, after PR 1 is built. I told you tooling is a major failure axis ("it is clearly tooling") and that I wasted days on teams that were not "even a v0.0.1". Suggested fix: probe the guard and `agentType` facts in stage 0 before any building, and state on the review page, in one plain list, what might not work and what the plan does then (for example: if the truth guard cannot tell my pilot session from a workflow agent, ship it as a CLAUDE.md rule only and say so).

Medium: There is no time or cost estimate for the two build runs. The plan counts agents (18 and about 75) and tiers but gives me no hours and nothing about my 20x limit, and it adds nested `claude -p` sessions run by the imposter, which "do not wait out usage limits". I have said "what then we blow up my usage limits?" and "Did I just waste a bunch of tokens". I am not scared of tokens, but I want them spent on purpose. Suggested fix: put a rough time and a rough share-of-weekly-limit per run on the review page (even as a range), say what happens if the limit is hit mid-run, and add a single "stop here and show me" point after the first half of Run B.

Medium: Stage 0 asks too much of me for something I want to be fast. I restart my session with a settings file and flags, click one protected-path approval, wait for a probe workflow, and have my words turned into dated constraint lines by the main conversation. I found "the enacted approval dance" tedious. Suggested fix: give me one copy-paste block that does the restart, tell me exactly the one click I will be asked for and why, and have the lead write my reply lines for me to glance at instead of a separate step.

Medium: The imposter that stands in for me is built from agent-extracted quotes I have never checked, and it is the thing that judges every pull request and answers every interview test. A wrong persona makes every verdict wrong in the same direction, and the agents then "treat it like canon". Also, the imposter installs the plugin in scratch clones using the marketplace name `DBHD-FlightDeck`, which is the same name as my real install, and the plan does not say that a scratch install cannot repoint or overwrite my real registration. Suggested fix: show `lab/personas/commander.md` (about ten lines) on the review page for me to correct before the build, state which verdicts rely on it, and say that scratch installs use a throwaway marketplace name and never touch my real plugin settings.

Medium: The six team recipes are invented and shipped as ready content in PR 1. I said "about 6 shapes" and never named them; the plan says so, calls the list a proposal and still writes eight files and entry text around it (Recon, Build and check, Spec first, Many hands, Root cause, Decide). The reading "a workshop is the place, a launch is one flight from it, an attempt is what a launch leaves behind" is also a guess, because I told you I don't know how launch differs from workshop. This is close to "dont invent shit and say 'done'" even though it is labelled. Suggested fix: on the review page show the six as a keep, rename or drop list with one plain line each, ship only the ones I keep (default: Recon, Build and check, Decide), and put the launch/workshop reading next to a plain "is this right?" box.

The plan isolates build branches for launches and for build-1 attempts, but an ordinary workshop is just a folder in `.flightdeck/` with a rule that agents must not edit another workshop. "Branch isolated" and "two workshops never touch each other" are two of the things I listed, and logs and verification are only implied under attempts. New words include pre-flight card, flight strip, board, shapes, ways to fly, entry points, officers (mine, but the plan's use is new), attempts, provenance marks, drills, sweep, remove-part, climb, static check and guard; the owner's file is called `constraints.md` while VISION says "truth", so I will look for a truth file and not find one.
