# Plan review: completeness against VISION.md, build.txt and the brief

Reviewed `.flightdeck/build-1/plan/plan.md` on 2026-10-10 against every VISION section, every asking sentence in build.txt, and every item in the brief under "What the owner left to you" and "What the owner did state". Constraints file is empty ("none yet"). Coverage is good: every VISION section has a part, all seven "left to you" decisions are made (section 2 a to g), and the "did state" items are met (instant try, imposter, dynamic workflows, model ceiling). The findings below are the gaps, contradictions and checks an agent cannot run as written. Facts checked on this machine: `claude plugin eval` has `--eval-dir`, `--case`, `--runs`, `--no-publish`, `--trust-plugin`, `--max-cost-usd`, `--json` and `--judge-model`; `claude plugin details`, `claude plugin test` and `claude plugin validate` exist (Claude Code 2.1.296).

## High

**High** — Section 5 stage 0 (build-settings.json), Run A. In Run A the "never push to main" rule rests only on the deny list, because PR 1's git rule does not exist yet, and the list has holes while `Bash(git *)` and `Bash(node *)` are allowed. Not matched by any deny pattern: `git push -u origin main`, `git push origin build-1:main`, `git push origin refs/heads/x:refs/heads/main`, `git push origin +main`, and remote branch deletion by `git push origin :branch` or `git push -d`. The plan calls the list a second layer, but in Run A it is the only layer, and the owner's hardest rule is "never push to main". Fix: replace the broad `Bash(git *)` allow with explicit allows (read-only git subcommands, `git push -u origin build-1-*`, `git push origin HEAD:build-1-*`) so every other push is not allowed, or have the lead add a small PreToolUse push-check hook in the settings file for Run A (a few lines, written and tested in stage 0). Also add denies for `git push * :*` and `-d`.

**High** — Section 4 PR 1 "Try" and "Checks"; section 3.1. The try step "push this branch to main and watch the guard refuse", and the live check "a `git push origin HEAD:main` is refused" run in a scratch clone whose origin is the real GitHub remote, with the owner's or the sandbox's push credentials. The git rule "fails open on any internal error" (section 3.4 and 3.8 say this for the guard), so if the guard misfires, a push to main really happens. A test of a safety rule must not be able to break the rule. Fix: live refusal checks use a scratch clone whose origin is a throwaway local bare repository (`git remote set-url origin <scratch>/bare.git`), and the owner's try says "push this branch to main with --dry-run" (the hook still sees `git push*`, nothing can be sent). Consider making the git rule fail closed for pushes (deny with "guard error") while the other two rules fail open.

**High** — Section 3.8 ceiling rule versus section 5 CONTEXT block and `build.js`. The ceiling hook "reads every string field of the input" and denies any call whose input or workflow script contains `fable`, `best`, `xhigh`, `max` or `ultracode`. But section 5 says every build agent gets a CONTEXT block stating the model ceiling, `build.js` is run by path (the hook reads the `.js` file), and the plan's own text lists those words. In Run B, with the guard active, every `agent()` prompt and the script itself would match, so the guard would block the build, or the CONTEXT block must avoid the words and cannot say what the ceiling forbids. The word `best` also matches ordinary prose ("best practices"). Fix: the hook must match only structured fields (`model`, `effort`, `agent type`, or `model:`/`effort:` keys and `model: '...'` option literals in a script), never free text; add hook tests for "prompt text that merely mentions fable is allowed" and "a script with `model: 'fable'` is denied", and say so in 3.8.

**High** — Section 3.2 officers versus section 3.4 truth guard. The truth guard allows owner-file writes from "a `claude --agent flight:pilot` session". Section 3.2 and the ways-to-fly page define officers as `claude --bg --agent flight:pilot --name officer-<topic> "<brief>"`, which are unattended background sessions with exactly that same `agent_type`. They pass the guard and can write `constraints.md`, `VISION.md` and `build.txt` with no owner present. The static check only forbids spawning the pilot as a subagent, so it does not catch this. This defeats the "stop agents writing the owner's own files" promise that the Human-energy section depends on. Fix: officers use a different agent (for example `flight:officer`, a thin agent without the owner-file exception), or the guard allows only interactive sessions (the hook input's session source or permission mode, verified in the PR 1 live check), or the officer recipe launches with an env var the guard treats as "not the owner". Add a hook test for it.

## Medium

**Medium** — Section 2(d) versus section 4. Size numbers do not add up. Section 2(d) and section 1 say "about 105 files and 6,500 lines"; the per-PR sizes in section 4 are 43, 9, 12, 11, 3, 22, 18 and 6 files (124) and 2,300, 800, 750, 1,000, 450, 1,100, 1,300 and 400 lines (8,100). The owner's cut decision ("if i like it but its too big") depends on these numbers. Fix: recompute, and show each PR's size on the review page.

**Medium** — Section 3.9 ownership rule versus sections 3.13, 3.4, 3.5 and 4. The rule "every advanced PR edits no file owned by another PR" is broken by the plan's own lists: PR 6 lists `lab/README.md (expanded)` and `lab/evals/pr1-adversary-planted-defect/` (both PR 1 files); PR 4's fallback says "the launch skill and README say to run it by path", but README is PR 1's; PR 3's list in 3.4 omits `skills/workshop/tests/fixtures/bundle-answer.txt` that section 4 lists. Also no file holds the "owned lists" that `static.mjs --owned <file>` and `remove-part.mjs` read, and no PR creates them. Fix: give each PR its own README note file (for example `lab/README-pr6.md` or a section included from PR 1's README by an empty-by-default include), add `lab/owned/pr<n>.txt` (or one `lab/owned.json`) to each PR's file list, and remove the duplicates.

**Medium** — Section 2(b) layout versus section 3.1 card and 3.6 CLI. The pre-flight card, board and `flight status` all show "each workshop's latest attempt" taken as the highest-numbered folder in `attempts/<k>/`, but build-1 uses `attempts/pr-<n>/a<k>/` and its planning run lives in `plan/` with no attempt folder at all. The card for the very first workshop the owner sees (build-1) would show nothing or the wrong thing, and the scaffold test ("a second attempt is numbered from the folder listing") does not cover the nested form. Also section 2(c) does not say where planning attempt 2 goes (the README says plan.js overwrites `plan/` unless `outDir` differs). Fix: define one rule that all three readers share (latest attempt = highest `a<k>` found at any depth under `attempts/`, grouped by `pr-<n>`), test it with a nested fixture, and say where planning retries land (for example `attempts/plan/a<k>/` via `outDir`).

**Medium** — Section 4 "Try in under five minutes" for PR 1, PR 3 and PR 6. PR 1's try is seven steps including two installs, `/flight:preflight` (runs validate, the hook tests and `plugin details`), a three-scout recon, and an Opus adversary attack on the README; the plan's own first-hour table puts the recon at 0:05 and the adversary at 0:10, so the real time is about 10 minutes. PR 3's try (interview, retry, promote with an Opus adversary diff check, a manual `decisions.md` edit) and PR 6's (a model-run `plugin eval` with `--max-cost-usd 2`, then the interview drill) are also over five. PR 4 is honest that the pull request takes 10 to 15 minutes. Fix: cut each try to what fits (PR 1: install, card, `/flight:preflight`, one refused push, plain chat; the recon and the adversary attack become "next, optional, about 5 minutes"), time each step in the imposter's report, and put "minutes measured" in the PR body.

**Medium** — Section 5 verify stage, adversary. The project adversary `.claude/agents/adversary.md` has tools `Read, Write, Grep, Glob, WebFetch, WebSearch`: no Bash. The plan has it "read `git diff origin/<base>...origin/<PR branch>`", be "read-only" and give evidence "a second reader can reproduce", and the same applies to the review step wording. Without Bash it cannot run git, and it has Write. Its body also tells it to reply with a heading template first if the context is not given. Fix: the brief stage writes the diff and the owned files to `<scratch>/pr-<n>/work/` and gives the adversary that path under `=== The Work ===`; or stage 0 adds `Bash` to its tools alongside the model fix (and say so in the one approved edit); remove `Write` for Run B's `flight:adversary` and state that in `agents/adversary.md`.

**Medium** — Section 5 imposter and integrate stages. Nested installs of the plugin by agents (`claude plugin marketplace add <clone> --scope local`, `install`, uninstall in the landing page rehearsal) use the same marketplace name `DBHD-FlightDeck` as the owner's real install and write to the shared user-level plugin registry and cache (harness-core says its own probe had to uninstall and delete cache folders). A build agent can repoint or remove the owner's working install, and parallel imposters per PR race on it ("serially" is only stated for the rehearsal). Fix: nested sessions run with a scratch config directory (`CLAUDE_CONFIG_DIR=<scratch>/home/pr-<n>` plus the credentials method the machine uses) or with a renamed marketplace in the scratch clone (for example `name` edited to `DBHD-FlightDeck-try-pr<n>`), and the plan states that no agent touches the owner's real install; probe item (5) checks this.

**Medium** — Sections 3.1, 3.6, 5 "Checks". Several checks cannot run as written. (a) `claude -p "run: command -v flight"` needs a Bash permission; harness-core says Bash needed approval in `-p` mode, so the check must pass `--permission-mode acceptEdits` plus an allow rule or `--allowedTools 'Bash(command -v *)'`. (b) "a workflow agent told to write `.flightdeck/build-1/constraints.md` is refused" needs a Workflow launched from a nested session; the plan does not say how. (c) The "Checks" stage is Haiku at low effort, but the PR 1 live checks (nested pilot session, plugin install, guard refusal, eval run) are Sonnet-sized work; nothing assigns them. (d) `--eval-dir lab/evals` is documented as "directory name below the plugin"; a nested path is untested. (e) `/flight:preflight` checks `worktree.baseRef` and `gh auth status`, which are owner-machine facts and read differently in a scratch clone. Fix: list the exact flags for each nested call, give the live checks to a Sonnet "live-check" agent with a read-the-files fallback marked [stated], add one probe for `--eval-dir` with a nested path (fallback: `evals/` at the root), and make preflight report owner-machine items as "owner machine: ..." not failures in CI.

**Medium** — Section 5 stage 0 and "Script shape". `build.js` is the heart of the retry and verification story, but no step writes it, and nobody tests it before the owner's "go". Stage 0 lists the settings file, the adversary edit, the probe and the launch; the script itself is "run by path" as if it exists, and there is no compile check (the stub-wrapped compile test exists only for plugin workflows in PR 4). Also the owner reply format that stage 0 "reads" is not defined. Fix: add to stage 0: the lead writes `build.js` from section 5, runs it with `args.dryRun` (stub agents) to prove it compiles and routes, commits it, and shows the owner its path; define the paste-back first line and fields for the review page's reply (kept PRs, changes as plain sentences).

**Medium** — Roleplay (VISION). The vision says "Military ranks set the tone for roles given their influence in the project." The plan gives names (Commander, Pilot, Officers, Crew) and says "each agent description opens with its rank" and the static check enforces it, but never lists the ranks: what rank is the scout, worker, reviewer, adversary, imposter or librarian, and what does influence mean for rank? Without a table the check cannot be written and the pages cannot carry it. Fix: add a short rank table (rank, agent, model tier, what it may decide), with influence tied to tier (Opus decides and checks, Sonnet builds and reviews, Haiku scouts), and make the static check read the table.

**Medium** — Workshops (VISION). The vision lists "Agent output, reports, plans, state, decisions, truth, logs, verification. Branch isolated." The plan's workshop has card, constraints, questions, decisions and attempts (brief, report, findings, pages); it says "there is no state file", has no named place for plans or logs, and does not say what "branch isolated" means: whether a workshop is tied to one git branch, and what happens when two branches edit the same workshop. Fix: state the mapping in one paragraph (plans live in `attempts/<k>/brief.md`, logs in `report.md`, verification in `findings.md`, state is derived from folders) and say how branch isolation works (each attempt branch only touches its own attempt folder; a workshop's `constraints.md` is edited on the base branch only).

**Medium** — Human energy and Manuals (VISION), versus PR order. The vision wants "rubrics, policies, schemas, templates, examples, manuals, library". Rubrics arrive in PR 7 (`library/rubric-guide.md`), yet reviewer, adversary and imposter judge every PR from PR 1 with no rubric; "policies" and "schemas" are not a deliverable anywhere; the librarian (reviews work against the corpus) is not wired into any launch or build stage, so "mid tier agents preside over the corpus, reviewing work against it" exists as an agent but not as a step. Fix: move a one-page rubric (yes-is-pass questions per role) into PR 1 and have the reviewer read it, name policies (the ceiling, push rules) and schemas (question block, findings) as files under `templates/` or `library/`, and add an optional "librarian check" stage to `build-and-check.js` (PR 4) or say it is deliberately later.

**Medium** — Section 3.7 versus section 3.1. The static check fails "if any shipped file calls `dw` or `dev-workspace`", but root `CLAUDE.md` (PR 1) must say "use `dw` where installed and plain git otherwise", and the manuals, README and build-1 decisions will mention dev-workspace. As written the check fails PR 1 on its own CLAUDE.md. Fix: narrow the check to executable content (hooks, workflows, `bin/`, scripts) and allow mentions in prose.

**Medium** — Section 3.9 and 3.8 static scan versus the scripts that do the scanning. The scan must find no `fable`, `best`, `xhigh`, `max` or `ultracode` in `agents/`, `skills/`, `hooks/`, `workflows/`, `output-styles/`, `templates/`, `lab/`, but `hooks/guard.mjs`, `hooks/tests/hooks.test.mjs`, `lab/checks/static.mjs` and `skills/launch/tests/workflows.test.mjs` must contain those words to detect them, and the recipes say "no ultracode". The word `max` is also ordinary text ("maxTurns", "max-cost-usd"). Fix: scan only structured values (`model:`/`effort:` keys and quoted option literals), exclude the checker and test files by path, and test the scanner with a planted bad file.

**Medium** — Section 3.5 and PR 4 try. The first PR 4 try step is `/flight:second-opinion README.md`, which depends on plugin workflows running as `/flight:<name>`, a feature the plan marks unverified, and the fallback ("run it by path, README says so") edits a PR 1 file. If it fails, the owner's first step fails. Fix: PR 4's try leads with `/flight:launch` (a skill, certain to work) and the script-by-path form, and uses `/flight:second-opinion` only as "also try", with the probe result recorded in the PR body.

## Low

**Low** — Section 3.6 versus VISION "Local CLI". The vision says agents can "manipulate and read the flightdeck" and "start web servers, bulk commit". The CLI is read-only except `commit`: it cannot create a workshop, open an attempt or file an answer, and it only exists on the PATH inside Claude's Bash tool (the owner's own shell needs `node bin/flight`). Acceptable for a first cut, but the review page should say it is deliberately small, and `flight new <title>` and `flight answer` are the obvious next two (the scaffold already exists in PR 3).

**Low** — VISION "Themed HTML page suite" and "Quality". The vision says "prompt builder and other ai tools" and "teams purpose built to improve the flightdeck". The plan builds one tool (the prompt builder) and a team drill; there is no standing improver team or second tool. State on the review page that these are left out on purpose, or add the cheapest one (a "review this page" tool using `second-opinion`).

**Low** — Section 5 "Numbers". Run B is estimated at about 10 agents per PR, but the stage list gives gather, brief, up to 3 builders, integrate, 3 verifiers, checks, triage, fix, recheck, land, which is up to 15 per PR, about 105 plus 3 for seven PRs. Fine against the cap, but the review page should give a rough Opus/Sonnet/Haiku mix and a cost class per PR, because the owner's concern is the 20X subscription, and the plan only promises estimates for launches, not for the build itself.

**Low** — Section 4 intro versus section 6. The "don't wait for me" option (cut PRs 2 to 8 from PR 1's branch) removes the guarantee that Run B is flown by merged, tried parts and stacks the diffs, which the plan elsewhere calls a judge problem it fixed. Also a PR 1 retry after Run B has started would conflict with PRs 2 to 8 (section 4 PR 1 "Nothing else needs re-cutting" holds only before Run B). Fix: drop the option or state its cost on the review page; say a late PR 1 retry means rerunning the dependent PRs.

**Low** — Section 3.4 truth guard. The guard stops subagents, but the main conversation in the owner's session (including the lead itself) writes `constraints.md` freely, so "only the owner's words" is advice in the pilot body, not a check. The stage-0 step writes owner changes "in the owner's own words" with no way for the owner to see the exact lines before they land. Fix: the writing step prints the exact lines first and the owner says yes, and `constraints.md` lines carry the date so a wrong line can be found and deleted.

**Low** — build.txt "rules". build.txt lists "rules" among the basic PR's Claude Code content. The plan ships rules as nested `CLAUDE.md` files and nothing in `.claude/rules/` (with good reason: plugins cannot ship rules and dev-workspace owns that folder). The review page should say this in one line so the owner does not think "rules" was skipped; also note `.claude/rules/context.md` imports a file that does not exist, as the risks list already does.
