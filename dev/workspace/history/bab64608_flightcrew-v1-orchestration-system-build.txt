what is fc commands?

------------------------------------------------------------

[ASSISTANT 💬]
`fc` is the single command-line runner the system ships, at `flightdeck/flightcrew/bin/fc`. It's the one surface a human or the orchestrator uses to drive a launch, so nothing has to be remembered beyond one entry point. It's invoked by path (nothing is installed), and every command exits 0 on success, 1 on a usage or environment error, 2 on a failed check or a blocking decision.

The commands, grouped by what they do:

- **Launch lifecycle:** `fc launch new <spec>` opens a run folder and pins the frozen spec; `activate`; `pin tests-map`; `phase <next>` moves through targets, plan, contracts, implement, verify, review, report; `gate G1|G2|G3 approve|exit` records your decisions; `escalate` halts the run for a human question; `end <outcome>` is the single ending and renders the report; `land` records the merge.
- **Verification:** `fc check` runs the locked checks and captures raw output as evidence; `boundary` lists files changed outside the allowed paths; `locked` lists changes to locked targets; `budget` compares event counts to the run's ceilings; `verify` runs all four.
- **Documents the run produces:** `fc plan write|render`, `evidence` (the HTML page you read at gates), `report` (the run report with provenance marks), `runlog stub` (the run-log entry with mechanical fields filled).
- **Dispatch and returns:** `fc worker render <unit>` builds a worker's sealed prompt; `worker merge` lands a worker's branch; `critic render` and `verifier render` build sealed prompts for the judges; `return <kind>` validates and stores a structured return.
- **Validation and harness:** `fc validate`, `fc lint spec`, `fc distribute` (copies crew and workflows into `.claude/` only when you pass `--apply`), `fc doctor`.

The hooks and the testbench call the same commands, which is why the suites can prove the whole journey end to end. The build workflow currently running is what implements it.

[ASSISTANT 💬]
Both, split by purpose, and the split follows the `tests.keep` note in that folder ("reusable across the git branch… do not store launch test results here").

**Universal (what lives in `testbench/`):**

- **The runner and library.** `run-all.mjs` and `lib/suite-lib.mjs` are the harness every suite uses: protocol, temp-dir hygiene, git snapshots, fixture builders, process runners. Any future suite for anything in flightdeck uses them.
- **The 29 suites.** They test the flightcrew system itself: the `fc` runner, hooks, validators, crew frontmatter, templates, workflows, manuals constraints. **Per-launch (what does not live there):**

- A real project's checks belong to the spec: `launch/specs/<name>/checks/` for scripts with no natural home, or the project's own test directory, mapped by the frozen tests-map.
- The results of running those checks are evidence and belong to the launch folder: `launch/<L>/evidence/`.
- The one gray area is this build itself: because the thing being built is flightcrew, the system's own tests-map points at the testbench suites as its T1 through T29. That is a property of this launch, not a rule. A launch that builds, say, a Rails feature maps its T ids to that project's test commands, and the testbench never sees it.

So a future run never adds to `testbench/` unless it changes flightcrew and needs a regression test for that change.
