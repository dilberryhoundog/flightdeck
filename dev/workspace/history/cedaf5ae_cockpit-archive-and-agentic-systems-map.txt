## What both missed

1. **Agent view is close to a native cockpit.**
   - `claude --agent <definition> --bg "<prompt>"` starts a background session, isolated in its own worktree by default. It commits, pushes or opens a draft pull request, and ends with a report.
   - The docs name `claude agents --json` as the supported way for "another Claude session that supervises background work" to read state.
   - Background sessions outlive the session that started them.

   The primers built everything inside one team session, around "one team per session, the lead is fixed, teammates are lost on resume". With background sessions, the lead dispatches sessions and supervises them. A team that needs peers runs inside its own dispatched session. The lead's own session can be short and disposable, and "pick up where I left off" becomes the session list plus reports on disk. `pilot.sh` already calls `claude agents --json`, but only to check whether a pilot is running.
2. **Mods.** These are hooks that load once and stay inside the session.
   - They can keep state, deny a call with a reason, register tools and slash commands, and draw UI.
   - `e.agentId` tells the main session's turns apart from subagents'.
   - `claude plugin test` runs a mod's tests against the real runtime.

   That gives four things:
   - A lock on the lead that doesn't also hit builders. A lock in settings would hit both.
   - Typed tools in place of prompted markdown formats. "Seeing like an agent" found prompted formats unreliable ("append extra sentences, drop options, or abandon the structure").
   - Automatic capture of denials and subagent turns, with no agent writing anything.
   - A live display of what's running and what's waiting on you.

   Caveats:
   - Mods need Claude Code 2.1.287; this machine has 2.1.283.
   - The API can change between releases.
   - The mods post calls them "a safety net, not a permission system". Hard blocks stay in permission rules.
3. **Compose a harness per task instead of keeping a catalogue.** The dynamic-workflows post says Claude "is now intelligent enough to write a custom harness tailor-made for your use case", and static harnesses come out generic. Both sides built catalogues: the cockpit has 44 seats, rosters and a team-builder team; the primers have 16 shapes, 8 bodies and lens cards. A Fable lead can compose a workflow from a handful of real agent definitions each time, and save one (`s`) only when it recurs.
4. **Less instruction, not more.**
   - Anthropic cut over 80% of Claude Code's system prompt for Fable and Opus 5 "with no measurable loss": "we were overconstraining".
   - The eval post's first hillclimb win came from removing "mandatory tool-call rituals, a scratchpad step, and contradictory rules".

  Strength scale: strong = first-party data or independent convergence; moderate = credible account with examples; thin = vendor, single post, or documentation without outcome data.
  
  ## 1. Improvement practices
  
  **Automated agent evals.** Run a task, score the transcript or end-state with code, model or human graders. Anthropic describes it from Claude Code and from Descript and Bolt, which built suites. "Demystifying evals for AI agents" (anthropic.com/engineering/demystifying-evals-for-ai-agents, 9 Jan 2026): code graders are fast but brittle, model graders flexible but need calibration, humans slow; start with 20-50 tasks from real failures; CORE-Bench went 42% to 95% after grading bugs were fixed. It separates pass@k from pass^k (75% per trial gives 42% for three straight passes) and capability evals (low pass rate) from regression evals (~100%), with saturated capability evals graduating into regression. Strength: moderate (convergent guidance and anecdotes; no controlled study that evals improve outcomes). Cost: moderate to build, cheap to rerun; maintenance recurs.
  
  **OpenAI's guidance** (undated pages, fetched Oct 2026). "Evaluation best practices" (developers.openai.com/api/docs/guides/evaluation-best-practices): evaluate early, log everything to mine cases, judge pairwise or pass/fail, handle position and length bias, validate judges against human labels. "Evaluate agent workflows" (.../guides/agent-evals): grade traces while debugging, then datasets and eval runs, then automatic prompt optimization. "Testing Agent Skills Systematically with Evals" (developers.openai.com/blog/eval-skills): 10-20 prompts, deterministic graders over `codex exec --json` traces plus rubric checks; no results. Strength: thin (documentation, no outcome data), but it converges with Anthropic. Cost: low.
  
  **Transcript and trace review.** Read full transcripts to tell an agent mistake from a grader rejecting a valid solution. Anthropic reads them routinely, built viewing tooling, and says manual review "doesn't scale" and suffers reviewer fatigue (same post). Strength: moderate (first-party practice, no measured effect). Cost: high per unit of coverage; weekly sampling advised.
  
  **LLM-as-judge with rubrics.** A second model scores checkable rubric claims, ideally pairwise, using a different model from the one under test (Anthropic hillclimbing post, claude.dev/blog/automating-eval-design-and-hillclimbing/, 28 Sep 2026; OpenAI agrees).
