Operator's manual · flightcrew

Driving a launch

You are not the builder. You open the run, approve three gates, read what comes back, decide what a halt means, and write the ending. This is the sequence you type and the judgements only you can make — the design's own division of labour, from the operator's seat.

§1

Your seat

Everything in flightcrew is arranged so that the interesting decisions land on you and the tedious ones don't. Agents write code, tests, plans and findings. You do exactly five things:

YouWhere it happens
Freeze the targets — decide the spec is right and the tests are fairbefore the run
Approve the plan — gate G1after fc plan write
Approve the shared surface — gate G2after wave 0 lands
Judge a halt — is the check wrong, or the code?any time a unit stops
Call the outcome — gate G3 and the run logat the end
The one rule that shapes everything

The system never tells you whether the run succeeded. report.md lays out what was mechanically checked, what an agent reviewed, and what was merely asserted — each labelled — and stops there. The verdict is yours, and it is the reason the gates exist.

Commands are run from the repo root, and fc is invoked by path — it is never on your PATH:

flightdeck/flightcrew/bin/fc launch status no active launch

Throughout this manual I write it as fc for brevity. Exit codes are consistent everywhere: 0 fine, 1 you asked wrong, 2 it is refusing you on the merits.

§2

What you can poke at safely

Before touching anything that changes state, know which half of the command surface is free. This is the most useful thing to learn first — nearly every "am I stuck?" question is answerable without changing a thing.

Run these freely

  • fc launch status — where am I
  • fc doctor — is the install whole
  • fc events summary — what happened
  • fc runlog show --spec <S> — past runs
  • fc validate <kind> · fc lint spec
  • fc evidence · fc report · fc plan render — pure re-renders
  • fc distribute without --apply — dry run
  • fc check · boundary · locked — overwrite evidence with current truth; re-running is how you clear a stale-evidence refusal

These change state

  • fc launch new — no delete command exists
  • fc launch phase · gate — append-only, no way back
  • fc worker merge — a real git merge, removes the worktree, deletes the branch
  • fc return … — overwrites the stored return for that id
  • fc launch end — final for that launch
  • fc budget — harmless to read, but appends a trigger event if a ceiling is exceeded, which then blocks phase moves
Worth knowing early

fc launch status warns you when the newest event is 24 hours old. Picking a run back up after a break, that line is how you tell "actively running" from "abandoned mid-flight".

Step A

Pre-flight — before a launch exists

You need a spec and a tests map, both frozen. Freezing is a human act: you set status: "frozen" and record the commit. No agent does it. These three commands are how you check you're entitled to.

# is the spec ready for a human to freeze? fc lint spec flightdeck/launch/specs/<S>/spec.v1.json --repo . # rehearse the freeze gate against a still-draft file fc validate spec flightdeck/launch/specs/<S>/spec.v1.json --for-freeze # and the map that will lock the build fc validate tests-map flightdeck/launch/specs/<S>/tests-map.v1.json

The linter is the one that catches what a schema can't: an open question still hanging, a file path named in the spec that doesn't resolve, a command in the verification text that isn't actually on PATH, a behaviour whose id appears nowhere in the verification section. It also warns — without failing — when a behaviour leans on unfalsifiable words like "robust" or "gracefully".

If the map's baselines have never been recorded, that happens here too, before any launch exists:

fc check --baseline flightdeck/launch/specs/<S>/tests-map.v1.json writes observed baselines into the map file itself, no evidence, no launch needed
Step B

Open the launch

B1Create the folderphase: targets
fc launch new flightdeck/launch/specs/<S>/spec.v1.json \ --kickoff base+shape-session+task-feature export FLIGHTCREW_LAUNCH=<name>

It prints that export line for you to run verbatim. Everything after this point acts on that launch.

Choose the kickoff parts deliberately — they set how the run is conducted, and the choice is recorded in three places for traceability. Default is base+shape-session+task-feature.

shapePick it when
shape-sessionEvery parallel wave fits inside the concurrency ceiling. One session dispatches subagents directly. Start here.
shape-workflowA wave holds more units than the ceiling. Hands the fan-out to a workflow script; you keep the gates.
shape-sessionsThe work needs hours rather than turns. Split across sessions, one conducting session owning the gates.
task typePick it when
task-featureBuilding something new. Vertical cuts, one behaviour per unit.
task-migrationA mechanical sweep. Units convert call sites as they stand and name defects rather than fixing them inline.
task-auditNo code changes. Cut by question; each unit needs a check that reproduces its finding.
task-agentBuilding a prompt, agent or workflow whose output varies between runs.
B2Pin the tests mapsets the lock
export FLIGHTCREW_LAUNCH=<name> fc launch pin tests-map flightdeck/launch/specs/<S>/tests-map.v1.json tests map pinned: <path> @ <commit>; lock <short> allow these commands so the checks can run: Bash(<command>)

This is the moment the run acquires teeth. It sets the allowed and locked path globs, flips boundary enforcement on, and records lock_commit — the baseline every later diff, boundary check and critic pass is measured against.

Paste the printed Bash(…) lines into your permission allowlist so the checks can actually run.

B3Activatedraft → active
fc launch activate launch <name> is active in phase targets

Only one launch may be active at a time. If the spec or map aren't frozen this refuses — --allow-draft waives it while you're still iterating, and stamps the launch so every later report says so.

Step C

Plan, then gate G1

fc launch phase plan # dispatch the planner agent, then store what it returns fc plan write plan.json (or --stdin) plan written: flightdeck/launch/<name>/plan.md

fc launch phase plan is the first command that can refuse you on the merits. It checks the spec and map are frozen, that launch.json and kickoff.md both validate, and — easy to miss — that every check's recorded baseline agrees with what the map predicted. A check that was supposed to fail on an empty tree and actually passed will stop you here.

fc plan write validates before it writes. An invalid plan leaves nothing on disk at all, so you can retry freely.

G1Is this plan worth running?

Read plan.md against the spec. The machine has already checked that every check id exists and every dependency points backwards. What it cannot check, and you must:

  • Does every unit own files no other unit writes? Overlapping ownership is the single most expensive planning mistake — it surfaces as merge conflicts in the last wave.
  • Is wave 0 genuinely the shared surface? If a type or library that six units need isn't in the contracts unit, you'll find out four waves later.
  • Are the abandon triggers observable? Each must name a command, an event or a file. "The run is going badly" isn't a trigger.
  • Is the pilot the right unit? It should be the riskiest thing in the wave, not the easiest. It is never the contracts unit.
fc launch gate G1 approve --note "plan read against spec; unit ownership disjoint; triggers observable" gate G1 approved; phase plan → contracts

The approve moves the phase for you. The note goes into the permanent record — write it for the person reading the report later, which is often you.

Step D

Contracts, then gate G2

One unit runs, alone: the one that lands the schemas, types and libraries everything else imports. Dispatch and land it exactly like any other unit.

fc worker render U0 # prints the sealed dispatch; give it to an implementer fc return worker ret.json --unit U0 fc worker merge U0 merged: U0 from <branch> at <commit>
G2Is the foundation sound?

The command refuses to record this approval unless wave 0's checks are green and ran at or after the lock commit — stale evidence doesn't count. So the mechanical question is already settled by the time you're asked.

What you're actually judging: six agents are about to build on this surface in parallel. Is it right? A wrong shared type discovered in wave 3 costs the whole wave. This is the cheapest moment in the run to change your mind.

fc launch gate G2 approve gate G2 approved; phase contracts → implement
Step E

Implement — per unit, per wave

Three commands per unit, repeated. Waves run in order; the pilot in each wave goes first and alone.

fc worker render U1 # sealed prompt → returns/U1.prompt.md # dispatch to an implementer; it works in its own worktree and branch fc return worker u1.json --unit U1 # schema-validated; invalid is never stored fc worker merge U1
What merge actually does

It stages with --no-ff --no-commit, re-runs the unit's checks against the merged tree, and only then commits. A unit passing in its own worktree proves nothing about the tree everyone else is building on. On conflict or a red re-run, the merge is aborted and nothing is left dirty.

Merge refuses unless the return is green, every dependency is already merged, and the repo is checked out on the run branch. That last one catches people out — check with git branch --show-current if merge says the repository is on the wrong branch.

A halt from any unit stops the whole wave, not just that lane. See §3.

Step F

Verify

fc launch phase verify fc verify verify: 29 pass, 0 fail, 0 error, 0 skipped; boundary clean; no locked change; within budget

Four stages in order — every check, then the boundary, then the locks, then the budget. All four must be clean. The locks stage is the one that catches a shell write the edit guards never saw, so don't skip straight to reading the check counts.

Optionally dispatch a verifier to independently re-run everything and try to break the result:

fc verifier render # needs fresh evidence at HEAD fc return verifier v1.json --pass 1

Its verdict is one boolean, refuted, true only if a check didn't reproduce, a locked path changed, or something landed outside the boundary.

Step G

Review, then gate G3

fc launch phase review fc critic render --pass 1 fc return critic pass1.json --pass 1

The phase move refuses on a dirty run: it wants fresh evidence at HEAD with zero failures, a clean boundary and no locked changes. If it refuses, re-run fc verify — that's usually all it takes.

Findings come back typed. What you do with each:

kindYou
correctness-gap blockingRoute to the implementer owning the unit whose paths hold the file. Re-verify, then take a fresh pass.
scope-violation blockingSame routing — the unit wrote outside its lines.
spec-conflict blockingDo not attempt a fix. Escalate. The spec itself is in question, and that is a between-runs decision.
observation non-blockingfc launch note and move on. It surfaces in the run log later.

Record a resolution without touching the frozen pass file:

fc return critic --resolve F1 --commit <sha> fc return critic --resolve F2 --dispute "the locked-path change was your v2 re-pin, not a run edit"

Review ends when a pass comes back with no gaps — or when you hit the pass ceiling with blocking findings still open, which is itself an abandon trigger. Not another pass, and not on to the report.

G3What is this run worth?

No blocker runs for G3 and it moves no phase. It is purely your recorded decision, and the report deliberately refuses to make it for you. Read, in this order: the Ledger (what merged, what stayed open, what was attempted and discarded), Verification (the raw counts), Review (findings joined with their resolutions), then Failures and interventions.

The question isn't "are the tests green" — you already know that. It's would I be comfortable defending this diff to someone who didn't watch it happen?

fc launch phase report fc launch gate G3 approve --note "…"
Step H

End it, and write the log

outcomeRequires
acceptedFresh evidence at HEAD, clean tree under the allowed paths (the launch's own folder is exempt).
accepted-with-reservationsMechanically identical to accepted. The difference is entirely your judgement — and the run log then asks you to name the reservation.
abandonedNothing. Add --at verify or --at G3 to record where it died.
partial--units U0,U1. Each kept unit needs a green return or a merge event, its dependencies kept too, and no open blocking finding under its paths.
fc launch end accepted-with-reservations → rewrites evidence.html and report.md → inserts a stub into flightdeck/launch/RUNLOG.md → prints the worktree and branch cleanup commands → prints the path to report.md
Two things it will not do for you

Cleanup is manual. It prints git worktree remove … and git branch -D … lines; you run them.

The run log stub is deliberately incomplete. Mechanical fields are filled in, but the diagnosis fields arrive as literal <fill> — cause, change, watch, kept, promote. That is your writing, and the planner reads it before cutting the next run for this spec. Fill it before you start the next version, not after.

Once the work lands on your main branch, record where:

fc launch land --commit <sha> --pr <url>
§3

Halts — a unit gave up

A halt is not a crash. It is the schema-enforced way an implementer says "I stopped, and here is why" rather than faking a pass. Any halt stops the whole implement wave, so you will be dealing with it immediately.

halt.kindMeansYou
test-contradicts-specA locked check asserts something the spec doesn't require, or contradicts it.Read the detail. Verify it against the spec text yourself. If the agent is right, escalate wrong-check — you cannot fix it in-run, the file is locked.
unsatisfiableNo faithful implementation could pass this check, regardless of who's wrong.Same. This is between-runs work: a new tests-map version.
blockedA permission it needed was denied.Check events.jsonl for PermissionDenied, lock_denied or boundary_denied near the halt timestamp to see what was actually refused.
budgetOut of turns. Also what you get automatically when a return is absent or malformed.Decide which: was the unit too big for its turn budget (fix the plan), or did the agent loop unproductively (read the transcript)?
boundaryTried to write outside its allowed paths.Almost always the unit's paths in the plan are too narrow. Fix the plan, don't override the guard.
The trap

Your instinct on test-contradicts-spec will be to just fix the test. You can't — the lock guard refuses, by design, because a worker that can edit its own assertion isn't being tested. Judge the claim on its merits instead. On the first real run of this system, the agent was right both times.

§4

Escalating

fc launch escalate wrong-check --detail "T11 expects 2 added lines; git numstat reports 3 under every counting mode"

Escalation is the one command whose job is to release a block. Writing one does three things: creates escalation.json, appends an escalation event, and re-renders the evidence page.

Its effect is immediate and broad — the stop gate checks for an open escalation first and releases the turn unconditionally, and a fired abandon trigger is silenced by any newer escalation event. A human's escalation always beats a red gate.

kindRaise it when
wrong-checkA specific check tests the wrong thing. The usual companion to a confirmed test-contradicts-spec halt.
spec-gapThe spec is silent or ambiguous about something the run needs decided.
blockedSomething outside the run — permissions, tooling, environment — is stopping progress.
triggerYou looked at a fired abandon trigger and decided to continue anyway.
budgetA ceiling has bound and continuing needs your decision, not a retry.
haltA worker halt that isn't cleanly one of the above, recorded as-is for the record.

You don't clear an escalation directly. It disappears on its own the next time you record a gate decision, move a phase, or end the run. So the shape is always: escalate → do the human thing the detail called for → advance.

§5

Stuck, stalled, and triggered

An agent's turn keeps getting blocked

The stop gate only runs in verify and contracts. When it blocks, you see the failing check id, its exit code and the last 20 lines of its output, and the turn ends.

Don't just keep hitting continue. The same check re-fails up to eight consecutive times — a hard ceiling regardless of what the launch config says — and then the gate gives up, records a stall, fires an abandon trigger and releases the turn anyway. You've spent eight turns to arrive at a worse position. Read the output at the first block and decide whether it's a real bug or a test-contradicts-spec situation. If it's the latter, escalate immediately.

An abandon trigger has fired

Two things fire one: the stall above, or fc budget finding a counter over its ceiling. While a trigger stands, the run is frozen — every edit is denied, no phase moves except to ended, and worker render and merge both refuse.

Two ways out. Record any gate decision, phase move or escalation — a newer event silences it and work resumes. Or, if the cause is real, end the run.

The session died mid-run

Nothing is lost. A launch's entire state is on disk — launch.json is where you were, events.jsonl is what happened, escalation.json is what's still open. Run fc launch status and pick up. Watch for the staleness warning.

§6

Why it just refused you

Exit 2 means it is refusing on the merits. The common ones, and the fix:

It saidFix
evidence/summary.json is absent; run fc verifyRun fc verify.
evidence/summary.json is at <x>, HEAD is <y>You committed after checking. Re-run fc check all (or fc verify).
<id>: observed <x> where the map expects <y>A baseline disagrees with its prediction. The map is wrong, or the tree isn't what the baseline was taken against.
abandon trigger <name>: end or exit the launchSee §5 — record a gate, phase or escalation, or end it.
<U>: the stored return is halt, and only a green return is mergedDeal with the halt. Merging isn't available.
<U>: the repository is on <x> and the run branch is <y>git switch <run branch> before merging.
<U>: <deps> not merged yetMerge dependencies first — waves are ordered for a reason.
illegal phase change: <a> → <b>; the next phase is <c>You skipped. --force exists but also skips the blocker checks, so know why.
two launches are active: X, YPass --launch <name> or set FLIGHTCREW_LAUNCH.
spec not frozen: … pass --allow-draftFreeze it, or accept a draft run knowingly.
working tree not clean under allowed pathsCommit or stash before ending. The launch's own folder is exempt.
<kind> return does not validateThe agent returned a malformed document. Nothing was stored — fix and re-submit.
§7

Flags and environment worth knowing

flagWhen you actually need it
--allow-draftIterating before a real freeze. Stamps the launch so every report says so.
--forceOn phase it skips both the ordering check and the blockers. On gate it re-records a decided gate. Know why before using.
--kickoffOn launch new — anything other than a plain session/feature build.
--branchSets the run branch (default run/<name>). Merge refuses unless you're on it.
--baselineOn fc check — record a draft map's baselines before any launch exists. Writes no evidence.
--for-freezeOn validate spec — rehearse the freeze gate against a draft.
--strictTurns validator warnings into failures. Use right before freezing, not while drafting.
--baseOn boundary/locked — measure from a commit other than the lock.
--at / --unitsOn launch end — where it died; which units a partial keeps.
--jsonAnywhere. Swaps the one-line output for a structured document.
--launch <name>Act on a launch other than your exported one, for one invocation.
variableSet it when
FLIGHTCREW_LAUNCHRight after fc launch new prints it. Also whenever two launches are ambiguous.
FLIGHTCREW_LAUNCH=noneDeliberately force "no active launch" — running launch-independent checks without picking up whatever is active.
FLIGHTCREW_ROOTInvoking fc from outside the repo and you want certainty about which repository it acts on. Overrides everything.
CLAUDE_PROJECT_DIRSet by the session. It is what hooks use exclusively — unset, a hook is a silent no-op.
Not an fc flag

--only belongs to the testbench runner, not fc: node flightdeck/testbench/run-all.mjs --only manifest runs a single suite. Handy — the full bench takes minutes.

§8

The whole run, on one card

# ── pre-flight ───────────────────────────────────────── fc lint spec <spec> --repo . fc validate spec <spec> --for-freeze fc validate tests-map <map> ← you freeze both, by hand # ── open ─────────────────────────────────────────────── fc launch new <spec> --kickoff base+shape-session+task-feature export FLIGHTCREW_LAUNCH=<name> fc launch pin tests-map <map> fc launch activate # ── plan ─────────────────────────────────────────────── fc launch phase plan fc plan write plan.json fc launch gate G1 approve --note "…" ← YOUR CALL · → contracts # ── contracts ────────────────────────────────────────── fc worker render U0 → dispatch → fc return worker … --unit U0 fc worker merge U0 fc launch gate G2 approve ← YOUR CALL · → implement # ── implement · per unit, waves in order ─────────────── fc worker render U<n> → dispatch → fc return worker … --unit U<n> fc worker merge U<n> # ── verify ───────────────────────────────────────────── fc launch phase verify fc verify checks · boundary · locked · budget fc verifier render → fc return verifier … --pass 1 # ── review ───────────────────────────────────────────── fc launch phase review fc critic render --pass 1 → fc return critic … --pass 1 fc return critic --resolve F1 --commit <sha> # ── end ──────────────────────────────────────────────── fc launch phase report fc launch gate G3 approve --note "…" ← YOUR CALL fc launch end <outcome> ← YOUR CALL ← you fill RUNLOG.md <fill> fields ← you run the printed cleanup commands fc launch land --commit <sha> --pr <url>
Learn from the two runs already on record

The first build of this system was abandoned at verify — two locked checks were genuinely wrong and no code could satisfy them. The second was accepted with reservations, carrying four spec conflicts forward to the next version rather than forcing a clean pass. Run fc runlog show before you plan anything; that is what it's for, and the planner reads it too.
