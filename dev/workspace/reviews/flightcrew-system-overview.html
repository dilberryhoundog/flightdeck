Inside Flightcrew

Flightcrew is the orchestrated half of FlightDeck: a system for having AI agents build software against a specification that was frozen before any of them started, and proving afterwards that they actually did. This page walks the whole thing from the outside in — what a run is, who does the work, and what stops an agent from marking its own homework.

scope · flightdeck/ 29 locked suites 10 crew roles 2 real runs on record
§0.1

The idea in one page

In plain terms

Ask a capable AI agent to "build this feature" and you get code plus a confident claim that it works. Flightcrew's whole design is a refusal to take that claim at face value. It splits the job into two halves separated by a hard freeze: first you write down exactly what must be true and how it will be tested, and lock those files; then agents build against them without being able to edit either one.

Everything else — the folders, the hooks, the ten agent roles, the twenty-odd commands — exists to make that separation hold under pressure.

The unit of work is a launch: one orchestrated run, living entirely in its own folder at flightdeck/launch/<name>/. A launch moves through eight phases in a fixed order, and pauses at three gates where a human — not an agent — decides whether it continues.

The eight phases of a launch, in order
1targetsSpec and tests map pinned to the run
2planWork cut into waves and units
↑G1Human reads the plan against the spec
3contractsWave 0 lands the shared interfaces
↑G2Human approves before the fleet runs
4implementUnits built in parallel, then merged
5verifyChecks, boundary, locks, budget
6reviewA critic hunts for gaps in the diff
7reportEvidence assembled, nothing judged
↑G3Human decides the outcome
8endedOutcome recorded, run log stubbed
phase — the machine advances gate — the run halts for a person

The phase list is not documentation prose; it is a literal array in the code (PHASES in checks/lib/launch-lib.mjs), and fc launch phase will only accept the immediately next one unless forced. You cannot skip verification on the way to a report.

Four documents, each frozen before the next is written

A run is really a chain of four documents. Each one is finished and locked before the next begins, so nothing downstream can quietly renegotiate what upstream decided.

DocumentAnswersWritten byLocked when
spec.v1.jsonWhat must be true when the work is donespec-builder, judged and attackedA human sets status: frozen and records the commit
tests-map.v1.jsonWhich commands prove each part of ittest-builder, before any code existsFrozen, then pinned to the launch — this sets lock_commit
plan.jsonHow this particular run is cut upplanner, once per launchApproved by a human at gate G1
kickoff.mdHow a run of this shape is conductedRendered from a template libraryVersion-stamped at render; never hand-edited

Notice the ordering trick: the tests are written before the implementation exists, and each check records a baseline — the test-builder's own prediction of whether it will pass or fail on the empty codebase, written down before it is ever run. A check that was supposed to fail and instead passed is itself a defect in the check.

§0.2

The map on disk

FlightDeck's top level splits into human-in-the-loop space and orchestrated space. Only two folders below are heavily built out today; the rest are staked-out ground with a one-line note explaining what they will hold.

flightdeck/ ├── missions/ ideas, decomposed — where a piece of work starts life ├── hangar/ the main agent loop's working directory (human-in-the-loop) ├── flightcrew/ the global assets every run uses — this page is mostly about here │ ├── bin/ the `fc` runner and one module per command │ ├── crew/ ten agent role definitions, one markdown file each │ ├── checks/ shared libraries, document validators, phase gates │ ├── hooks/ six scripts that intercept what an agent tries to do │ ├── schemas/ JSON schemas for every document the system writes │ ├── templates/ spec / plan / launch / dispatch / kickoff templates │ ├── workflows/ three scripts that fan agents out in bulk │ └── MANIFEST.txt every file the system ships, one path per line ├── launch/ the runs themselves, one self-contained folder each │ ├── specs/ the canonical home of every spec and tests map │ ├── RUNLOG.md cross-run history — read before planning the next run │ └── <launch>/ one orchestrated run, start to finish ├── testbench/ 29 locked regression suites + fixtures + the rubric bench ├── blackbox/ archives (placeholder for a later `archive` command) └── radar/ visualisation panels and decks (stubbed)

The important structural fact: nothing here is installed. fc is invoked by its path, hooks run in place, and only the crew definitions and the workflow scripts are ever copied out into a consuming project's .claude/ directory.

§0.3

The fc tool

In plain terms

fc is the one command anybody — human or agent — uses to touch a run. Agents in this system hold almost no write permissions; instead of editing launch.json they run fc launch phase verify, and instead of saving a result they run fc return worker. Every state change goes through a command that validates first and refuses cleanly.

flightdeck/flightcrew/bin/fc is a four-line shell shim that execs fc.mjs. Two flags work anywhere in the argument list: --json switches a command's one-line output for a single structured document, and --launch <name> forces which run to act on.

How it finds the run you mean

Two separate resolutions happen before any command body runs.

  • The root is the first of $FLIGHTCREW_ROOT, $CLAUDE_PROJECT_DIR, the git toplevel of the working directory, or the repository holding fc itself, that names a directory at all. The first one that names a directory settles it — if that directory has no flightdeck/launch/ under it, that is an error, not a reason to try the next candidate. A stated root can never be silently swapped for a different repo.
  • The launch is whatever $FLIGHTCREW_LAUNCH names, regardless of its status; the literal value none means "no launch, disable enforcement for this session". Only when that variable is unset does fc look for the unique launch with status: active — zero or two both being errors.

Exit codes carry the meaning

codeMeansExamples
0SuccessChecks green, document valid, merge landed
1Usage or environment errorBad flag, missing file, no launch resolves, two launches active
2A failed check or a blocking decisionTest failed, boundary violated, budget exceeded, invalid return, merge conflict

The convention on output is equally tight: one line on success, unless the command's whole purpose is a document or a listing — launch status, events summary, runlog show, the renderers, validate all and doctor are the named exceptions.

The full command surface

Two design details worth knowing. Validators are separate programs, not library calls — fc validate spawns checks/validators/<name>.mjs as its own process and adds nothing to its output, so the same verdict is reachable with or without the CLI. And one shared loader feeds both renderers: evidence.html and report.md read the launch folder through the same loadLaunchData(), so the two documents cannot disagree about what happened.

Phase 1

targets — the spec and the tests

In plain terms

Before a single line is built, two files are written, argued over, and frozen: a spec saying what must be true, and a tests map saying which commands prove it. Freezing means literally stamping the file frozen with the git commit it was frozen at. From that point the files are read-only for the rest of the run, enforced by a hook that refuses to edit them.

What a spec actually is

One JSON file of typed, ID-prefixed nodes across nine required domains. Every node carries a status, and any node that is not ok must carry a note explaining why.

idDomainHolds
INTintentThe outcome and why — exactly one
SCnscopeWhat is in and, just as importantly, what is deliberately out
CnconstraintsNon-negotiables about how
IninterfacesNamed contracts and types, each declaring what it reuses
BnbehavioursObservable, testable outcomes
EnedgesBoundary and failure cases, each stating an outcome
DndecisionsThings decided elsewhere or deliberately deferred
VERverificationHow the spec expects to be proven, behaviour by behaviour
ACCacceptanceThe conditions that end the work, and which paths may change
Qnopen_questionsUnresolved items — must be empty before a freeze

The system's own spec, flightcrew-v1, is a good sense of scale: 54 behaviours, 24 edges, 14 interfaces, 18 decisions, 9 scope entries and 9 constraints, frozen at commit 5f69a94.

Two rules give the spec its unusual discipline. IDs are permanent — a removed node moves to a retired list rather than disappearing, and live plus retired ids must together form an unbroken run from 1 to N per prefix. And a frozen file is never edited: a change means copying to the next version number, appending the old header to previous_versions, and starting again as a draft.

The adversarial loop that gets it there

Three agents, deliberately kept apart, cycle until the spec stops producing findings.

The attacker's rule against padding is telling: if a full pass finds nothing, it returns the literal string no findings, because "a manufactured finding costs a provider round and teaches the chain to ignore you."

What the readiness linter catches that a schema cannot

fc lint spec is separate from fc validate spec. The validator checks shape — ids, statuses, freeze invariants. The linter checks whether a human could responsibly freeze it. Nine failing rules and two warnings:

  • lint-domains — all nine domains non-empty, unless the spec says which is empty by decision and why
  • lint-open-questions — any open question at all fails
  • lint-sequential — ids form an unbroken sequence per prefix
  • lint-out-list — at least one scope entry is kind: out: what the spec is not is as much a boundary as what it is
  • lint-artefacts — every file path named in interfaces or verification must actually resolve in the repo, or be explicitly promised as a deliverable
  • lint-commands-run — every command named in verification must be an executable really on PATH
  • lint-claimed — every behaviour and edge id appears literally in the verification text, so every claim names its proof
  • lint-boundary — acceptance names at least one path glob, so the diff boundary is stated
  • lint-class-tags — for an "agent-shaped" product, every behaviour opens with [deterministic], [property], [statistical] or [judged]

Plus two warnings that never block: warn-impression flags a behaviour leaning on unfalsifiable words ("robust", "gracefully", "properly"), and warn-length flags a spec past roughly 12,000 characters or 60 nodes — beyond what a reader holds in one sitting.

The tests map, and what "locked" means

The tests map is the executable half: one check per T id, each naming the spec nodes it covers, the shell command that runs it, and a baseline — an expect written before running anything, and an observed filled in by the first baseline run.

The map also declares the two path sets that govern the whole run:

  • allowed_paths — globs a unit may write into.
  • locked_paths — globs no edit may touch once the run is past targets. In practice this covers the suite files, the fixtures, the map itself and the spec folder. An implementer cannot rewrite the test it is being judged by.

Coverage is enforced, not aspirational: every live behaviour, edge, constraint and interface node of the pinned spec must appear in some check's covers, or be explicitly listed under unverified with decided_by: "human".

How a wrong check gets fixed mid-run

This is not hypothetical — it happened on the first real run of this system. Two locked suite cases asserted values no faithful implementation could produce (T11 expected 2 added lines where git numstat reports 3; T24's import scanner matched a string literal). The implementer could not edit them, so the sequence was:

  1. The worker returned status: "halt" with halt.kind: "test-contradicts-spec".
  2. The orchestrator escalated with fc launch escalate wrong-check.
  3. A human decided the checks were wrong, not the spec.
  4. A new frozen tests-map.v2.json was cut — same 29 check ids, two marked status: "changed" with notes saying exactly what was wrong — and re-pinned.

The spec itself never changed; the pin still points at spec v1 at commit 5f69a94. That is the point of versioning the two documents independently.

Phase 1b

kickoff — opening the run

In plain terms

fc launch new creates the run folder and writes a kickoff — the standing instruction sheet the conducting agent follows for the whole run. It is assembled from a small library of parts rather than written by hand, so "how we conduct runs" is a versioned thing that improves across runs instead of drifting per run.

The division of labour between the four documents is stated crisply in the kickoff library's own README: the spec says what must be true, the plan says how this run is cut, the project constitution says how the project always works, and the kickoff says only how to conduct a run of this shape.

Three parts, always in this order

  1. A generated header — the launch path, spec and tests-map paths with their pinned commits, the assembled version string, a pointer to RUNLOG.md, and any prior reports for the same spec.
  2. base.md — what every run shares: the seven-step conduct sequence, the three halting gates, the escalate rule, roles, budgets, outputs, and a "never" list.
  3. One shape + one task type — see below.

Every part file opens with <!-- version: N -->, and the assembled kickoff's version is the joined list — for example base@1+shape-workflow@1+task-feature@1. That string is recorded in three places (launch.json, plan.json, and the run log entry), so any run traces back to exactly which conduct rules it followed. Improving conduct means bumping a part's version, not editing a rendered kickoff.

The three shapes — how units get dispatched

shape-session

One Claude Code session dispatches subagents directly, one per unit. The default, used when every parallel wave fits inside the concurrency ceiling.

gates halt the session's own turn
shape-workflow

The session keeps the gates and every fc command but hands a whole wave to a workflow script. Used when a wave holds more units than the ceiling allows.

both real runs used this
shape-sessions

The run is split across several sessions against one launch — one conducting session owning the gates, plus a session per stream of units.

for work needing hours, not turns

The four task types — how work gets cut

task-feature

Cut vertically, one testable behaviour per unit. Wave 0 is the single contracts unit; the last wave carries the acceptance check.

task-migration

A mechanical sweep. Wave 0 lands the new form plus a compatibility surface; the last wave deletes it and proves the old form is gone. A unit that finds a defect converts the call site as it stands and names the defect — it never fixes it inline.

task-audit

No code changes. Cut by question, each unit needing a check that reproduces its finding. Wave 0 builds a shared harness; later units write only into their own findings folder.

task-agent

For building agent-shaped products whose output varies run to run. Behaviours are tagged by evidence class, and a judged verdict is appended to the event log as a stated fact.

Selecting parts is a flag: --kickoff base+shape-workflow+task-feature. A rendered kickoff is then validated — its header must parse, its pointers must resolve, and every backticked role name under ## Roles must have a matching file in flightcrew/crew/.

Phase 2

plan — cutting the work

In plain terms

The planner reads the frozen spec and the pinned tests map and produces one document: how this run is cut into units (chunks of work owned by one agent) grouped into waves (things that can run at the same time). The governing rule is ownership: if two units must write the same file, they are one unit.

A unit names the spec nodes it makes true, the checks that prove it, the paths it alone may write, and which units it depends on. Dependencies may only point at strictly earlier waves — which is what makes a wave safely parallel.

fieldCarries
id / nameUnit id, and the branch suffix — the unit branch is <launch>/<name>
kindcontracts · feature · integration · proof
spec_refsThe behaviour and edge ids this unit makes true — its dispatch carries these and no others
checksCheck ids from the pinned map. Never empty
pathsGlobs this unit alone may write, inside the map's allowed paths
depends_onUnit ids in strictly earlier waves
pilotRuns first, alone, before the rest of its wave commits
budget_turnsTurn ceiling, capped by the implementer role's own declared maximum

Twelve coded rules validate a plan before it can be stored, and they cross-reference the other documents: a check id absent from the pinned map, a spec ref absent from the pinned spec, a dependency pointing sideways, a parallel wave wider than the concurrency ceiling, a turn budget above the implementer role's own maxTurns — each is a named, individually testable failure. The turn ceiling is genuinely read out of the crew file's frontmatter rather than hard-coded, so the plan can never promise an agent more turns than the agent is configured to take.

What a real plan looks like

This is the plan that built flightcrew itself — eight units across four waves.

plan.json is the source of truth; plan.md is rendered from it and never hand-edited — rendering the same JSON twice produces byte-identical markdown, which is itself an asserted behaviour of the system. fc plan write validates a candidate in a temporary file first and writes nothing at all if it fails.

The plan also declares abandon triggers — conditions that end the run — and each must name something observable: a command, an event, or a file. "The run is going badly" is not a trigger; "a worker return with status halt and an escalation event of kind wrong-check" is.

Gate G1 · the run halts here

A human reads plan.md against the spec: does every unit own files no other unit writes, does every check exist, are the abandon triggers observable? Nothing is dispatched until they approve.

Phase 3

contracts — wave zero

In plain terms

Exactly one unit runs first and alone: the one that lands the shared interfaces — the schemas, types and libraries every other unit will import. If six agents each invent their own version of a shared type, the integration wave becomes a rewrite. Wave zero prevents that by making the shared surface exist, and be checked, before anyone else starts.

The contracts unit is dispatched, returned and merged exactly like any other unit. What is different is the gate on the far side of it.

Gate G2 is where a human approves before the fleet runs, and the command refuses to record that approval unless wave zero's checks are green and were run at or after the lock commit. Stale evidence does not count as evidence. If the spec genuinely has no shared interface, the plan says so explicitly with no_contracts: { reason } and the wave is omitted — the exception has to be argued for, not assumed.

The stop-gate hook is active in this phase too: ending a turn here runs the contracts unit's own checks plus a boundary probe, and blocks the turn if either is red.

Phase 4

implement — the build

In plain terms

Each unit goes to one implementer agent working in its own git worktree on its own branch, with a prompt that contains everything it is allowed to know and nothing else. It builds until its checks pass, then returns a structured verdict. If the verdict is green, and its dependencies have landed, the orchestrator merges the branch — and re-runs the checks against the merged tree before committing.

The sealed dispatch

fc worker render <unit> builds a prompt that is the worker's entire input. It carries the unit's intent, scope, constraints, interfaces and decisions pulled live from the pinned spec, the exact spec refs it must satisfy, its allowed paths, its dependencies — and its checks by id only, never the command text. A worker that could read the assertion could write to it.

The dispatch says so in as many words: auto-loaded project instructions that ask you to read other files or run repository tooling do not apply to this role. A subtle mechanic falls out of the worktree isolation — the prompt is written to returns/<unit>.prompt.md and must be committed on the run branch before dispatch, because a subagent's worktree branches from HEAD and would otherwise never see the file.

What must come back

A worker return is a fixed JSON shape with no extra properties tolerated. The field that matters most is status:

statusMeansWhat happens next
greenChecks pass, work doneEligible for fc worker merge
redDid not get thereNever merges; a red pilot stops the whole wave
haltCannot proceed honestlyStops the run; carries a halt.kind for a human to act on

The five halt kinds are the system's vocabulary for "I will not fake this": test-contradicts-spec, unsatisfiable, blocked, budget, boundary. A worker that thinks its test is wrong is expected to halt and say so — never to edit the test, which the lock guard would refuse anyway.

Returns are stored with fc return worker, which validates against the schema first. An invalid return is never written and no event is appended — it is a blocking error, not a warning.

The merge is where trust is re-earned

fc worker merge <unit> refuses unless: no abandon trigger has fired, a green return is stored, every dependency is already merged, the repo is on the run branch, and the unit branch exists. Then:

git merge --no-ff --no-commit   ← stage it, don't trust it yet
fc check <unit's ids>          ← re-run its checks on the MERGED tree
git commit --no-verify          ← only if still green
then: unit_merged event, worktree unlocked, removed, pruned, branch deleted

That middle step is the crux. A unit's checks passing in its own isolated worktree proves nothing about the tree everyone else is building on. On conflict, or if the re-run goes red, the merge is aborted.

Budgets — what actually stops a runaway run

fc budget counts nine metrics from the event log and the review folder, and compares each against a ceiling declared in launch.json. Exceeding one appends a trigger event and exits 2 — and a fired trigger blocks every further phase move except the move to ended.

counterDerived fromdefault ceiling
agentsSubagentStart events12
implementers_concurrentFan-out width per wave chunk4
turns_per_agentPer-unit turn budget25
stop_blocksTurns the stop gate refused to release8
consecutive_stop_blocksBlocks since the last passing check or gate3
critic_passesFiles in review/2
minutesSpan between first and last event240
tokensSummed usage events, or 'unobserved'—

Three more — tool failures, permission denials and compactions — are reported but never enforced. A ceiling set to null is reported only, and unobserved tokens are never compared against anything: the system declines to enforce a limit on a number it did not actually measure.

Phase 5

verify — is the green real?

In plain terms

Every unit says it passed. Verification asks whether the tree as a whole passes, whether anything was written outside the lines, and whether the run stayed inside its budget. Then, optionally, a separate agent re-runs everything and actively tries to break the result.

fc verify runs four stages in a fixed order, and all four must be clean for exit 0:

  1. 1check allEvery check in the pinned map, each writing its own evidence file with exit code, verdict and the last 40 lines of output.
  2. 2boundaryEvery path changed since the lock commit, flagging any that falls outside the allowed and locked globs.
  3. 3lockedAny changed path matching a locked glob — the backstop that catches a shell write the edit hooks never saw.
  4. 4budgetThe nine counters against their ceilings, spawned as its own process so the counting lives in exactly one place.

The verifier's job is to fail

The verifier role opens with the premise: a green board is a claim, not a fact. It is deliberately denied the implementer's reasoning and the stored returns, because "a worker's account of why a check passes is exactly the claim under test."

It returns a verdict with one decisive boolean, refuted, set true in exactly three situations: a recorded check verdict did not reproduce when re-run; a locked path changed since the lock; or a change landed outside the boundary. Everything else it notices goes into supporting lists — unverified spec nodes, test_file_changes, outside_boundary, and free-text reasons — without on its own flipping the verdict.

Phase 6

review — hunting for the gap

In plain terms

Passing tests only proves the tests pass. The critic reads the whole diff against the frozen spec and asks a different question: is the thing actually built, is it in scope, were the tests weakened, are errors handled or just swallowed? It reports findings and fixes nothing.

Review cannot even start on a dirty run. fc launch phase review refuses unless the evidence summary exists, was written at HEAD, shows zero failures and errors, and the boundary and locked probes are both clean.

The critic's dispatch is sealed: the spec text at its pinned commit, the diff since the lock, the evidence summary and the locked-path change list are all inlined. It reads no repository file to obtain them. It works a fixed checklist in order — behaviours actually implemented (not merely asserted by a check), scope held, tests untouched, errors handled rather than suppressed — under the instruction to assume the diff contains at least one gap and look for it.

Findings and what happens to them

kindSeverityRouted to
correctness-gapblockingThe implementer owning the unit whose paths hold the file
scope-violationblockingSame — the unit that wrote outside its lines
spec-conflictblockingStraight to escalation. No fix is attempted — the spec itself is in question
observationnon-blockingRecorded as a note; sent to no agent. Surfaces later in the run log

A pass file is frozen once written. When a finding is later fixed or contested, that goes into a separate resolutions.json keyed by finding id, and the report joins the two at render time. The audit trail of what the critic originally said survives intact.

Each pass runs in a fresh context and is denied the previous pass's findings — a prior verdict would anchor this one. In the real second run, pass 2 raised six findings pass 1 had never mentioned, precisely because it was not looking at pass 1's list.

Review ends one of two ways: the critic returns no gaps and the run moves to the report, or the pass ceiling is reached with blocking findings still open — which is itself an abandon trigger. Not another pass, and not on to the report.

Phase 7

report — evidence, not verdict

In plain terms

The report has one unusual and deliberate property: it never says whether the run succeeded. It lays out what was mechanically checked, what was reviewed by an agent, and what was merely asserted by someone — each labelled — and leaves the judgement to the human at gate G3.

That labelling is built into the headings themselves:

HeadingprovenanceContents
Ledgerchecked · reviewed · statedOne row per unit: checks and verdicts, branch, merge commit, return status; plus what merged, what stayed open, what was attempted and discarded
VerificationcheckedStraight from the evidence summary counts
ReviewreviewedEvery critic finding joined with its resolution state
Phasesrecorded · statedThe phase and gate events as they happened
Agentsrecorded · statedWho was dispatched, and what came back
Failures and interventionsrecordedStop blocks, denials, escalations, triggers
Orchestrator notesstatednotes.md, verbatim

Every section shows a placeholder when its input never happened, so the document has the same shape for a run that barely started as for one that finished — you can always tell the difference between "clean" and "never ran".

Phase 8

ended — and what carries forward

A human ends the run with one of four outcomes: accepted, accepted-with-reservations, abandoned, or partial. For the accepted family the command first demands current, matching evidence and a clean working tree under the allowed paths; for partial it validates that the units being kept are dependency-consistent and carry no open blocking findings.

Ending then re-renders the evidence page and the report, and inserts a stub into flightdeck/launch/RUNLOG.md. The stub is the interesting part: mechanical fields are filled automatically, but the diagnosis fields arrive as literal <fill> placeholders — cause, change, watch, keep, promote. An entry is never silently complete. The symptom line is pre-filled from the recorded ending event and never hand-written.

The planner reads that file before writing a plan for the same spec. That is the loop that makes the system get better rather than just repeat: a run's failure becomes an input to the next run's plan. Cleanup is never automatic — the ending prints the worktree-removal and branch-deletion commands for a person to run.

The two runs on record

flightcrew-buildout
abandoned at verify

Escalated wrong-check: two locked suite cases could not be satisfied by any faithful implementation. A human cut tests-map v2 rather than letting an agent edit the tests.

flightcrew-buildout-2
accepted with reservations

Two critic passes, 22 findings between them. Reservations recorded rather than waved through — including that the run used a shared branch rather than per-unit worktrees.

Worth sitting with: the system's own first build run was abandoned by its own rules, and the second was accepted only with reservations, both recorded in its own run log. That is the machinery working, not failing.

§9

The crew

In plain terms

Ten roles, each one markdown file: frontmatter sets the model, the tools and the limits; the body is the system prompt. The single most important column in the table below is the last one — what each role is forbidden to see. A reviewer who reads why something was done will rationalise it rather than test it.

rolemodelJobMust not see
orchestratorinheritConducts the run; dispatches, records, holds gates open. Holds no write toolsWorker transcripts, the spec interview, a critic's reasoning
plannerfableCuts the spec into waves and unitsWorker transcripts, another launch's returns, the implementation
implementeropusBuilds one unit in its own worktree, 25 turnsThe plan, the kickoff, any other unit's dispatch or return
verifiersonnetRe-runs the checks and tries to refute the green boardImplementer reasoning, stored returns, the plan
criticfableReviews the diff against the spec; reports, never fixesThe plan, worker reasoning, earlier passes' findings
explorerhaikuAnswers one narrow factual question with citations and a confidence ratingAnything but the question and the paths it names
spec-builderfableWrites the spec via a structured interviewRepository source — every fact must arrive via a cited explorer return
spec-judgefableScores the draft against the rubric, yes/no with a required quotationEverything except two files: the rubric and the draft
spec-attackerfableFinds the holes before freeze; returns no findings if there are noneThe rubric, the standard, the interview
test-builderopusTurns a frozen spec into the tests map and the check scriptsA plan, an implementation, a prior run's returns

Only the implementer runs with worktree isolation and edit permissions. The verifier, critic, explorer, judge and attacker hold read-only tools — they physically cannot change what they are assessing.

The roster README states the principle once, for all of them: a role that reads the plan or another role's reasoning stops being an independent witness. The adversarial roles simply turn that isolation outward into an explicit mandate to find fault — the verifier against the evidence, the critic against the spec-versus-code claim, the attacker against the draft's completeness.

§10

Workflows and fan-out

In plain terms

When a wave holds more units than one session should juggle, the orchestrator hands the fan-out to a small JavaScript script. These scripts are pure dispatchers: they cannot read a file, run a command, touch git, or even ask what time it is. They call agents and return a payload; nothing they return counts as evidence until the orchestrator stores it with an fc return command.

fc-implement.js

Dispatches a launch's implementers wave by wave: pilots first, then the rest in chunks capped by the concurrency ceiling.

stops on the first halt, or a red pilot
fc-review.js

Runs the critic → route → fix → re-verify loop, routing each finding to the unit whose path globs match the file.

capped by critic_passes
fc-explore.js

Fans one read-only explorer per open question, all at once. A bad answer is dropped, not escalated.

no waves, no halting

The prohibition on clocks and randomness is not advisory — a locked testbench suite checks every workflow script for Date.now, new Date and Math.random, and verifies that the JSON schemas inlined in each script are byte-identical to the canonical ones in flightcrew/schemas/. A timestamp has to arrive as an argument.

How the fan-out actually behaves

  • Waves run strictly in order. A later wave never starts before an earlier one finishes or halts.
  • Pilots go first, alone. If a pilot comes back red, the wave stops there — the "prove the risky bit works before committing the fleet" gate.
  • The rest run in chunks. Units inside a chunk are genuinely concurrent; the next chunk waits for the whole current one.
  • A missing or malformed return becomes a synthetic halt, never a silent gap. A stuck subagent still produces a well-formed record.

Above all of this sits the orchestrator's own gating: three human gates plus any halt return or fired trigger stop the run regardless of what a script would have done next.

§11

Isolation, permissions and guards

In plain terms

Six small scripts sit between an agent and the filesystem. Two refuse edits it shouldn't make, one checks that whatever it just wrote still parses, one refuses to let it end its turn while the tests are red, and two exist purely so the run leaves a record. None of them can crash a session: every one is wrapped so that any error is swallowed and logged, and every one is a complete no-op when no launch is active.

hookfires onDoes
lock-guardPreToolUseDenies an edit to a locked path in any phase past targets — "report a wrong or unsatisfiable check instead of editing it"
boundary-guardPreToolUseDenies an edit outside the paths the current phase permits
structural-checkPostToolUseRuns a per-extension syntax command on the file just written; exits 2 with the last 20 lines on failure
stop-gateStopIn verify and contracts only, runs the phase's gate and refuses to release the turn while it is red
event-logmanyAppends one well-formed event line per recorded event. Blocks nothing
session-endSessionEndBest-effort, 1.5 second budget: re-renders the evidence page and report so they survive the session

Boundaries and locks

The two guards read the same declaration in launch.json and answer different questions. Locked means "nobody may edit this at all past the targets phase" — the tests, the fixtures, the spec. Boundary means "this phase permits writes only here" — in the build phases, the unit's allowed paths plus the launch's own folder.

Both guards refuse by returning a decision, not by exiting non-zero, and both are honest about ambiguity: when two launches are active or launch.json is unreadable, they return ask rather than guessing, handing the decision to a person.

There is one gap they cannot close, and the system says so plainly rather than pretending otherwise: a shell command that writes a file never triggers an edit hook. A sed -i, a redirect, a git checkout — none pass through Edit or Write. Three backstops cover it together: harness-level deny rules on the locked paths, a filesystem sandbox deny list that applies to Bash and its children, and fc locked / fc boundary running inside fc verify so a shell write is still caught before a run can be accepted.

Worktree isolation

Each implementer works in its own git worktree under .claude/worktrees/, gitignored and excluded from every changed-path calculation. One configuration detail is load-bearing: worktree.baseRef must be head, or subagents branch from the remote default branch and never see the run's own branch at all.

Worktree creation is deliberately left unhooked, and the reason is a nice piece of harness knowledge: a hook on that event does not observe creation, it replaces it — a logging hook attached there would break every isolated subagent.

The stop gate, and the escape valve

The stop gate is the only hook granted a raised timeout (600 seconds) because it runs real checks. If the gate is red it records a block, prints the failing check ids with their output tails, and exits 2 — refusing to let the turn end.

But it will not do that forever. After a hard ceiling of consecutive blocks it records a stall and a trigger, prints a message pointing at fc launch escalate, and releases the turn. An open escalation also releases it immediately. The design position is explicit: a human's escalation always beats a red gate, and an agent trapped in a retry loop is a failure to hand back, not a failure to grind through.

The one-paragraph threat model

Each layer answers a distinct way a semi-autonomous coding agent goes wrong. The lock and boundary guards stop a worker silently rewriting the tests it is judged by, or wandering outside the files its unit was scoped to — the two most direct routes to an agent marking its own homework. The structural check catches a broken file the instant it is written, before the mistake compounds across further edits. The stop gate stops an agent declaring a phase done while its checks are red, and its block ceiling stops it looping forever. The event log and session-end hook block nothing at all; they exist so the audit trail and the rendered evidence survive however the session ends. Underneath, the no-op rule — silence whenever a launch cannot be confidently resolved — plus the retrospective fc boundary and fc locked probes form the failure-safe backstop: hooks never crash or hang a session, and the one gap the guards structurally cannot see is closed by the harness's own deny rules and by verification refusing to pass a run with a dirty tree.

§12

Testing and checks

In plain terms

"Checking" happens at six layers, and it is worth keeping them apart. At the bottom, a schema says what shape a file must have. At the top, a regression suite spawns the real command as a subprocess and asserts on its exit code. In between sit the semantic validators, the phase gates, and the hooks that call them.

  1. L1schemas/JSON schema files describing the shape of every document the system writes. They declare; they run nothing.
  2. L2schema-lib.mjsA hand-rolled validator covering exactly the keyword subset the bundled schemas use — no dependency, no more surface than needed.
  3. L3validators/Semantic rules a schema cannot express: the 13 spec invariants, the 13 tests-map invariants plus coverage, the 12 plan rules, the kickoff and launch rules.
  4. L4gates/Decide whether a phase transition may proceed. They report a verdict and never decide what to do about it — the caller decides.
  5. L5hooks/Live interception, wired declaratively to tool events, calling the gates.
  6. L6testbench/suites/29 locked regression suites that spawn the real commands, hooks, validators and gates against temporary fixture repositories and assert on real output.

The testbench

node flightdeck/testbench/run-all.mjs [--only <substring>]

ok bin-boundary (12/12, 7050 ms)
ok bin-check    (17/17, 16056 ms)
…
ok workflows    (4/4, 171 ms)
hygiene: ok

Every suite follows one protocol: a pass or FAIL line per case, then exactly one covers: line naming the spec node ids it proves, then a count line. Exit 0 if every case passed, 2 otherwise — never 1, and never a silent crash, since an uncaught error becomes a FAIL line.

Two hygiene rules run around the whole thing: each suite gets a private temp directory and anything left in it is a leak that fails the run, and a git status snapshot before and after catches any file written outside the runs folder.

The 29 suites map one-to-one onto the 29 check ids of the pinned tests map — the end-to-end journey, each command family, each hook, each validator, plus static scans for imports and network use, hook timing, schema round-trips, the kickoff template assembly, the manifest, and the workflow scripts. Implementation units may add suites under unit-*/; they may never edit a locked one.

Fixtures, the manifest, doctor, and what a "bench" is

Fixtures are golden inputs that suites copy and mutate — never mutate in place. sample-project is a tiny real codebase with real tests; sample-spec holds a spec, tests map and plan; sample-launch is a complete realistic launch folder with events, evidence, returns and a review pass, used as the reference for launch-folder shape.

MANIFEST.txt lists every file the system ships, one repository-relative path per line. fc doctor and a dedicated suite both check every listed path exists and is non-empty — and the suite checks the reverse too, that no shipped file is missing from the list.

fc doctor is the installation health check: Node version, git on PATH, no two launches active, crew frontmatter complete, every script passing node --check, every schema parsing, the sample launch validating, the manifest whole, the implementer declaring a turn cap. With --target it also checks a distributed .claude/ — crew files byte-equal to source, every hook command present in settings, hook interpreters resolvable, worktree.baseRef set to head, worktrees gitignored, and no name collision with the project's other agents.

A bench is not a suite, and run-all does not run it. The rubric bench under testbench/benches/ asks a question no pass/fail assertion can: given one draft and one rubric, do different judges converge on the same findings, and if not, which rubric questions are responsible? It tracks "flips" — a question a chain passed and then failed on unchanged text, which disqualifies that question's wording. It is calibration data for a judged process, kept deliberately outside the green/red status of the testbench.

§13

The launch folder and what it leaves behind

In plain terms

Everything a run produces lands in one self-contained folder. A person who never watched the run can open it afterwards and reconstruct what happened, what was proven, and what was only claimed — because the outputs are deliberately separated along exactly that line.

flightdeck/launch/<run>/ ├── launch.json state: status, phase, pins, paths, ceilings, gates, outcome ├── kickoff.md the conduct rules, rendered and version-stamped ├── specs/<S>/ pinned copies of the spec and tests map ├── plan.json source of truth for the run's shape ├── plan.md rendered from it, byte-deterministically ├── events.jsonl append-only: what the hooks and fc recorded ├── hooks.log raw hook diagnostics ├── evidence/ one JSON per check + boundary, locked, budget, summary ├── evidence.html the self-contained page a human actually reads ├── returns/ every stored agent return, plus its sealed prompt ├── review/ critic passes (frozen) + resolutions.json (mutable) ├── notes.md orchestrator notes, quoted verbatim into the report └── report.md the ledger — final at `fc launch end`

The provenance split

Three words recur across the outputs and they mean three different things:

sourceMeansTrust
hookA Claude Code hook observed it happeningRecorded mechanically; no agent chose to write it
fcA command wrote it as part of doing somethingTied to a validated state change
statedA human recorded something that happened outside the hooksA claim, labelled as one

The event log recognises a fixed vocabulary — phases, gates, stop blocks, stalls, triggers, escalations, lock and boundary denials, check runs, returns, unit merges, usage, and the ending — so tallies are meaningful rather than free text.

evidence.html is the display surface: one self-contained page with no network dependencies, re-rendered at every check, gate, phase change, return and ending, with a fixed section order that puts what is unproven first — Unverified, Quarantined, Test-file changes, Boundary, Changed since lock, Findings, Phases, Agents, Failures, then every check's raw output. The kickoff states the corresponding rule for the conductor: the evidence page is the display, and the session's own scrollback is not evidence.

§14

Why it's built this way

Reading across the whole system, the same handful of convictions keep reappearing in different clothes. They are the actual design, and the folders and commands are just how they are expressed.

  • Freeze before you build.The spec and the tests are finished, argued over and locked before implementation starts. Everything downstream is measured against something that cannot move to accommodate it.
  • Nobody grades their own work.The implementer cannot edit its tests. The verifier is denied the implementer's reasoning. The critic is denied its own previous findings. The judge sees two files. Independence is enforced by what each role is allowed to read.
  • A green board is a claim.Checks are re-run on the merged tree, not just in the worktree that produced them. A verdict is refuted, not confirmed, and evidence recorded at the wrong commit does not count.
  • Refusing is a valid outcome.Halt kinds, escalation kinds, abandon triggers and the stop gate's release ceiling all exist so that an agent stuck against something wrong hands back rather than improvising. The first real run of this system was abandoned by its own rules.
  • Say what kind of claim it is.Checked, reviewed, stated. Recorded versus asserted. The report is structured around the distinction and refuses to collapse it into a verdict — that call belongs to a person.
  • Rendered, never hand-edited.plan.md from plan.json, kickoff.md from versioned parts, report.md and evidence.html from one shared loader. A hand-edited copy drifts, and a drifted copy is worse than none.
  • Failure is an input.The run log carries deliberate <fill> gaps a human must complete, and the planner reads it before cutting the next run for the same spec. What went wrong last time is meant to change what happens next time.
