How Dynamic Workflows Run

A dynamic workflow is a saved JavaScript script that the Claude Code runtime executes to spawn agents in a fixed order, with fixed fan-out and fixed stop conditions. The script decides the shape. The agents do the work. This page describes what the runtime actually does when it runs one, and where its edges are.

What a workflow is

A workflow is one file. It begins with a pure literal that names it and lists its phases, and the rest is plain JavaScript that calls a small runtime API. Saved under the project's workflows directory it runs as a slash command by name, and a structured args value can be passed to it. The script itself never touches the repository: it cannot read a file, run a command, or look at the clock. Everything that touches disk is done by an agent the script spawns.

export const meta = {
  name: 'implement-wave',
  description: 'Build one wave of units in parallel, each in its own worktree',
  phases: [{ title: 'Pilots' }, { title: 'Units' }],
}
phase('Pilots')
const pilots = await parallel(args.pilots.map(u => () =>
  agent(u.prompt, { label: u.id, schema: WORKER_RETURN, agentType: 'implementer', isolation: 'worktree' })))
if (pilots.filter(Boolean).some(r => r.status !== 'green')) return { stopped_on: 'pilot' }
phase('Units')
const units = await pipeline(args.units,
  u => agent(u.prompt, { label: u.id, phase: 'Units', schema: WORKER_RETURN, agentType: 'implementer', isolation: 'worktree' }))
return { pilots, units }

Three things in that example carry the whole model. The script holds the loop and the branching. Each agent() call is a real subagent session. The return values are validated objects, not prose.

The script API

CallWhat it doesEdge to know
agent(prompt, opts)Spawns one subagent and returns its result. With schema, the agent is forced to return an object matching that JSON Schema and the runtime validates it; the model retries on mismatch.Returns null if the agent dies on a terminal error or the user skips it. Filter nulls.

What happens when it runs

Agents are real subagent sessions

An agent the script spawns receives its own system prompt from its agent definition, the environment, the delegation message, the project's instruction files and any preloaded skills. It does not receive the parent's conversation. It has whatever tools its definition allows, so it can read, write, run commands and use git. Hooks configured in the project settings fire on its tool calls, and the hook envelope carries the agent's id and type. Its transcript is written to disk under the session's subagents folder.

Returns are typed

Without a schema, an agent's final text is its return value. With a schema, the runtime forces a structured-output tool call and validates the object before the script sees it. The subagent is told its final text is data, not a message to a person. This is the mechanism that makes a script's branching trustworthy: a red status is a field, not a sentence to interpret.

Limits the runtime enforces

  • Concurrency. At most sixteen agents run at once per workflow, fewer on machines with fewer cores. Excess calls queue. You can pass a hundred items and they all complete.
  • Total agents. One thousand per run, a backstop against a runaway loop. One call accepts at most 4,096 items.
  • Tokens. If the turn has a token target, it is a hard ceiling shared across the main session and every workflow. Reaching it makes further agent calls throw.
  • Size guideline. A per-session setting bounds how large a workflow the session will accept, from small to unrestricted. Permission rules approve launching a workflow by name.

Repeatability and resume

Every run is journaled: each agent's actual return value is recorded. Relaunching the same script with the same arguments replays entirely from cache. Edit one call and the longest unchanged prefix of agent calls returns cached results instantly, while the edited call and everything after it runs live. This is why the clock and randomness are forbidden in the script: a value that changed between runs would break the prefix match. Timestamps arrive through args and are stamped after the workflow returns.

What a workflow cannot do

  • Take human input mid-run. Only a permission prompt can pause it. A decision that needs a person is the end of one workflow and the start of the next.
  • Touch the filesystem or shell. Recording, rendering and committing are done by the agents it spawns, not by the script.
  • Nest deeper than one level. A workflow can call a saved workflow. That child cannot call another.
  • Read the clock or draw randomness. Both throw.

What fires around a spawned agent

EventWhenCan it block?
SubagentStartEach agent the script spawns beginsNo, record only
PreToolUseBefore any tool call inside the agent, with the tool name and inputYes, exit 2 or a deny decision refuses the call
PostToolUseAfter a tool call, with its resultNo, but exit 2 shows stderr to the agent
SubagentStopThe agent is about to endYes, exit 2 holds it, the same way a Stop hook holds a session
WorktreeRemoveAn isolated agent's worktree is cleaned upNo

The point for gating: a hook that refuses to let a worker finish until its checks pass belongs on the subagent-stop event, not on the session's stop event. The session-level stop hook holds the orchestrator's turn, which under a workflow is not where the work happens.

The shape of a good script

  • Default to pipeline(). Reach for a barrier only when a stage needs every earlier result at once, for a dedupe or an early exit.
  • Put a schema on every agent whose return the script branches on.
  • Name the agent type per call so each stage runs the role it should, on the tier it should.
  • Use worktree isolation only for agents that write files in parallel.
  • Log what was dropped or capped, so a bounded sweep does not read as a complete one.
  • Return one object. The caller reads it; nothing else leaves the script.
