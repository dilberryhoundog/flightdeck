Workflows in Flightcrew

The first explainer described what the Claude Code workflow runtime does. This one places it inside flightcrew: which part of a run a workflow owns, which parts stay with hooks, leaf scripts and the human, and what that does to the kickoff, the phase state and the runner. It describes a shape, not a finished design. The decisions it leaves open are listed at the end.

The division of labour

A run has four kinds of work that used to be done by one person at a terminal. Each has a natural owner once a workflow is in the picture.

Nothing on that list is left for a runner to own except scaffolding: creating a launch or a run folder. Everything else has a home that is either the runtime, a hook, a leaf, or a person.

A run as a sequence of workflows

Under this shape the phase is where the script is. There is no phase field to advance, because a run is the list of workflows that have been invoked and the gates a person passed between them. What remains as state is only what the human decided: which run is current and which gates it has cleared. That is the whole of what the launch's index file needs to hold.

What this does to the kickoff

The method's sources describe the kickoff as the human's standing instructions for how a run is conducted, and separately describe the dynamic workflow as a saved script that runs the same shape every time. Those are one thing seen from two sides. The kickoff is the readable statement of the run's shape; the workflow is its executable form. The v1 build resolved the seam by making the kickoff a list of runner commands and putting the deterministic steps behind them. This shape resolves it the other way.

The runtime already takes an arguments object. So the kickoff becomes a workflow name plus the arguments it accepts. A base set of defaults lives in the script. A run overrides only what differs. That is a machine-readable kickoff by construction, and a page can render it, edit it and hand it back.

// what a kickoff reduces to: which script, and what this run changes
{
  "workflow": "implement-wave",
  "spec": "launch/flightcrew/specs/spec.v2.json @ 3f9a1c2",
  "run": "launch/flightcrew/runs/run-3",
  "plan": "launch/flightcrew/runs/run-3/plan.json",
  "ceilings": { "implementers_concurrent": 4, "iterations_per_unit": 6 },
  "models": { "unit": "sonnet", "critic": "opus" },
  "timestamp": "2026-09-08T04:12:00Z"
}

What the orchestrator used to read as prose becomes the agent definitions and the rendered dispatch prompts, which is where the sources put role conduct anyway. What the human used to type as commands becomes a page that writes this object and invokes the workflow.

What this does to the runner

The v1 runner owned every phase transition, every gate flip, every pin and every render, and was the surface the human, the orchestrator, the hooks' backstops and the tests all talked to. Under this shape it keeps its leaves and loses its spine.

What the v1 build did instead

Three workflow scripts were shipped, one each for exploring, implementing a wave and running the review loop. They follow the right division: they only dispatch agents and return payloads, and the kickoff part that selects them keeps the gates with the orchestrator. Three things stopped them from being the system's spine.

  • They end with an export default. The runtime expects a top-level return. The locked suite that checks them rejects a top-level return as a syntax error, so no file can satisfy both the check and the runtime.
  • They were never executed. The suite reads them and never runs them. Neither recorded run invoked them, though both runs selected the workflow shape in their kickoff.
  • They return payloads and the orchestrator persists them afterwards by typing runner commands. The persistence that should happen inside the agent happened in the session, by hand.

The scripts that actually built the system were also workflows, written in the session's scratchpad, hardcoding a machine path. They did what the shipped scripts describe. The system had the right idea in two places and connected them in neither.

Gotchas the shape carries

  • The script cannot persist. Every return must be written to the run folder by the agent that produced it, through a leaf, before that agent returns. A script that relies on the orchestrator to store payloads afterwards recreates the v1 problem.
  • Worktrees branch from HEAD. A dispatch prompt rendered into the run folder and not committed is invisible to the worker spawned into a worktree. Render, commit, then spawn, or render inside the worker.
  • Gate on subagent stop. A hook that holds a worker until green must be on the subagent-stop event. The session stop hook holds the wrong turn.
  • One level of nesting. A run-level script can call a saved wave script. That wave script cannot call another. Plan the composition with that ceiling.
  • No human mid-run. Anything a person decides is a workflow boundary. Escalations that need a decision end the script with a typed field, not a question.
  • Caching follows the prefix. Editing one agent call reruns it and everything after it. Timestamps come in through arguments and are stamped afterwards.
  • Agents are named per call. The script names the agent type for each stage from the crew directory. The crew definitions stay where they are; the script chooses among them.

Decisions this leaves open

  • How the stages are cut into workflows: one per gated span as drawn, or finer, with the run-level script composing saved wave scripts.
  • Whether an orchestrator session survives as a conductor between workflows, or the human at a page is the conductor and the orchestrator role dissolves into the scripts.
  • What the base set of workflows is, and which arguments each accepts as its overrides.
  • Where the leaf that persists a return lives, and whether every agent definition ends by calling it.
  • What the launch index holds beyond the current run and the gates cleared.
