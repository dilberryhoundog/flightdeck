# Docs verification for agent-body build (T015)

## 1. --agents JSON shape
Verdict: confirmed. Source: https://code.claude.com/docs/en/sub-agents.md
Top-level object keyed by agent name; each value takes `prompt` (the body, mapped from the markdown file's body), `description` (required), `tools`, `disallowedTools`, `model`, `permissionMode`, `mcpServers`, `hooks`, `maxTurns`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation`, `color`, `effort`, `initialPrompt`, `experimental`. All non-`prompt`/`description` fields mirror file-based frontmatter 1:1. `effort`, `initialPrompt` and `hooks` are all accepted in the JSON form.

## 2. --agent selects a JSON-only agent as main session agent
Verdict: confirmed. Source: https://code.claude.com/docs/en/sub-agents.md (combined example: `claude --agents '{"code-reviewer": {...}}' --agent code-reviewer`) plus local `claude --help`: "`--agent <agent>` Agent for the current session. Overrides the 'agent' setting." No on-disk file is required; the JSON entry alone is enough. Definition-source precedence when names collide: managed settings, `--agents` CLI flag, `.claude/agents/`, `~/.claude/agents/`, plugin `agents/`.

## 3. `model` in agent def applies as main session agent; precedence
Verdict: confirmed, precedence order not fully pinned by primary source. Source: https://code.claude.com/docs/en/sub-agents.md ("the same way `--system-prompt` does" for prompt; frontmatter table lists `model`) and local `claude --help` ("`--model <model>` Model for the current session..."). The order agent-model > --model > settings model > default was reported by a fetch but I could not pin it to an exact quoted sentence in the primary doc; treat as undocumented-with-moderate-confidence, not hard-confirmed. Builder: do not hard-code this order into a manual without re-testing (launch with conflicting `--model` and an agent `model` field and observe the header).

## 4. `effort` in agent def applies to main session agent; precedence vs effortLevel; is `medium` valid
Verdict: partially confirmed. `medium` is a valid value — local `claude --help`: "`--effort <level>` Effort level for the current session (low, medium, high, xhigh, max)". `effortLevel` settings-reference.md: "Set a default effort level for models without a saved level of their own" — implies it is a fallback, so a model/agent-level effort should win, but no sentence explicitly ranks agent-frontmatter `effort` against `effortLevel`. Builder: treat as undocumented for the exact precedence; the existing manual's claim "settings file pins effort, resume keeps it, model does not" (pilot.sh comment) should be tested empirically (launch, then resume, and read the effective effort from `/status` or debug output) rather than asserted from docs alone.

## 5. initialPrompt behavior
Verdict: confirmed for main-session firing; --resume and -p combination undocumented. Source: https://code.claude.com/docs/en/sub-agents.md frontmatter table: "`initialPrompt` — Auto-submitted as first user turn when agent runs as main session." Commands and skills are processed in it, and it is prepended to any user-provided prompt. No sentence found describing behavior on `--resume` (does it re-fire?) or when combined with `-p "<prompt>"` in headless mode. Builder: do not assume it re-fires on resume or that it merges cleanly with `-p`; test directly (resume a session that had an `initialPrompt` agent, and separately run `-p "hello"` with such an agent, then check the transcript for turn order).

## 6. --resume: are --agents/--agent needed again, restore from transcript
Verdict: confirmed, mixed with the settings-and-launch.md manual. Source: https://code.claude.com/docs/en/sub-agents.md: "the choice persists when you resume the session: Claude Code restores the agent's tool restrictions and model along with the conversation" and "If the agent no longer exists when you resume, the session continues with the default tools and shows a warning naming the agent." So the agent choice is restored from the transcript and `--agent`/`--agents` do not need to be repeated for the agent itself to apply — this contradicts the existing manual line "Command line flags are not [re-read at resume]: `--settings`, `--agent`, ... must all be passed again" for the specific case of which agent is active (transcript restores it), though other flags in that list (`--settings`, `--system-prompt`, `--add-dir`, `--name`) are still session-only per cli-reference. Builder: pilot.sh's resume path currently omits `--agents`/`--agent` on resume by design (per script comment) — that is correct behavior per docs, not a gap. If the JSON agent definition is not passed again and the transcript's agent can't be resolved (e.g. name renamed), the session falls back to default tools with a warning; it does not error out.

## 7. --append-system-prompt still appends when --agent is set
Verdict: undocumented directly for the interactive case; the existing manual's claim is not contradicted but has no primary-source quote. Source checked: https://code.claude.com/docs/en/sub-agents.md and cli-reference.md — neither states explicitly that `--append-system-prompt` still appends on top of an agent body in the interactive session; the closest documented statement is for headless/subagent mode: `--append-subagent-system-prompt` appends to every subagent's prompt "nested subagents included, apart from a forked subagent." The agent-replaces-default-prompt statement ("the same way `--system-prompt` does") only says `--system-prompt` is superseded, not what happens to `--append-system-prompt`. Builder: pilot.sh's core assumption (append survives on top of the agent body) matches the existing manual and is plausible by analogy to `--system-prompt-file` + `--append-system-prompt-file` behavior, but treat as unverified until tested — launch pilot with `--agent` and `--append-system-prompt` together and check the effective system prompt in `/status` or a debug dump.

## 8. Do teammates/subagents spawned from a main-session agent inherit its body?
Verdict: contradicted (no, they do not). Source: https://code.claude.com/docs/en/sub-agents.md: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history..." and "System prompt: the agent's own prompt plus environment details that Claude Code appends, not the Claude Code system prompt." A spawned subagent uses its own definition's prompt, never the parent main-session agent's body. Builder: if the pilot's body needs to reach crew, it must be passed explicitly in each dispatch brief (per cockpit CLAUDE.md rule "Crew see only their brief"), not assumed to flow through automatically.

## 9. Does an @path import expand inside an agent body?
Verdict: undocumented in primary sources checked; the existing local manual and pilot.sh comment both assert it does not expand, but no official page confirms or denies this for agent-definition bodies specifically. Sources checked (no relevant text found): https://code.claude.com/docs/en/sub-agents.md, https://code.claude.com/docs/en/sub-agents (fetched twice, different framing). Builder: treat pilot.sh's own comment ("an @ import inside an appended file does not expand (notepad tests T9, T12)") as the operative fact — it is a first-party empirical test result recorded in the script itself, stronger than an absent doc line — but do not cite it as doc-confirmed; cite it as tested behavior.

Notes: --effort CLI flag also accepts `ultracode` per one fetch not corroborated by local `claude --help` (which lists only low/medium/high/xhigh/max); local help is authoritative for this install (v2.1.278) — do not add `ultracode` to any manual without separately confirming it exists.
