## 2. Validator engine
Hand-written, no library. No package.json exists anywhere in the repo (`git ls-tree -r <branch> | grep package.json` empty on every branch checked) and no branch's checks/bin code imports anything but `node:*` builtins (`git grep '^import'` on flightcrew-buildout:flightdeck/flightcrew/{checks,bin} shows fs/path/child_process/process/url only — no ajv, no third-party import anywhere).
The engine is flightdeck/flightcrew/checks/lib/schema-lib.mjs (buildout family, 215 lines; main's equivalent flightdeck/flightcrew/checks/validators/schema-lib.mjs is 86 lines, an earlier and much thinner version). Exports `validate(schema, data)`, `loadSchema(name)`, `schemaPath(name)`, `formatErrors`, `describeErrors` (schema-lib.mjs:1-11 header comment names them). It supports a documented keyword subset only (type, required, properties, additionalProperties, enum, const, pattern, minimum, maximum, minLength, minItems, items, oneOf, anyOf, $defs+$ref); `format` and `$schema` are ignored — this is not JSON-Schema-complete, it is a bespoke checker matching what the local schemas use.
Runs on bare Node, no `npm install` needed. Requires ES modules (`.mjs`, `import`/`export`) — Node ≥ ~14 for ESM but the header comments say "Node 22 ES modules" is the house style; this machine has `node -v` → v22.22.3, so it runs as-is.
Other validator files (buildout family, by line count): validate-spec.mjs 106, validate-plan.mjs 336, validate-tests-map.mjs 323, validate-launch.mjs 209, validate-kickoff.mjs 256, validate-return.mjs 139, validate-all.mjs 164 (orchestrates the others), spec-lib.mjs 312 (shared spec-node helpers), output.mjs 112 (EXIT codes, fail/print/warn). [--strict]` (file header, line 2) — no `fc` runner needed for direct use, only for the `fc lint spec` alias.
Checks nine rule ids (RULES const, spec-readiness-lint.mjs:24-33): lint-domains, lint-open-questions, lint-sequential, lint-out-list, lint-artefacts, lint-commands-run, lint-claimed, lint-boundary, lint-class-tags, plus two non-failing warnings (warn-impression, warn-length) that become failures under `--strict`.
Input: a frozen/draft spec JSON file plus optional `--repo` root and repeatable `--deliverable` paths (for artefacts a spec names that don't exist yet). Exit contract: 0 clean, 2 on any rule failure (header, line 12; RULES export at spec-readiness-lint.mjs:24).
Path-resolution logic lives in `resolvesUnder(token, {repo, deliverables})` (spec-readiness-lint.mjs:111-116, uses `fs.existsSync(path.resolve(repo, wanted))`) and a runner-existence check (line 121, `fs.existsSync(process.execPath)` for `node`), used by the lint-artefacts and lint-commands-run rules (lines 233-249).

## 4. Markdown and frontmatter
Two separate frontmatter parsers exist, both buildout-family only (main has none):
- flightdeck/flightcrew/bin/cmd/doctor.mjs:65-77, function `frontmatter(text)` — a hand-rolled flat key:value scanner (splits on first `:` per line inside a `---`…`---` block), used at doctor.mjs:146, 213, 227, 276 to check crew-file frontmatter fields (CREW_FRONTMATTER = ['name','description','tools','model'], doctor.mjs:19).
- flightdeck/flightcrew/checks/validators/validate-plan.mjs:99-100 — a regex-based frontmatter block extractor (`/^---\r?\n([\s\S]*?)\r?\n---/`) used to read an implementer crew file's `maxTurns` (validate-plan.mjs:91 comment).
Neither is a general YAML parser — both are narrow scalar-key scanners scoped to the fields each caller needs; no branch pulls in a YAML library.
ID/path resolution over document text: flightdeck/flightcrew/checks/lib/spec-lib.mjs:284-296, function `artefactTokens(text)` — tokenizes interface/verification prose, strips quoting punctuation, and keeps tokens that look like paths (contain `/`) or end in a known artefact extension (`.mjs .js .json .md .sh`); consumed by `artefactRefs(spec)` (spec-lib.mjs:299+) which walks every interfaces-section node and the verification text to build `[{id, token}]` pairs in document order. This plus `resolvesUnder` (item 3 above) is the closest thing in the codebase to "does this document's cited ids/paths actually resolve" — it resolves file paths, not internal document IDs (SC/C/I/B/E/D node ids) against each other; sequential-id integrity is a separate rule (`lint-sequential`, spec-readiness-lint.mjs RULES list).

## 6. Reuse verdict
- schema-lib.mjs (checks/lib/, buildout family) — reusable as is; self-contained (fs/path/url only), reads schemas/ beside it via relative path, would need only the SCHEMA_DIR constant adjusted (or schemas copied in) to point at flightdeck/.cockpit's document shapes.
- spec-readiness-lint.mjs pattern — pattern to copy only; its nine rules (domains/open-questions/sequential/out-list/artefacts/commands-run/claimed/boundary/class-tags) are specific to the spec document's node structure, not directly applicable to cockpit markdown, but the rule-table/RULES-export/exit-code shape is a good template.
- doctor.mjs `frontmatter()` (bin/cmd/doctor.mjs:65-77) — reusable with extraction; it's a ~13-line pure function with no external calls, easy to lift out for cockpit frontmatter field checks (name/description/etc equivalents).
- artefactTokens/artefactRefs + resolvesUnder (spec-lib.mjs, spec-readiness-lint.mjs) — reusable with extraction; would need cutting away the spec-node-shape assumptions (SECTIONS, nodesOf) and keeping just the tokenizer + fs.existsSync resolution, to check that cockpit doc-cited paths/ids exist.
- validate-{spec,plan,tests-map,launch,kickoff,return}.mjs and the three gates — reusable with extraction only as far as their shared plumbing (schema-lib calls, output.mjs EXIT/fail/print/warn helpers, 112 lines, self-contained); their document-specific field checks are not applicable to cockpit shapes.
- Best starting point: flightcrew-buildout:flightdeck/flightcrew/checks/lib/schema-lib.mjs paired with flightcrew-buildout:flightdeck/flightcrew/checks/lib/output.mjs — smallest, most self-contained, dependency-free pair; write new cockpit-shape schemas (JSON files matching the supported keyword subset) and a thin cockpit-specific lint script on top of these two, rather than trying to reuse the spec-specific validators.
- spec-readiness-rubric.md (flightcrew-buildout:flightdeck/flightcrew/checks/rubrics/spec/spec-readiness-rubric.md, current at 93e18c5) — pattern to copy only; it is a yes/no question rubric tuned to the spec judge's model and the nine-domain spec shape (per spec-judge.md:14,37 — "the rubric is tuned to its judge's model"), not a generic checklist; a cockpit rubric would need to be authored fresh in the same block/question format, not copied verbatim.
- spec-builder.md / spec-judge.md crew agents — pattern to copy only; the newest version (93e18c5, buildout family) is the clean reference for how to wire a linter + rubric-judge handoff into an agent definition (hardcoded `fc validate`/`fc lint` calls, two-file-only judge dispatch to avoid contaminating the verdict — spec-judge.md:17,37); the older working-tree/main version (5845bf1) is the same design without hardcoded paths, useful only as the earlier draft.
