## Area 2 — Identifiers

**Closed by O046 to O049.** Final set: work `M`, `WS`, `P`; desk `Ds`, `Rq`, `CA`; commander `Or`, `De`; pilot `T`, `Sp`; retired `C`. Rule: a single capital for a commonly recognised unit; capital plus lowercase where the lowercase guides a single-word kind; one capital per word for multi-word kinds; three digits; never reassigned after the cutover, never reused. What remains is the migration and the named tier.

**The set cannot be derived, only enumerated.** Whether a name is one word or two is a judgement — `Ds` for Dossier, `WS` for work shop — so the linter can enforce shape and membership but never compute a prefix from a name. The set is an explicit list in the schema store, failing loudly when a new kind appears.

**`C` is retired** (pilot's ruling): minted only in the frozen `logs/crew-manifest.json`, superseded by `T`. It belongs in the old-prefix map as never-reissued, and it is unavailable to question 5 — it is the obvious prefix for numbered crew seats and cannot be both.

**The one dangerous rename is `P`.** Every other change vacates a prefix, so a stale citation stays unambiguous. `P` alone is reassigned: it dies as request and is reborn as procedure, so `P004` means a request in a frozen log and a procedure in a new one. Since procedures carry no numbers today, nothing renumbers — numbering them from `P101` costs nothing and makes every `P###` self-disambiguating for good, with no date rule for any reader or tool to carry. Taken as a ruling, not a question.

**Safe-rename mechanics.** Anchor the three digits immediately after the prefix, or `S` matches `Sp` and `W` matches `WS`. Two-step `git mv` for `Ds` alone, `core.ignorecase` being measured `true`; every other rename changes length or letters. Case-sensitive grep throughout. Numbers preserved one-to-one. Frozen and scratch left alone, which is what reduces 1230 occurrences to 518 live: 231 scripted, 278 reviewed, 9 never touched.

## Area 4 — Frontmatter

Consistent YAML frontmatter replacing bolded metadata, for searchability. The problem is real: DS001 carries the same facts three times, and P004 reached the desk with `status` empty while `proposals.json` carries a populated status for the same proposal.

**Frontmatter is inert to the harness,** so the idea rests on convention alone — and an unenforced convention is what produced the 24 stale references. Area 5 gives it a read path, so the options below are weighed as enforced.

- **F0, keep the bolded blocks,** and the duplication stands. **F1, uniform frontmatter replacing them:** searchable across 78 files, but the facts then live in frontmatter and in the manifest row with no stated owner. **F4, fields plus a checker comparing them:** duplication allowed but cannot drift, at the cost of two sources a human reconciles.
- **F2, the markdown owns and the manifest is generated.** One owner, unit file complete alone. Costs a generator and a manifest nobody may hand-edit, which rule 10 invites.
- **F3, the manifest owns and frontmatter carries `type` and `unit` only.** Cheapest, duplication impossible; but a file handed to crew by path arrives with no date, status or lineage.
- **F5, split ownership by the kind of fact.** The markdown owns what a lone reader must have; the manifest owns what belongs to the collection. What two rooms already do unnamed.
- **F6, the manifest owns and the linter regenerates the frontmatter block into the file.** New this pass, and it dominates F3 and F5 on their own terms: a crew member handed a file by path gets everything, and drift is impossible because the block is derived rather than authored. Costs a writer, which sharpens question 3 — and the silent-overwrite cost is worse than I weighed it. The five worked frontmatter examples this area is built on are the commander's own hand edits, still uncommitted; DS001's `stamp`, `generates` and `context` exist in no manifest, so a first regeneration would not correct them, it would **delete** them, and by H1 the guard cannot see the write that does it. Pilot drift and destroyed commander content are not the same magnitude of error. **F6 is only safe if constrained:** write only fields the manifest demonstrably owns, refuse to write any field present in the document and absent from the row, and print every field changed.

**Fields.** All types: `type`, `unit`. ID-based work documents: `work`, `context`, a date. Type-specific: `status` and `recorded` for requests, `generates` for dossiers, session and author for dossiers. Crew and officer documents have no identifier at all, so they need `seat: "explorer"` or the named tier from question 5.

**Leaning: F5. A regenerating lint is out.** The lint reports; if it ever writes frontmatter at all it writes only fields the manifest demonstrably owns, refuses any field present in the document and absent from the row, and prints every change — and the commander's five hand-edited examples are uncommitted work that must not be regenerated under any setting. Both are declared per type in area 5's schemas rather than ruled globally, which makes question 4 answerable as a default rather than as eleven separate judgements.

## Area 5 — Schema store

O045: "a schema store, so we can specify document shapes, stored in base, callable by a linter". It ends the condition this paper keeps circling: every convention here is unenforced, and the unenforced convention is what rots.

**Scope (A).** 11 typed markdown kinds and 15 JSON manifest shapes. 7 of 15 manifests are fully uniform and 8 vary almost entirely by optional fields, so a lenient schema passes nearly everything on day one — checked against the engine, whose header confirms `type` accepts a string or an array of strings and which types null, so the eight variants pass. READMEs, keeps and notepad files are furniture and excluded, which O045 makes the commander's own position.

**The gate on every option below is question 3, who may write.** The pilot's proposal, which I think holds: crew build and test the engine, the checker and the schemas *outside* the cockpit — a scratchpad or a worktree — adversaries review them, and the pilot lands the reviewed files into `base/`, the same route a crew report already takes into the notepad. Rule 1 is kept intact and the pilot authors nothing. Every option here is costed on that footing.

**Staging, and stage A needs no engine at all.** Fusing the checker with the shapes makes the urgent, decision-free half hostage to eleven schemas that need questions 4 and 5 answered first. **Stage A — the resolution table, the field map and the reference checker** — is pattern scanning over text, field lookups in JSON and path resolution. **None of it is JSON Schema validation**, which is the entire value of the 327 reusable lines. So stage A is written in what `base/bin/` already runs, sh and python3, both resolving from `/usr/bin` on a bare PATH — `json` is stdlib, and it was `yaml` the auditor found missing, not `json`. **Stage A parses JSON, scans text, and parses no frontmatter at all;** where a frontmatter field must be addressed, the declared subset makes `^unit:` a line-prefix match inside the fences, a regex rather than a parser. That matters because two strict-subset readers in two languages would have to agree exactly — the divergence argument arriving from the other side — so **the single subset reader exists once, in stage B, and is what the fixtures pin.** **Stage B — the document shapes** — is where the engine is decided, after questions 4 and 5. I had the engine gating the urgent half for three passes; it does not.

### Where the engine lives

`checks/lib/schema-lib.mjs`, 215 lines, importing only `node:fs`, `node:path`, `node:url`, exporting `validate(schema, data)` over the keyword subset every cockpit shape needs; no `package.json` on that branch. Paired with `output.mjs`, 112 lines.

- **E1, call it in place.** One implementation, but the files live on flightcrew branches, rule 6 makes an outside dependency a proposal, and `flightcrew-core`'s draft SC1 clause schedules that tree for deletion.
- **E2, copy it into `base/`.** 327 lines, self-contained, inside the cockpit's write boundary. Costs a fork.
- **E3, extract to a shared location.** Avoids the fork, but is a change outside the cockpit: a rule 6 proposal blocked behind M002.
- **E4, write the lint in Ruby and reuse nothing.** `/usr/bin/ruby` is on the system path with psych and json built in. **But it is underpriced, and measuring it settles the question:** on the system interpreter with a bare PATH, `require 'json-schema'` and `require 'json_schemer'` both raise LoadError — Ruby's stdlib has **no** JSON Schema validator. So E4 means losing the 327 verified lines *and* hand-writing an equivalent, or adding a gem and with it the install step E4 exists to avoid.

**The runtime cost I understated, and the false dilemma I then built on it.** Measured on a bare PATH, **node is not found** — a mise install visible only in the pilot's shell, while ruby and python3 resolve from `/usr/bin`. I proposed pinning its path in `pilot.settings.json`. That cure is the disease: the only thing to pin is a user-specific absolute path under `~/.local/share/mise/`, committed to version control — precisely the `cockpit-guard.py` defect this paper spends a section on. And the dilemma was unnecessary, because stage A does not use the engine. **This whole choice is deferred to stage B**, where JSON Schema validation is actually wanted. **Split the decision by stage and both leanings stop being contested.** **Stage A carries no engine dependency at all** — scanning, JSON lookups, path resolution — so it runs on sh and python3 and E1 to E4 gate stage B only. **Stage B is left open for the commander rather than leant:** the pilot's reading is E2 on the merits rather than on sunk cost — E4's apparent appeal was that Ruby avoids the runtime question, but Ruby has no validator to avoid it with, so the real choice is 327 verified lines against writing them again. The wrapper resolves node by probe with a `$FLIGHTDECK_NODE` override — **never a pinned path**, since the only thing to pin is a machine-specific path under one user's home, committed to version control, which is the `cockpit-guard.py` defect this paper files two sections later. A hook-run lint is where the runtime bites, which argues W1 and W3 over W2.

### How frontmatter gets parsed — my position loses

I proposed a flat subset whose cost was "`generates` becomes a repeated key or a comma string the schema validates by `pattern`". That comma string is the DS001 shape that broke every parser the three of us ran, written into policy. The pilot's subset admits a **bracketed** list, which is valid YAML — system ruby returns the array — so the pilot's subset is a strict subset of YAML and mine was not. Mine is withdrawn.

**Adopted: the strict subset, fail closed on anything outside it, with psych as a test rather than a dependency.** DS001's fix becomes two brackets, and every cockpit file stays readable by any real YAML tool, including the yaml-language-server frontmatter validation the scout documented. A fixture set — DS001 as a golden failing case, a bracketed list as a golden passing one — pins the reader's behaviour, and psych runs once as a conformance test that the subset never leaves YAML. This avoids a second runtime, which the F4 finding has just made expensive, and avoids psych's stderr noise on every call here.

### When it runs

The proven in-house model, verified at `spec-builder.md:26-28`: `fc validate spec <draft>` after each domain, `fc lint spec <draft> --repo <root>` once when whole, both exit 0 before a judge is dispatched.

- **W1, two-stage.** A per-document shape check as a file is written, and a whole-corpus lint at session end, before commit and before a dossier reaches the desk. The only option that sees cross-file breakage, and it fails soft.
- **W2, a `PreToolUse` hook on every write.** The only thing that can block a malformed file, at the cost of latency and a hard stop when the linter's own rule is wrong. It would inherit both `cockpit-guard.py`'s hardcoded-path defect and the Node-runtime problem.
- **W3, a git pre-commit hook or the dev-workspace commit path.** New this pass. Catches the whole corpus at the one moment that matters — nothing reaches history unchecked — without touching per-write latency, and the cockpit already commits through dev-workspace procedures. **Leaning W1 plus W3:** W1 for the working session, W3 as the gate that cannot be skipped.

### What else the store holds

- **Zone per FIELD PATH, not per file or per type.** Wrong in earlier passes, and `orders.json` falsifies it concretely: 49 IDs sit in `id` and must rename, 9 sit in `text` and must not. O048's "(O001 is not very readable)" repaired to "(Or001 is not very readable)" says the opposite of what the commander said. `decisions.json` is a *different* hazard and an earlier pass wrongly called it the same one: its prose is pilot-authored and repairable, and freezing it would have stranded the seven stale references sitting in its `by` field. `logs/topics/` is safe — all 56 IDs are in `ref` and `superseded_by`, none in a statement value, which the adversary checked before claiming it.
- **Two tiers, not three zones — because per-field is still one level too coarse.** `decisions.json` proves it: 22 of its 25 rows carry my own summaries in `decision`, but D018, D021 and D024 embed quoted commander words in that same field, D024 reading `Read by the commander: "stubs are good, yours to promote."` The same field path is pilot prose in 22 rows and verbatim in three, so no per-field rule can be right for both — freeze it and stale references stand in a live register, repair it and three quotations are falsified. The workable rule is **three tiers, and the test is the value, not the field name**.
  - **Tier 1, applied by the script: whole-value references** — the entire field value is one id or one path — in live JSON, plus file renames. Measured: **231** (175 in live JSON, 56 in `logs/topics/`, all of those in `ref` and `superseded_by`). A per-type declaration names which fields are *expected* to pass; the test still decides.
  - **Tier 2, proposed by the script and applied only after review:** every other live occurrence, markdown and JSON prose alike. Measured: **278** (169 markdown, 109 live JSON prose). The script emits a dry-run diff per file and a reviewer accepts or strikes each hunk, so these are reviewed diffs, never hand edits.
  - **Tier 3, never touched:** `orders.json.text` (9), every frozen file, all scratch.
  231 plus 278 plus 9 is the 518. **`by` fails the tier-1 test and I had it wrong:** its 25 values are short prose — `commander` twelve times with no pointer at all, others naming sessions or decision lines — and only seven carry a path. A field-name list would have scripted them; the whole-value test sends them to tier 2, still cheap and honestly placed.
- **Authorship decides what a reviewer may rewrite, not what the script may do.** It is decidable because the tool never decides it: authorship is **declared once per field path in the store**, exactly as the zone is, and the tool applies the declaration. One class resists a per-field declaration — a field mixed row by row, which is `decisions.json.decision` — and that class is machine-detectable as a quoted span inside a pilot-authored field. Per the closed audit no identifier currently sits inside one, so the rule is prophylactic rather than load-bearing. My earlier axis (structural / path / verbatim prose) is falsified inside a single file: `orders.json`'s `purpose` is my own prose carrying `"../../logs/topics/"`, which must move when the room moves, while its `text` is commander-verbatim and O034's `commanders-desk/out-advice/DS001.md` is a path inside quoted words that is already stale and must stay stale. Both prose, both path-bearing, opposite treatment. Only the author decides.
- **Cross-room paths are mostly scriptable, correcting my own claim.** I said five of six `../` strings were prose. A full walk finds seventeen: thirteen structural (twelve `file` values in `base/proposals.json`, one `workshop` in `missions.json`) and four prose (`orders.json.purpose`, `crew.json.convention`, `rosters.json.convention`, `cockpit.json.convention`). So a refactor team scripts thirteen and hand-reads four, rather than hand-reviewing all of them as I implied.
- **Two tables, not one, and they are not the same artifact.** I claimed X3's rename mapping and the checker's prefix map were one file written once. They are opposites: the **rename table** is a substitution rule, exhaustive over what it touches and silent about everything else; the **resolution table** is a reading aid over strings that are never edited. They disagree on exactly the two entries that matter. `C` belongs in the resolution table with a null successor and **must not appear in the rename table at all**, or the script acquires a `C` rule and rewrites frozen history. `P` belongs in the resolution table as one-to-two by zone and the 100 boundary, and **must not be a blanket `P` to `Rq`** in the rename table, or new procedure citations are renamed into requests. Precisely: there is **one authored table and one derived view**.
