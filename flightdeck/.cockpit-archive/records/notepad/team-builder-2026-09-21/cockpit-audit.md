## 1. What each document type carries, and what it leaves out

Roster (`base/verify/schema/roster.json:7-39`): required `kind`, `name`, `purpose`, `seats` (a bare name list); optional `shape`, `updated`. No field for axis coverage, team type, a pilot-entry-point pointer, or improvement criteria/tests. `team/rosters/decision.json:1-13` and the other three rosters carry only these fields, confirming the schema is exhaustive in practice.

Seat dossier (`base/verify/schema/crew-dossier.json:7-51`): required `type`, `unit`, `room`, `agent_type`, `model`, `status`, `stamp`, `context` (T-ids flown); `additionalProperties: false` at line 8, so nothing beyond these keys is legal frontmatter without a schema change. Body convention per `team/crew/README.md:9`: title, one purpose line, `## How to dispatch`, `## Record`, `## Next time`; flightcrew dossiers add `## What to watch for` (`team/crew/README.md:5`). No axis field anywhere, no team-type field, no testing/criteria section. Two body shapes coexist: cockpit dossiers use `Record`/`Next time` (e.g. `team/crew/cockpit/adversary.md:19-27`); `team/crew/flightcrew/explorer.md:20-33` and `team/crew/general/harness-guide.md:20-26` use the older `Observed`/`Improvements`/`What to watch for` shape the README does not describe for flightcrew as `Record`/`Next time` — a drift the schema does not catch since these fields sit only in the body, unchecked by `crew-dossier.json`.

Crew manifest row (`team/crew/MANIFEST-crew.json`, one row e.g. lines 51-58): `name`, `room`, `agent_type`, `model`, `status`, optional `note`, `legacy`, `superseded_by`, `path`. No axis, team-type, or test field; identity only, per the file's own `convention` line 5.

Dispatch unit (`base/verify/schema/dispatch.json:7-93`): required `kind`, `id`, `date`, `session`, `mission`, `purpose`, `seats[]` (`name`, `reason`, `returns`), `status`; optional `roster`, `shape`, `outcome`, `lessons[]`, `subagents[]`. No axis-coverage field, no team-type field, no pilot-entry-point field, no test/criteria field, and `roster` (line 38-42) is a bare pattern-matched string with no reference check against `team/rosters/`.

What the idea's Setup list needs and none of the four carries: an axis tag (speed/coverage/quality/alignment/security/adversarial) on roster or dossier; a team-type field (Autonomous / Pilot leader / Commander in the room / the fourth type) on roster or dispatch; a pointer from roster to the procedure that is its pilot entry point (P002 pairs procedure and roster only by convention, `work/procedures/cockpit/P002-forming-a-team.md:16`, not by a field); and any improvement-criteria or test field on any of the four types. **Revised (adversary F19):** this is not a uniform schema obstacle. Only `crew-dossier.json:8` sets `"additionalProperties": false`; `roster.json` and `dispatch.json` set no such line, so an axis tag or a team-type field could be added to a roster or a dispatch unit today, with no schema change, and would validate. The dossier alone is actually blocked; the other three are merely unfilled.
