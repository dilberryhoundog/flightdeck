## 1. What makes a team effective, mapped to the six axes

Source: anthropic.com/engineering/multi-agent-research-system (fetched 2026-09-21, raw HTML with tags stripped). anthropic.com/engineering/building-effective-agents (same fetch method, same date).

**When a team beats a single agent** — "We've found that multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools." Preceding sentence: "most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time." Maps to **speed** and **coverage**; also names a domain (coding/sequential work) where teams underperform, which the six axes don't name as a negative condition.

**Model choice per seat** — "We found that a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." This is the strongest evidence for a mixed-model roster (a stronger lead, cheaper workers), maps to **quality** and **speed** together. Supporting: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7" — model choice outweighs token spend.

**The 95%-variance finding** — "three factors explained 95% of the performance variance in the BrowseComp evaluation... token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." Maps to **coverage** (token/tool-call volume) and **quality** (model choice).

**Cost** — "agents typically use about 4x more tokens than chat interactions, and multi-agent systems use about 15x more tokens than chats. For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." No axis covers cost; unnamed by the six.

**Team size, the section this report missed until E27** — `agent-teams.md`, quoted whole, preceded by "Include task-specific details in the spawn prompt:" (end of "Give teammates enough context") and followed immediately by "### Size tasks appropriately":

> ### Choose an appropriate team size
>
> There's no hard limit on the number of teammates, but practical constraints apply:
>
> * **Token costs scale linearly**: each teammate has its own context window and consumes tokens independently. See agent team token costs for details.
> * **Coordination overhead increases**: more teammates means more communication, task coordination, and potential for conflicts
> * **Diminishing returns**: beyond a certain point, additional teammates don't speed up work proportionally
>
> Start with 3-5 teammates for most workflows. This balances parallel work with manageable coordination. If you have 15 independent tasks, 3 teammates is a good starting point.
>
> Scale up only when the work benefits from having teammates work simultaneously. Three focused teammates often outperform five scattered ones.

This is the official answer to team size and it sources the cost gap inside the same page the report already quotes eleven times elsewhere, not only in the 4x/15x blog figures above. It bears directly on the idea file's "audits existing seats for suitability, suggests new seats to complete roster": the official guidance is that adding seats past a small number stops paying, which the commander should weigh beside his own C03 note (small teams good, arbitrary limits bad) — the two agree on "small," and this page puts a number, 3-5, and a rationale under that agreement.

**Delegation/briefing** — "Teach the orchestrator how to delegate... Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." Maps to **alignment** and **coverage**.

**Adversarial review** — `agent-teams.md`: "Investigate with competing hypotheses" section — teammates made "explicitly adversarial: each one's job is not only to investigate its own theory but to challenge the others'"; "multiple independent investigators actively trying to disprove each other." "Start your first agent team" section — "one playing devil's advocate" (corrected per F32; not "Best practices"). Maps directly to **adversarial**, sourced correctly (see F1 above) — this is a named official pattern, not an inference from evaluator-optimizer.

**Review/verification as a distinct, separate pattern** — building-effective-agents' evaluator-optimizer workflow: "one LLM call generates a response while another provides evaluation and feedback in a loop... particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value." This is collaborative refinement between a producer and a checker, a second official pattern distinct from the adversarial one above — maps to **quality**, and weakly to **adversarial** only if the loop is framed as challenge rather than refinement.

**Security** — `agent-teams.md`, Permissions section: "Teammate permission prompts appear in the lead session, so approve them there yourself." And: "Claude Code tells the receiving agent the message came from another Claude session, not from you. A teammate can't approve a permission prompt or supply consent on your behalf, and a teammate that was denied an action can't relay it to another teammate to bypass the check." And the auto-mode classifier "treats an approval claim relayed from another agent as untrusted input rather than confirmation from you." Maps to **security**: permission authority stays centralized at the lead/human regardless of team size, and inter-agent messages are never trusted as consent. Per E30: this centralization is not a policy choice a seat dossier can vary — `permissionMode` in a seat's frontmatter is discarded under the classifier's checks (section 3), so per-seat permission differentiation is unavailable in this cockpit's `auto` mode regardless of what a roster records.

**Judge design (bears on quality, corrected per F2)** — "We used an LLM judge that evaluated each output against criteria in a rubric: factual accuracy (do claims match sources?), citation accuracy (do the cited sources match the claims?), completeness (are all requested aspects covered?), source quality... We experimented with multiple judges to evaluate each component, but found that a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements." Maps to **quality**. Corrected reading: this is evidence *for* a single rubric-driven judge call, and *against* splitting judgement across multiple judge seats — the opposite of what round 1 implied.

**Core design principles** (building-effective-agents): "Maintain simplicity in your agent's design. Prioritize transparency by explicitly showing the agent's planning steps. Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing." No axis owns "simplicity" or "transparency of planning" directly; closest is alignment, but the source names something closer to auditability.

## 2. The fourth team type — human enters a teammate's session directly

Source: code.claude.com/docs/en/agent-teams.md (fetched 2026-09-21; page states "as of v2.1.178"). Documented and works today, **subject to the Limitations section below**, most importantly that agent teams are experimental, off by default, and require an interactive session.

Exact quote, opening paragraph: "Agent teams let you coordinate multiple Claude Code instances working together. One session acts as the team lead, coordinating work, assigning tasks, and synthesizing results. Teammates work independently, each in its own context window, and communicate directly with each other. **You can also talk to any teammate directly without going through the lead.**"

Section "Talk to teammates directly": "Each teammate is a full, independent Claude Code session. You can message any teammate directly to give additional instructions, ask follow-up questions, or redirect their approach."
- "**In-process mode**: use the up and down arrow keys in the agent panel to select a teammate, then press Enter to view its session and type to send it a message. Press `x` on a selected teammate to stop it. Press Ctrl+T to toggle the task list."
- "**Split-pane mode**: click into a teammate's pane to interact with their session directly. Each teammate has a full view of their own terminal."

Selection mechanics: "**Up and down arrows**: select a teammate. **Enter**: open the selected teammate's transcript and message it directly. **Escape**: clear the selection. While you're viewing a teammate's transcript, Escape interrupts that teammate's current turn." Idle-row behaviour: "As of v2.1.199, an idle teammate's row stays in the panel while any teammate or subagent is still working... Once every agent in the panel is idle, idle rows hide after 30 seconds and reappear on the teammate's next turn; the teammate stays running and addressable while hidden." v2.1.181-v2.1.198 hid idle rows after their own turn ended even while others worked; before v2.1.181 idle rows were never hidden.

**What "entering" a teammate's session actually does (corrected per F6)**: "While you're viewing an in-process teammate, plain text and skills go to that teammate, but built-in commands still run in the lead's session." Also: "/model and /fast only change the lead's settings," and "/effort still applies to the viewed teammate's later turns." Combined with Escape interrupting the teammate's current turn, viewing a teammate routes your typed input and skill invocations directly to it and lets you interrupt its turn — this is a real occupation of the seat for plain messaging and skills, bounded by: built-in slash commands stay routed to the lead, and model/fast-mode settings stay the lead's, not the teammate's.

Display modes: "**In-process**: all teammates run inside your main terminal... Works in any terminal, no extra setup required." "**Split panes**: each teammate gets its own pane... Requires tmux, or iTerm2." Default `"in-process"`; `"auto"` upgrades to split panes under tmux or iTerm2+it2; `"tmux"` forces split-pane; as of v2.1.186, `"iterm2"` forces native iTerm2 panes (needs the `it2` CLI and iTerm2's Python API enabled).

A fact that decides part of this, corrected per F31: idle notification still goes to the lead, not to whoever is at the seat. "How agent teams work" section: "**Idle notifications**: when a teammate finishes and stops, it automatically notifies the lead and includes its final answer in the notification. A teammate whose turn ends on an API error notifies the lead that it failed and includes the error text." So when the commander sits at a seat via the fourth type, that seat's completion and its final answer still go to the pilot, not to him — the fourth type changes who talks to the seat, not who is told it has finished.

Not documented: the human "becoming" the teammate's principal in place of the lead, or any restriction/allowance on the lead observing a direct human-teammate exchange.

Verdict, qualified: the fourth type is CLI-native behavior available today wherever agent teams are enabled and the session is interactive — see Limitations for exactly what that excludes.

## 3. Mechanisms for making a team repeatable

Source: code.claude.com/docs/en/sub-agents.md and agent-teams.md (fetched 2026-09-21 via curl).

**Agent definition files**: ".claude/agents/" (project) or "~/.claude/agents/" (user), Markdown with YAML frontmatter, "Only `name` and `description` are required." Full field list from the table: `name`, `description`, `tools`, `disallowedTools`, `model` (`sonnet`, `opus`, `haiku`, `fable`, a full model ID, or `inherit`), `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory` (`user`, `project`, or `local` — "Enables cross-session learning"), `background`, `omitClaudeMd`, `effort`, `isolation` (`worktree`), `color`, `initialPrompt`, `experimental` (`cacheTtl`). **`permissionMode` has no effect in this cockpit's mode (added per E30)**: permission-modes.md, on how the classifier checks subagent work: "While the subagent runs, each of its actions goes through the classifier with the same rules as the parent session, and any `permissionMode` in the subagent's frontmatter is ignored." For a teammate the same holds by a different route — agent-teams.md:287, already quoted above, "you can't set per-teammate permission modes at spawn time." A seat dossier that records `permissionMode` is recording a field the harness discards whenever the session runs in `auto`, which this cockpit's lead does.

**Body handling diverges by display mode (added per F7)**: "**Body**: for an in-process teammate, Claude Code appends the definition's body to its default system prompt as additional instructions. For a split-pane teammate, Claude Code uses the body in place of its default system prompt." The same seat dossier produces a different effective system prompt depending on display mode — a repeatability hazard the team-builder needs to account for if it targets both modes.

**Trust loss on resume (added per F7)**: "For a teammate it brings back, Claude Code re-applies a definition that came from a project's `.claude/agents/` directory or an `--add-dir` directory only if you've trusted the folder the agent file is in. Trusting a parent folder doesn't count. Until then, the teammate comes back with none of the definition's tools or instructions, keeping only the tools Claude Code adds to every in-process teammate." A seat dossier is not durably repeatable across a resume unless its folder is independently trusted.

**`--agents` JSON flag**: "accepts JSON with a `prompt` field plus these frontmatter fields: `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `mcpServers`, `hooks`, `maxTurns`, `skills`, `initialPrompt`, `memory`, `effort`, `background`, `omitClaudeMd`, and `isolation`." Its `permissionMode` carries the same E30 caveat as the frontmatter field above — ignored under a subagent's classifier checks, and not settable per teammate at spawn.

**Reuse as teammate**: "you can reference a subagent type from the project, user, or managed subagent scope when spawning a teammate in either display mode... This lets you define a role once, such as a security-reviewer or test-runner, and reuse it both as a delegated subagent and as an agent team teammate." Caveat: "Claude Code doesn't apply the definition's `skills` to a teammate in either display mode. The teammate loads skills from your project and user settings."

**Managed/plugin subagents**: managed subagents from org admins take precedence over project/user subagents of the same name; plugin subagents "don't support the `hooks`, `mcpServers`, or `permissionMode` frontmatter fields," for security reasons.

**Team config exists but is not a roster (corrected per F8)**: `~/.claude/teams/{team-name}/config.json` is auto-generated at session startup, updated as teammates join/idle/leave, and "removed when the session ends." It "holds runtime state such as session IDs and tmux pane IDs, so don't edit it by hand or pre-author it: your changes are overwritten on the next state update." "There is no project-level equivalent of the team config. A file like `.claude/teams/teams.json` in your project directory is not recognized as configuration; Claude treats it as an ordinary file." Pre-authoring a harness-native roster is explicitly ruled out, not merely absent — the cockpit's `team/rosters/` must stay outside the harness's own config path.

**Memory as the harness's native Maintenance mechanism (added per F9)**: the `memory` frontmatter field (`user`, `project`, or `local`) "Enables cross-session learning" — this is the only harness-native answer to "a standing team that improves over runs" in the sources read; the team-builder's Maintenance topic should reach for it rather than only inventing a cockpit-side harvesting process.

**Hooks on teammate events**: "`TeammateIdle`: runs when a teammate is about to go idle. Exit with code 2 to send feedback and keep the teammate working." "`TaskCreated`: runs when a task is being created. Exit with code 2 to prevent creation and send feedback." "`TaskCompleted`: runs when a task is being marked complete. Exit with code 2 to prevent completion and send feedback." Plus `SubagentStart`/`SubagentStop`, which also fire inside teammates. The cockpit manual's note that "exact task payload schema is not documented" checks out.

## 4. Evaluating and improving agents/teams over time

Source: platform.claude.com/docs/en/test-and-evaluate/develop-tests (fetched 2026-09-21 via the `.md` endpoint, 3326 lines).

**Success criteria must be Specific, Measurable, Achievable, Relevant**: "Bad: Safe outputs. Good: Less than 0.1% of outputs out of 10,000 trials flagged for toxicity by the content filter." "Bad: The model should classify sentiments well. Good: The sentiment analysis model should achieve an F1 score of at least 0.85 (Measurable, Specific) on a held-out test set of 10,000 diverse Twitter posts (Relevant), which is a 5% improvement over the current baseline (Achievable)."

**Grading methods, in the source's stated preference order (corrected per F5)**: "choose the fastest, most reliable, most scalable method": (1) "**Code-based grading:** Fastest and most reliable, extremely scalable, but also lacks nuance for more complex judgments that require less rule-based rigidity" — exact match, string match; (2) "**Human grading:** Most flexible and high quality, but slow and expensive. Avoid if possible"; (3) "**LLM-based grading:** Fast and flexible, scalable and suitable for complex judgment. Test to ensure reliability first then scale." Code-based is the source's first choice, not LLM-based — this is the standard for the cockpit's own improvement tests: measure files on disk where possible, before reaching for an LLM judge. Tips for LLM grading when it is used: "Have detailed, clear rubrics... A given use case, or even a specific success criteria for that use case, might require several rubrics for holistic evaluation."

**Building the test set**: "Automate when possible: Structure questions to allow for automated grading (for example, multiple-choice, string match, code-graded, LLM-graded)." "Prioritize volume over quality: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals."

**Judge design, corrected per F2**: a single LLM call with a single prompt against a rubric beat multiple judges per component: "We experimented with multiple judges to evaluate each component, but found that a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements." If the team-builder designs a judge seat, this argues for one judge call per rubric, not a panel.

**Harvesting transcripts as a method** is not named on the evals page by that term, but a native mechanism exists and round 4's F30 is correct that section 4 missed it (fixed here). `code.claude.com/docs/en/plugin-evals.md` (fetched 2026-09-21, 629 lines, raw) documents `claude plugin eval`: a case is "a realistic prompt plus one or more graders," and "A grader is a pass/fail check on what Claude produced, such as a regex over the reply, whether a particular tool was called, or a rubric that a second model judges the reply against." Graders check "the final reply, the transcript, or a file Claude created" — this is measurement against files and transcripts, the standard this flight wants. Runs per case: "One run of a non-deterministic agent tells you little, so each case runs three times by default." The baseline: "each case's runs are repeated with no plugin loaded by default, and you get two scores, `WITH` and `W/OUT`. Their difference, `Δ`, is what the plugin contributed. If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass." CI gating: "In your CI job, run the suite with `--json` to write the result for archiving, and fail the build on the exit code... pin both models so scores are comparable over time... set a cost ceiling as an upper limit." This is a ready-made shape for testing whether a roster helped or the work would have passed anyway, including a CI gate. The `memory` frontmatter field (section 3) remains the closest mechanism for cross-session learning specifically; `claude plugin eval` is the closest mechanism for measuring whether a roster or seat change is an improvement.

## Limitations of agent teams, verbatim, what each bars

Source: code.claude.com/docs/en/agent-teams.md, code.claude.com/docs/en/permission-modes.md (both fetched 2026-09-21). Section named per bullet, corrected per F32 — the first two bullets below are not from "Limitations" itself, only the remaining nine are; a twelfth (idle-row collapse) is from "Start your first agent team".

**Dropped per E29, the lead's ruling**: round 1's per-type scoring is withdrawn. Its stated rule (F34) did not match its own assignments — the `-p` bullet was scored to Autonomous in the same sentence that said it barred all four; "No nested teams" was scored to two types with no reason given why the other two escape a fact that holds identically regardless of who is at the seat; three bullets were scored against things that are not one of the four types at all (the standing team-builder idea, "any type that expects background fan-out," "the fourth type's split-pane variant"). Each limitation below is quoted verbatim with one plain sentence on what it bars, unscored. The paper maps these onto the four team types itself.

- From the top **Warning** block: "Agent teams are experimental and disabled by default," requiring `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Bars: any team of any kind before the flag is set.
- From **"Enable agent teams"**: "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates, and a subagent that Claude names runs as an ordinary subagent even with agent teams enabled." Bars: any team at all in a headless or SDK run; what runs instead is ordinary subagents.
- The remaining bullets are from **"Limitations"** itself:
- "**No session resumption with in-process teammates**: `/resume` and `/rewind` do not restore in-process teammates. After resuming a session, the lead may attempt to message teammates that no longer exist." Bars: an in-process team surviving `/resume` or `/rewind`; the lead must respawn teammates afterward.
- "**Task status can lag**: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks." Bars: a dependent task starting on time when its blocker's teammate hasn't marked it done — though the harness auto-unblocks once completion is marked ("Claude Code manages task dependencies automatically: when a teammate completes a task that other tasks depend on, it unblocks the dependent tasks without any action from you"), and `TeammateIdle`/`TaskCompleted` hooks (exit 2) let a lead force a stuck teammate to keep working or block a wrong completion with no human present. **Not currently binding in this cockpit (E35)**: this session and its teammates run models outside the default Task-tool list (see the task-list follow-up below), measured with `TaskStop` present and the other four absent — there is no task list here for status to lag on, and no `TaskCompleted` event for the hook to fire on.
- "**Shutdown can be slow**: teammates finish their current request or tool call before shutting down." Bars: an immediate stop; a shutdown request waits out the current tool call.
- "**One team per session**: a session has exactly one team, scoped to that session. You can't create additional named teams or share a team across sessions." Bars: a team persisting or being shared beyond the session that spawned it.
- "**No nested teams**: teammates cannot spawn their own teammates. Only the lead can manage the team." Bars: any teammate, at any seat, forming its own team — this holds identically no matter who is talking to that seat.
- "**No background subagents from in-process teammates**: an in-process teammate's own subagents run in the foreground... Claude Code returns an error when a teammate spawns a subagent whose definition sets `background: true`." Bars: an in-process teammate fanning further work into the background.
- "**Lead is fixed**: the main session is the lead for its lifetime. You can't promote a teammate to lead or transfer leadership." Bars: any handoff of the lead role, including to a teammate a human is directly addressing.
- "**Permissions set at spawn**: teammates start with the permission mode described under Permissions. You can change an individual teammate's permission mode after spawning, but you can't set per-teammate permission modes at spawn time." Bars: choosing differentiated permission modes per seat at spawn time — see the Autonomous precondition below for what mode a team actually runs under.
- "**Split panes require tmux or iTerm2**: the default in-process mode works in any terminal. Split-pane mode isn't supported in VS Code's integrated terminal, Windows Terminal, or Ghostty." Bars: split-pane display specifically on those three terminals; in-process mode is unaffected.

Bars: seeing or selecting an individual idle seat past three without first expanding the collapsed row — the normal case, not an edge one, at this cockpit's usual five-to-six-seat rosters.

**The Autonomous precondition, stated plainly (F33, refined per E28 against permission-modes.md)**: from agent-teams.md's Permissions section: "Teammate permission prompts appear in the lead session, so approve them there yourself." "Teammates start with the lead's permission mode, except `dontAsk` mode, which they don't inherit. If the lead runs with `--dangerously-skip-permissions`, all teammates do too." A team that "runs to a finish and reports" with no human watching halts at the first tool call that is not pre-approved and is not in a mode that skips prompting — and `dontAsk`, the one mode built for pre-approved-only work, is precisely the mode teammates do not inherit from the lead. But this cockpit's lead runs in `auto` mode (this session's teammate `meta.json` records `permissionMode: auto`), and auto mode does inherit: only `dontAsk` is excluded from inheritance, so a lead in `auto` gives its teammates `auto` too. Auto mode does not "stop and ask" the way Manual or `acceptEdits` do — "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read. Explicit ask rules still force a prompt."

Precondition (b) has an operating budget, not a single trip-wire that ends the run at the first block. permission-modes.md's "When auto mode falls back" section: "**Repeated blocks**: if the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting. Approving the prompted action resumes auto mode. These thresholds are not configurable." So a team under (b) tolerates isolated blocks and reverts to prompting only after 3 consecutive or 20 total — and once it does, the session prompts indefinitely with nobody present to answer, since the thresholds aren't configurable and nothing else clears the fallback. The same section names the third route for a session that must answer its own prompts: "**Sessions that can't prompt**: a non-interactive `-p` run without a `--permission-prompt-tool` has no prompt to fall back to. When repeated blocks reach a threshold, the action doesn't run and Claude keeps working." `--permission-prompt-tool` supplies that fallback for a headless run, but it doesn't rescue Autonomous as the idea file defines it: F11 already bars agent teams from `-p` runs entirely, so the tool answers prompts for a headless single agent or subagent, never for a team.

So Autonomous is possible today under either of two preconditions, not one: (a) the lead runs with `--dangerously-skip-permissions`, or (b) the lead runs in `auto` mode and the team's actions stay under the 3-in-a-row/20-total block budget before it reverts to prompting. A roster offered as Autonomous without naming which precondition it relies on, and its budget under (b), will eventually revert to a prompting session that nobody is present to clear.

For the commander's ruling, not a defect in this report: "One team per session" plus "No nested teams" together mean the team-builder as described (a standing team whose product is other teams) cannot itself be the mechanism that spawns the teams it designs within one continuous session — it produces dossiers and rosters that a *different* session's lead then forms into a team.

## Follow-up: tying task claims to agent types

Source: code.claude.com/docs/en/hooks.md (fetched 2026-09-21 raw, 3848 lines), plus agent-teams.md and sub-agents.md already fetched.

No hook fires on a claim or an owner change. Only `TaskCreated` and `TaskCompleted` exist among task events; `grep -n "^### Task"` over hooks.md returns exactly those two, nothing for claiming or ownership.

`TaskCreated`/`TaskCompleted` input, beyond common fields: `task_id`, `task_subject`, optionally `task_description`, `teammate_name`, `team_name` (deprecated) — no `agent_type`, no `owner`. `TeammateIdle` carries only `teammate_name` and `team_name`. None of the three carries the task's owner or any metadata field; none is documented for a task's `owner` at all. Exit code 2: `TaskCreated` deletes the task and returns the message as the tool's error; `TaskCompleted` blocks the completion and feeds the message back; `TeammateIdle` keeps the teammate working. `SubagentStart`/`SubagentStop` do carry `agent_type` — "the `name` field from the agent's frontmatter" — and fire "each time an in-process agent team teammate handles a new message," so a teammate's turn is treated as a subagent call for these two events specifically.

`PreToolUse` "[m]atches on any tool name except `EndConversation`," so a matcher on `TaskUpdate` is available, but hooks.md gives no per-field `tool_input` schema for `TaskUpdate` the way it does for `Bash` or `Write` — the `owner` field the pilot measured is undocumented here too. Common input fields add `agent_id`/`agent_type` "when the hook fires inside a subagent call" or under `--agent`; whether a `PreToolUse` hook on an in-process teammate's own tool call counts as "inside a subagent call" for this purpose is not stated outright — `SubagentStart`/`Stop` say so explicitly for teammates, `PreToolUse`'s common-fields note doesn't name teammates, so this is an inference, not a quote.

Teammate spawn from a definition (agent-teams.md, "Use subagent definitions for teammates") applies exactly five parts, named as a closed list: `tools` (plus `SendMessage`, and the four Task tools when the session has them), `model`, `Body`, `skills` (explicitly *not* applied — "The teammate loads skills from your project and user settings"), and `mcpServers` (split-pane only). `hooks` and `memory` are absent from that list; sub-agents.md's own hooks section says frontmatter hooks "fire when the agent is spawned as a subagent through the Agent tool or an @-mention, and when the agent runs as the main session via `--agent`" — teammates aren't named. Checked twice for "teammate" beside "memory" and "hooks" across both pages: no other occurrence. A definition's `hooks` and `memory` fields appear not to reach a teammate at all.

Task `metadata`: not documented. No occurrence of a task metadata field in hooks.md, tools-reference.md, interactive-mode.md, or agent-teams.md.

**On Or079**: `agent_type:` frontmatter, well-written, reaches `SubagentStart`/`SubagentStop` reliably for a teammate's own turn boundary, and (unconfirmed) may reach `PreToolUse` on the teammate's calls. It reaches no task-claim event, because none exists, and it does not travel with `TaskCreated`/`TaskCompleted`/`TeammateIdle` at all — those carry `teammate_name`, a seat's chosen name, not its type. Relying on `agent_type:` to gate *which task a type may claim* has no hook to enforce it on; enforcing "only this type claims this task" today would need a `PreToolUse` hook on `TaskUpdate` reading the undocumented `owner`/type fields from `tool_input` and the inferred `agent_type` from common fields — built and tested, not read off the docs.
