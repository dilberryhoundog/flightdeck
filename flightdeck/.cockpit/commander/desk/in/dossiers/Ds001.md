## The situation in one paragraph

Flightcrew has a finished, unmerged test suite that describes it whole, a held core spec waiting on that suite, and a three-launch roadmap written by the commander that only ever reached launch 1's spec. Both runs that ever succeeded were conducted by hand because the tooling could not conduct them. The doctrine layer is stable and good; the harness facts under it are partly folklore. The next move is to land the suite, and the next two moves after that are already written in the commander's own plan.

## What a launch is

Corrected by the commander on 2026-09-18: a launch is an intent to complete a piece of work and includes all the infrastructure to do it, the runs (attempts at completing the work), the spec and its versions as runs converge on done, and the run-generated artefacts. What follows is the v1 runner's mechanical view of one run, kept because it is what the commands do today. A run sits in a folder under `../../../launch`, produced in a fixed order: the launch record, the pinned spec and tests map, the kickoff rendered from parts, the plan, the returns of each dispatched agent, the event and hook logs, the evidence per check, the critic passes, notes, the report, and finally a ledger entry in the runlog. Phases run targets, plan, contracts, implement, verify, review, report, ended, and three human gates sit at plan, contracts and report. A check is one row of the tests map; a gate is a barrier that reports red checks and leaves the decision to the caller. The one complete example is the buildout-2 launch folder. Detail: `runs-recon.md` sections 1 and 2.

## How the system got here

1. **Main** is the first foray, early September: scaffold, doctrine by hand, a crew manifest, four mission notes the commander wrote and never opened. Its flightcrew directory is a different system from everything after it; treat nothing in it as current.
2. **Three early branches** tried to build piece by piece: engage-crew built roles, constitution-research wrote the orchestration principles, rubric-testing measured judges across model tiers. All three stopped without an ending. Their difficulty forced the all-in-one build.
3. **Buildout** is the all-in-one build by a workflow agent: runner, hooks, workflows, crew, schemas, manuals, a 30-suite testbench. It ran itself twice. The first run was abandoned at verify because two locked checks could not be satisfied by any faithful implementation. The second passed all checks and was accepted with reservations, one of which is that the run edited locked files and legitimised it afterwards by re-pinning. The commander's discovery pass then found 58 defects, distilled them to ten problems, and wrote the ten-feature roadmap split into three launches: core (the ground), conduct (a run under its own power), verdicts (the check rail). The last commit on buildout, 15 September, added the spec-altitude doctrine and rewrote the interfaces domain; no later branch has either.
4. **Core** is launch 1's spec, driven by the ten problems. It was frozen, then reopened for the altitude rewrite, so its freeze is void. It carries no repair work. Its one commit of its own is the commander saving 47 suites a test-builder wrote against the future system. The core run never ran: its logs are zero bytes. The spec has nine contradictions and 71 lint errors to clear before it can freeze again.
5. **Characterization** is the test suite for the system as it stands, so the core repair can be made with eyes open. Run 1 was abandoned when ten tooling faults stopped the contracts unit with no return; its runlog entry is the best diagnosis in the repo and names what must reach the core spec. Run 2 was fixed by not using the tooling: a custom workflow, no runner, no hooks, every agent on Opus, contracts first then a four-unit fan-out. Result: 58 of 61 checks green, six defects pinned. The three reds are all human decisions, not crew work. This finished suite lives only on the run 2 branch, 16 commits past the branch anyone would look at, with no pull request and no runlog entry.
