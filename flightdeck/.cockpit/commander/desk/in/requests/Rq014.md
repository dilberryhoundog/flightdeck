# Rq014 — Build the pilot's agent body

A build request. The commander's orders Or036, Or060 and Or061 are the standard. Pass 2, revised after a commander-advocate attack (`records/notepad/agent-body-2026-09-20/advocate-rq014.md`, twelve findings, all taken). Every ruling of the pilot's is under "Pilot's rulings" and may be struck.

## Mini-spec

### Goal
- The pilot is launched as an agent. What Or036 says was lost, "do no work, manage teams instead", is stated in the agent body in plain words, with the session start and end procedures. The cockpit `CLAUDE.md` holds only rules of the place, so crew working in the cockpit never mistake themselves for the pilot. The session opens already logged on, without the commander typing the order.

### Scope in
- `team/officers/pilot/pilot.md`, the agent definition, beside `job.md`. Frontmatter is the agent's own keys and nothing else: `name: pilot`, `description`, `model: fable`, `effort: medium`, `initialPrompt`. The body carries, first and in plain words, the role scoping: the pilot flies the mission and does no work; it manages teams instead; it presides over the room, distils, requests, and the commander approves, denies or changes. Then: chain of command and the two standing orders now in `job.md`; session start; session end; and what the cut below sends it.
- `initialPrompt` is an order to log on that is safe to fire twice: if this session's log already exists, the pilot reports status and opens no second log or manifest row.
- `base/bin/pilot.sh`: reads `pilot.md`, builds the `--agents` JSON from its frontmatter and body, passes `--agents` and `--agent pilot` on every start and every resume. It appends `identity.md` and `commander.md` and no longer `job.md`. The model it re-asserts on resume is read from `pilot.md`. `--check` names the files actually joined (today the placeholder is a fixed string) and can print the agents JSON so it can be inspected.
- `base/settings/pilot.settings.json`: `model` and `effortLevel` removed. Everything else stays.
- `base/bin/session-start.sh`: the line telling the session to follow the session start procedure is removed, as Or036 says the body does that now. The hook keeps printing the facts the body cannot know: session id, log name, mission, awaiting requests.
- Cockpit `CLAUDE.md`: cut by the test under "Pilot's rulings". The "Who is here" line on the pilot names `pilot.md`.
- `job.md`: stays on disk for the commander to judge and remove. Its "Where the rules are" paragraph is corrected to say the rules of the job are in `pilot.md` and that the launcher no longer loads this file, so the copy he judges is not false.
- References that name `job.md` as where the rules of the job live (`team/officers/pilot/README.md`, `identity.md`, `base/README.md`, the launch manual) follow.

### Scope out
- `procedures.txt` (Or060: later). Hooks stay in the settings file; making the injected settings redundant is later (Or061: "eventually"). Removing `job.md`: the commander's act. Any file outside the cockpit, including `.claude/agents/`. The guard. A schema for `pilot.md`.

### Constraints
- The body is written for any model in the seat and any session: no session context, no callsign (that is `identity.md`), universal terms.
- Nothing is lost in the move: every sentence leaving `CLAUDE.md` is in `pilot.md`, or the builder's report names it as dropped with a reason. The adversaries check this; no table is kept.
- `*.keep` files, session logs and order texts untouched. Small, plain shell; the frontmatter reader is a few lines of `python3`, which the launcher already uses.
- Crew do not commit. The pilot verifies and commits.

### Decisions already made (the commander's)
- The body replaces the default system prompt (Or060). `pilot.md` goes in the pilot office beside `job.md`; flightdeck keeps a store of agents, and when it becomes distributable a simple command transfers them (Or060, Or061). No schema; the path kept out of the yaml (Or061). Model and effort in the agent body, not the settings (Or061). The session auto prompted (Or061). The commander tests teammate inheritance after the build (Or061). What moves out of `CLAUDE.md` is the pilot's to rule (Or060).

### Pilot's rulings
- The cut test: a line leaves `CLAUDE.md` when it is addressed to the pilot by role, or when a crew member obeying it would do wrong. By that test: session start and session end leave (crew would open logs); rule 5 leaves (crew are sent to dig); rule 10 leaves (crew update only what a brief scopes); rule 12 leaves; crew protocol items 4 to 7 leave (verifying and filing crew reports, keeping teammates, recording the team are the pilot's); the triggers import leaves, becoming a plain instruction in the body to read `work/procedures/triggers.md`, since an `@` import does not expand outside `CLAUDE.md`. Crew protocol items 1 to 3 stay (teammate or subagent, name the model, brief completely), because crew who dispatch need them. Rule 7 stays. Each rule that leaves keeps its number as a one-line pointer, as rule 1 did, so numbers cited across the cockpit do not shift.
- Lint: the existing glob `team/officers/**/*.md` catches `pilot.md` and faults it for having no `type` (tested by the pilot with a probe file). Settled by the commander (Or062, De028): narrow the glob to the three dossier files unless the linter supports exclusions. It does (`lint.yaml` already carries `!**/README.md`), so one line is added, `!team/officers/pilot/pilot.md`.
- No `--legacy` flag. The fallback is the restore commit: if the new launch fails, `git revert` of the build commit restores today's launcher and settings together. A legacy path would lose its model and effort the moment the settings keys go.
- If the harness verifier finds that `effort` in an agent definition does not apply to a main session agent, or does not hold on resume, `effortLevel` stays in the settings file, the finding goes in the launch manual, and a workshop item carries it. The model half lands regardless.
