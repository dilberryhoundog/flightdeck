=== 1. ORIGINAL ===
Create consistency in json data.

MANIFESTS:
lightweight named manifest (recognisable in streaming output) eg orders/MANIFEST-orders.json
points towards JSON file units. eg orders/Or001.json

IDENTIFIERS:
shape = <abbreviation> + <number>
abbreviation = 1-3 letters.
  single capital - commonly recognised units. eg teams = T, Procedure = P
  double/triple capital - Reconisable words combined. eg Commanders Advice = CA
  number - 3 digits. eg 001, 002,

NAMING:
- change desk/in/proposals to desk/in/requests. Prevents conflict with procedure ID. eg Rq001, Rq002. Replace existing "proposal" and "P" references.

The manifest records the collection of units. token efficient, enough data for unit disclosure.
Units allow rich recording of data. prevents large singular files of data that blows budgets.
Flow = agent needs context --> manifest --> unit

Identifiers used across the application. each ID mentioned in claude.md simple two column table.
suggested patterns Ds = dossier, P = procedure,

Pilot requests changes to commander. refactor team helps, including mini adversaries.

=== 3. WHAT EXISTS NOW ===
Identifiers in use: M mission, WS work shop item, P procedure (P001 to P006), Sp spark, Ds dossier, Rq request, CA commander's advice, Or order, De decision, T dispatch; C retired. The table is in CLAUDE.md. Accumulating items are filed by ID alone (Ds006.md, Rq013.md, Or057.json); missions and procedures by ID and name; rosters and crew seats by name.
Manifests: fifteen MANIFEST-<collection>.json files, each with kind as its first key and a units array whose rows give id or name, a one-line title or verbatim summary, date, status where there is one, and the unit's path. Orders, decisions, dispatches, workshop items and rosters were single files and are now a manifest plus one JSON unit each (126 units); the rest point at markdown units. One global MANIFEST-dispatches.json; dispatch units in records/dispatch/cockpit/. Order text is byte-identical to before.
