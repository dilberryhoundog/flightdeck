# Practice scout — official Anthropic guidance on cross-session knowledge

Fetched 2026-09-19 via `curl` on raw HTML/markdown, greenpaths confirmed against the raw file, not the WebFetch summariser. Claude Code docs versioned to whatever `code.claude.com/docs` currently serves (no CLI version banner on the page itself, unlike the pilot's own harness records).

## CLAUDE.md (instructions the pilot writes)

What: version-controlled markdown loaded into every session as a user message after the system prompt. Confirmed-raw, https://code.claude.com/docs/en/memory.md, fetched 2026-09-19.
Loads: always, at session start, for every level of the directory hierarchy above the working directory. Nested CLAUDE.md files load on demand when files in that subdirectory are opened.
Size guidance (confirmed-raw): "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Files over 4 MiB are skipped entirely.
When to add (confirmed-raw, exact list): "Claude makes the same mistake a second time" / "A code review catches something Claude should have known about this codebase" / "You type the same correction or clarification into chat that you typed last session" / "A new teammate would need the same context to be productive." If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead.
Writing guidance (confirmed-raw): "Specific, concise, well-structured instructions work best" — concrete over vague ("Use 2-space indentation" not "Format code properly"), markdown headers/bullets over prose paragraphs.
Consistency: contradicting rules across files cause Claude to "pick one arbitrarily" — review periodically to remove outdated/conflicting instructions.
Survives `/compact`: only project-root CLAUDE.md is re-read from disk and re-injected after compaction. Nested CLAUDE.md and path-scoped rules reload only as files they cover are opened again. A conversation-only instruction is lost unless written to CLAUDE.md.
Relevance to the pilot: `records/` under the cockpit's own docspec is functionally a hand-rolled CLAUDE.md-adjacent mechanism, but records are not auto-loaded — they are read on demand, closer to a skill or rule in loading behaviour, not to CLAUDE.md itself.

## `.claude/rules/` (path-scoped instruction files)

What: one file per topic in `.claude/rules/`, each covering one topic with a descriptive filename. Confirmed-raw, same source, fetched 2026-09-19.
Loads: rules with no `paths:` frontmatter load unconditionally at launch, same priority as `.claude/CLAUDE.md`. Rules with `paths:` frontmatter (glob patterns) load only when Claude reads a file matching the pattern — genuine just-in-time loading tied to file access, not topic relevance.
Quoted distinction (confirmed-raw): "Rules load into context every session or when matching files are opened. For task-specific instructions that don't need to be in context all the time, use skills instead, which only load when you invoke them or when Claude determines they're relevant to your prompt."
Relevance: this is the mechanism closest to "load a note only when it's needed," but the trigger is a file-path match, not a semantic judgment of relevance — it would not fit "load a record when the pilot is about to do X kind of work" unless X always touches a specific path.

## Skills (`SKILL.md`)

What: markdown with YAML frontmatter; body content only loads when the skill is invoked (by the model recognizing relevance from `description`, or by explicit `/name`). Confirmed-raw, https://code.claude.com/docs/en/skills.md, fetched 2026-09-19.
Loads: on demand — "Unlike CLAUDE.md content, a skill's body loads only when it's used, so long reference material costs almost nothing until you need it" (confirmed-raw). Anthropic's context-engineering post calls this general pattern "progressive disclosure" (see below); the skills doc itself never uses that phrase, so the label is the engineering post's, not the product doc's.
When to create one (confirmed-raw): "when you keep pasting the same instructions, checklist, or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact."
Two content types named in the doc: "reference content" (knowledge Claude applies inline — conventions, patterns, domain knowledge) versus "task content" (step-by-step procedures, often invoked directly with `/name`). This maps directly onto the T009 question's split between a record (a settled fact/topic) and a procedure.
Persistence once loaded: "the rendered SKILL.md content enters the conversation as a single message and stays there across later turns... Claude Code does not re-read the skill file on later turns, so write guidance that should apply throughout a task as standing instructions rather than one-time steps." A stale skill snapshot can outlive an edit to the file within one session.
Conciseness instruction (confirmed-raw): "Keep the body itself concise... every line is a recurring token cost. State what to do rather than narrating how or why, and apply the same conciseness test you would for CLAUDE.md content."
Compaction: re-attached after auto-compaction up to a combined 25,000-token budget across all invoked skills, most-recent-first; older skills can be dropped entirely.
Relevance: a skill triggered by topical `description` match is the closest official mechanism to "the pilot reads one file for one question at the right moment" — closer than a rule (path-triggered) or CLAUDE.md (always-on).

## Subagent `memory` field

What: gives a named subagent definition a persistent directory (`.claude/agent-memory/<name>/` for project scope) that survives across separate subagent invocations, holding an index `MEMORY.md` plus topic files, exactly mirroring the auto-memory shape. Confirmed-raw, https://code.claude.com/docs/en/sub-agents.md, fetched 2026-09-19.
Loads: subagent's system prompt always includes the first 200 lines or 25KB of its `MEMORY.md`, whichever is smaller; topic files are read on demand by the subagent's own tool calls, not preloaded.
Recommended scope (confirmed-raw): "`project` is the recommended default scope. It makes subagent knowledge shareable via version control."
Recommended prompting pattern (confirmed-raw, given as a literal instruction to put in the subagent's own markdown body): "Update your agent memory as you discover codepaths, patterns, library locations, and key architectural decisions. This builds up institutional knowledge across conversations. Write concise notes about what you found and where." Also: explicitly tell the agent to consult memory before starting ("check your memory for patterns you've seen before") and to update it after finishing ("save what you learned to your memory").
Relevance: this is Anthropic's own recommended shape for exactly the T009 problem — a long-running role that must retain settled knowledge cheaply. It is a second, independent instance of the MEMORY.md index + topic-file pattern below, confirming it's a deliberate design, not a one-off.

## Auto memory (main-conversation `MEMORY.md` + topic files)

What: Claude writes its own memory files without being asked, using four typed categories in frontmatter: `user`, `feedback`, `project`, `reference`. Confirmed-raw, same source, fetched 2026-09-19 — this is the literal template this session's own `~/.claude/.../memory/` directory already follows (visible in this conversation's system reminders).
Storage: `~/.claude/projects/<project>/memory/MEMORY.md` (index) plus one file per memory, `type_slug.md`.
Loading rule (confirmed-raw, exact number): "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Content beyond that threshold is not loaded at session start." Topic files are never preloaded — read on demand with normal file tools.
Self-pruning behaviour (confirmed-raw): "If the file is near a limit, Claude Code reminds Claude to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries. If the file is over a limit, the write still succeeds, but Claude Code returns an error telling Claude to rewrite the index, because everything past the limit is dropped on the next load." This is a built-in, tool-enforced staleness/size discipline — the harness itself nags the agent to prune, rather than relying on a human editor.
Filtering rule (confirmed-raw): "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." And: "Claude doesn't save something every session. It decides what's worth remembering based on whether the information would be useful in a future conversation" — i.e. the trigger is "will this matter later," decided by the writing agent itself, not a scheduled or externally-imposed cadence.
Validation/currency: no built-in review step beyond the size nag; `modified` frontmatter timestamp (ISO 8601, added automatically once a file has frontmatter, v2.1.214+) is the only freshness signal, and it's descriptive, not enforced. Human review is manual via `/memory`.
Relevance: this is the single closest official precedent to the whole T009 question, including the index/topic-file split the cockpit's `records/` + `README.md` already mirrors, the "one line per entry in the index, detail lives in the topic file" pattern, and the "write it only when it would help a future session" trigger the commander is independently reaching for in DS003.

## SessionStart hooks

What: hook script fires at session start/resume/clear/compact/fork, stdout injected as context. Confirmed-raw, https://code.claude.com/docs/en/hooks.md, fetched 2026-09-19.
Explicit boundary (confirmed-raw): "For static context that doesn't require a script, use CLAUDE.md instead." Anthropic positions hooks for dynamic, computed context (recent changes, open issues), not for static reference notes — this rules hooks out as a record-delivery mechanism unless a record's content must be computed at read time.
Relevance to T009: low. Records are static prose, not computed state; a hook is the wrong tool for delivering them, confirming records belong in a file the pilot reads, not a script that injects them.

## Structured note-taking / compaction (engineering blog: "Effective context engineering for AI agents")

Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents, fetched 2026-09-19, confirmed-raw against the page's stripped text.
Just-in-time vs preloading (confirmed-raw): "Rather than pre-processing all relevant data up front, agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools." Followed by: "Letting agents navigate and retrieve data autonomously also enables progressive disclosure — in other words, allows agents to incrementally discover relevant context through exploration... Agents can assemble understanding layer by layer, maintaining only what's necessary in working memory and leveraging note-taking strategies for additional persistence."
Structured note-taking defined (confirmed-raw): "a technique where the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times... This strategy provides persistent memory with minimal overhead. Like Claude Code creating a to-do list, or your custom agent maintaining a NOTES.md file, this simple pattern allows the agent to track progress across complex tasks."
Compaction defined and scoped (confirmed-raw): "Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary... Compaction typically serves as the first lever." Explicitly compared to note-taking: "Compaction maintains conversational flow for tasks requiring extensive back-and-forth; Note-taking excels for iterative development with clear milestones." This is a direct statement of when each applies — the pilot's cross-session gap (no conversational continuity at all) is squarely the note-taking case, not the compaction case.
Closing principle (confirmed-raw, worth quoting whole): "the guiding principle remains the same: find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome." This is the standard the commander's "cost in proportion to use" framing in DS003 already matches.

## Multi-agent memory-under-truncation (engineering blog: "Multi-agent research system")

Source: https://www.anthropic.com/engineering/multi-agent-research-system, fetched 2026-09-19, confirmed-raw.
Plan persistence against truncation (confirmed-raw): "The LeadResearcher begins by thinking through the approach and saving its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan." This is the closest official statement to "write it down before it can be lost," applied to a coordinator role analogous to the pilot.
Handoff pattern under context limits (confirmed-raw): "We implemented patterns where agents summarize completed work phases and store essential information in external memory before proceeding to new tasks... they can retrieve stored context like the research plan from their memory rather than losing previous work when reaching the context limit." Distinct from auto memory: this is manually engineered by the application, not the harness's built-in feature — evidence that "summarize a finished phase into a persistent note" is a validated pattern independent of which product surface implements it.
Artifact-and-reference pattern (confirmed-raw): "implement artifact systems where specialized agents can create outputs that persist independently. Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator." Maps onto the cockpit's crew-writes-to-notepad / pilot-reads-a-reference structure already in place.

## API memory tool and context editing (platform.claude.com — lower relevance)

These are raw-API primitives (`memory_20250818` tool type; `context-management-2025-06-27` beta for `clear_tool_uses_20250919`), confirmed present on the pages fetched 2026-09-19, but they are building blocks for someone implementing an agent harness from the API directly, not a Claude Code feature the pilot can invoke. The memory tool's own house rule, quoted verbatim from its system-prompt template (confirmed-raw): "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" and "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory" — the same discipline Claude Code's auto memory and subagent memory already build in for the pilot, so no new mechanism to adopt here, just corroboration of the same design principle from a third independent surface.

## `@` imports in a nested CLAUDE.md (added for the trigger-manifest option)

Source: https://code.claude.com/docs/en/memory.md, same fetch, confirmed-raw against the raw file, re-checked 2026-09-19.
Nested file, not root, still supports `@` imports: the import syntax is stated generally — "CLAUDE.md files can import additional files using `@path/to/import` syntax" — with no restriction to the root file. But whether the import fires at launch or on demand depends on where the *importing* file sits relative to the session's working directory, not on the import mechanism itself. Confirmed-raw, "How CLAUDE.md files load": "Claude Code loads CLAUDE.md and CLAUDE.local.md from your current working directory and every directory above it." And separately: "Claude also discovers CLAUDE.md and CLAUDE.local.md files in subdirectories under your current working directory. Instead of loading them at launch, they are included when Claude reads files in those subdirectories." So: if the cockpit `CLAUDE.md` sits at the pilot's own working directory (the environment reminder for this session gives the working directory as `flightdeck/.cockpit`), it loads at launch like a root file, and its `@` import of the trigger manifest expands at launch too. If some other session instead launches from the repo root with `flightdeck/.cockpit/` as a true subdirectory below its working directory, that CLAUDE.md — and its import — would load only once that session reads a file inside `.cockpit/`, not at startup. Worth the option-maker confirming which working directory the pilot's sessions actually launch from before relying on always-at-launch behaviour.
Relative path resolution (confirmed-raw): "Both relative and absolute paths are allowed. Relative paths resolve relative to the file containing the import, not the working directory." A relative path in the cockpit CLAUDE.md's `@` import resolves from `flightdeck/.cockpit/`, wherever the session's working directory actually is.
Recursive expansion and depth (confirmed-raw): "Imported files can recursively import other files, with a maximum depth of four hops." So the manifest file could itself `@import` further files, up to four hops deep from the CLAUDE.md that first references it.
Code spans and fenced blocks are excluded (confirmed-raw): "Import parsing skips Markdown code spans and fenced code blocks. To mention a path in your CLAUDE.md without importing it, wrap it in backticks: writing `` `@README` `` keeps the text literal, while `@README` outside backticks imports the file." An `@path` written inside a fenced code example anywhere in the manifest or the CLAUDE.md is inert, not an import.
First-use approval dialog (confirmed-raw): "An import in a project-level memory file is external when its path resolves outside your working directory... The first time Claude Code encounters external imports in a project, it shows an approval dialog listing the files. If you decline, the imports stay disabled and the dialog doesn't appear again." This only triggers for a path that resolves *outside* the working directory — a manifest file living inside the repo (e.g. still under `flightdeck/.cockpit/`) is not external and shows no dialog; a manifest imported from somewhere like the commander's home directory would be, and a one-time accept/decline gates it silently thereafter with no further prompts either way.
Size guidance for CLAUDE.md plus imports (confirmed-raw): "target under 200 lines per CLAUDE.md file" applies per file, including the importing CLAUDE.md and the imported manifest separately — there's no combined budget stated, but also no discount: "Splitting into `@path` imports helps organization but doesn't reduce context, since imported files load at launch." A 4 MiB hard cap applies to any single file; anything larger is skipped outright rather than trimmed.

## What the docs imply for a record-keeping method

Three independent official surfaces — auto memory, subagent `memory` field, and the multi-agent research post — converge on the same shape: an index file capped small (200 lines / 25KB is the harness's own number) listing one line per topic, with full detail in separate topic files read only on demand. The cockpit's `records/README.md` + `records/*.md` already is this shape; DS003's complaint was about production (written speculatively, from one thin source) not structure.
Trigger: official guidance never schedules note-writing; it triggers on "would this matter to a future session" (auto memory) or "before truncation, before ending a phase" (research system) — both retrospective, judged by the agent that just did the work, matching the commander's "write it when the pilot drifts or underperforms" instinct rather than upfront production.
Loading: CLAUDE.md is always-on and penalizes size; rules load on path match; skills load on topical relevance (closest to "the pilot reads one file for one question at the right moment"); auto memory's topic files load only when opened. A record equivalent to a `records/*.md` file behaves most like a skill or an auto-memory topic file, not like CLAUDE.md — it should never be preloaded in bulk.
Validation: no official mechanism reviews agent-written memory before it's trusted; the only safeguard found is size-triggered self-pruning (auto memory) and the human's own `/memory` audit. The commander's insistence on reading records before they land, and on a team validating before promotion, has no official counterpart to defer to — it is a locally-invented control, and the docs don't argue against it.
Cost: the "4× tokens vs chat, up to 15× for multi-agent" figure from the research-system post is a caution specifically about production cost of using teams to write records, not upkeep cost of records once written — worth naming to the option-maker as the actual cost driver DS003 is reacting to.
