## 5. Markdown metadata

Two metadata conventions currently coexist:
- **Legacy bolded list** (`- **Field:** value`), used throughout most existing markdown: mission files, proposal bodies (below the frontmatter block — see below), dossier bodies, README files, records. Fields vary freely by author/document, e.g. dossiers use Written/From/Mission/Proposals arising (`commanders-desk/in-dossiers/README.md`); proposals use Status/Raised/Mission/Dossier (`base/README.md`); missions use a longer numbered header per `missions/README.md`.
- **New YAML frontmatter**, present only in the five worked examples the commander left uncommitted: `DS001-flightcrew-recon.md`, `P004-open-missions-from-the-cut.md`, `CA001.md`-`CA003.md`. Fields by document:
  - DS001: `type, unit, stamp, work, context, generates` (6 fields). `stamp` bundles date + pilot name + session id into one value; `generates` lists 4 proposal ids.
  - P004: `type, unit, status, recorded, work, context` (6 fields, `status` and `recorded` both left empty/null).
  - CA001/CA002/CA003: `type, unit` only (2 fields each) — no `stamp`, `work`, or `context`, i.e. the shape is not yet consistent even across the five examples the commander supplied.
  - Duplication against JSON manifests: `unit` duplicates the id already minted in the room's JSON register (`dossiers.json`, `base/proposals.json`); `work` (mission id) is not currently tracked per-dossier or per-proposal in either manifest, so it isn't a duplicate yet, but would become one the moment a manifest schema added a `mission` field; `status` on P004 is currently blank in the frontmatter while `base/proposals.json` already carries a `status` field per proposal — if both were populated, this is the clearest duplicate-source-of-truth risk named in the pilot's working view.
- YAML validity, tested with `python3 -c "import yaml"` via a local venv (`pyyaml` installed for this check, base interpreter had no `yaml` module): **P004, CA001, CA002 and CA003 parse as valid YAML.** **DS001 does not parse** — both its `stamp:` line (`stamp: "2026-09-18", "Pilot: Ace", "session dcb75456"`) and its `generates:` line (`generates: "P004", "P005", "P006", "P007"`) are comma-separated quoted strings with no flow-sequence brackets (`[...]`), which is not legal YAML scalar or block syntax; a strict parser raises `while parsing a block mapping ... expected <block end>, but found ','` at the `stamp` line first. Isolating `generates` alone (with `stamp` removed) confirms it independently fails the same way. This is the single worked example with the richest field set and it is also the one that would break any tool trying to actually parse the frontmatter as YAML.
- How an agent would search it today: there is no tooling in the cockpit that reads frontmatter (no script greps `^unit:` or similar); the only "search" mechanism referenced anywhere is prose instruction (CLAUDE.md, README files) telling the pilot which JSON manifest or index file to open for a given fact. Frontmatter's stated purpose (`frontmatter.txt`: "better searchability across markdown corpus") is not yet backed by any read path — a grep across `type: "Dossier"` would work today by accident (plain text match) but a real YAML-aware query would fail on DS001, the only example with enough fields to be worth querying.
