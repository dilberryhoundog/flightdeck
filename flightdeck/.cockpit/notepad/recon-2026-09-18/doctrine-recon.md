## 1. Terms a pilot must know
- check — any executable verification, test or otherwise, that returns pass or fail. `flightcrew-characterization:library/terms.md`
- target — a check that exists before the work and is locked against it. `flightcrew-characterization:library/terms.md`
- gate — the point where check results decide whether work stops or continues. `flightcrew-characterization:library/terms.md`
- class — one of the kinds of check, distinguished by what it proves. `flightcrew-characterization:library/terms.md`
- verdict — the signal a check returns: exit code, ratio, or verdict sheet. `flightcrew-characterization:library/terms.md`
- probe — a fresh session/agent whose only job is to be an ordinary user of the artefact. `flightcrew-characterization:library/terms.md`
- record — the captured transcript and outputs of one probe run. `flightcrew-characterization:library/terms.md`
- fixture — the known input a check runs against. `flightcrew-characterization:library/terms.md`
- check class — the declared method by which a behaviour will be falsified. `flightcrew-characterization:library/terms.md`
- scenario — a fixed starting prompt and context under which the agent is exercised. `flightcrew-characterization:library/terms.md`
- judge — an isolated evaluator that grades a transcript/artefact against a rubric. `flightcrew-characterization:library/terms.md`
- ID — the stable number a behaviour, edge case or constraint carries for life. `flightcrew-characterization:library/terms.md`
- domain — one of the nine named parts of a spec. `flightcrew-characterization:library/terms.md`
- freeze — the moment a spec stops changing and work begins against it. `flightcrew-characterization:library/terms.md`
- rubric — the written instrument a judge grades against. `flightcrew-characterization:library/terms.md`
- verdict sheet — the judge's output: per-question answers with quotations. `flightcrew-characterization:library/terms.md`
- critical question — one whose failure fails the behaviour outright. `flightcrew-characterization:library/terms.md`
- launch — one self-contained orchestrated build run with its own specs and checks. `main:flightdeck/STRUCTURE.md`
- deck — a single installed `flightdeck/` scaffold within a project. `main:flightdeck/STRUCTURE.md`
- keep file — a `<task>.keep` file naming/describing a folder's default task. `main:flightdeck/STRUCTURE.md`
- gate G1/G2/G3 — human decision points at plan, contracts-landed, and report. `flightcrew-characterization:flightdeck/flightcrew/crew/orchestrator.md`

## 3. The spec doctrine
- **Description** (`flightdeck/manuals/spec/spec-description.md`, frozen, unchanged main→tip): a spec is the single written definition of a piece of work, organised into nine domains — Intent, Scope, Constraints, Interfaces and contracts, Behaviours, Edge cases and failure modes, Prior decisions and non-goals, Verification, Definition of done. Order of completion is fixed (intent alone first; scope+non-goals together; constraints; interfaces; behaviours+edge cases together; verification+definition of done together, last). A spec freezes before work begins and changes only via a new version, never after work starts; zero open questions at freeze.
- **Conventions** (`spec-conventions.md`, frozen, unchanged): schema rules (immutable version files, canonical node IDs `B`/`E`/`C`/`D` etc., `retired` registry, one decision per entry), human/agent-building/agent-reading/hygiene/run conventions, and an explicit "what a spec is not" list (not a plan, not the kickoff, not a PRD, not documentation, not a wish list, not a prompt).
- **Verification addendum** (`verification-addendum.md`, frozen, unchanged): governs agent-shaped work. Four check classes in preference order — Deterministic, Property, Statistical, Judged — each behaviour tagged with exactly one, never reworded into a cheaper class. Trajectory checks are invariants over the path, never a golden-trajectory comparison. Definition of done restated per class, plus one human-read transcript chosen by the reviewer.
- **Altitude** (`spec-altitude.md`) existed only on `flightcrew-buildout` (84 lines) and was **deleted going into `flightcrew-characterization`** — a whole doctrine document ("altitude is everything," the too-high/too-low antipatterns, the draftsman analogy) that never reached the tip. `git diff flightcrew-buildout..flightcrew-characterization` shows it as a pure deletion, no replacement content elsewhere. [Pilot: added after the fork by 1c81888; never on the tip. See header.]
- **Who judges / what freezes it**: the human decides readiness and performs the freeze; the spec-judge answers a fixed rubric (`checks/rubrics/spec/spec-readiness-rubric.md`) with yes/no+quotation, never a score; the spec-attacker (fresh context, draft + project root only) hunts holes; the interviewer/spec-builder never freezes its own work. `flightcrew-characterization:flightdeck/flightcrew/crew/{spec-judge,spec-attacker,spec-builder}.md`, `library/spec/interview-session-conventions.md`.

## 4. Testing and versioning doctrine
- **Testing description** (`testing-description.md`, frozen, unchanged): seven check classes — Structural, Behavioural, Artefact, Invariant, Project rules, Statistical, Judged — three verdict types (exit code / ratio / verdict sheet), a four-rung gating ladder (in the prompt → goal condition → deterministic gate → second-opinion refutation), and four placements a check migrates through (standalone → embedded → chained → enforced).
- **Testing conventions** (`testing-conventions.md`, frozen, unchanged): checks belong to a spec, map bidirectionally to `B`/`E`/`C` IDs, one check proves one thing, checks are locked/read-only to implementing agents, humans freeze targets and update goldens, "tested thoroughly" is not evidence.
- **Rubric guide** — moved from `library/rubrics/rubric-guide.md` (main, buildout) to `flightdeck/manuals/testing/rubric-guide.md` (characterization); content unchanged, just relocated into the manuals tree and reclassified from library ("for humans") to a crew-facing manual. Defines rubric anatomy (header, question blocks, pass rules, verdict-sheet format), writing rules (answerable from material alone, quotable by construction, uniform polarity, one fact per question), and a mandatory calibration step against 3–5 pre-graded examples.
- **Spec versioning** (`spec-versioning.md`, frozen) and **tests-map versioning** (`tests-map-versioning.md`, frozen): immutable version files per spec/map, permanent IDs, `status` field (`new`/`ok`/`changed`) relative to the previous version only, append-only `retired` registry with mandatory `note`, a map pins the exact spec commit it satisfies and goes stale if a newer spec freezes. The tests-map file differs from main only in line-wrap formatting — content is byte-identical in substance (confirmed by direct comparison of main vs. tip text).

## 5. Rubric doctrine and adversarial mandate
- Rubric guide: see §4. Key discipline — a rubric is not a scoring scale; every question is binary, quotable, and tuned by calibration against human-graded examples; a rubric the producing agent can edit is "a target that moves."
- **Adversarial mandate** (`library/review/adversarial-mandate.md`, unchanged across all three branches): the universal review template. A finding concerns correctness or a stated requirement only — never style/taste/restructuring. Every finding carries severity (S-H/M/L, judged by number of criteria offended weighed against importance) and confidence (C-H/M/L), plus reproducible evidence quoting the work and the criterion. Findings are sorted severity-then-confidence with `F1`, `F2`… identifiers; "no findings" requires accounting part-by-part for why none exist. This mandate is literally the instrument used to produce the constitution-research review in §6.

## Follow-up: spec-altitude and the interfaces rewrite (doctrine-recon, 2026-09-18)

Pilot's verification: spec-description.md is the same blob on main and the tip (86d94bfb); buildout's copy (b8f3e449) differs. The tip still reads "a seam is a promise". So both changes in 1c81888 live on buildout only. Doctrine-recon's closing claim that the rewritten paragraph is on the tip today is wrong and its earlier drift line ("2 lines changed main→buildout, unchanged buildout→characterization") was a directional misread of the same commit. Corrected here.

**spec-altitude.md, in a pilot's terms** (`flightcrew-buildout:flightdeck/manuals/spec/spec-altitude.md`): teaches how far above the code a spec statement should sit. Too high ("harden this feature") gives the builder nothing checkable, so it guesses. Too low ("exit 0 must convert to a code-safe message format") writes in the system's own vocabulary, so the spec just restates the implementation. The right altitude is the largest statement that is still one falsifiable thing: plain language, no internal terms, one true/false claim, like "the user must be authenticated before entering the main page." The spec writer is a draftsman between an engineer (intent) and a builder (implementation). A spec is the last document in Flightcrew that speaks human language; everything after is Flightcrew's own vocabulary or the system being built.

**The spec-description.md change, same commit, buildout only**: the "Interfaces and contracts" opening was rewritten. Before (main and tip): "Interfaces fix the seams: the exact shapes through which the work will meet everything around it. Once agreed, a seam is a promise, and each side of it can proceed on the promise alone." After (buildout): interfaces are "common locations and languages", framed from the lens of the isolated build agent; an interface is built first so no isolated agent invents its own; if one isolated agent could build it alone it is not an interface; "Interfaces belong to many... like the town square, not owned, shared, where many meet and speak together."

Two pieces of doctrine the commander wrote on 2026-09-15 that the test-suite line never received. Mission seed: carry buildout's late doctrine forward when the suite merges.
