## The store, `base/store/`

Four JSON files plus `README.md`, each carrying `kind`, `version`, `updated`. Paths inside are cockpit-relative, always, and resolved against whatever `--root` is in force, never against the machine.

**`prefixes.json`** — `kind: "cockpit-prefix-table"`. One row per prefix; a row is the whole truth about that prefix, including its future.

    {"prefix":"DS","name":"Dossier","addressed":"id","state":"live","zone_default":"live","range":[1,999],
     "register":{"file":"commanders-desk/in-dossiers/dossiers.json","array":"dossiers","id_field":"id"},"succession":{"type":"renamed","to":"Ds","keep_number":true}}

- `addressed` is `"id"`, `"name"` or `"both"` (O053). A `"name"` row (rosters, crew seats) names a `name_field` instead of `id_field`, and a declared name is a link target, unique in its manifest; a `"both"` row (M, and P from 101) carries both.
- `state` is how today's set and the ruled set live in one table. `live`: ids minted, must resolve. `planned`: ruled but nothing minted — never a finding, `register: null`. `retired`: `C`, resolves against the frozen manifest only, and the rename tool refuses it. `superseded`: the rename has been executed, so the prefix resolves **only** in frozen and scratch, any live hit is a finding, and the rename tool refuses it — which is what stops a finished `--prefix DS=Ds` being run a second time, a thing `retired` cannot express because `C` never had a successor and `DS` has used one. Today DS, P, O, D, S, W, M, T, CA are `live`; Ds, Rq, Or, De, Sp, WS are `planned`; C is `retired`; nothing is `superseded` yet. **After the identifier pass the pilot flips `live`→`superseded` and `planned`→`live` and the same table is still correct** — no rewrite, and the checker never fails the cockpit as it stands today.
- `P` is the one row with `segments` instead of a single register and range, because the commander reassigned it: segment `[1,100]` is Request, register `base/proposals.json`, `succession {"type":"renamed","to":"Rq","keep_number":true}`; segment `[101,999]` is Procedure, register `procedures/procedures.json`, `state:"planned"`, `succession {"type":"none"}`. The invariant is **one minting register per prefix segment**, and `P` is the only prefix with two segments.
- `CA` has no register today: `"register":null,"resolve_by":{"files":"commanders-desk/out-advice/CA###.md"},"until":"CA gets MANIFEST-commander-advice.json"` — a `CA###` id resolves if that file exists, case-sensitively; a stated stopgap, so the row changes in one place when the register arrives.
- `known_gaps: ["S005"]` — the permanent recorded gap. `planned_ids`: ids a live document proposes that nothing has minted yet, each sourced to the document that proposes them — `[{"id":"M003","source":"P004"},{"id":"M004","source":"P004"},{"id":"M005","source":"P004"},{"id":"M006","source":"P004"}]`, P004 being a live, amended, undecided request whose whole job is asking the commander to open those missions. Both are counted as notes, never findings, and both are checked: if `source` itself stops resolving, or a `planned_id` is later minted, the row is reported as stale so the list cannot rot quietly.
- **Second register.** A duplicate `prefix` key in the table is a `store` finding and exit 2. Separately the checker observes the disk: if ids of prefix X appear as whole values of an `id`-shaped field in a live JSON array that is not X's declared register, it reports `second-register` naming both files. That observation is the check that catches real drift.
- **Three declarations** are a derived view, not a second file: `renamed` = rows with `succession.type == "renamed"` (DS→Ds, O→Or, D→De, S→Sp, W→WS, and P[1,100]→Rq); `retired` = C, successor null; `reassigned` = P, range-qualified. `cockpit-rename` consumes only this derived subset and **refuses** a prefix whose succession is `retired` or `none`, or whose state is `retired` or `superseded`.

**`zones.json`** — `kind: "cockpit-zone-map"`. `"rooms_from":"filesystem"`: rooms are listed from the root at run time and used only to anchor path candidates, never to decide a zone. An ordered rule list, first match wins, most specific first, every pattern keyed below room level:

    {"base/bin/fixtures/**":"excluded"}, {"records/notepad/**":"scratch"}, {"notepad/**":"scratch"}, {"logs/crew-manifest.json":"frozen"}, {"logs/*.md":"frozen"},
    {"**/*.keep":"commander-verbatim"}, {"commanders-desk/out-ideas/**":"commander-verbatim"}, {"commanders-desk/out-advice/**":"commander-reviewed"}, default "live"

`live` read and repairable. `scratch` and `excluded` never opened. `frozen` and `commander-verbatim` read and reported, never proposed — a renamed id inside the commander's own idea falsifies it exactly as it would inside an order's `text`. `commander-reviewed` read, reported, and every occurrence in it proposed as a diff and never applied, whatever its shape, because the commander sees the diff of their own files before it lands (DS006 decision 2) and the pilot applies it by hand (D027). `excluded` exists because the fixtures plant broken references, stale ids and a second register on purpose while `base/` is otherwise live: without the rule the proving run reports the real cockpit as having two registers for that prefix, the planted faults bury the real findings, and an `--apply` run silently repairs the suite. A `paths.planned` entry cannot do this job — it only stops the path being reported when some other file *mentions* it. **The rule is root-relative**, which makes it work in both directions: with `--root` at the real cockpit it hides `base/bin/fixtures/stage-a/`, and with `--root` at a fixture tree the fixture's own files sit at `quarters/…`, `base/store/…` and are scanned normally.

**`fields.json`** — `kind: "cockpit-field-map"`. One entry per JSON document kind, matched by path glob today and by a `kind` field later. Two lists: `whole_value`, the fields *expected* to hold one id or one path entire, and `verbatim`, the fields never scanned and never proposed.

    {"name":"orders","match":"quarters/commander/orders.json","whole_value":["orders[].id","orders[].superseded_by"],"verbatim":["orders[].text"]}
    {"name":"topics-unit","match":"logs/topics/*.json","whole_value":["record","statements[].ref","statements[].superseded_by"],"verbatim":["statements[].statement"]}

`verbatim` is the only declaration that removes text from view; anything undeclared is still scanned and lands in tier 2. `logs/topics/*.json` `ref` is the composite form `path#ID` — a shape the spec does not name, and where 33 of the advice references sit. Both halves are resolved and the pair counts as one whole value.

**`paths.json`** — `kind: "cockpit-path-map"`. `renames`: old→new pairs, seeded with `commanders-desk/out-advice/DS001.md` → `CA001.md` and DS002, DS003; this is where `cockpit-check` gets an exact replacement for a stale path, and what the ordering gate below counts. `planned`: ruled-but-absent paths that are not findings (`records/manuals/`, `records/extracts/`, `records/notepad/`, `work/`, `commander/`, `team/`, `dispatch/cockpit/`, `dispatch/flightcrew/`, `base/store/`, `base/bin/cockpit-check`, `base/bin/cockpit-rename`, `base/bin/test_cockpit_check.py`, `base/bin/test_cockpit_rename.py`, `MANIFEST-*.json`). `external`: roots outside this branch or outside the repo (`flightdeck/library/`, `flightdeck/manuals/`, `flightdeck/runs/`, `flightdeck/templates/`, `flightdeck/crew.json`, `flightdeck/flightcrew/`, `checks/`, `.claude/`, `run/`). Planned and external hits are counted as notes and never affect the exit code.

## How a reference is recognised, and how false positives are held down

**Ids.** `(?<![A-Za-z0-9])(ALT)([0-9]{3})(?![0-9])`, where `ALT` is the store's prefixes sorted longest-first (`DS|CA|Ds|Rq|Or|De|Sp|WS|P|O|D|S|W|M|T|C`). Longest-first plus the digit anchor is what makes `S` never match `Sp` and `W` never match `WS`; the trailing `(?![0-9])` stops `P1010` reading as `P101`. Held down by: placeholders (`DS###`, `P00x`, `CA00N`) never matching, because `[0-9]{3}` needs digits — free, no list; `verbatim` fields not scanned; `planned` prefixes and `planned_ids` never findings; `known_gaps`; `CA` resolved by file; and the quotation rule below. Measured residue: 3 findings.

**A quotation is never rewritten, and is never hidden either.** Pass 2 suppressed ids inside quoted spans from being *read*. That was wrong on the plan's own top line: an id the checker does not read is an id `cockpit-rename` does not rewrite, so a quoted `"P004"` would survive the identifier pass stale and permanently invisible. The rule is therefore a **tier** rule, not a read rule. Every id is read and resolved wherever it sits; an id inside a double-quoted span **inside a JSON prose value** is pinned to tier 3, so the rename tool never rewrites it and lists it in the change list as `quoted, not rewritten` for a human to judge. That is the `decisions.json` D018/D021/D024 class the paper named — freeze it and the quotation stands, rewrite it and three quotations are falsified — and it is prophylactic: measured at zero identifiers inside such a span today. **There is no markdown half and no frontmatter fence.** Pass 2 had one, confined to the body to avoid blinding the checker to the `work`/`context`/`generates` chain in frontmatter. Re-measured this pass, its entire remaining gain was `C023`, since `Or001` is already filtered as a planned prefix and `M003`–`M006` as planned ids; the pilot has fixed `C023` at source in DS006, so the gain is now zero and the rule and its positional fence go with it. The one quoted body id left in the corpus, `M002` in `CA001`, resolves. **The standing rule:** a false finding is cured at its source or by a declared store row, never by not reading. One remnant of the fence stays, because stage B needs it: a markdown file opening with `---` and no closing fence within its first 40 lines draws a `format` note — measured harmless today, since all five live or commander files with frontmatter close by line 7 — and, there being no body suppression left to fail open into, the note is the whole of its effect.

**Paths.** A candidate is taken only from a backtick span, a markdown link target `](…)`, or a JSON string value — measured to lose one resolving hit and no unresolved hit across the whole live cockpit, which is what kills `pass/fail`, `they/them`, `work/` and `crew/` without a single hand-written exception. Then: trailing `.,;:)]>'"-` stripped; skipped if it contains or is preceded by `$`; skipped if the line has `://` before it; a leading `@` stripped (`@procedures/triggers.md`); skipped if it starts with `/` and does not exist absolutely; a trailing `#ID` split off and checked as an id. It must then be **anchored** — end in a known extension (`md json py sh txt keep mjs js yml yaml toml jsonl`), or start with `./`, `../`, `flightdeck/`, or a room enumerated from the filesystem. **Resolution is case-sensitive**: `os.path.exists` lies on this filesystem, so resolution walks the components and matches each against a cached `os.listdir` of its parent, exactly. Three roots are tried in order — the citing file's own folder, the cockpit root, the repo root — and the first exact hit wins, with the root used named in the finding. This is also what makes a case-only rename verifiable.

## The three tiers, decided mechanically

The test is the value, never the field name. For an occurrence in file F, at field path Q, in string value V:
- **Tier 3**, never touched and never proposed: Q is declared `verbatim`; or the match sits inside a double-quoted span within a JSON prose value, which is read and reported like anything else but listed as `quoted, not rewritten` rather than proposed; or F's zone is `frozen`, `scratch`, `excluded` or `commander-verbatim`. `scratch` and `excluded` are never opened at all; `frozen` and `commander-verbatim` are read and counted so the checker can report them, and `cockpit-rename` prints their counts without a diff.
- **Tier 2**, proposed as a unified diff per file and **never applied, even under `--apply`**: every live occurrence that is not tier 1, JSON prose and markdown alike; and **every** occurrence in `commander-reviewed`, whatever its shape, including a rename of a commander-owned file. Markdown has no fields, so every live markdown occurrence is tier 2 by construction.
- **Tier 1**, applied under `--apply`: F's zone is `live`, Q is not `verbatim`, and the match spans the whole of `V.strip()`, or `V.strip()` is exactly `<path>#<ID>` and the match is one of the two halves; plus file renames inside zone `live`. A field declared `whole_value` whose value fails that test falls to tier 2 anyway and the checker reports the stale declaration as a `store` note — the declaration says what is expected, the test decides. This is why `decisions.json.by` lands in tier 2 on its own: 12 of its 25 values are the bare word `commander` and only 7 carry a path.

## CLI

`cockpit-check [--root PATH] [--zone live|frozen|commander|all] [--json] [PATH …]` — defaults to the root found by walking up from the script, zone `live`. `--zone commander` covers both commander zones; `--zone all` adds frozen; neither `scratch` nor `excluded` is reachable by any flag. Positional paths narrow the scan to files or folders inside `--root`. **It writes nothing under any flag and there is no `--fix`.** Exit 0 clean, 1 findings, 2 tool or store error. The commander's ruling that the lint is non-blocking governs how a gate wraps the tool — a commit gate prints exit 1 and lets the commit through — not the tool's own exit code, which must stay informative.

`cockpit-rename --root PATH [--id OLD=NEW]… [--path OLD=NEW]… [--prefix OLD=NEW]… [--from FILE] [--apply] [--json]` — dry run by default, and it always scans `live` plus `commander-reviewed`, because the commander's files are where its tier-2 diff has to come from. `--prefix DS=Ds` expands through the derived succession subset, range-qualified. `--apply` is refused unless `--root` was given explicitly on the command line and never by default, so a test can point it at a fixture copy and nobody can apply to the real cockpit by accident; it touches tier 1 only. It prints the change list and the pre-pass count per old id and path, so a post-pass run proves zero remain. It runs no git command and never commits.

**The ordering gate.** `--prefix X=Y` is refused, exit 2, while any `paths.renames` entry **whose old path contains an id token of prefix X** still has outstanding hits, and the message names each colliding entry with its count and the token that collides: `refusing --prefix DS=Ds: commanders-desk/out-advice/DS001.md contains DS001 and still has 24 hits (+33 in logs/topics/), DS002.md 19, DS003.md 1 — run the path repair first`. Without it, `--prefix DS=Ds` rewrites `out-advice/DS001.md` to `out-advice/Ds001.md` in 57 places, a path that has never existed, and because `paths.renames` is keyed on `DS001.md` the exact replacement is gone afterwards and every finding degrades to a basename guess. Scoping it to the colliding token matters because DS006's closing runs the identifier pass and the room move as two commits of one refactor flight, so both sets sit in the table at once: a room-move entry like `records/` → `records/manuals/` carries no id token, no prefix pass can corrupt it, and it must not refuse the run. The gate counts **tier 1 and tier 2 hits only**: the one reference inside `orders.json.text` is tier 3 and uncountable by construction, and were it counted the gate would deadlock the identifier pass forever on a string nobody is ever allowed to repair.

## A case-only file rename, safely

`core.ignorecase` is true here, so the tool never trusts `os.path.exists`. It (1) lists the parent directory and asserts the exact new name is absent and the exact old name present; (2) `os.rename(old, old + ".cockpit-rename-tmp")`; (3) `os.rename(tmp, new)`; (4) re-lists the parent and asserts the exact new name is present and the exact old name absent, restoring from the temp name and failing loudly if not. No `git mv`, because the tool changes no git state; it prints both paths for the pilot to stage.
