# T010 practice-scout report — frontmatter, YAML, searchability, manifests, identifiers, layout

Fetch date for all web sources: 2026-09-20. Rank 1 = official Anthropic docs/engineering. Rank 2 = spec text or widely-used static-tool convention, marked per item.

## 1. Frontmatter in the harness

Every place the harness itself parses YAML frontmatter, confirmed against `code.claude.com/docs/en/*` (rank 1, redirected from `docs.claude.com`):

- **Subagents** (`/docs/en/sub-agents`). Required: `name` (unique id, lowercase+hyphens, becomes `agent_type` for hooks), `description` ("Claude uses each subagent's description to decide when to delegate tasks... This field is critical for auto-selection"). Optional fields the harness reads: `tools` (allowlist, inherits all if omitted), `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills` (preloads full skill content), `mcpServers`, `hooks`, `memory` (`user`/`project`/`local` persistent memory scope), `background`, `omitClaudeMd`, `effort`, `isolation`, `color`, `initialPrompt`, `experimental.cacheTtl`. Confirmed-raw: not re-curled (WebFetch tool output only) but content matches the doc's own table structure; treat as confirmed-by-fetch, not confirmed-raw.
- **Slash commands** (`/docs/en/slash-commands`, and note "Custom commands have been merged into skills" — a `.claude/commands/*.md` file and a `.claude/skills/*/SKILL.md` now do the same thing). Fields: `description`, `allowed-tools`, `argument-hint`, `model`, `disable-model-invocation`. Command files support the same fields as skills **except `name` and `paths`**.
- **Skills** (`/docs/en/skills`). Fields: `name` (defaults to directory name), `description` (required in practice — "Only `description` is recommended so Claude knows when to use the skill"), `disable-model-invocation`, `user-invocable`, `allowed-tools`, `context: fork`. Confirmed-raw against `skills-docs.html`: "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files" and "the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing to reduce context usage" (cap configurable via `skillListingMaxDescChars`).
- **Rules with `paths:`** (`/docs/en/memory#path-specific-rules`). `.claude/rules/*.md` files use YAML frontmatter with a `paths:` list of glob patterns; a rule with `paths` only loads into context when Claude reads a matching file. A rule with no `paths` field loads unconditionally, same priority as `.claude/CLAUDE.md`. Confirmed-raw against `memory-docs.html`. This project's `.claude/rules/*.md` files (context.md, dev-workspace_commands.md, dev-workspace_guide.md) carry no frontmatter at all in this repo, so all three load unconditionally at launch — none is path-scoped.
- **Output styles** (`/docs/en/output-styles`). Fields: `name`, `description` (shown in `/config` picker), `keep-coding-instructions` (default `false`), `force-for-plugin` (plugins only, default `false`).
- **Auto memory files** (`/docs/en/memory#auto-memory`). Claude itself writes a `type` field (`user`/`feedback`/`project`/`reference`) into frontmatter, and Claude Code stamps a `modified` ISO-8601 timestamp into any memory file that already has frontmatter, on every write, requires v2.1.214+. This is the one case where the harness writes to frontmatter rather than only reading it.
- **CLAUDE.md / AGENTS.md files themselves**: no frontmatter fields are documented for these; the doc describes only `@path` imports and HTML-comment stripping, no YAML block.

**Does frontmatter in an ordinary markdown file the agent merely Reads have any harness effect?** No official statement was found saying it does, and by exclusion: the doc lists frontmatter fields only for the five mechanisms above (subagents, slash commands, skills, path-scoped rules, output styles) plus auto-memory. A dossier/proposal/advice file such as this project's `DS001` or `P004` is read by the pilot via the Read tool like any other file; nothing in the harness docs parses or acts on frontmatter in a file reached that way. It is inert data to the harness — meaningful only if the pilot's own CLAUDE.md/prompt tells it to look for and interpret those fields. This is an argument from silence across the full harness doc set searched, not a positive statement; mark as **not officially stated either way**, but no mechanism was found that would give it effect.

## 2. YAML validity

Ran PyYAML 6.x (`yaml.safe_load`) in a scratch venv (no system PyYAML was installed; installed fresh for this test).

- `stamp: "2026-09-18", "Pilot: Ace", "session dcb75456"` — **invalid**. PyYAML raises `ParserError: while parsing a block mapping ... expected <block end>, but found ','`. A quoted scalar followed by a bare comma outside `[...]` is not a YAML list; YAML's flow sequence requires square brackets, and a block mapping value is a single scalar unless wrapped in `[...]` or given as a block sequence.
- `generates: "P004", "P005"` — **invalid**, same error class (confirmed by direct PyYAML run).
- The full DS001 frontmatter block (`type`, `unit`, `stamp`, `work`, `context`, `generates`) — **fails to parse as a whole document** because the `stamp:` line alone breaks the parser (`ParserError` at line 4); YAML aborts the whole document on first structural error, it does not skip the bad line and parse the rest. This means DS001's frontmatter, as filed on disk right now, is not valid YAML and any tool doing `yaml.safe_load` on it (a script, a static site generator, gray-matter, front-matter, PyYAML) throws rather than returning partial data.
- Valid ways to write a list of strings on one line: flow sequence with brackets, `generates: ["P004", "P005"]` → parses to `['P004', 'P005']` (confirmed). Comma-separated bare scalars with no brackets is never valid YAML for a mapping value, per the YAML spec's block-mapping grammar (a mapping value is a single node unless the flow indicators `[`, `{` are used).
- Valid way across lines: block sequence —
  ```
  generates:
    - "P004"
    - "P005"
  ```
  parses to `['P004', 'P005']` (confirmed).
- Empty value: `status:` (nothing after the colon) parses to Python `None` (YAML null) — confirmed for both `status:` and `status: ` (trailing space). This matches the file on disk: `P004-open-missions-from-the-cut.md` has `status:` and `recorded:` both empty, both of which are valid YAML (`null`), unlike DS001's malformed `stamp:`/`generates:` lines.
- Spec citation (rank 2, YAML 1.2): a block mapping's value node is parsed as one scalar, sequence, or mapping; comma is not a block-context separator — it is only meaningful inside flow collections (`[...]`, `{...}`). This is why bracket-less comma lists fail: the parser reads `"2026-09-18"` as the complete scalar value for `stamp`, then finds a stray `,` where it expects the next key or end of block, and errors.
- Practical implication for the frontmatter idea: none of the three "comma without brackets" fields currently on disk (`stamp` and `generates` in DS001, and the same pattern would apply to any field the commander drafted the same way) are machine-parseable frontmatter today. `type`, `unit`, `work`, `context` in DS001 are fine (plain quoted scalars). The fix is either `["P004", "P005"]` flow syntax or a block list — both confirmed valid above.

## 3. Searchability

Official guidance found is **thin and indirect** — no dedicated Anthropic page on "how to make files greppable," but relevant statements from rank-1 sources:

- Just-in-time context engineering (anthropic.com/engineering/effective-context-engineering-for-ai-agents, confirmed-raw not needed — quoted directly, WebFetch-sourced): "agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools." And: "the presence of a file named `test_utils.py` in a `tests` folder implies a different purpose than a file with the same name located in `src/core_logic/`. Folder hierarchies, naming conventions, and timestamps all provide important signals that help both humans and agents understand how and when to utilize information." This is a direct argument for descriptive paths/names as an implicit index, but it is about general agent behavior, not Claude Code's grep/glob mechanics specifically.
- Skills progressive disclosure (anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills, confirmed-raw): "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt" (level 1), full `SKILL.md` loads only if relevant (level 2), bundled files loaded by explicit reference only as needed (level 3). "Pay special attention to the `name` and `description` of your skill. Claude will use these when deciding whether to trigger the skill." This is the clearest official statement of a metadata-first / progressive-disclosure discovery pattern, but it describes the skill-loading system specifically, not a general corpus-search convention for markdown notes.
- Memory doc (code.claude.com/docs/en/memory, confirmed-raw): the auto-memory directory pattern — one `MEMORY.md` index (one line per memory) plus one topic file per fact, with topic files read "on demand using its standard file tools when it needs the information" — is Anthropic's own working example of an index-plus-unit layout for a markdown corpus meant to be searched by an agent. Naming shown in the doc's example tree: `user_role.md`, `feedback_testing.md` — descriptive, type-prefixed, kebab/snake-case filenames, not opaque IDs.

**Where the sources are silent**: no official guidance was found on short ID-based filenames for grep/glob discoverability specifically (e.g., whether `DS001.md` is more or less findable than `dossier-flightcrew-recon.md`), on directory-level README-as-index conventions, or on any general "corpus searchability" checklist outside the skills/memory subsystems. The commander's four idea files ask about this directly; the official record does not answer it — the memory-directory pattern is the closest analogous example and favors descriptive names over bare codes, though it is a narrow, single-purpose subsystem, not general guidance.

## 4. Manifest and unit

- Skills' three-level progressive disclosure (metadata always in context → SKILL.md on trigger → bundled files on further reference) is Anthropic's own worked design pattern for exactly the manifest/unit shape being explored. Confirmed-raw figure: SKILL.md capped at 500 lines by convention ("Keep SKILL.md under 500 lines"), description+when_to_use truncated at 1,536 characters in the listing (configurable). No figure is given for bundled/reference file size — "the amount of context that can be bundled into a skill is effectively unbounded" (confirmed-raw) because those files are read only on demand, not preloaded.
- Memory index/topic-file split, confirmed-raw figures: `MEMORY.md` loads only its "first 200 lines... or the first 25KB, whichever comes first" at every session start; content past that is dropped on load, and Claude Code returns an error prompting a rewrite if the file exceeds the limit after a write. Topic files (`user_role.md` etc.) are **not** loaded at startup at all — "Claude reads them on demand using its standard file tools when it needs the information." This is the same manifest→unit flow the commander's `json-data-consistency.txt` describes (`agent needs context → manifest → unit`), demonstrated by Anthropic's own subsystem, with the manifest (index) capped small and units read lazily.
- CLAUDE.md size: "target under 200 lines per CLAUDE.md file... If your instructions are growing large, use path-scoped rules" and separately "Claude Code loads a CLAUDE.md file of up to 4 MiB in full and skips a larger file" (confirmed-raw, both figures). Splitting via `@path` imports "helps organization but doesn't reduce context, since imported files load at launch" — a direct, confirmed statement that an import-based manifest does NOT save tokens the way lazy-loaded units (skills, memory topic files, path-scoped rules, subdirectory CLAUDE.md) do. This is the key distinction for the commander's manifest idea: only lazy/on-demand references (Read tool calls, skill triggers, path-matched rules, subdirectory CLAUDE.md discovered when a file in that subtree is opened) actually defer cost; `@import` front-loads everything regardless of a lightweight-manifest intent.
- Read tool: no explicit line/token limit figure was found documented for the Read tool itself in the pages fetched; the `by-line, "cat -n" format` behavior is tool-description text (already in this session's own tool list), not sourced from a fetched doc, so it is **not confirmed against an official doc page** in this pass — mark not-confirmed.
- Applied to the cockpit's actual JSON files: this scout did not measure `dispatch/cockpit.json`, `logs/index.json`, or `missions/missions.json` line/token counts — that was out of the read boundary (repo files not named in the brief). The option-maker or a room-scoped crew member would need to run `wc -l`/token counts on those specific files to size the manifest/unit tradeoff per file; this report supplies only the general mechanism and its confirmed thresholds, not per-file cockpit numbers.

## 5. Identifier conventions (rank 2, marked)

- **ADR numbering** (cognitect.com/blog/2011/11/15/documenting-architecture-decisions, rank 2, confirmed-raw): "ADRs will be numbered sequentially and monotonically. Numbers will not be reused." Reversal handled by keeping the old record and marking it superseded, never by editing or renumbering: "If a decision is reversed, we will keep the old one around, but mark it as superseded." Filename convention widely followed (adr.github.io and derivatives, rank 2, not independently curled): 4-digit zero-padded prefix, e.g. `0001-record-architecture-decisions.md`.
- **RFC numbering** (IETF, rank 2, via secondary summary not directly curled): RFC numbers are sequential, global, and never reused; a superseding document gets a new number and references ("obsoletes") the old one rather than replacing it in place. Same never-renumber, supersede-don't-edit principle as ADRs.
- **Ticket keys / Jira** (Atlassian Confluence, rank 2, confirmed-raw against `confluence.atlassian.com/adminjiraserver/changing-the-project-key-format-938847081.html`): project keys are constrained to "two or more uppercase alphabetical characters" by default (`[A-Z][A-Z]+`), 2–10 characters, must start with a letter, unique per instance; issue keys are `<PROJECT-KEY>-<NUMBER>`, uppercase prefix, auto-incrementing number, and the key format cannot be changed after creation without side effects — practically "never renumber" for the same reason ADRs don't.
- **Pattern common to all three** (rank 2 across the board, no rank-1 equivalent found): fixed-width or monotonic numeric suffix, one consistent case register for the prefix (uppercase in every example found), a prefix chosen once and never reused for a different kind of thing within the same system, and superseding/amending is done by adding a new record, not by mutating or renumbering an old one. This maps directly onto the commander's `json-data-consistency.txt` collision concern (P as both Proposal and Procedure, DS vs the proposed Ds) — the convention found nowhere permits one prefix letter-string doing double duty for two different unit kinds in the same corpus; each of ADR/RFC/Jira reserves its prefix for exactly one kind.

## 6. Directory layout

- Nested CLAUDE.md / AGENTS.md loading (confirmed-raw, code.claude.com/docs/en/memory): "CLAUDE.md and CLAUDE.local.md files in the directory hierarchy above the working directory are loaded at launch." Files in **subdirectories** under the working directory are different: "Claude also discovers CLAUDE.md and CLAUDE.local.md files in subdirectories under your current working directory. Instead of loading them at launch, they are included when Claude reads files in those subdirectories." So a deeper folder tree with its own nested CLAUDE.md per room is not free at launch — it costs nothing until an agent actually opens a file in that room, at which point that room's CLAUDE.md is added to context. This is the direct mechanism behind the `paths:` rule too (same "on read, not on launch" trigger), confirmed-raw: "Path-scoped rules trigger when Claude reads files matching the pattern, not on every tool use."
- `@path` imports: confirmed-raw max recursion "a maximum depth of four hops," and confirmed-raw that imports do NOT defer cost — "imported files still load and enter the context window at launch" — so restructuring into more `@import`-linked files (as opposed to more subdirectory-discovered files) buys organization only, not token savings.
- Cost/benefit for the `cockpit-setup.txt` regroup specifically: moving rooms deeper (e.g. `records/manuals/claude-code/`, `records/dispatch/cockpit/`) is free at launch as long as no room gets its own CLAUDE.md that the pilot would need loaded unconditionally; if a room does get its own CLAUDE.md (as the current `commanders-desk`-adjacent structure implies it might, mirroring the existing `.cockpit/CLAUDE.md`), the doc confirms it loads lazily on first read in that subtree, not at every session start — a genuine benefit over one large root file, matching the 200-line/4-MiB thresholds already established for the root file in section 4. No official guidance was found on an optimal nesting depth, a maximum number of rooms, or naming for room-level CLAUDE.md files beyond the filename itself (`CLAUDE.md`, `.claude/CLAUDE.md`, or `AGENTS.md`).

## 7. Schema store and lint tooling (follow-up)

**(a) JSON Schema draft and frontmatter-validation practice.** Current spec (json-schema.org/specification, confirmed-raw): "The current version is 2020-12! The previous version was 2019-09." Validating YAML frontmatter against JSON Schema is established editor/tooling practice, not exotic — rank 2, confirmed via GitHub source: `redhat-developer/vscode-yaml` (the YAML Language Server behind VS Code's YAML support) reads a schema pointer either as a modeline comment `# yaml-language-server: $schema=<url-or-path>` at the top of the file, or an IntelliJ-compatible `# $schema=<url-or-path>` comment, or a top-level `$schema` property in the YAML body itself, and validates the document against JSON Schema drafts "04, 07, 2019-09, and 2020-12." The same language server extends this to Markdown frontmatter specifically — "the yaml-language-server can validate YAML frontmatter in Markdown files when properly configured," via a schema-to-Markdown-glob mapping in settings. This is the same mechanism JetBrains IDEs use for the `$schema` comment form, so it is cross-editor convention, not one vendor's quirk.

**(b) How schemas are conventionally keyed to documents.** Two established patterns, both rank 2:
- **In-document pointer**: a `$schema` field (or the language-server comment form above) inside the document itself names the schema by URL or relative path. This is JSON Schema's own vocabulary — `$schema` in a schema file declares which meta-schema it conforms to, and the same keyword is reused by convention as "which schema validates me" when placed in an instance document rather than a schema document.
- **External catalog / fileMatch**: SchemaStore.org's `catalog.json` (github.com/SchemaStore/schemastore, confirmed via search of the live file) keys schemas to documents by filename glob rather than an in-file pointer — each catalog entry carries a `fileMatch` array of glob patterns (e.g. `tsconfig*.json`, `**/.claude/settings.json`), and "bare filename patterns... are automatically expanded to also match nested paths." Editors consult the catalog by the file's own name/path, no field inside the file required. A `type:` field (as this cockpit's frontmatter already carries) is a third pattern in practice, common in headless CMS/content-collection tooling (Astro content collections, Contentlayer) that key a document to its schema by a discriminator field's value rather than filename or in-document URL — not sourced to an official spec, general tooling convention, rank 2, not independently curled this pass.

**(c) Anthropic guidance on validating agent-written files / hooks as validators.** No official Anthropic guidance recommends schema validation of agent output specifically; but the hooks mechanism that would carry it is documented and confirmed-raw (code.claude.com/docs/en/hooks): `PostToolUse` fires "After a tool call succeeds" — confirmed-raw against the raw page. For Write/Edit, the file has "already executed successfully" by the time the hook runs (confirmed-raw), so a `PostToolUse` linter hook can only **report**, not block or revert: it may return `additionalContext` (added to Claude's conversation), `systemMessage` (shown to the user), and `terminalSequence`; it does not support `permissionDecision` or `updatedInput`. To actually block a bad write before it lands, the hook must be `PreToolUse` instead, which does support `permissionDecision: "deny"`. Exit-code behavior for `PostToolUse` (from the hooks doc's own exit-code table): exit 2 "Reports a `<hook name> hook error` notice; tool already executed" — never blocks, because the action is already done. Latency: default `timeout` is confirmed-raw at "600 for `command`, `http`, and `mcp_tool`" hook types (600 seconds); other hook types default lower (30s for `prompt`, 60s for `agent`, per the same table, not independently re-curled). On timeout or non-zero non-2 exit, Claude Code reports a non-blocking error with a stderr-derived message; stdout is parsed for the JSON decision fields when present. Net effect for this cockpit's guard idea: a schema-store linter wired as `PostToolUse` on Write/Edit for cockpit markdown/JSON can only warn the pilot after the fact (matching how `base/bin/cockpit-guard.py` is described as a `PreToolUse` guard in this repo's own CLAUDE.md — that guard blocks; a schema linter added as `PostToolUse` would not).

**(d) Validators with no install vs. lightest install.** Checked directly on this machine (not sourced to a doc): stock command-line tooling does not include a JSON Schema validator on any of the standard runtimes. `python3` is present here via Homebrew (`/opt/homebrew/bin/python3`), not Apple's system Python — a genuinely stock, un-configured macOS typically prompts for Xcode Command Line Tools before `python3` resolves at all — and even where `python3` is present, `pyyaml` and `jsonschema` are not stdlib (confirmed on this machine: `import yaml` raises `ModuleNotFoundError` until installed). Node/npm here come from `mise` (`~/.local/share/mise/installs/node/22`), also not a macOS default. So: **no validator runs with zero install on stock macOS** — every path needs at least one install step. Lightest options, ranked by footprint:
- **Single static binary, no package manager**: `yajsv` (github.com/neilpa/yajsv, confirmed-raw from its README) — "Command line tool for validating JSON and/or YAML documents against provided schemas," with "pre-built static binaries for Windows, Mac and Linux on the releases tab." Drop the binary on `PATH`; no Python, Node, or Go toolchain needed at runtime. This is the lightest option for a hook script.
- **Node**: `ajv-cli` (npm, rank 2, not independently curled beyond the search snippet) wraps `ajv`, "the fastest JSON schema Validator," supports JSON, JSON5, and YAML input; install via `npm install -g ajv-cli`. Needs Node/npm already present (as it is on this machine via mise).
- **Python**: `pip install jsonschema pyyaml` (this session's own scratch venv used exactly this pattern for section 2's YAML tests) — most flexible for a custom script that reads frontmatter with `yaml.safe_load` and validates with `jsonschema.validate`, but needs two packages, not one, and a venv is the clean way to avoid the PEP 668 "externally managed environment" error this session hit on first `pip install --user` attempt.
- **check-jsonschema**: mentioned in search results as a Python-ecosystem CLI validator but not independently confirmed this pass — flag as not-confirmed, would need its own README fetch before relying on it.
