# T011 — Stage A of the paperwork check: build spec

Mission M001. Dispatched by session `pilot` (Ace), 2026-09-20, under request P013 as amended by the commander (decisions D026, D027 in `base/decisions.json`). The commander is the human owner; the pilot links this team to the commander.

## Why

Nothing checks the cockpit's references. A rename of three files left 24 broken references in live files and nothing noticed. The commander has ruled a new identifier set that touches about 518 live references. Stage A is the tooling that makes that safe. The design behind it is `notepad/ideas-2026-09-20/paper-final.md` (read area 2, area 5 and the order of change) and `commanders-desk/in-dossiers/DS006-cockpit-paperwork.md` (read "What is ruled" and the closing section, which overrides the paper where they differ). The commander's orders on the subject are O044 to O055 in `quarters/commander/orders.json`.

## What is built

Python 3 standard library only, compatible with Python 3.9 (`/usr/bin/python3` on this machine is 3.9.6; test under it), `#!/usr/bin/env python3`, in the style of `base/bin/cockpit-guard.py` and its table test. Parses JSON, scans text. Parses no YAML and no frontmatter. No network, no git commands that change state.

1. **The store**, JSON files under `base/store/`. Each carries a `kind` field saying what it is.
   - A prefix table. One row per prefix: the prefix, the kind's name in full, whether the kind is addressed by ID only, name only, or both (O053), its one minting register (file and where ids sit in it), its number range, its state. It must describe the cockpit as it is today (DS, P, O, D, S, W, M, T, CA, C) and carry the ruled change as three separate declarations: renamed one to one (DS to Ds, O to Or, D to De, S to Sp, W to WS), retired with no successor (C), reassigned (P: ids below 101 are requests and become Rq keeping their number; procedures take P from 101). A prefix has exactly one minting register; the checker reports a second. CA has no register today; say how it resolves until it has one.
   - A zone and field map. Zones are keyed on paths below room level, never on a top-level room name, and rooms are enumerated from the filesystem, never from a typed list. Zones: live (checked, repairable), scratch (ignored: `notepad/` today, `records/notepad/` later), frozen (reported only, never edited: session logs `logs/*.md`, `logs/crew-manifest.json`), and the commander's own files (`*.keep`, `commanders-desk/out-ideas/`, `commanders-desk/out-advice/`: reported, never edited by the tool). An excluded zone, never scanned and never written by either tool: `base/bin/fixtures/` (the fixtures plant broken references, stale ids and a second register on purpose; scanned as live they would bury the real findings and an `--apply` run would silently repair the test suite). The table test asserts this exclusion as its first case. Per JSON document kind, the fields expected to hold a whole-value reference (the entire value is one id or one path), and the fields never touched (`text` in `quarters/commander/orders.json`).
2. **`base/bin/cockpit-check`**, the reference checker. Reports every id and every path cited in live files that does not resolve: an id against its register, a path against the file's own folder, the cockpit root and the repo root. Case-sensitive. Writes nothing. Exit 0 and one short line when clean; exit 1 with findings otherwise. Each finding is one line a reader can act on without another tool call: file, line, what is wrong, and the exact replacement where one is known. Keep false positives low: prose contains things that look like paths and ids and are not (globs, placeholders such as `DS###`, examples, future paths); say in the plan how each is handled. A `--zone` and a `--json` option are welcome; keep the surface small.
3. **`base/bin/cockpit-rename`**, the rename tool. Takes a mapping (ids by prefix, or paths old to new) and defaults to a dry run. Tier 1, applied with `--apply`: whole-value references in live JSON fields, and file renames (two-step for a case-only change on this case-insensitive filesystem). Tier 2, never applied by the tool: every other live occurrence, emitted as a unified diff per file for a reviewer to accept or strike. The commander's own files split in two. `commanders-desk/out-advice/` is commander-reviewed: always tier 2, whatever the shape of the occurrence, proposed as a diff and never applied, so the pilot repairs it with an exact change list and the commander sees the diff. `*.keep` and `commanders-desk/out-ideas/` are commander-verbatim: tier 3, like the `text` of an order, because a renamed id inside the commander's own idea falsifies it. Tier 3, never touched and never proposed: verbatim fields, frozen files, scratch, the excluded zone. Digits are anchored to the prefix so `S` never matches `Sp` and `W` never matches `WS`. It prints a change list and the pre-pass count per old id so that a post-pass run proves zero remain in live files. It never commits.
4. **`base/bin/test_cockpit_check.py` and `base/bin/test_cockpit_rename.py`**, table tests over a fixture tree under `base/bin/fixtures/stage-a/`. The rename test works on a temporary copy of the fixtures and proves the boundary between dry run and `--apply`, and between the tiers, since the rename tool is the one that writes. Cases must include: the commander's order O048, `(O001 is not very readable)` inside an `orders.json` `text` field, coming through a full rename untouched; a decision row whose prose quotes the commander; a `by`-style field that is short prose containing a path (not whole-value); a stale path in a whole-value field; a stale path in prose; `P004` and `P101` under the reassignment; a `C` id in a frozen file; a scratch file full of stale ids that is ignored; a case-only file rename; a second register for one prefix.
5. A section for `base/bin/README.md` describing the two tools, and `base/store/README.md` indexing the store.

## Not in scope

Running the identifier pass. Moving rooms. Any schema validation, frontmatter, or the Node engine (stage B). Editing the guard, `pilot.sh`, `session-start.sh`, `base/settings/`, `CLAUDE.md`, or any cockpit content outside the write boundary below.

## Write boundary

New files only, under `base/store/`, `base/bin/cockpit-check`, `base/bin/cockpit-rename`, `base/bin/test_cockpit_check.py`, `base/bin/test_cockpit_rename.py`, `base/bin/fixtures/stage-a/`, `base/store/README.md`, and this folder `notepad/stage-a-2026-09-20/` for plans and reports. The README section for `base/bin/README.md` is delivered as text in the report; the pilot lands it. Everything else in the repository is read-only to this team. No commits.

## Order of work

1. `tool-builder` writes `plan.md` here: the store's file shapes, the CLI of both tools, the output format with examples, how references are recognised in text and how false positives are held down, the case list. 120 lines at most. It may ask `option-maker`, who holds the design, anything.
2. The pilot freezes the plan and the `adversary` attacks it by pass number.
3. `fixture-writer` builds the fixture tree and the table test from the accepted plan while `tool-builder` builds the store and the tools; the test is written to the plan, not to the code.
4. Green under `/usr/bin/python3`. Then both tools are run read-only against the real cockpit: the checker's findings and the rename tool's dry run for the three advice files (`out-advice/DS001.md` to `DS003.md`, now `CA001.md` to `CA003.md`) go in `report.md`.
5. The `adversary` attacks the result. The pilot runs the test and the proving run itself before anything is relied on.
