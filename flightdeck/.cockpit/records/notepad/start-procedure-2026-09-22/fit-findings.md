# Fit findings — session start procedure

Seat: fit-critic, team T018, mission M001. Angle: fit — is the claim true at the file it cites, is the fix in the right room, does it restate, does it leak session context, does it put the pilot on crew work.

## Round 0 — own, before the first trace round

**F1 — Steps 1 and 3 have the pilot re-fetch what the hook already handed him.** `base/bin/session-start.sh:28` prints `current_mission=`, `:32-33` prints `requests_awaiting=N` with the ids. `pilot.md:50` tells him to read `MANIFEST-missions.json` and `:52` to check `MANIFEST-requests.json` for anything awaiting. The manifest reads are still needed for the unit files, but the procedure never says the hook has already answered the question, so the pilot opens two manifests to learn two lines already in his context. Severity: medium.

**F2 — Step 1 names a record shape that does not exist.** `pilot.md:50` says "the open mission file marked `current`". No unit in `work/missions/MANIFEST-missions.json` carries a `current` field; `current: "M001"` is a top-level key, and both M001 and M002 are `status: in_progress`. A pilot looking for a marked unit finds two in progress and no mark. Severity: medium.

**F3 — Step 3's second half asks a question the records cannot answer, and answers it with the pilot's own reading.** `pilot.md:52` says check `commander/desk/out/advice/` "for advice not yet acted on". `commander/desk/out/advice/MANIFEST-commander-advice.json` has no acted-on field: rows carry `id`, `answers`, `date`, `path`, and only CA004 has an ad-hoc `status: "answered"`. The requests half of the same sentence works because requests have `status`. So the only way to apply the test is to open all four CA files — bulk reading, which `pilot.md:16` says is crew work. Severity: medium-high.

**F4 — The standing-orders digest delivered at launch is stale, and nothing in Session start refreshes it.** `pilot.sh:24` appends `team/officers/commander/commander.md` to every launch. That file says "Dated, verbatim statements are in `MANIFEST-orders.json` (64 as of 2026-09-21)" and then "What stands and is stated nowhere else in the cockpit". `commander/orders/` holds 84 order files; `MANIFEST-orders.json` is `updated: 2026-09-22`. Or065 to Or084 — twenty orders, including Or084's rulings on dispatch records and `records/events/` — are therefore outside the digest and outside the start procedure, which never reads orders at all. The pilot starts each session believing a closed list that is twenty orders short. Severity: high.

**F5 — Step 2's rule is written twice, in two rooms, and the copies differ.** `pilot.md:51` carries the full mechanics. `records/logs/README.md` also states it: "Add this session's entry to `MANIFEST-logs.json` at session start with a placeholder summary, and finish the summary at session end, so a crashed session is still indexed." The README copy omits the `session_id`/`session` keys and the `indexed` flag, so a reader who lands there gets the rule without the part that stops a second log opening. `CLAUDE.md` rules 5, 10 and 12 show the cockpit's own discipline here — point at the owning room, do not restate. Severity: medium.

**F6 — `indexed=yes` proves a manifest row, not a log file.** `session-start.sh:21-24` sets `indexed` from a row match in `MANIFEST-logs.json` alone. `pilot.md:51` reads it as proof of both: "the row and the log exist: read the log and open nothing." Step 2 has the row written at session start, so a session that crashed between writing the row and creating the file resumes with `indexed=yes` and no file, and the procedure forbids opening one. Severity: low.

**F7 — The procedure is written for one entry; the hook fires on four.** `base/settings/pilot.settings.json:16` matches `startup|resume|clear|compact`, and `session-start.sh:25` prints `source=`. No step in `pilot.md:48-54` reads `source`, and only step 2 handles re-entry. After a compact or a `/clear` the pilot gets the same hook block and, on the plain text of the procedure, re-runs steps 1, 3 and 4 and greets the commander again mid-flight. The hook already prints the field that would settle it. Severity: medium.

**F8 — The one document the start procedure writes is the one the Paperwork rule cannot govern.** `CLAUDE.md` Paperwork says "Before writing a document, read its schema in `base/verify/schema/<type>.json`; after writing, run `base/verify/cockpit-lint <file>`", and "A markdown document opens with its frontmatter". There is no `log.json` in `base/verify/schema/` (17 schemas, none for logs), and `records/logs/2026-09-22_f6216b95.md:1` opens with `# 2026-09-22 — session f6216b95`, no frontmatter. The exemption is real but lives only in a comment at `base/verify/lint.yaml:3` — "the session logs ... are not linted" — in a file nothing in the start path tells the pilot to open. A pilot obeying CLAUDE.md at step 2 goes looking for a schema that is not there. Severity: medium.

**F9 — "Latest log" names two different things.** `session-start.sh:29-31` computes `latest_log` as the last row in file order excluding this session's rows. `pilot.md:51` says "the latest log listed in `records/logs/MANIFEST-logs.json`" — and the same step has the pilot add his own row to that manifest, so read literally after the write, the latest listed log is his own empty one. Severity: low-medium.

## Round 1 — against trace.md T1 to T11

**F10 — T1's defect is right; its fix puts the pilot on reading that grows without bound.** Attacks T1 (agrees with my F2 on the defect). T1 proposes "open every unit with status `in_progress`". `work/missions/MANIFEST-missions.json` declares one `current`, and `CLAUDE.md` rule 7 says the commander closes missions, so an `in_progress` set only grows between closures — step 1 would open two mission files today and more later, for a question the hook answers in one line (`session-start.sh:28`). The mismatch is in the record, not in the step: either step 1 reads the manifest's `current` id and opens that one file, or the missions record needs a way to say two missions are live, which is a request to the commander, not a reword of the pilot's body. Severity: medium.

**F11 — T2's severity is inflated, and it walked past the fit defect in the same file.** Attacks T2. The stale paths are real (`commander/desk/README.md:5,6,7,9` against `in/dossiers/`, `in/requests/`, `out/advice/` on disk), but `pilot.md:52` names both step-3 paths literally, so the desk README is not on the procedure's path and nothing in the start procedure breaks — this is a stale index, not a break. What T2 passed over is on my angle: `commander/desk/README.md:9` states step 3 itself — "The pilot reads `out-advice/` at session start for anything not yet acted on" — a third room carrying a rule `pilot.md` owns, alongside the `records/logs/README.md` copy in my F5. Severity: medium.

**F12 — Both of T3's fixes are wrong at the file, and the second rests on a false statement in the record.** Attacks T3 (agrees with my F3 on the defect). Option A adds an `acted` field to the advice rows: that puts pilot-progress state into the commander's outbound room, where `base/verify/schema/commanders-advice.json` already defines `status` as his writing state — two owners, two meanings, one field. Option B cross-checks CA ids "against the `by` field in `commander/decisions/MANIFEST-decisions.json`": the manifest's rows carry only `id`, `date`, `subject`, `path` — no `by` — and in the units all 28 decision files carry `"by": "commander"`, the actor, never a CA id. So Option B needs 28 files opened to replace four, and its premise comes from a false line in `commander/desk/out/advice/MANIFEST-commander-advice.json`, whose convention claims decisions name "the advice file in each decision's `by` field". Fix the false convention line first; track pilot action where it is already tracked — the request rows' `status` and the session log. Severity: high.

**F13 — T8's two fixes go to two rooms and only one is the right room; its schema count is wrong.** Attacks T8 (agrees with my F8 on the defect). "Add the log's shape is in `records/logs/README.md` to step 2" is right. "State the session-log exemption in the Paperwork section" is not: `base/verify/lint.yaml:1` declares itself "The only file in base/verify/ that names cockpit paths. A room move means editing this file and nothing else here", and already carries the exemption in its header; copying the list into `CLAUDE.md` makes a second place to edit and a second place to go stale. Paperwork should say the lint globs decide what it governs and point at `lint.yaml`. Two corrections to T8's evidence: `base/verify/schema/` holds 17 schemas, not 18; and a pointer added to step 2 without removing `pilot.md:51`'s restatement of the README's placeholder-row rule leaves the two copies of my F5 standing. Severity: medium.

**F14 — T6 is right and names two of the three places; the duplication it leaves is what produced T7.** Attacks T6. `work/procedures/README.md:5` also calls `triggers.md` "the manifest" — "one line per approved procedure, under its trigger kind. Read by the pilot at session start" — so the mislabel is in three rooms, not two, and that line restates step 4 as well. Renaming does not close the hole: `triggers.md` and `MANIFEST-procedures.json` both list the same six procedures, one with status and one without, which is exactly how a draft procedure came to sit in the live trigger list. Severity: medium.

**F15 — T7's first fix is not the pilot's to take, and the room's own rule already decides the second.** Attacks T7. `work/procedures/README.md:20` says a `Draft:` procedure "has no manifest line", and `:24` puts approval with the commander — the `Approved:` line carries the date he approved or last adjusted it. `work/procedures/cockpit/P006-writing-a-request.md:11` reads "Draft: proposed under De027, not yet approved by the commander." So "either approve P006" is not an option the pilot holds; the line comes out of `triggers.md:6` now, and approval goes to the commander as a request. Severity: medium.

**F16 — T11 cites a rule that contradicts itself, and its fix would add restatement.** Attacks T11. `CLAUDE.md:78` says "Each directory has a README that indexes it", while rule 9 says "an index in every directory" — and `MANIFEST-requests.json` and `MANIFEST-commander-advice.json` are those indexes, both carrying `convention` prose. Writing READMEs into those two rooms would restate their manifests. Reconcile `CLAUDE.md:78` with rule 9 so that a manifest counts as the room's index; write nothing. Severity: low.

## Round 2 — against trace.md T12 to T18

**F17 — T14 moves a records question into the machinery.** Attacks T14 (same root as T1/F10). The hook prints what the record says; `MANIFEST-missions.json` names one `current`, so having `session-start.sh:28` print "the ids of every `in_progress` unit" has the machinery assert a plurality the record does not carry, and grows every session's opening context with a list that only shrinks when the commander closes a mission (`CLAUDE.md` rule 7). The hook is not the room to settle whether two missions can be current. Settle it in the missions record, as a request; the hook then prints whatever the record then says. Severity: medium.

**F18 — T15's fix does not fix the case it is aimed at, and its "cosmetic today" is not established.** Attacks T15. Sorting `others` by `date` cannot order the three rows dated 2026-09-18 in `MANIFEST-logs.json` (8e74fffb, 49f87e44, dcb75456); Python's sort is stable, so those ties fall back to file order — the defect, unchanged, on the one day the log has more than one flight, which `records/logs/README.md:7` says is expected ("A pilot may fly more than once a day"). And nothing dates them relative to each other: all three files were added to git in the single refit commit `d1c827d`, so "the rows happen to be in order" is unverified, not verified. Two fixes for one defect, as well: if the hook sorts, the README ordering rule is redundant; if the rows are ordered by rule, the sort is. One or the other. Severity: medium.

**F19 — The hook can die silently and step 2 has no fallback. Own, under T15.** `session-start.sh:10-14` guards the file read, but the row accesses do not: `mine[-1]["path"]` at `:24` and `others[-1]["path"]` at `:31` raise on a row without `path`, which kills the python block and the whole `[cockpit]` output with it. `pilot.md:51` is single-sourced on that output — "Open this session's log using the `log_name` printed by the SessionStart hook" — and names no fallback, so a pilot who receives no hook block has no log name, no `indexed` flag and no instruction covering the case. **F20 — T17 is right and its fix closes the label while leaving the break.** Attacks T17 (agrees with my F14 and F15). Its own evidence establishes two faults: the three-room mislabel, and the P006 line that `work/procedures/README.md:20` forbids sitting live at `triggers.md:6`. The fix lists only `pilot.md:53`, `CLAUDE.md:76` and `work/procedures/README.md:5` — renames alone. The draft line the pilot is routed through at step 4 comes out as well, and approval goes to the commander (`work/procedures/README.md:24`). Severity: low-medium.

**F21 — T16 is sound; two qualifications on its fix.** Attacks T16. ## Round 3 — against trace.md T19 to T24

**F23 — T19 is the sharpest finding of the trace, and one of its two fixes would break rule 2 a second way.** Attacks T19. The contradiction is real and deeper than stub-versus-authority: `records/manuals/cockpit/write-permissions.md` is prescription end to end (`:15` "The commander writes anywhere", `:19` "The pilot writes only in the cockpit", `:29` "The pilot gives the scope"), and `CLAUDE.md:24` rule 2 sets the vehicle test — "a manual is for a durable fact the pilot will need to look up, not for a rule, a routine or mission knowledge". **F24 — T22 checks the stamps of a pair that is not the launch pair, and contradicts T13 in doing it.** Attacks T22. `base/bin/pilot.sh:24` sets `APPEND_FILES` to `identity.md` and `team/officers/commander/commander.md`. `job.md` is not appended — T13 establishes this at the same line, citing `job.md:21` and `team/officers/pilot/README.md:7` — so "Both officer dossiers are delivered at launch" and "Both files are appended to the pilot's system prompt by `pilot.sh:24`" is false for `job.md`, and its stale stamp reaches no prompt. The file that is appended and was not checked is `commander.md`: its stamp is current (`["2026-09-21", "Pilot: Ace", "241bff25"]` against a last change at `b388481`, 2026-09-21), and its body is not — the 64-orders line of my F4. **F25 — T24's no-finding states the gap and then dismisses it; four seats have no dossier of their own.** Attacks T24. `team/crew/MANIFEST-crew.json` holds 41 rows, one without a path (`records-writer`), so 40 rows carry paths — but those 40 paths resolve to only 37 distinct files: `cockpit/adversary.md` is the path of three rows (`adversary`, `pool-adversary-a`, `pool-adversary-b`) and `cockpit/body-tester.md` of two (`body-tester`, `task-probe`). Against `pilot.md:46`, "Every seat has a row in `team/crew/MANIFEST-crew.json` and a dossier in `team/crew/<room>/<name>.md`", either four seats are missing their dossier or the rule permits variants to share one and does not say so. **F26 — T21 is right, and it is the second exemption proposed for the same wrong room.** Attacks T21 (and joins my F13). ## Round 4 — against the standing findings S1 to S27

**F28 — S14 accepts the write the trace refused three rows earlier, and it is the larger one.** Attacks S14. Answering T8 the tracer rejected a hook that creates the log file "because that makes the machinery a writer of cockpit records without a line in the log saying who wrote what". Take both or neither; as written the list refuses the smaller write and accepts the larger. Severity: high.

**F29 — The owner column has no consistent test.** Attacks S7, S10, S12 against S17.
