## 1. Structure and keep files

- `flightdeck/STRUCTURE.md` — the authoritative map. Declares FlightDeck as "an orchestration workflow tool for agentic software building… intended to eventually replace the dev-workspace system"; `flightdeck/` is the scaffold installed into a project the way dev-workspace installs `dev/`. Records directories only, never files. Defines vocabulary: deck, launch, keep file, manuals vs library.
- Keep-file convention: each folder carries `<task>.keep` naming its default job; these are permanent, not placeholders.
  - `flightdeck/flightcrew/orchestration.keep` — "Orchestrated agentic building"
  - `flightdeck/flightcrew/bin/runners.keep` — runnable scripts needed for every launch
  - `flightdeck/flightcrew/checks/checks.keep` — universal check harnesses
  - `flightdeck/flightcrew/crew/agents.keep` — the lineup of agents called on every launch
  - `flightdeck/launch/runs.keep` — "Orchestrated build runs. self contained."
  - `flightdeck/testbench/tests.keep` — harnesses reusable across the branch; save to `main` for global access; merge-protect; launch results must NOT be stored here; `runs/` is local results
  - `flightdeck/manuals/documentation.keep`, `flightdeck/blackbox/archive.keep` (placeholder for a future CLI `archive` command), `flightdeck/hangar/workspace.keep` (main agent loop working dir), `flightdeck/HUD/visuals.keep` (stub for `panels`/`decks`)
- **Contradictions vs the real tree:** STRUCTURE.md documents `radar/` (with `decks/`, `panels/`) but on disk the folder is `flightdeck/HUD/` with those same subfolders; it documents `launch/example-launch/{checks,specs}` which does not exist; and it does not mention `flightdeck/.controlcenter/` (holds `control-panel.keep`) which does exist. No root `flightdeck/README.md`; root `README.md` is two lines and calls the human-in-the-loop half "controltower" while the tree calls it `.controlcenter`/`.cockpit` — three names for the same idea.
- STRUCTURE.md's own branch note admits `launch/agent-types/specs/` (twelve v1 agent-type specs) lives only on `engage-crew`, and that `crew/spec-interviewer.md` "is deliberately empty… what the next launch builds".

## 2. `flightdeck/flightcrew/`

- `bin/` — only `bin/worker/render-worker-prompt.mjs` (237 lines, zero-dependency Node). Renders worker prompts deterministically from `plan.json` + `spec.vN.json` + `tests-map.json` against `templates/worker.template.md`; supports `--unit/--all`, plan-hash approval verification, `--allow-draft`. Looks complete and self-documented. **No `fc` CLI exists here** although the testbench logs exercise one extensively (see §4).
- `checks/` — `spec-readiness-lint.mjs` (192 lines, part one of the readiness rubric; `--run-commands` opt-in) plus `checks/validators/`: `schema-lib.mjs`, `validate-spec.mjs`, `validate-plan.mjs`, `validate-tests-map.mjs`, `validate-md.mjs`, `validate-all.mjs` (bulk walker with 0/1/2 exit codes). All substantial and apparently complete.
- `crew/` — role definitions (YAML frontmatter + body), all `model: fable` except workers (`sonnet`):
  - `spec-builder.md` (82 ln) — turns an intention/rough draft into a self-contained spec via explorer waves plus a targeted interview; dispatches judge and attacker; never freezes its own work.
  - `spec-judge.md` (39 ln) — fresh context; judges a linter-clean draft against the readiness rubric; yes/no answers with quoted evidence only, no scores or edits.
  - `spec-attacker.md` (50 ln) — fresh context hole-hunter after the judge: forks, missing outcomes, unwritten checks, false seams, silent dependencies, contradictions.
  - `test-builder.md` (44 ln) — builds checks, one acceptance proof, and the tests map from the frozen spec alone, before any plan; refuses to read plans or implementations.
  - `worker.md` (61 ln) — implements exactly one plan unit against pre-written checks and locked interfaces; fenced by `owns`; iteration ceiling; contradiction = stop.
  - `isolated-worker.md` (62 ln) — byte-identical to `worker.md` in body; frontmatter differs only by `name: worker-isolated` and `isolation: worktree`. **Duplication smell** — two files, one behaviour.
  - `spec-interviewer.md` — **0 bytes, deliberately empty** (per STRUCTURE.md, the next launch builds it).
  - `crew.json` (778 ln) — a project-agnostic manifest of the whole orchestrated-run pattern: conventions (model tiers strong/standard/small, context hygiene, evidence, `worker_return_contract`) plus roles `spec-interviewer, spec-attacker, test-builder, orchestrator, explorer, interface-builder, worker-general, worker-strong, unit-adversary, run-verifier, reviewer, report-assembler, human` and gates `spec-freeze, targets, plan, interfaces, final`. **Naming drift:** the manifest has roles (orchestrator, explorer, interface-builder, unit-adversary, run-verifier, report-assembler) with no `.md` file, and `.md` files (spec-builder, spec-judge, worker, reviewer) whose ids do not all match manifest ids (`worker-general`/`worker-strong` vs `worker`/`worker-isolated`; `spec-interviewer` vs `spec-builder`).
- `schemas/` — `spec.schema.json` (451 ln), `plan.schema.json` (323), `tests-map.schema.json` (133), plus `schemas/worker/worker-agent.docspec.json` and `worker-prompt.docspec.json` (30 and 15 ln — thin by comparison).
- `templates/` — `liftoff.template.yaml` (323 ln, see §3), `spec.template.json`, `plan.template.json`, `tests-map.template.json`, `worker.template.md` (handlebars-style `{{unit.id}}`, `{{#each spec_entities}}`), and three markdown spec templates under `templates/spec/`: `agent-harness`, `decision-research`, `reference-library` (~43 ln each).
