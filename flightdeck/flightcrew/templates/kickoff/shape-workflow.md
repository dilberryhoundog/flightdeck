## Shape: workflow
The orchestrator hands a wave to a dynamic workflow script — the scripts are kept at flightdeck/flightcrew/workflows/ and run from the copies `fc distribute --apply` places in the harness directory's workflows folder — and keeps the session for the gates and the fc commands. This run takes the workflow shape because a wave holds more units than the implementers_concurrent ceiling, so the fan-out needs a script to hold it. The orchestrator session keeps the three gates, every fc command and every stored return; only the dispatch mechanism moves into the script.
Dispatch: the scripts are invoked as `/fc-implement`, `/fc-review` and `/fc-explore`, each with a structured args object; flightdeck/manuals/harness/workflows.md carries the args every one takes, the payloads each returns and the command that stores each payload. `/fc-implement` fans the wave's implementers, pilots first and the rest in chunks; `/fc-review` runs the critic, fix and re-verify loop; `/fc-explore` fans the planning questions. Before `/fc-implement`, run `fc worker render <unit>` for every unit of the wave and commit each rendered prompt, because a subagent worktree branches from HEAD; before `/fc-review`, run `fc critic render --pass <n>` and pass that sealed path. The scripts replace only the dispatching in conduct steps 1, 4 and 6; every fc command in those steps stays with the orchestrator, and after a workflow completes the orchestrator persists every payload with `fc return` and lands units with `fc worker merge`.
Progress: while a script runs, its phase lines in the `/workflows` view are the display and never evidence; progress is the returns stored with `fc return` and the evidence page once the workflow completes.
Stopping: a workflow stops dispatching on the first halt payload and returns it; `/fc-review` returns an escalation payload on a spec conflict and a trigger payload at the critic-passes ceiling with blocking findings open. The orchestrator records each with `fc launch escalate <halt|spec-gap|trigger> --detail "…"` and ends the turn; findings under `unrouted` and answers under `rejected` are placed by the orchestrator before anything is stored. Gates are never inside a script — the script ends and the session halts at the gate.
