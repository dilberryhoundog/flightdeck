# Plan: flightcrew-v1 · flightcrew-buildout

## Approach

The system is cut along the ownership lines of the design's build-unit table, so that no two units write the same file. Wave 0 lands the contracts every other unit imports: the ten JSON schemas and the seven check libraries. Wave 1 builds the four pillars that only depend on those contracts - the validators and gates, the fc runner and its command modules, the five hooks, and the crew definitions - with the runner as the pilot, because every other unit's checks invoke fc and a broken runner would waste the whole wave. Wave 2 adds the templates, the kickoff library and the workflow scripts alongside the manuals, both of which read the finished interfaces rather than defining them. Wave 3 is a single serial integration unit that writes MANIFEST.txt, produces this launch folder with the real commands, and fixes whatever the cross-unit suites still refuse. Every unit is proved by named suites of the pinned tests map; the suites themselves, the fixtures, the runner and the spec-stage assets are locked for the whole run.

## Risks

- Six units write into flightcrew/ at once and every one of them calls fc; a runner that does not dispatch would fail every other unit's checks, so the runner is the wave-1 pilot and the rest of the wave only starts once its return is green — reaction: mitigate (source: the design's build-unit table)
- The suites are written before the implementation and are locked, so a suite whose assertion no implementation can satisfy stops a unit rather than being edited; the unit halts and reports the case id instead — reaction: watch (source: spec I9)
- Units disagree about a shared interface - the gate modules the stop gate imports, the command modules the hooks invoke - and each half passes its own suite while the pair does not work; the integration unit re-runs the whole testbench and reconciles them against the design — reaction: mitigate (source: spec B33)

## Gates

- G1: plan.md read against the spec: every unit owns files no other unit writes, every unit names checks that exist in the pinned map, the waves respect the contracts-first order, and the abandon triggers are observable
- G2: the wave-0 schema and library check T26 green since lock_commit, and the changed-since-lock list confined to flightcrew/schemas/ and flightcrew/checks/lib/
- G3: the evidence page and report.md: the twenty-nine checks with their raw output, the boundary and locked results, the open findings, the three unverified lines and the cost line

## Abandon triggers

- a locked suite carries an assertion that contradicts the frozen spec and no implementation can satisfy it — observable by: a worker return with status halt naming the suite and case id; an escalation event of kind wrong-check
- the acceptance check T1 stays red after the stop gate's cap of consecutive blocks in phase verify — observable by: stall and trigger events in events.jsonl; fc budget consecutive stop blocks
- any change outside flightdeck/flightcrew/, flightdeck/launch/, flightdeck/testbench/ and flightdeck/manuals/, or any change under a locked path — observable by: boundary_denied or lock_denied events; fc boundary or fc locked exit 2
