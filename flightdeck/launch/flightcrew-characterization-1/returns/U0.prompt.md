## Intent
Flightcrew's test suite checks only its runner's commands. Nothing exercises a role, a hook or a workflow the way a working session does, because the manuals for testing agent-shaped work came after the build. Flightcrew is about to be refactored, and without a suite that describes it whole, every part the refactor touches is changed blind. This work builds that suite over flightcrew exactly as it stands, every part, using the full range of checks. This run utilises flightcrew for the first time, so the run's own faults become valuable for later improvements. Success: one command proves every part of flightcrew green, breaking any part turns its check red, and the run that built the suite can be read end to end.

## Decisions
- D1: The suite covers the whole system as it stands rather than a chosen subset, because which parts survive the refactor is the refactor's decision, and a refactor leans on the entire test surface: tests over what stays hold it in place, tests over what changes change with it, tests over what is removed go with it.
- D2: The suite is built with the seven classes of check and the three verdicts from the testing manuals, and agent-shaped parts follow the verification addendum, because the first build used exit-code scripts for everything and that is the gap this work closes.
- D3: Statistical and judged checks are used only where no cheaper class can falsify the behaviour, and no class is required to exist: where the builders find no part that needs a live scenario, the checks over scenarios and sheets pass empty, because every trial spends tokens and the run has one subscription behind it.
- D4: The run's own record is kept whole, mistakes included, rather than tidied, because the first run of flightcrew on itself is wanted as evidence for the refactor and a tidied record is not evidence.
- D5: The existing thirty suites are not a settled asset: they test the runner's commands with exit codes and were written without the testing manuals, so the new suite may absorb or replace them.
- D6: Judged checks run on opus against a rubric calibrated with fable, because the owner's own testing found opus judges as well as fable once the rubric has been strengthened by it, and a judge's reliability comes from the instrument, not the tier.
- D7: Statistical scenarios are premade at a fair difficulty and run on opus or below, with their threshold tuned so that opus stands in for fable, because a fair scenario capped at opus still reproduces the harder real run and the tier cap keeps every trial affordable.
- D8: Under the current tooling a gate reads exit codes only, so the ratio and the sheet live in the suite output beside the exit code, because the tooling's result shape has no place for them and leaving those classes out would repeat the first build's gap.
