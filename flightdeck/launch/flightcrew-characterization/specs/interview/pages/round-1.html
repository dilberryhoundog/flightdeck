interview round 1

bundle P-scope · scope

The scope names what the characterization covers and where its run lives, but four of its nodes rest on a choice the sources do not make.

Q1 SC8

fc launch new creates its own folder, flightdeck/launch/<spec.name>-1/, beside the new-layout folder that holds this spec. Where does this launch's run live?

The v1 tooling copies the spec into a launch folder it names and resolves the active launch by scanning for launch.json; the new-layout folder already carries one.

Q2 SC10

When a characterization test finds that a kept part behaves wrongly today, what does the suite do?

Standard characterization pins what the system does, not what it should do; the rebuild then knows the wart is there. Skipping loses the coverage; fixing contradicts the no-change rule.

Q3 SC12

Thirty tracked suites already exist and most test the runner's commands rather than the observable boundary. How do they relate to the characterization suites?

A boundary-level tracked suite is already a characterization; a runner-shaped one proves the wrong thing and would be deleted with the runner.

Q4 SC4

No hooks are installed in this project's .claude/settings.json today. How are the enforcement behaviours characterized?

The existing hooks-* suites drive each hook script with a synthetic event and read its decision; a live session would prove the wiring too but is agent-shaped and slow.

Q5 SC2 SC5

The spec chain and the crew are agent-shaped. How far does their characterization go?

Role files, dispatch rendering and return shapes are deterministic; the judge's verdicts are not. The rubric bench under flightdeck/testbench/benches/rubrics/spec/ already holds human-graded drafts, so one judged check has golden material without a new grading session.
