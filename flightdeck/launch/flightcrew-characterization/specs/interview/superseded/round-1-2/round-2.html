interview round 2

bundle P-runner · scope

The runner. fc has nineteen commands today. The core spec keeps ten scripts by path, defers a flight wrapper, and says no command a human types advances a run. Some of fc's current behaviour survives under those scripts: validate and lint verdicts, check's evidence per check, render's sealed dispatch, distribute's copy into .claude. The suite needs your stance on whether any of that is the runner's behaviour or the system's.

Q1

Is the runner in the suite at all?

A suite that pins fc's commands is the v1 mistake again. A suite that pins only the effects (a spec that breaks an invariant is refused naming it; a check run leaves one evidence file per check) survives the runner's removal because the test-builder re-points the command later.

Q2

fc distribute copies crew files, the hook settings fragment and the workflows into .claude. The core spec's install derives the same surface from the crew folder. Is that derivation a kept behaviour?

If kept, the suite pins today's distribute effect (what lands in .claude and that it matches the source). If goes, the installed surface is characterized only as files that exist.

bundle P-workflows · scope

Workflows. Three fc-* scripts exist under flightcrew/workflows (explore, implement, review) and two build scripts under .claude/workflows written for the v1 build. The core spec replaces them with a suite of workflows driven by liftoffs. Round 1 also decided this launch's own run is conducted by a workflow you ask Claude to run directly.

Q1

Are the existing workflow scripts goes entirely, or do the behaviours inside fc-implement count as kept?

fc-implement already does pilot-first, chunked fan-out, stop on a red return and validated returns. If those are the behaviours the new build workflow must reproduce, characterizing them now against fc-implement gives the rebuild a target; if the scripts are simply replaced, nothing is pinned.

Q2

The workflow authoring contract (meta literal first, no filesystem, shell, clock or randomness, args binding, return shapes inlined as literals) is enforced today by a static scan. Is that contract a kept rule the suite pins?

It is a harness constraint rather than flightcrew's invention, and every future workflow must satisfy it; a static scan is cheap and deterministic.

Q3

Which workflow conducts this launch's own run?

Round 1 chose a directly invoked workflow over the v1 tooling. The v1 suites were built by a hand-written flightcrew-targets.js with five test-builders in parallel, each refuted and fixed once; fc-implement expects a plan and rendered dispatches.

bundle P-enforcement · scope

Enforcement. Six hook scripts exist, wired into settings at run time by distribute, with a no-op rule (stay silent when unsure a run is in progress) and an ask decision on ambiguity. The core spec moves hooks into role frontmatter, reads freeze from the document's own status, adds the Bash sandbox, drops phases, and says every guard fails closed. You said this is not settled.

Q1

Do the six hook scripts stay as implementations with only their wiring moving, or are they rewritten with only their effects kept?

The answer decides whether the suite drives today's scripts with synthetic events and pins their decisions, or pins only the observable effects and leaves the mechanism to the rebuild.

Q2

Today a guard that cannot be sure it speaks for a run stays silent, and on ambiguity prints ask. The core spec says a guard that cannot decide refuses. Which is the kept behaviour?

Pinning today's silence would pin the hole the rebuild is meant to close; pinning refusal would fail against today's system.

Q3

Locked paths remain a mechanism beside the frozen status field. Today lock-guard reads paths.locked from launch.json by phase. Is locked-path refusal a kept behaviour to characterize?

The source of the locked list changes (the tests map's dependencies rather than launch.json), the effect does not.

bundle P-crew · scope

The crew. Ten role files live in flightcrew/crew and eleven in .claude/agents (adversary exists only there). The spec chain is byte-frozen. The core spec keeps explorer, planner, orchestrator, implementer, verifier, critic and test-builder, adds steward, adversary, interface-builder, scribe and a stronger-tier retry, and declares each role's reach in its own file with the installed settings derived from the crew folder.

Q1

What does a characterization test of a role file assert?

A role file is a harness document. Its frontmatter is a contract (the fields the constitution requires, the tools it may hold, isolation and permission mode); its body is prose. Live behaviour is the test-builder's and the judge's business, not this suite's.

Q2

Are the seven surviving role bodies kept as they are, or rewritten around workflows?

If kept, the suite may pin body-level facts; if rewritten, only the frontmatter contract and the separations are stable enough to pin.

Q3

adversary.md exists only in .claude/agents, not in flightcrew/crew. Is it a kept role or a stray from the v1 build?

The core spec names an adversary role; crew/ is the source of truth for roles.

bundle P-dispatch-returns · scope

Dispatch and returns. Four dispatch templates, a three-layer render (role file, project template, per-unit fill) and four return schemas (worker-return with halt kinds, explorer-return, critic-findings, verifier-verdict) exist, with a validator and fc return storing returns. The core spec keeps the sealed dispatch, commits it before spawn, captures the return by hook, and moves the schemas under schemas/run.

Q1

Are the four return shapes kept as they are, so the suite pins their fields?

The core spec reuses all four schemas by path. If their fields are stable, a conforming and a non-conforming document per shape is a cheap deterministic pin; if halt kinds or fields will change, only the rule that a return validates is stable.

Q2

Is today's rendering the kept behaviour, or only the sealed-dispatch rule?

Today fc worker render fills the template from the plan unit; the rule is that nothing outside a slot reaches the worker and the rendered prompt is a file.

bundle P-documents · scope

Run documents and the log. The spec shape is untouched. launch.json changes almost entirely; the tests map gains a verdict field; the plan loses gates and ceilings and gains a scout flag; events lose phase and gain run; evidence and check results stay; RUNLOG.md becomes FLIGHTLOG.md with the same diagnosis fields. You said: just write the test and let the test-builder reshape it after the core spec freezes.

Q1

For a document whose shape changes, what does the suite pin now?

Pinning the whole current shape gives the test-builder a complete test to reshape; pinning only survivors gives it less to undo but leaves today's document half-described.

Q2

Is the run log's contract a kept behaviour: an entry per run with the human's diagnosis fields (seen on, cause, fixed on, change, watch, kept, promote), a symptom pre-filled and never hand-written, and no new run opening while a fill line stands?

The file is renamed and the entry is written by a role instead of a command, but the fields and the blocking rule are the method's, not the runner's.
