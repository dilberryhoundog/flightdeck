Intent 1

INTstatus: ok

An AI engineer who has outgrown one-shot chat turns needs a crew of agents that builds what a spec says, beginning with itself, until it can build other things; the product is agent-shaped. Flightcrew v1 was built by a dynamic workflow that wrote its own spec and chose a fully testable command surface as the system's driver, and both recorded runs were driven by hand and transcribed into its format, so nothing it claims about a run has been observed. This version is the human's correction: the accepted foundations are kept, the first attempt's mistakes are corrected, and the result is a simpler system, just as capable, that runs under its own power for the first time. The elements of a run — a valid spec, its tests, the kickoff, the plan, the roles, the units built, verified, attacked and merged, the review, the record of events, the log entry and the clearing of build residue — each exist as files and as Claude Code's own tooling (hooks, agents, workflows, settings), each element stands alone and doesn't need active control. The engineer's vision is front-loaded into frozen documents before building begins. The outcome is discovered not built; workflow state is shaken out progressively, it rests 'hardcoded'; and what a run records is what the next run inherits.

In flightdeck/flightcrew/schemas/run/tests-map.schema.json each check carries verdict: 'exit'|'ratio'|'sheet' (replacing class), kind as it stands, depends_on: [glob] (paths whose change invalidates the check, locked with it), baseline { expect, observed } as it stands (observed written by flight check --baseline), and for ratio { trials: int, threshold: number } and for sheet { rubric: string, a path under runs/run-<n>/checks/rubrics/ }; allowed_paths and gate_only are removed (the plan owns the boundary); fixture and run_all stay. Decisions 21

D1status: ok

Node ES modules with zero dependencies and no package.json, because the harness must run identically on any machine with Node 22 and git; hooks, leaves and workflows are JavaScript so one testbench covers them.

D2status: ok

The runner is named flight and is a thin dispatcher over leaves that run by their own path, because nothing may depend on the dispatcher and no command a human types advances a run.

D3status: ok

The launch is the unit of work and the run the unit of attempt: launch/<name>/ holds the spec series and every run, runs are numbered and never reopened, and the log is FLIGHTLOG.md beside all launches, because two attempts at one piece of work must share an address.

D4status: ok

A launch is opened from an idea before any spec is frozen and holds no run until one is frozen; flight run new opens each attempt and cuts its branch from the branch the human is on at that moment, because a branch cut before the spec is frozen is based on a commit the run cannot use.

D5status: ok

A run has no phase field and no gate switch: it is a liftoff's sequence of workflows, each ending where a human reads what it wrote and tells the orchestrator to invoke the next, because a phase a program advances and a gate a human flips were the spine the first attempt built itself around and neither is in the sources.

D6status: ok

The liftoff is a JSON recipe in a library, naming the workflow sequence, its overrides and settings, pasted into the orchestrator session, because tooling is a failure axis and a run that needs different tooling gets a different liftoff, not a different workflow; the markdown kickoff parts end and the task parts become planner templates.

D7status: ok

The gate that holds a worker red is the SubagentStop hook in the worker's own frontmatter, not the session Stop hook, and it counts its own blocks and writes a stalled event before Claude Code's eight-block override, because the override displays nothing and a stall must reach the workflow as a return.

D8status: ok

plan.json is the source of truth and plan.md is rendered from it, because a hand-edited copy drifts and machine consumers need the structured form.

D9status: ok

Worktree isolation is requested per agent() call for implementer and strong-worker only, the settings set worktree.baseRef to head, a rendered dispatch is committed before the worker is spawned, and WorktreeCreate is not hooked, because a worktree branches from HEAD and a command hook there replaces Claude Code's own worktree creation.

D10status: ok

Hooks run in place from flightdeck/flightcrew/hooks/ through $CLAUDE_PROJECT_DIR and are never copied, because a copied hook loses its relative imports and a second copy drifts.

D11status: ok

The spec chain and its rubric corpus are unchanged because they carry calibration evidence this launch cannot reproduce; spec-builder is a session agent and spec-judge and spec-attacker are subagents it dispatches, which is why their files declare inputs differently from the run chain.

D12status: ok

The two v1 attempt folders and the old spec folder stay as history rather than being migrated, because migrating means editing two frozen maps and two records for evidence no flightcrew run produced.

D13status: ok

The tests map lives beside the spec under specs/ and the checks it names live in the run, joined by the {run} token in each command, because the map is a versioned series that absorbs the log's decisions while checks change between runs.

D14status: ok

After the report, everything is the human's: reading the report, merging or rejecting the pull request, deleting branches, writing the diagnosis and starting the next run; the system's part of an ending is the report, the log stub, the worktrees removed and the pull request opened, because the sources put every step after the final review in the human's hands and no remote automation is in scope.

D15status: ok

B71, B72, B74, B75, B87, B22, B23 and B24 have no edge of their own because each is a whole-set property with one violating result — a file that fails the parse, the reading, the render, the schema, the pacing rule or the run — and that result is the check's failure line.

D16status: ok

This run's schemas and dispatch templates live under schemas/run/ and templates/dispatch/, and the crew stays flat under crew/ as the source of truth for every agent, because the spec schema and template must sit outside the folders the run rewrites while a role file's folder is what install and the dispatch list read.

D17status: ok

The run in progress is resolved from flightdeck/.controlcenter rather than by scanning for an active record or reading an environment variable, because a file a launch command writes is the variable made durable, and a worktree reads the main checkout's copy so workers need nothing of their own.

D18status: ok

Budgets — concurrency, agents, tokens, turns — belong to the workflow runtime and the agent files, because the runtime enforces them without consulting the agent and a ceilings object in a document is a number nothing reads.

D19status: ok

A merged unit's worktree and branch are removed by flight merge and the run's remaining worktrees by fc-report with their branches kept, because the runtime removes a worktree by itself only when it finishes without changes and deletes the branch when it does, so a run's own cleanup must be explicit and must not lose a red unit's evidence.

D20status: ok

Workflows run leaves and git through a steward role that holds Bash alone, because a workflow script cannot touch disk, the orchestrator is not inside it, and giving a building role the leaf would let it merge its own work.

D21status: ok

This launch's own launch.json, run-1 and FLIGHTLOG.md predate the leaves that would create them, because the tools that open a launch and a run are themselves deliverables of the run; every later launch is opened by flight launch init and every later run by flight run new.
