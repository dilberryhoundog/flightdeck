bundle P-intent-wording · gap · intent

The intent node now reads: “An AI engineer who has outgrown one-shot chat turns needs a crew of agents that builds what a spec says, beginning with itself, until it can build other things; the product is agent-shaped. Flightcrew v1 was built by a dynamic workflow that wrote its own spec and chose a fully testable command surface as the system's driver, and both recorded runs were driven by hand and transcribed into its format, so nothing it claims about a run has been observed. This version is the human's correction: the accepted foundations are kept, the first attempt's mistakes are corrected, and the result is a simpler system, just as capable, that runs under its own power for the first time. The elements of a run — a valid spec, its tests, the kickoff, the plan, the roles, the units built, verified, attacked and merged, the review, the record of events, the log entry and the clearing of build residue — each exist as files and as Claude Code's own tooling (hooks, agents, workflows, settings), never as a program a human types into to advance a run. The engineer's vision is front-loaded into a spec with no gaps and judged back into it, never dispensed through the build; the outcome is discovered across cheap retried attempts; the state is shaken out as open documents any program can read; and what a run records is what the next run inherits.”

Q1Does that sentence stand as the intent?

Every later node hangs from it. A change here is cheap now and a version later.

bundle P-scope-runner-as-leaf-tooling · dual-path · scope

The runner is 21 modules, 4,732 lines; launch.mjs alone is 887 and is the only writer of launch.json (new, activate, phase, gate, pin, end, land, escalate, note). The commands that write exactly one artefact from arguments are boundary, locked, budget, check, the three renders, evidence, report, plan render, runlog stub, return and events append. distribute and doctor are installation. Fifty-seven of v1's 78 behaviours name the runner.

Q1What becomes of fc?

Fixes whether the spec has an interface node for a command program at all. A kept name keeps its shim, output library and one-line rule; scripts by path have none of those and each stands alone.

Q2Which built commands survive as leaves? (pick any)

Each kept leaf is a reused asset no unit rebuilds; each dropped one is retired code and retired test suites. The launch state subcommands are excluded on the problem's own terms.

Q3Which new leaves does the layout need, since nothing today creates a launch folder or a numbered run?

A launch and a run are now folders with a defined file set. Something must scaffold them, and whether that is a script or a copied template decides whether the interval before a spec exists is modelled.

Q4Is this the spec seam for v2: a node about an artefact's state, a hook's enforcement, a role's inputs and outputs or a rendering's contents stays; a node about arguments, resolution order, exit codes or which subcommand does what leaves?

This is the rule I will retire v1 nodes by. Roughly forty behaviours and edges fall to it. What survives of the runner is one constraint on leaf scripts (exit codes, one-line success output, its named exceptions) and the artefacts they write.

Q5The four manuals written as command sequences (launch-anatomy, journey, workflows, review): in this run?

Manuals are context an agent cannot test. Rewriting them to the seam is a unit of work; leaving them is a false premise handed to every role that reads them.

bundle P-scope-roster-and-separations · dual-path · scope

Ten crew files exist. spec-judge and spec-attacker lack the inputs sentence and a return block; the orchestrator's model is inherit; only the implementer declares isolation; no role declares hooks, though agent frontmatter can carry hooks natively. The test-builder is a subagent on paper (maxTurns 40, acceptEdits) and a session in practice. The permission fragment denies the path the test-builder is told to write.

Q1Which of the four hats the constitution names become roles in this run? (pick any)

Each new role is a crew file, a dispatch template, a return schema and a place in the workflow. Each one not taken is either a kickoff rule or a workflow stage and I will write it as that.

Q2Is the test-builder a session agent or a dispatched subagent?

A session agent holds the ask-user tool, has no turn budget and is started by the human; a subagent gets a sealed dispatch with a run folder in it and a return schema. The file must be one or the other.

Q3Where is a role's reach declared?

Today frontmatter and the settings fragment are two hand-written files that contradict. One source with the other derived, or a check that the two agree, closes the hole.

Q4The spec chain (spec-builder, spec-judge, spec-attacker): frozen for calibration, or brought under the crew rules?

D4 froze them byte-for-byte; the builder was rewritten anyway. Frozen files cannot gain the inputs sentence, a return schema or a rendered dispatch.

Q5Role-scoped hooks: used in this run?

Agent frontmatter can carry its own PreToolUse/PostToolUse/Stop hooks. A worker-only test-after-edit hook or a critic that cannot write even if its tools widen can only be expressed there.

Q2What happens to the existing folders: launch/flightcrew-buildout/, launch/flightcrew-buildout-2/ and launch/specs/flightcrew-v1/?
