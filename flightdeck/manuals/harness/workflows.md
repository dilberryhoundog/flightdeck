# Workflows

The three dynamic workflow scripts under `flightdeck/flightcrew/workflows/` carry the fan-out of a wave, the review loop and the planning questions when a run takes the workflow shape. They only dispatch agents and return payloads; nothing they return exists until the orchestrator stores it with `fc return`. The stage numbers used below are those of `flightdeck/manuals/orchestration/journey.md`.

## Choosing the shape

- `shape-session` is the default: the orchestrator session dispatches subagents itself, at most `implementers_concurrent` at a time.
- `plan.shape` accepts three values, `session`, `workflow` and `sessions`. This manual covers the session and workflow pair; `flightdeck/manuals/orchestration/kickoff.md` carries `shape-sessions`.
- `shape-workflow` is chosen only when a wave holds more units than `implementers_concurrent`, so the fan-out needs a script to hold the chunking and the stage results outside any context window.
- Under either of these two shapes the orchestrator session, the gates, the `fc` commands and the stored returns are identical; only the dispatch mechanism, the progress view and the stopping differ.
- Gates are never inside a script: a script ends, and the session halts at the gate.
- `plan.shape` must equal the shape part in the kickoff version; `fc validate plan` refuses a mismatch.

## The three scripts

The orchestrator builds each `args` object from the launch: `units` and their `depends_on`, `pilot`, `paths` and `checks` come from `flightdeck/launch/<L>/plan.json`, `implementers_concurrent` and `critic_passes` from that plan's `ceilings`, `spec_path` from the pinned spec copy recorded in `launch.json`. Each script is invoked as `/<name>` with the `args` object passed as structured data, and `args.timestamp` is an ISO-8601 UTC string.

| script            | run as          | `args`                                                                                                                                                     | does                                                                                                                                                                                                                                                                                                                                                                                                                                           | returns                                                                                                    |
|-------------------|-----------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `fc-implement.js` | `/fc-implement` | `{launch, units: [{id, name, prompt_path, checks, depends_on, pilot}], implementers_concurrent, timestamp, agent_type?, model?}`                           | derives waves from `depends_on`; per wave runs `pilot: true` units first and continues only on green returns; dispatches the rest in chunks of `implementers_concurrent`; validates every return against the worker-return shape; an absent or invalid return becomes `status: halt, halt.kind: budget`; the first halt stops dispatch, and a red pilot return also stops dispatch, filling `stopped_on` with the unit while `halt` stays null | `{workflow, launch, timestamp, dispatched, returns, halt, stopped_on}`                                     |
| `fc-review.js`    | `/fc-review`    | `{launch, spec_path, critic_prompt_path, units: [{id, name, paths, checks}] with `paths` the globs `plan.json` carries, critic_passes, timestamp, model?}` | fresh critic pass; routes `correctness-gap` and `scope-violation` to the implementer of the unit whose `paths` hold the file, with the finding, the spec and that unit's checks; re-verifies; takes a fresh pass; a `spec-conflict` stops with an escalation payload and no fix; observations are carried and never dispatched; at `critic_passes` with blocking findings open returns a trigger payload                                       | `{workflow, launch, timestamp, passes, fixes, verifications, unrouted, observations, escalation, trigger}` |
| `fc-explore.js`   | `/fc-explore`   | `{questions: [{id, question, stage, scope_paths}], timestamp?, model?}`                                                                                    | one read-only explorer per question, answering within `scope_paths` and citing what it read; a return that does not match the explorer-return shape is listed under `rejected`                                                                                                                                                                                                                                                                 | `{workflow, timestamp, asked, answers, rejected}`                                                          |

- `prompt_path` is `flightdeck/launch/<L>/returns/<unit>.prompt.md`, which `fc worker render <unit>` writes beside printing; commit it before the dispatch, because a subagent worktree branches from HEAD and an uncommitted launch-folder file is invisible to the worker (the commit-points line under the stages table of `flightdeck/manuals/orchestration/journey.md`). `critic_prompt_path` is the sealed file `fc critic render` wrote; a script hands an agent that file and nothing else.
- `agent_type` is `implementer` when `.claude/agents/flightcrew/implementer.md` exists, `general-purpose` otherwise; `fc distribute --apply` copies `crew/*.md` to `<target>/agents/flightcrew/` alongside the workflow scripts.
- Timestamps arrive through `args`: `Date.now()`, `new Date()` and `Math.random()` throw in the workflow runtime.
- Each script opens with `export const meta` as a pure literal whose `name` equals the basename with the `.js` extension removed (`fc-implement`, not `fc-implement.js`), and inlines every return schema as a literal identical to `flightdeck/flightcrew/schemas/<kind>.schema.json`; the suite at `flightdeck/testbench/suites/workflows/` proves both.

## Persisting payloads

After a workflow completes, the orchestrator stores every payload through `fc`; until then nothing a script did is evidence.

| payload                                          | command                                                                                                                                                                                                                                       | stored at                                         |
|--------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------|
| each worker return in `returns`                  | `fc return worker <file> --unit <id>` (alias `fc worker return <id> <file>`)                                                                                                                                                                  | `flightdeck/launch/<L>/returns/<unit>.json`       |
| each green unit                                  | `fc worker merge <unit>` in wave order                                                                                                                                                                                                        | the run branch; `unit_merged` event               |
| each critic pass in `passes`                     | `fc return critic <file> --pass <n>`                                                                                                                                                                                                          | `flightdeck/launch/<L>/review/pass-<n>.json`      |
| each fix in `fixes`                              | `fc return critic --resolve F<n> --commit <sha>`                                                                                                                                                                                              | `flightdeck/launch/<L>/review/resolutions.json`   |
| each verification in `verifications`             | `fc return verifier <file> --pass <n>`                                                                                                                                                                                                        | `flightdeck/launch/<L>/returns/verify-<n>.json`   |
| each answer in `answers`                         | `fc return explorer <file> --id X<n>`                                                                                                                                                                                                         | `flightdeck/launch/<L>/returns/explore-X<n>.json` |
| a `halt` payload                                 | `fc launch escalate halt --detail "…"`                                                                                                                                                                                                        | `escalation.json`; `escalation` event             |
| a `trigger` payload                              | `fc launch escalate trigger --detail "…"`                                                                                                                                                                                                     | `escalation.json`; `escalation` event             |
| a red-pilot stop (`stopped_on` set, `halt` null) | `fc launch escalate blocked --detail "…"` naming the unit and its red checks                                                                                                                                                                  | `escalation.json`; `escalation` event             |
| an `escalation` payload (spec conflict)          | `fc launch escalate spec-gap --detail "…"`                                                                                                                                                                                                    | as above                                          |
| `unrouted` findings                              | the orchestrator matches each finding's file against every unit's `paths` and dispatches it to that unit's implementer as the row for its kind describes; a finding no unit's `paths` match goes to `fc launch escalate blocked --detail "…"` | —                                                 |
| usage from the runtime                           | `fc events usage <json>`                                                                                                                                                                                                                      | `usage` event                                     |

- `fc return` validates each file by kind and exits 2 on a file that does not match; an invalid payload is a halt, never a stored return.
- `fc worker render` and `fc worker merge` exit 2 while a trigger is fired, and so does `fc launch phase` for every move except the move to `ended`, which is how a triggered run is closed; so a trigger payload stops the run in `fc` as well as in the script.

## The /workflows controls

- `/workflows` lists the runs of the current session with their phases and progress; a running script reports its phase lines there and through `phase(title)` and `log(msg)` in the script.
- A run can be stopped from the progress view; a stopped run returns nothing; the orchestrator runs `fc launch escalate halt --detail "…"` with a detail naming the last stored unit returns and the wave that was in flight.
- Runs are resumable in-session: re-invoke the same `/<name>` with the same `args` in the same session, and a completed agent returns its cached result, so the re-run does not re-dispatch finished units.
- The runtime keeps each run's script under the session directory in `~/.claude/projects/`.
- Limits: up to 16 concurrent agents (fewer with fewer CPUs), 1,000 agents per run; the plan's `implementers_concurrent` is the binding cap, not the runtime's.
- `Workflow(fc-implement)`, `Workflow(fc-review)` and `Workflow(fc-explore)` in `permissions.allow` approve the launches in `-p` runs; the `workflowSizeGuideline` setting bounds the size a session will accept.

## Distribution

- `fc distribute --apply --target .claude` copies every `workflows/*.js` to `.claude/workflows/`, where Claude Code runs it as `/<name>`; without `--apply` it prints the planned copies and writes nothing.
- A target file with different content lists as a conflict and nothing is copied unless `--force`.
- The scripts are edited under `flightdeck/flightcrew/workflows/` and redistributed; a copy edited in place drifts and `fc doctor --target` does not compare workflow copies, so redistribute after every change.
- A change to a script's stage boundaries is a change on the tooling axis (`flightdeck/manuals/orchestration/run-log.md` defines the three axes) and is committed together with its entry in `flightdeck/launch/RUNLOG.md`.
