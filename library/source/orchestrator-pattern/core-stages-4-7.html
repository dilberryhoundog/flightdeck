What the internals actually look like

The core.

Stages 4 to 7 of an orchestrated run in Claude Code: from a fresh orchestrator session reading a frozen spec, through the plan, the seams, the parallel workers, and the whole-feature verification that decides when the run stops. The part of the process that is almost entirely agents, with the human at two gates.

Orientation

Everything in the core follows from one idea inherited from human-in-the-loop work: build the earlier structure before the dependent one. The core writes that ordering down and enforces it.

Entering the core, three things exist and are frozen: spec.json at a commit, the tests derived from it (read-only to anything that writes code), and the kickoff that says how this run is conducted. The orchestrator is a fresh session started from the kickoff. It has never seen the interview that produced the spec and never will.

The core goes green in predetermined phases. Interfaces first, so every unit can test its seams. Then waves of parallel workers, each accountable for a slice of the spec, each fenced to its own paths, each unable to edit the tests or the seams it builds against. Then the whole feature, on the merged branch, against the acceptance script. At each phase the stop condition is a check result, and the human appears exactly twice, at the two moments where a wrong assumption is about to be multiplied by the number of workers.

The worked example throughout is the classic Rails blog, and the run is comments: a nested resource under posts, a model, a controller with create and destroy, a form and a list in the post view.

The comments run, entering the core

Frozen: specs/comments/spec.json with behaviours B1–B7 (posting, listing, ordering, validation, deleting) and edges E1–E3 (empty body, missing post, unauthorised delete). Tests in spec/: model, routing, request and system specs mapped to those numbers, plus a comment factory. Branch run/comments-1. Kickoff names three worker roles, two gates, an iteration ceiling of five per unit, Sonnet for workers and Opus for everything else.

Stage 4

Plan

The orchestrator reads, explores, and produces a plan. Nothing is built. This is the cheapest moment in the run to be wrong.

Main characterorchestrator, in plan mode
Seeskickoff · spec · test map · constitution · prior reports
Producesruns/<id>/plan.json
Ends atgate 1

Why plan mode

Plan mode restricts the session to read-only tools. The orchestrator can explore the codebase, read the spec and tests, spawn explorer subagents, and write a plan; it cannot edit files. Three consequences matter. The plan phase cannot leak into implementation no matter how confident the orchestrator is. The orchestrator's context stays small, because no edit results, hook outputs or test runs have entered it yet, and that context is the scarce resource for the rest of the run. And approving the plan is the act that takes the session out of plan mode, so gate 1 is a switch rather than a convention.

The kickoff must say to write the plan to a file. Plan mode's default output is conversational; the plan is consumed later by dispatch and by the report's ledger, and both need runs/<id>/plan.json.

The plan is data

A plan for an orchestrated run is read three times, by the orchestrator to dispatch, by the assembler to reconcile plan against outcome, and by the human to scan for gaps. All three want rows. Each unit is a pointer into things that already carry the detail, spec entity IDs, interface IDs, check names, paths, and the plan restates none of it. That is why a good plan is short on disk and reads rich on screen: the viewer resolves the IDs.

// plan.json — one unit; every value is a reference, never a copy { "id": "<unit-id>", "name": "<unit-name>", "spec_refs": ["<B|E ids>"], // what this unit is accountable for "owns": ["<paths>"], // the only paths it may write — its diff boundary "needs": ["<I-ids>"], // interfaces it consumes "produces": ["<I-ids>"], // interfaces it defines (stubbed at stage 5) "checks": ["<check names>"], // its stop condition, from the test map "worker": "<role>", "model": "<tier>", "group": "<wave id>", "size": "S|M|L", "flags": ["produces-interface", "modifies-existing", "risk", "human-decision"], "decisions": ["<a call made where the spec was silent>"] } // top level: "spec": "<path>@<commit>", "interfaces": [{id, name, reuse|new, check}], // "order": [["wave-1 groups"], ["wave-2 groups"]]

Interfaces are first-class objects at the top of the plan, each with its own contract check; that list is the entire input to stage 5. order is explicit waves, the dispatch schedule for stage 6. decisions is where a human-decision flag points, so every judgement call the plan made can be read in one pass. Status is not on the plan; that is the report's job.

Without a template the orchestrator writes prose, because that is what plans look like in its training. A plan schema in orchestration/schemas/, named by the kickoff, is what makes the plan parseable rather than interpreted.

The comments plan

Interfaces: I1 comments migration (new), I2 Comment belongs_to :post and Post has_many :comments (modifies-existing), I3 nested route create/destroy (new), I4 comment_params permitting body (new). Units: U1 model behaviour (B3 validation, E1) owning app/models/comment.rb; U2 controller (B1 B5 E2 E3) owning app/controllers/comments_controller.rb; U3 views (B2 B4) owning the comment partials and the post show template. Order: wave 1 is U1 and U2 and U3 together, because none needs another's implementation, only the seams. U2 carries a risk flag for the authorisation edge and one decision: delete is restricted to the post author because the spec named "owner" without defining it.

Gate 1

Plan approval

A page, not a reading exercise. The mechanical half of the gate runs before the human looks at anything.

Human The gate is a local page that opens the run directory, reads plan.json, resolves every reference against spec.json, and derives the checks a person would otherwise do by eye: every behaviour and edge in exactly one unit, and the uncovered ones listed; every needs matched by a produces or an existing interface; no two units owning the same path; every named check present in the test map; spec version of the plan equal to spec version of the tests. Those appear as flags at the top. What remains for the human is judgement: unit size, decomposition, and each entry in decisions.

Three outcomes, each a file. Approve writes an approval block into the plan (approved: {at, spec_version, plan_hash}) so the orchestrator and the assembler can verify they are working from the plan the human saw. Edit writes a new plan revision; the kickoff tells the orchestrator the plan file is the source of truth and to re-read it after the gate, so edits win without a conversation. Comment writes comments.json keyed by unit ID, and the page renders the comments as a revise-plan prompt to paste into the orchestrator session; it re-plans, the page reloads. Only approve leaves plan mode.

In Chrome the File System Access API lets the page read and write the run directory in place, so there is no export and import step. The same page family, with a different lens, serves the spec freeze before the core and the report after it.

Exit A plan that cannot be fixed by editing units is a spec problem. The run stops here and re-enters at stage 1. Nothing has been spent.

Stage 5

Interfaces

The seams are built before anyone builds a room: everything a worker will import from another worker, declared and not implemented, checked, committed, and locked.

Main characterorchestrator, or one worker in sequence
Seesthe plan's interfaces list · the spec's interfaces section · the contract checks
Producesone commit on the run branch · the protected path set
Ends atgate 2

What is created

Not empty files. For each interface in the plan's list, the orchestrator does one of three things. An interface marked reuse gets nothing created; the existing type or contract is confirmed to be where the spec says and the contract check references it. An interface that is its own implementation, a type, a schema, a migration, a route, an association, a permitted-params list, is written in full, because there is nothing to defer. An interface that has behaviour behind it, a function or an action, is written as a signature whose body raises a not-implemented error carrying the unit ID that will implement it. If units own module files that do not exist yet, those are created with their exports declared, so every import a worker will write already resolves.

The stub raises; it never returns. A stub that returns plausible data, an empty result or a fake redirect, lets a behaviour test pass falsely and lets a worker build against fake behaviour. A raise with the unit ID means every failure in the next phase names the unit that has not been done yet.

The comments seams

Written in full and run: the migration (post reference, body, timestamps), so db/schema.rb in this commit is the contract. Written in full: belongs_to :post in the new model, has_many :comments added to Post, resources :comments, only: [:create, :destroy] nested under posts, comment_params permitting body. Stubbed: CommentsController#create and #destroy, each raise NotImplementedError, "U2". Created for U3: the partial files the controller will render, so render resolves. Untouched: validations, ordering, counter caches, anything that is behaviour.

The signal

Checked The stubs do not produce a signal; the stage-2 tests do, and what stage 5 changes is the reason they fail. Before this stage a request spec fails with a routing error or a missing constant, the wrong reasons. After it, the same spec fails with the not-implemented error naming U2, which is reaching the stub. Meanwhile every check that tests only shape goes green: the routing spec, the association spec, the schema after migrating the test database, factory lint, the autoloader check, the linter. The stop condition for the phase is that specific pattern in the output, green structure and contracts, red behaviour for the right reason, and the Stop hook holds the turn open for it.

PASS spec/routing/comments_routing_spec.rb PASS spec/models/comment_spec.rb (associations) PASS FactoryBot.lint · zeitwerk:check · rubocop FAIL spec/requests/comments_spec.rb B1 NotImplementedError: U2 ← reached the stub FAIL spec/system/post_comments_spec.rb B2 NotImplementedError: U2 diff boundary: db/migrate, config/routes.rb, app/models, app/controllers, app/views within plan

Commit and lock

One commit, interfaces: comments, on the run branch. It does two things: every worker's worktree will inherit the seams, and the interface paths join the protected set, so the block-writes hook now stops workers from changing them. That is the point of the phase. Without it two workers sharing a type each invent their own; with it the shared vocabulary is fixed before anyone speaks, and a worker that needs a seam to change has to stop and report.

The lock is by path, so it is clean where a file is pure interface (the migration, routes.rb, schema.rb, the factory) and awkward where interface and implementation share a file, which in Rails is the model: the association line is interface, the validations the worker will add are implementation, and a line cannot be locked. For those files the contract test is the lock. The association spec lives in the read-only test directory; a worker that changes the association breaks a test it cannot edit. Lock the file when you can; where you cannot, make sure a contract test covers the seam.

Two things belong on the gate 2 diff for a reason. has_many :comments on Post changes a model already in production, which the plan flagged modifies-existing. And the migration is executed, not stubbed; it is the one thing before stage 6 that is not trivially reversible.

Gate 2

Interfaces approval

The last moment a wrong seam costs one agent's work instead of a wave's.

Human The gate 2 page shows the interfaces commit as a diff with the contract check results beside each interface, and the modifies-existing and risk flags highlighted. One question: are these the seams the spec's interfaces section described, and are they the ones every worker should build against.

Exit If the seams are wrong the fix is upstream, in the spec's interfaces section or the plan's reading of it, never in the code. The branch is left as it is and the run restarts where the fix lands.

Approval writes the approval block, the interface paths are confirmed in the protected set, and the seams become canon. From here the wiring is verified three times: it was verified when built, it is verified continuously because every worker's check set includes the contract checks, and it is verified again on the merged branch at stage 7. That is what lets canon be canon without anyone watching it.

Waves and the chain of checks

Within a wave, units depend on each other's interfaces and never on each other's implementation; that is what lets them run in parallel. Where a unit genuinely needs another's finished behaviour, the plan puts it in a later wave, and the later wave's check set includes the earlier wave's behaviour tests as well as the contracts. Wave two cannot go green by breaking wave one, because wave one's tests are in wave two's stop condition and wave two cannot edit them. Regression protection grows wave by wave, from the plan's order field and the check-set rule, not from anything a worker decides.

Where the worker prompt comes from

Not the plan. The plan unit is data; the prompt is rendered from it at dispatch time, from three layers each kept in one place.

LayerLives inCarriesVaries
Agent definition.claude/agents/worker.mdRole, tools allowed and denied, model tier, worktree isolation, the return shapenever
Worker templateorchestration/templates/worker.mdThe sections, the rules, the order; the place the "must not see" boundary is implemented, because what is not a slot cannot reach the workerper project
The fillplan.json resolved against spec.jsonThe unit's spec entities verbatim, interface signatures, paths, check names and commandper unit
// worker.md — slots; nothing else reaches the worker <unit id and name> <spec entities, verbatim: the behaviours and edges this unit is accountable for> <interfaces consumed: signatures, marked read-only> <interfaces produced: already stubbed, to be implemented> <paths this unit may write> <checks that must be green, and the exact command> <rules: tests and interfaces are read-only · outside "owns" is out of bounds · on a contradiction between a test and the spec, stop and return blocked> <iteration ceiling> <return shape: unit · spec refs · artefacts written · status · blocked-on>

The orchestrator does not tell the worker how. It tells the worker what it is accountable for, what proves it, and where the fence is; the decomposition, the ordering and the fences are the orchestrator's contribution, all upstream of the prompt. The procedural part, how to implement B5 in this codebase, is the part the model is better at than a prompt-writer at the unit level, and leaving it out is not withholding guidance.

Render the prompt deterministically, with a small skill or script over the two JSON files, rather than having the orchestrator compose it freehand. Freehand composition is where orchestrator context leaks into workers and where a slot is quietly dropped under context pressure. It also makes the report's agents table honest: the task a worker was given becomes a recorded file rather than a stated recollection.

Model tier

This shape is what makes tiering safe. A unit prompt is narrow, its target is executable, and iteration is cheap: a smaller model iterating against a deterministic check converges on tasks it would fail if asked to get right in one pass, because the check loop is doing work that raw capability would otherwise do. The default is a smaller tier for workers, with escalation driven by the plan's flags: size L, a risk mark, or a unit with entries in decisions gets the stronger model, since interpretation is doing more of the work there than iteration. A useful kickoff rule is escalation on failure: a worker that hits its iteration ceiling is retried once on the stronger tier before returning blocked. Everything upstream of the workers stays on the strongest model: the orchestrator, the test-writer, the reviewer.

The human-in-the-loop instinct that bigger is always better comes from one-shotting. In the core, a cheaper model throwing tokens iteratively at a goal with a deterministic check deciding "done" is the intended mode, and the strong model's job is to make the goal and the check precise.

When a worker meets the wiring

Tries to edit a locked file

The block-writes hook refuses the write before it happens and the worker sees why. Nothing goes red because nothing changed.

Breaks a contract in a shared file

The contract test goes red in the worker's own check run. It cannot edit the test, so the only way back to green is to undo its change. The worker fixes its own mistake.

Discovers the wiring is wrong for its unit

It must not route around the contract; that produces code that satisfies the tests while not doing what the spec meant. It stops, returns status: blocked with the contract it needs changed and the spec entity that requires it. Exit Either the spec's interfaces section or the plan's reading of it was wrong, and only a human says which.

How a block reaches the human

Depends on the run's shape, because Claude Code handles a mid-run stop differently in each. In the interactive shape, an orchestrator session dispatching subagents, the blocked status is the worker's return value landing in the orchestrator's context. The kickoff and the orchestrator's agent definition say what to do with it: stop dispatching, do not resolve the contract yourself, write the block to the run directory, ask the user. An interactive session waits whenever it ends its turn with a question. What makes this deterministic is a PostToolUse hook on the subagent tool that reads the returned result, appends a blocked event to events.jsonl on a match, and injects a line into the orchestrator's context saying dispatch must halt; a notification hook pings the human at the same time.

In the workflow shape, dynamic workflows do not accept user input during execution, only a permission prompt can pause one, and the script has no filesystem access of its own. A block there is a stop condition the script handles: skip dependents, finish or stop the wave, return the block as the final result to the session, which then asks. A block almost always means a spec or plan change, which means a new run. This is why the core runs interactively through gate 2 and only the parallel waves of stage 6 are candidates for a workflow: the stages with gates need a session that can stop and ask; the stage where the human has already chosen not to be present is where a script that cannot ask is the right tool.

A per-unit adversary, if wanted

Findings go to the orchestrator, never straight to the worker whose context is the thing being challenged. The reviewer returns a structured result; the orchestrator dispatches a fresh fix-worker with the finding, the spec entities it cites, the unit's checks and the diff, and nothing of the original worker's reasoning. A finding is resolved when the fix-worker's checks are green and, if the kickoff asks, the reviewer re-checks once. The orchestrator does not adjudicate: a finding the fix-worker disputes stays open and reaches the report marked disputed. Per-unit review is usually reserved for risk-flagged units; the whole-diff review after the core covers the rest.

The comments wave

U1, U2 and U3 dispatched together into three worktrees on Sonnet, U2 escalated to Opus for its risk flag. U1 replaces nothing, adds the presence validation and the ordering scope, turns the model specs green in two iterations, commits, returns. U3 builds the form and the list partials against the stubbed controller, turns the system spec green only as far as rendering, and returns with B4 noted as dependent on U2. U2 replaces the two raises, hits the request specs green in four iterations, and on E3 stops: the spec's "owner" is undefined and the plan's decision (post author) contradicts a test that expects the comment's author. Returns blocked. The hook halts dispatch; the orchestrator asks. The spec gets an owner definition; the run re-enters at stage 2 with one test changed.

Stage 7

Verify

The whole-feature version of what each worker did for its unit, and the jail the orchestrator cannot break out of.

Main characterthe Stop hook; the orchestrator merges and re-dispatches
Runsthe full check set on the merged branch
Producesruns/<id>/checks/ · the evidence display in its final form
Ends byacceptance green, or the stall cap

Checked Workers went green in isolation against their own checks. Stage 7 is the first time everything exists in one place and asks the question no worker could. The orchestrator merges the wave worktrees onto the run branch and the full set runs through the check wrapper, every result captured verbatim: structural checks, every contract and behaviour test, and for the first time the acceptance script from stage 2, plus the diff boundary over the run's entire diff, the list of spec behaviours with no green check, and the list of test files changed since stage 2, which should be empty.

Units interact in ways their own checks cannot see: two changes pass separately and fail together, a shared factory is satisfied by one unit and broken by another, a count is right in the model spec and wrong on the page. The acceptance script is the only check that exercises the feature the way a user would, and it is what the run's stop condition is built on.

The comments acceptance

Full spec suite; a system spec that visits a post, writes a comment, submits, sees it rendered in order, deletes it as the owner, and is refused as someone else; migrations from scratch on a clean database; RuboCop; diff boundary over the whole run diff against the union of every unit's owns.

The stop condition

The Stop hook runs the acceptance command and refuses to let the orchestrator's turn end until it exits zero. On failure the orchestrator reads the output, identifies the unit from the failing check's spec mapping, dispatches a fix-worker with that check as its target, on the stronger tier if the kickoff says so, re-merges, and the hook runs again. The orchestrator cannot declare done; only the command can.

After eight consecutive blocks Claude Code overrides the hook and ends the turn. Eight is Anthropic's number, a runtime safeguard so a broken check cannot trap a session forever; it is not chosen, it is exploited. A tighter ceiling is the hook script counting its own blocks, writing a stalled event on the fourth or fifth and exiting zero to end the turn cleanly, with the built-in cap as backstop. Either way the number is a stall detector. Exit The useful question at exit is which check kept failing, and the report says.

A verification subagent, if the kickoff asks for one, runs here: given the merged branch and the check results and told to try to refute them. It is a refinement on top of the deterministic gate, not a substitute for it.

What stage 7 leaves behind

The evidence display in its final form. Through gate 2 it showed intentions, the plan and the seams. From here it shows results: commands, exit codes, output lines, spec coverage, what was not verified, test files touched, cost per unit and per phase. This is the flip from an approval tool to a verification tool. Everything after the core, the whole-diff review, the report, gate 3, is judgement and record laid on top of these facts, and none of it should run if stage 7 is not green.
